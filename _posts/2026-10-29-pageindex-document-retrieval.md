一份长报告里，相关内容可能集中在一个章节，也可能分散在定义、结果和附录中。检索返回几段相似文字之后，回答者仍要判断：读到的是完整证据，还是只碰到了相同术语？章节关系、表格说明和跨节引用，都会影响这个判断。

PageIndex 尝试让检索保留文档的组织方式。它先把标题层级和页范围整理成树，再让模型借助结构与摘要选择阅读位置，通过工具取回原页。在官方 Flash 示例中，面对一份 47 页的 Kimi K3 技术报告，模型回答“测试了哪些 benchmark”时，先调用 `get_document_structure`，再调用 `get_page_content` 读取第 25—31 页。这段官方示范展示了它的基本动作：**先确定去哪里读，再用读到的材料作答。**它没有证明这条路径总能找全证据。

这也是理解“无向量 RAG”的入口。PageIndex 可以用结构导航承担文档内的检索，省去这条路径上的向量相似度排序；相关性判断则转移到树的质量、摘要和模型的阅读决策上。把它接成完整知识库，还要解决先选哪份文档、哪些版本有效、当前用户能读什么，以及漏证据时怎样发现和修正。

以下机制以 PageIndex 0.2.10、源码提交 `b81465d` 为准；托管服务依据截至 2026-10-29 的官方资料单独说明。文中的工具序列来自官方示例，源码分析不代表已经实测模型检索质量。

## 从 PDF 文字布局建立可导航的树

树首先是一份位置索引。一个节点保存标题、节点 ID、起止页和子节点；启用摘要后，还会保存这部分内容的概述。父节点的范围覆盖整棵子树，查询时可以先观察一个大章节，再决定进入哪个子节，或者直接阅读其页范围。

这与固定长度切块有不同的起点。固定窗口先按长度划分材料，检索器再判断哪些片段相关；结构索引先尝试恢复作者已经建立的章节关系。结构节点仍然划定文本范围，页也仍然是阅读单位。“不切块”不能理解为完全不分区，它主要指不依赖固定窗口的 embedding 分块来完成这条检索路径。

当前本地 SDK 的默认构建模式是 Flash，另保留 `standard` 路径。以下聚焦默认 Flash 的实现。Flash 的结构抽取从 PDF 的文字层开始：读取字符位置和样式，将字符聚成行，处理分栏、行号与文本块，再识别页眉页脚、水印、图注、正文和标题候选，最后组织层级。这里的顺序有实际作用。页眉如果先被当作标题，后面的树就可能反复出现同一项；双栏阅读顺序如果错了，标题与正文的关系也会跟着错。

PDF 自带书签也可以参与构建，但并非一律照收。细致且可信的书签可以作为层级框架，布局检测补回遗漏标题；只有粗粒度章节的书签可以提供上层结构，再把检测出的细节挂进去；不可信的书签会被忽略。对应实现见固定提交的 `pageindex/flash/main.py` 与 `pageindex/flash/api.py`。

页范围还有一个容易忽略的问题：父标题之后、首个子标题之前的正文应当归谁？Flash 会用介绍节点覆盖这段内容，文档首个标题之前的材料也有相应的前言节点。否则，树看起来层级完整，沿子节点阅读时却可能跳过定义和适用条件。结构是否漂亮，和原文是否被覆盖，是两项检查。

这些范围采用从 1 开始的 **PDF 物理页码**。封面、目录也计入页数，因而它可能与页面上印刷的页码不同。回答和查看器必须使用一致的编号方式，否则用户拿着正确引用也可能打开错误位置。

### Flash 抽取、树优化和摘要分别做什么

“Flash 抽树不调用 LLM”只描述了布局抽取阶段。默认完整流程还会优化结构并生成摘要，其中部分工作使用模型。

优化要处理两种相反的问题。树过细时，模型为了读很少的内容，可能先经过多层目录；树过粗时，一次选中节点又要读很长的章节。`pageindex/tree_optimize.py` 用页数构造一个近似成本模型，在导航层数与阅读范围之间取舍。

对一个尚未展开的章节，直接阅读的成本是整节页跨度。尝试拆成子节后，近似成本是一次路由加上页跨度最大的子节所占页数；代码把一次路由按一页计算。只有后者更小，展开才值得保留。模型负责提出文档中已经存在的子标题与起始页，程序再据此计算、检查和组织节点。提示要求模型不要创造标题，但这一要求本身不保证每次识别正确。

合并则自底向上进行。若继续保留子树的近似成本不低于扫描父节，就折叠这一层；被移除的标题保留为父节点的 `key_items`，尽量保存路由线索。同页的多个末端节点还可能合并，因为无论进入其中哪一个，页级工具最终读到的都是同一页文本。

这个优化目标解释了树为什么可能变化，也限定了变化的意义。它优化的是以页数近似的最坏路径成本，不能直接换算成 token、延迟或账单，更不能据此推导相关性最优。一个章节按页数适合合并，合并后的摘要仍可能淡化其中的例外条款。

在 Flash 接口中，`optimize="full"` 包含确定性合并与模型展开，`optimize="merge"` 只做确定性合并；摘要另由 `summary` 控制。关闭摘要，并将优化关闭或设为仅做确定性合并，即 `summary=False` 配合 `optimize=False` 或 `optimize="merge"`，可以构成不调用模型的建树路径。本地 SDK 默认提交流程会开启摘要，因此仅关闭优化还不足以得到无模型索引。这些差别应在估算建库成本、选择模型后端和判断数据去向时一起考虑。

### 结构抽取失败会怎样传到检索

本地入口先检查 PDF 能否提取出文字。没有可读文字的文件会被拒绝，不能指望后面的推理从空文本恢复证据。如果有文字却找不到可靠层级，Flash 可以降级成每页一个节点；过大的平铺树还会被本地客户端或命令行拒绝。降级保留了页的位置，却失去了章节树缩小阅读范围的主要依据。

所以第一次接入时，应先查看原页文本、标题和页区间能否对应，再调查询提示词。文字层缺失需要补解析或 OCR；阅读顺序错误需要修文档抽取；树漏掉某段则需要检查覆盖关系。换一个更强的回答模型，并不能直接修好这些输入状态。

## 模型如何沿工具调用走到原页证据

当前开源 SDK 已经有本地聊天与检索工具，并非只负责生成目录。`pageindex/local_chat.py` 将工具接入模型循环，模型提出调用，程序执行后返回结果，模型再决定继续读取还是形成回答；`max_turns` 限制循环轮数。

这里的“树搜索”应理解为模型利用树作阅读决策。源码没有把整个过程固定为严格的深度优先或广度优先遍历，也没有保证每条相关分支都会访问。模型可以根据当前所见跳入某一节、读一组页，再决定是否补读其他位置。

一条完整的本地取证路径包括：

1. **确认目标文档。** 已提供 `doc_id` 时，先验证并绑定该文档；未指定时，通过 `browse_documents` 分页查看名称和描述，选择候选。
2. **确认材料可用。** `get_document` 返回文档信息和状态，避免把尚未就绪的材料当成可读索引。
3. **查看结构。** `get_document_structure` 提供标题、摘要和页范围，供模型判断阅读位置。
4. **读取证据。** `get_page_content` 返回选定页的实际文本，模型据此回答，必要时继续补读。
5. **保留出处。** 最终内容带上能够回到相应文档物理页的引用。

这一顺序也说明，索引存在与检索成功之间还隔着多次判断。文档选错，后面的页读得再准确也没有帮助；文档选对但摘要引导错误，模型仍可能进入错误章节；页已经读到，回答也可能误解其中的限定条件。工具记录能帮助区分这些错误发生在哪一步。

接口参数会影响这条路径是否真的节省上下文。直接调用 `get_tree` 时，默认 `include_text=True`、`node_summary=False`；若目的是先获得紧凑导航，应明确要求 `node_summary=True`、`include_text=False`。SDK 的结构工具已经采用适当参数，但自行接入时照默认值读树，可能把正文也送进模型。工具输出还有大小限制与分页，不能假设超长目录一次就完整可见。对应实现集中在 `pageindex/agent_tools.py`。

### 用官方报告示例理解“先导航，再阅读”

回到 Flash cookbook 的 47 页报告示例。问题询问测试过哪些 benchmark，结构工具先让模型观察报告的组织，再读取第 25—31 页。这段记录的价值在动作与证据之间：目录承担缩小候选范围的任务，取页工具承担提供正文的任务。

它同时给出了一个清晰的检查入口。如果只读结构就回答，回答依据实际停留在摘要；如果取回了页，但相关定义或表注位于其他页，仍需扩读。看到模型成功发起七页读取，只能确认一次取页动作发生，不能由此断言报告中所有相关证据都已覆盖。

对于这类需要列全项目的问题，检查重点还应包括其他章节是否另有实验、表格缩写是否需要回到定义处解释，以及附录是否补充了正文未列内容。这些是由“列全”的回答目标推导出的核验动作，不能把官方示范中的一次导航序列扩写成已经完成的全面评测。

当摘要与原页的关系不清楚时，应以原页为依据；当原页指向其他章节时，继续取回被指向的内容；当补读后仍无法确认完整性时，回答应缩小到已经取得的材料。导航减少的是需要立即阅读的范围，阅读范围是否充分仍取决于问题。

### 引用需要检查位置、版本和支持关系

本地路径提供页级定位。Cloud 的较新索引还能提供带 `block_id` 和边界框的块级定位，便于查看器突出显示原文；缺少这些信息的旧索引需要重建，不能仅靠更换回答格式获得块坐标。这里的块用于定位出处，也不等于本地检索已经变成块级向量搜索。能力说明来自官方《Citations》及 `pageindex/agent_tools.py` 的引用指引。

一个引用至少有三层含义：这个位置存在；它属于回答所用的文档版本；该位置的内容支持对应断言。页码或块 ID 合法，只满足第一层。引用工具提示要求模型基于实际读取的内容作答、复制真实块 ID，也不能自动完成第三层判断。

因此，检索记录最有用的部分是可观察动作：选了哪些文档、拿到了哪些结构、读取了哪些页、最终引用了哪些位置。模型隐藏的推理过程不能替代这些记录。面对错误答案，应能区分证据从未进入上下文、证据已进入却被误读，以及答案写对但出处绑定错误，后续修正才有明确方向。

## 单文档树进入知识库后，责任如何变化

在一份报告里找页，与在很多报告里找答案，之间增加了一次关键选择：先找对文档。本地 `browse_documents` 可以分页提供名称与描述，让模型作选择，但这不等于已经具备高效的全库语义召回。局部目录再好，也无法挽回入口处漏掉的文档。

PageIndex 名下的几条路径应在这里分开：

| 对象 | 主要工作 | 需要区分的范围 |
|---|---|---|
| 本地 SDK 0.2.10 | PDF 文字提取、Flash 建树、本地存储、工具导航与聊天 | 已有多文档浏览；不能据此推定具备云端文件夹搜索与企业知识库治理 |
| Cloud 文档与元数据接口 | 托管解析、文件夹、带类型的元数据与筛选 | 依赖所选托管服务；文档还列有 OCR、图片理解及 Word、PPTX 等输入能力 |
| Cloud File System | 用主题层级等方式组织跨文档导航 | 官方描述的企业级跨文档设计，不能当成本地 SDK 默认行为 |
| Page Search API | 按问题对文档页面进行相关性评分，返回候选页 | 独立检索路径，其评测不能直接说明本地树导航效果 |

本地并非完全不能保存元数据。`LocalAPI` 会接收并保存 JSON metadata；Cloud 则进一步提供文件夹元数据 schema 与 `search_documents` 筛选。保存一个年份字段，和让搜索接口按该字段可靠地筛选候选，是不同的工作。

官方《Metadata》cookbook 用 120 份财报演示元数据检索，可以帮助理解先按文档属性收窄范围、再进入文内阅读的顺序。对同时涉及公司、时间和文档类型的问题，先把这些约束落实到候选文档，比仅凭文件名让模型猜测更可检查。这个示范说明接口怎样配合，不构成规模吞吐或全库召回的独立证明。

官方《PageIndex File System》还描述了虚拟主题节点、多父归属和按查询组织导航等设计。一份文档可以从多个主题入口抵达，缓解物理文件夹只能放在一个位置的限制。但跨文档导航是否漏掉材料、主题如何更新、权限如何随归属传播，仍需依据实际服务验证；这些问题不能由“看起来像文件系统”直接推出答案。

### 保存对象之后，还要定义更新语义

本地索引保存为 `tree.json`、`pages.json` 和 `doc.json`，分别承载树、原页文本与文档信息，列表另有 manifest 缓存。提交会生成新的 `doc_id`，同名文档可以加后缀保存。源码也有单个 JSON 文件原子写入及 POSIX 文件锁，保护相应保存操作。实现见 `pageindex/local_store.py` 与 `pageindex/local_api.py`。

这些机制让索引能够落盘，并不自动定义“同一资料的新版本”。文件名相同、内容相近或新 ID 出现，都不足以让应用知道旧版何时失效。单文件原子写入也不能直接推成多份状态之间的数据库事务。

要服务持续更新的知识库，应用应先定义稳定的来源身份，再把内容版本和索引版本挂到这个身份上。例如保存来源 ID、内容哈希、生效时间和索引代次；新索引完成并通过必要检查后，再切换当前可见版本。撤回资料时，候选列表、页读取和回答缓存也要一起处理。这里是从存储边界推导的建设要求，不能当作 SDK 已经提供的版本工作流。

引用尤其需要绑定版本。同一个物理页码在更新后可能承载不同内容，历史答案若直接打开最新文档，出处就会漂移。可以保留历史快照，也可以明确告知旧版已经不可取回；关键在于回答生成时选定的版本，与之后回源时解释的版本保持一致。

这类来源与目录记录的关系，也可结合 [Bakabase 从文件扫描建立资源目录的过程](/posts/bakabase-resource-catalog/)理解：识别出一个可索引对象之后，身份、同步与内容变化仍需要各自的规则。文档知识库还多了一层要求，旧内容可能已经成为答案证据。

### 权限要覆盖导航、阅读和回源

权限过滤应从候选文档枚举开始。名称、描述和结构摘要本身就可能透露材料内容，等到最后取正文才检查授权，已经太晚。读结构、读页、进入模型上下文、命中缓存与打开引用位置，都需要对应身份和访问判断。

`folder_id`、`doc_ids` 可以限定一次查询的范围，但选择范围本身不能证明调用者有权访问。固定源码能看到本地选定文档范围的检查，以及云端访问错误的传播；这些观察不足以承诺完整的企业 ACL 继承与撤销传播。采用时要核对所选模式下的认证入口、权限归属和失效行为。

同样，“本地索引”主要说明索引保存与接口执行的位置。默认摘要、展开以及聊天模型可能接收文档材料，数据是否外发取决于实际模型后端和部署方式。需要资料留在特定边界内时，应同时检查解析、索引模型、查询模型与日志的去向。

这些问题与 Agent 的会话持久化也要区分。[Agno SDK 中 Knowledge 与会话存储的说明](/posts/agno-sdk-execution/)讨论过两条不同的数据路径：记住前次对话，不能替代当前资料检索。知识库里的版本与授权还必须约束历史消息和缓存，否则旧材料可能绕过当前检索重新进入回答。

## 与关键词、向量和混合检索在同一层比较

评估 PageIndex 时，合适的比较对象是另一条“从资料中选出证据”的路径。关键词倒排依据词项匹配取候选，向量检索依据语义相似度取候选，混合检索组合两者，随后还可以重排。Elastic 官方《Hybrid search》所描述的一个实现方式，就是将全文与向量结果通过 RRF 融合。

这些路径也能携带页码、文档元数据并返回原文，还可以配合查询改写和历史上下文。因此，不能用一个最简 embedding 余弦排序器代表所有 RAG，也不能把可引用性独占地归于树导航。共同问题是：在给定预算里，哪种候选方式能把所需证据带进阅读范围？

| 比较维度 | 关键词 / 向量 / 混合检索 | 树导航 |
|---|---|---|
| 候选依据 | 术语、编号、语义相似度，或多路排名融合 | 标题、层级、摘要与模型的阅读判断 |
| 文档语境 | 可通过父文档、相邻片段、页范围扩读补充 | 层级与页范围直接提供组织线索，仍可能需要跨分支补读 |
| 主要失败位置 | 解析、候选未召回、融合或重排失误 | 解析、结构错误、摘要遗漏、过早排除分支 |
| 查询成本 | 召回、重排及最终阅读，各阶段分别计量 | 目录阅读、多轮模型与工具调用、原页阅读 |
| 跨文档使用 | 可先在全库形成候选，再扩大上下文 | 需要文档入口选择，再进行文内定位 |

显式层级清晰、问题指向一个完整章节、证据需要连贯阅读时，树导航值得验证。查询含有精确编号、错误码或罕见名称时，关键词匹配能提供直接入口；需要从大量措辞不同的文档里寻找候选时，向量或混合召回也有合理位置。

两者可以组合：先用全库混合检索和元数据过滤形成少量文档候选，再利用候选内部的树展开阅读。这样组合的理由，是把跨文档入口选择与文内连续阅读分开处理。这是可采用的架构方案，尚不能写成已经由当前研究证明的性能优势。

### Page Search 的召回数字回答了哪一个问题

Page Search API 对文档页面按查询打相关性分数，是另一条检索路径。官方 `page-search-benchmark` 报告的 Top 10 证据页召回率为 97.5%。其条件是：使用 80 个单文档问题，涉及 8 家公司的 39 份 10-K，文档平均 186 页；原任务中另有 20 个跨公司、多文档问题被排除。

这个指标衡量前十个候选页覆盖标注证据页的情况，不能读成最终回答准确率。对照向量方案是每页取前 12,000 个字符做 embedding，再按余弦相似度排名，没有加入混合检索和重排。因此，它支持的是官方所设条件下的页召回比较，不能直接推出 PageIndex 胜过完整 hybrid RAG，也不能把托管 Page Search 的结果移给本地 Flash 树导航。

同理，返回更少的页面只说明后续阅读量可以减少。完整成本还包含解析、索引、检索服务、模型多轮调用与回答生成。若要比较反复查询的延迟，还需区分新文档首次处理与索引建好后的查询；把两种状态放在一个数字里，会改变采用判断。

## 按证据进入回答的路径验证采用条件

第一次评估应从固定资料与固定版本开始。选择可核对原页的公开文档，为问题标记所需证据范围，再检查解析文本和树覆盖。此时最关键的结果是：正确材料是否能被工具读取，结构是否给出了可用入口。索引生成成功只完成了准备工作。

之后在相同解析文本、回答模型和上下文预算下，比较树导航与 BM25 关键词检索、dense 稠密向量检索、RRF 排名融合，以及需要时加入重排的路径。问题应覆盖明确术语、跨节限定、表格脚注、多文档汇总和跨版本差异，同时包括资料中没有答案、当前用户无权读取的情况。否则，一组只指向清晰章节的问题会掩盖入口选择与拒答的缺陷。

结果至少分开看四项：

- **证据是否找全。** 单个证据页命中之外，检查需要多处材料的问题是否全部命中；一次命中不能替代完整性。
- **答案是否受支持。** 核对答案正确性、引用支持关系、无答案时的拒答，以及权限边界。
- **花费发生在哪。** 分别记录建索引、选文档、导航、取页与回答的时间、token 和服务费用，并观察查询延迟分布。
- **错误在哪一层。** 保留候选文档、工具动作和已读页，用来区分文档漏选、节点漏选、读页不足和生成误解。

这是一套需要执行的评估方法，而非已经取得的本地成绩。官方 `tests/test_local_chat.py` 使用 fake backend 驱动真实工具，可以证明受测的数据传递与调用行为，无法代替真实模型的相关性评估。

采用决策也应落在错误所在的位置。若可靠层级能够帮助模型取得完整章节，且实际查询的成本与延迟可接受，可以将树导航用于这类长文档；若主要损失发生在全库漏选文档，应先补入口召回；若页面文字已丢失，应先修解析。只有证据已经完整进入上下文，才适合把主要问题归到回答模型。

PageIndex 提供的可迁移设计，是把一次检索变成可观察的阅读动作：结构告诉模型哪里值得看，工具记录它实际读过哪里，引用把回答重新接回资料。知识库能否可信，最终取决于这条路径是否持续指向正确、有效且有权访问的证据。
