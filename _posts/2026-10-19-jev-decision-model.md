Jev 是 TypeSafe 提供的决策模型。应用给它一份材料和一组带类型的问题，它返回类别、等级或命题概率，供程序继续分支、排序和路由。它面向的是软件中的语义判断：判断文本属于哪类、是否表达某种意图、在给定标准上处于什么位置。

Jev 将允许的答案及其概率分布直接提供给调用程序。开发者先组织材料，定义问题和候选答案；模型返回判断后，代码再决定接受结果、补充材料还是转交复核。返回格式规定了程序怎样读取判断，采用规则则决定这个判断会触发什么动作。

## 从生成回答到提供决策输入

普通生成式模型可以写回复，也可以在结构化输出约束下做分类。Jev 则围绕一项窄判断组织输入输出：共享材料放在 `state`，问题放在 `questions`，结果按问题 ID 返回。调用方可以直接读取相应类型及其概率，而无需先从自然语言解释中提取结论。

这使它适合放在现有程序的一处判断节点。上游可能已经读到文档、工单或候选资料；Jev 判断其中的语义；下游代码决定进一步查资料、交给专用流程，还是提交人工确认。外层也可以是 Agent，但一个普通服务同样能够调用它，不必先建立多轮 Agent 循环。

模型版本会影响这些判断。当前 `jev-latest` 与 `jev-preview` 均指向 `jev-1.14.0`；前者表示最新稳定版，后者在存在预览版时可以领先。需要比较版本或维护接纳阈值时，应保存响应中的实际 `model`，并在请求中固定已验证的版本。

## 问题定义决定模型究竟在判断什么

`state` 可以是字符串、对象或数组，用来承载判断所需的材料。`questions` 中每个问题都有类型和说明，Choice 与 Score 还需要候选或等级。问题 ID 用于对齐响应，不会送入底层模型，因此不能靠一个名为 `risk` 的键名代替风险的具体定义。

官方 Choice 文档以鞋店客服分流说明类别定义：用户收到尺码不合的跑鞋，希望换货；调用方给出退换货、物流等处理类别，要求 Jev 选择首先负责的部门。这里的类别对应处理职责，用户消息提供判断材料。

类别定义对结果有直接影响。“要求换货”应归退换货，“一直没收到货”应归物流；一条材料包含两件同等重要的事时，是否允许多选、使用其他类，还是拆成独立问题，需要在设计问题时确定。输出始终合法，也可能合法地选错类别。

同一次请求可以包含多个问题。官方 Speculative fan-out 示例同时询问工单类别、故障严重程度、是否有复现步骤、是否要求退款及挫败程度。类别用 Choice 返回，严重程度与挫败程度用 Score 表达，复现步骤和退款诉求则是 Noul 命题。

官方的消费逻辑先读取类别：`bug_report` 只在严重程度高于 1.5 且复现概率高于 0.6 时升级工程处理，否则进入普通故障队列；`billing` 才读取退款概率，用 0.7 作为是否附加退款标记的分界。挫败程度则独立决定是否优先回复。这些数字是官方演示的分支常量，实际阈值要由本任务标签与错误代价决定。

这样安排省掉的是“先分类，再发严重程度请求”的一次往返。非故障工单的严重程度已经求值，只是代码不消费它；模型没有先等待类别再决定要不要回答下一问。

这里的并行是每个问题独立地读取同一 `state`，不是后一个问题先读取前一个答案。若下一问真正依赖前一步生成的信息，应由代码发起后续请求，或提前提供足够材料。执行上的独立也不意味着这些事件在统计上互不相关，不能因此随意把概率相乘。

## 三种原语保留不同的判断信息

### Choice 给出候选之间的分布

Choice 面向无序类别。候选名称与描述共同送给模型，响应包含最高概率选项 `choice`、所有选项的 `probabilities` 和由分布计算的 `confidence`。

保留完整分布很有用：同一个最高选项，可能远高于其他项，也可能仅比第二名略高。只保存最终类别，就失去了后续决定补材料还是复核所需的信息。候选集合还要覆盖应用愿意接纳的情况；官方文档中的其他类可以为候选之外的输入提供出口，高概率的“其他”仍可能需要人工处理。

### Score 把描述性等级变成有序分布

Score 面向可描述的有序尺度。官方示例以 bug 严重程度组织等级，等级编号由 `criteria` 数组中的位置决定，从 0 开始。响应的 `score` 是等级位置的概率期望，可能落在两档之间。

一个纯数学例子可以说明含义：三个等级的概率为 `(0, 0.8, 0.2)`，期望是 `0×0 + 1×0.8 + 2×0.2 = 1.2`。它表达模型对等级的分布，数值单位来自开发者定义的尺度；它不是故障损失、停机分钟数或金额的直接测量。

因此，不同评分标准得出的 1.2 不能直接比较。等级顺序、描述和适用范围都应随评测版本保存。已经有权威数值的计算，应由代码或数据系统完成；Score 更适合材料到描述等级的映射。

### Noul 返回命题为真的概率

Noul 面向是非判断，例如消息是否要求退款、简历是否提到分布式系统。它返回 0 到 1 的 `noul`，没有独立的 `confidence` 字段。接近 0.5 表示对该命题的判断不集中。

命题最好是材料能支持的内容。“消息有没有提出退款诉求”与“客户是否符合退款资格”需要不同证据。后一项若依赖身份、订单和政策，必须先把可靠条件取得并落实到业务接口，不能把用户一句话同时当成事实和授权。

## 概率、confidence 与校准分别解决什么问题

Choice 的 `confidence` 由同一份概率分布计算。候选数为 n，最高概率为 pmax 时：

```text
confidence = (pmax − 1/n) / (1 − 1/n)
```

在四选一的数学模型里，均匀基线为 0.25；若最高概率为 0.94，confidence 为 0.92；若最高概率为 0.42，则约为 0.227。这组公式复算表示最高选项相对均匀分布的集中程度；confidence 与 probabilities 来自同一份分布，没有增加一次独立的答案核验。Score 还考虑等级之间的距离，采用不同公式。

校准则讨论一批预测与结果的关系：被预测为大约 0.8 的事件，实际发生比例是否接近 80%。一次输出再集中，也不能单独证明校准；厂商以校准为训练目标，也不能替代新语言、新行业和新候选定义上的数据。

这直接影响采用策略。阈值提高，通常会让自动处理覆盖减少，但已接纳部分是否足够准确，需要真实标签验证。两个错误代价不同的类别，也未必适合共用同一个阈值。模型概率是策略输入，策略还要考虑误判代价、补充信息成本和人工容量。

对一批有真实标签的 N 条预测，设阈值为 t，接纳集合 A(t) 包含达到阈值且属于允许自动处理类别的预测。自动接纳率为 `|A(t)|/N`，已接纳准确率为其中正确条数除以 `|A(t)|`；空集时后一个量无定义。两条曲线因而分别回答自动处理多少，以及自动处理的部分错多少。

再给错误类别附上代价，阈值选择才连到实际取舍。一个明确的二元数学模型是：预测为正的概率 p 已校准，错误放行代价为 C，人工复核代价为 H，复核能正确解决该项。自动放行的期望损失是 `(1−p)C`，低于 H 时才比复核便宜。若 C=100、H=2，分界是 p>0.98。这是按假设复算的决策边界；真实部署还要估计复核错误、等待与不同类别的代价。即使某个置信区间内表现稳定，也应保留候选外、资料不足和接口错误的独立分支；这些情况不应被强行压成某个正常业务类别。

## 接入：先取得判断，再让程序选择动作

Python 调用需要安装 `typesafe-sdk` 并设置 `TYPESAFE_API_KEY`。下面按官方 Choice 示例改写为一个最小请求，固定使用 1.14.0；执行会访问真实服务。

```python
from typesafe_sdk import Choice, TypeSafeClient

with TypeSafeClient() as client:
    response = client.system_one(
        model="jev-1.14.0",
        state="My running shoes arrived in the wrong size. Can I swap them for a size 10?",
        questions={
            "department": Choice(
                instructions="Which team should handle this request first?",
                criteria={
                    "returns": "Exchanges, wrong or damaged items",
                    "shipping": "Delivery status and missing parcels",
                    "other": "Requests outside these categories or unclear ownership",
                },
            )
        },
    )

answer = response.choices["department"]
print(answer.choice, answer.probabilities, answer.confidence)
```

代码通过 `response.choices["department"]` 取出这一问的类别、分布和 confidence。它到这里提供的是分流判断；是否将请求交给对应部门，还是因材料不足先复核，要由应用接着决定。

完整集成可以分成三个决定。首先从可信系统取得当前材料和身份，把与窄问题无关的长上下文排除。其次按照固定标准发出请求，保存模型版本、问题版本、结果与调用状态。最后将结果交给已验证的分支策略：接受、补查、复核，或报告服务错误。实际写操作仍通过已有接口验证身份与权限。

并行多问能减少一部分串行往返，也会增加问题文本与输入消耗。若每问都依赖尚未取得的不同材料，提前发送所有问题未必有益。应先区分共享材料上的独立观察，以及必须等待上一步结果才能成立的判断，再决定请求怎么组织。

## 采用评估要覆盖整条决策链

对 Jev 的评估至少有三层。类型检查确认接口能消费；判断质量检查类别、等级与概率；流程检查采用策略最终带来了什么结果。接口能够解析，只说明程序取得了结果；判断是否准确、采用后是否改善流程，还要分别测量。

官方 AutoResearch 路线与原始 `jev-phishing-bench` 还使用了另一种组合：将 Jev 对多项问题的判断作为语义特征，交给下游传统模型综合。此时最终分类依赖两部分：Jev 提供怎样的特征，下游模型怎样利用带标签样本学习这些特征。评估因此要同时固定问题定义、训练样本和留出集，才能区分特征与下游训练各自带来的变化。

准备样本时，需要覆盖清晰输入、边界输入、材料不足和候选之外的情况，并保留目标语言与真实长度分布。当前官方 Models 指出英语是主要训练语言，其他语言能力并不等同；中文任务要独立评测，不能根据英文示例的可读性估计效果。

比较规则、监督分类器、Jev 与生成模型，应使用同一任务、同一材料与可用预算。有稳定字段和明确条件时，规则直接可查；标签稳定且数据充足时，监督分类器值得比较；判断标准需要经常用自然语言修改时，Jev 的问题接口有价值；需要同时生成长回答和复杂工具推理时，生成模型承担更广的任务。Agent 框架在外层编排这些调用，不是同层替代品。

成本也要按被正确接纳的结果计算。官方当前列表价为每百万输入 token 0.042 美元，输出免费；`state` 和问题说明都占输入。真正的流程还包含重试、补查、人工与误判修复。低调用单价只有与任务质量、接纳覆盖和后续成本一起测量，才构成采用理由。

适合 Jev 的起点是一项答案空间清楚、材料可取得、错误可回退且能收集真实标签的语义判断。先在旁路记录结果，验证问题定义、概率与采用规则；当三者共同满足任务要求，再让它参与实际分支。问题、候选或模型版本改变，就重新比较整条流程。
