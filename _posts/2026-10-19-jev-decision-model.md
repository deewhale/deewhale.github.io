一张工单写着：“本月账单出现两笔相同扣款，请核对。”应用需要先决定归属：账单团队、技术团队、账号团队，还是人工分诊。这个环节的产物是一个类别，以及是否足以采用这次分类的依据。正式回复、业务查询和退款操作，都在后面。

这类窄判断是 Jev 的目标任务。开发者给出上下文和问题，指定允许的答案类型，服务返回类型化结果与概率，应用程序再决定如何行动。它可以嵌在 Agent 的工具链中，也可以直接被普通业务代码调用。

要把这项能力用好，需要连起三件事：问题怎样定义结果的含义，概率怎样影响采用策略，错误怎样被业务流程接住。**输出属于合法类别，只建立了接口约束；应用是否应该采用它，需要任务数据和执行规则共同回答。**

以下依据截至 2026 年 10 月 19 日的官方资料，示例固定 `jev-1.13.0` 与 Python SDK `typesafe-sdk==0.7.5`。文中的工单、候选类别、阈值和概率表均为假设设计；离线验证覆盖 SDK 数据解析与应用分支，未调用真实 Jev 模型。

## 先看清 Jev 在系统中的位置

生成式模型可以根据工单生成说明，也可以按结构化输出约束返回分类。Jev 的接口直接围绕判断组织：输入共享的 `state`，加上一组带类型的 `questions`，返回按问题 ID 对齐的 `answers`。开发者无需先让它写一段正文，再从正文提取分类。

这改变的是模型与应用之间的契约。程序知道自己要读的是候选类别、等级分布还是命题概率，可以直接使用相应字段。语义错误仍然可能发生：模型可以合法地返回 `technical`，而正确归属其实是 `billing`；所有类型约束依然满足。

TypeSafe 将 Jev 归为 System One 模型，公开介绍提到并行 sampler 与 RLCD，即以校准决策为目标的强化学习方法。这些资料说明了产品目标，尚不足以复现内部网络和训练过程。理解和采用时，应以可核对的输入输出、概率定义与任务表现为依据。

版本也属于契约的一部分。核查时，1.14 已可通过 preview 使用，但 `jev-latest` 仍指向稳定的 1.13.0。固定模型 ID，并保存响应报告的 `model`，才能解释以后回归测试为什么发生变化。当前文档也有需显式启用的实验图片输入，以及 1.14 的 Box 原语；官方仍将其标为尚未生产就绪。下面聚焦稳定文本判断链路。

## state 提供材料，questions 定义观察方式

对这张工单，可以提供以下上下文：

```json
{
  "message": "本月账单出现两笔相同扣款，请核对。",
  "locale": "zh-CN"
}
```

`state` 可以是字符串、对象或数组。这里的 `message` 和 `locale` 是应用选择的字段，并非服务要求的固定字段。它们负责把判断所需的材料放到模型面前。

接着定义三个问题：由谁首先处理、是否明确要求人工、业务影响有多大。问题 ID 分别叫 `team`、`human_requested` 和 `urgency`，方便程序对齐响应。官方 API 说明 ID 不送入底层模型，因此不能只起一个有意义的键名，就省略真正的问题说明。

问题语义由 `instructions` 和 `criteria` 建立。比如账单类别包括退款咨询，账号类别包括登录问题，遇到多个同等重要问题时使用 `other`。这些规则决定了“正确分类”的含义。类别边界没有写清，后面再精细地讨论概率也无法补上任务定义。

一次请求中的多个问题面向同一个 `state`，独立并行求值。`urgency` 不会先读取 `team` 的答案，再决定怎样评估紧急程度。需要使用前一步结果的问题，应由代码发起后续调用，或把可能需要的窄问题同时提出，再由代码选择相关答案。

## 三种原语分别保留什么信息

### Choice：在候选集合里比较归属

`Choice` 用于无序候选。工单团队没有高低顺序，`billing`、`technical`、`account` 和 `other` 只是不同归属。每个候选都需要描述，使模型能够比较它与工单的关系。

返回值包含最高概率候选 `choice`、完整 `probabilities` 分布，以及由分布计算的 `confidence`。下面两行是手工设计的示意输出：

<div style="overflow-x: auto;" markdown="1">

| 工单情况 | billing | technical | account | other | 最高候选 |
|---|---:|---:|---:|---:|---|
| 明确的重复扣款咨询 | 0.94 | 0.02 | 0.02 | 0.02 | billing |
| “付完钱就登录不了，钱是不是没退？” | 0.42 | 0.38 | 0.10 | 0.10 | billing |
{: style="min-width: 720px;"}

</div>

两行都能返回 `billing`，但第二行的账单与技术归属接近。应用若只保留最高类别，就丢失了决定是否转人工所需的信息。

`other` 还承担候选覆盖不足的出口。如果客户询问一个完全不属于这三个团队的事项，模型可能很确定地选择 `other`。因此，“概率集中”与“业务可以自动处理”是两项不同条件。

### Score：在有序等级上形成分布

`Score` 用于存在顺序的等级，至少两档。例如把业务影响分为：

```text
0：普通咨询，可按队列处理
1：业务受影响，但仍有替代办法
2：核心业务阻断，且无替代办法
```

等级位置由 `criteria` 的数组顺序确定。返回的 `score` 是等级概率的期望。假设三个等级的概率为 `(0, 0.8, 0.2)`，则：

```text
score = 0×0 + 1×0.8 + 2×0.2 = 1.2
```

1.2 表示分布主要在等级 1，部分落到等级 2。它不是对故障某种物理量的直接测量。改变等级描述或顺序，会改变这个数字的意义。实际损失、停机分钟数等已经有权威数据的量，应由业务系统提供或计算。

### Noul：对一个命题返回概率

`Noul` 返回命题为真的概率。这里问“客户是否明确要求人工客服”，示意返回 0.05，表示对该命题的低概率判断；接近 0.5 时，判断较不确定。这个原语没有另一个单独的 `confidence` 字段。

命题应针对文本能够支持的事项。“是否表达退款意图”可以从工单判断；“这个人是否有权退款”需要身份、订单和业务规则。后者应由可信业务系统验证，不能仅凭一段用户文本回答。

## confidence 与校准回答不同问题

Choice 的 `confidence` 可以直接从候选概率算出。若候选数是 `n`，最大概率是 `pmax`，则：

```text
confidence = (pmax - 1/n) / (1 - 1/n)
```

四选一的均匀基线是 0.25。示意输出最大概率 0.94 时，`confidence=(0.94-0.25)/0.75=0.92`；最大概率 0.42 时，结果约为 0.227。

因此，`confidence` 不是在类别概率之外，又有一个独立判断器证明答案可靠。它描述最高候选相对于均匀基线的集中程度。Score 的 confidence 还考虑等级之间的距离，计算方式不同，也不能套用上述公式。

校准讨论的则是一批判断。如果很多事件被预测为大约 0.8，它们实际发生的比例是否接近 80%？需要收集预测和真实标签才能回答。单次返回 0.94，没有提供这批事件的实际发生频率；新业务上的校准表现，也不能从厂商的训练目标直接推定。

还有一层容易混淆：API 中问题“独立求值”，指每个问题不读取其他答案。它不说明“要求人工”和“情况紧急”在业务上统计独立。把两个 Noul 概率相乘来得到整体风险，需要额外的统计假设和数据检验。

## 用程序把判断接到下一步

下面把三种问题和路由策略连成完整调用。安装 `typesafe-sdk==0.7.5`，设置自己的 `TYPESAFE_API_KEY`，保存为 `triage.py` 后运行 `python triage.py`。这段入口会请求真实服务；本文未执行该真实调用。

```python
import json
from typesafe_sdk import (
    Choice, Noul, Score, SystemOneResponse,
    TypeSafeClient, TypeSafeError,
)

MODEL = "jev-1.13.0"
STATE = {
    "message": "本月账单出现两笔相同扣款，请核对。",
    "locale": "zh-CN",
}
QUESTIONS = {
    "team": Choice(
        instructions=(
            "应由哪个团队首先处理 message？"
            "多个问题同等重要或信息不足时选 other。"
        ),
        criteria={
            "billing": "重复扣款、发票、支付、退款咨询",
            "technical": "功能故障、报错、配置问题",
            "account": "登录、账号资料、账号访问",
            "other": "以上均不适合、归属不明、多个问题同等重要",
        },
    ),
    "human_requested": Noul(
        instructions="message 是否明确要求人工客服？"
    ),
    "urgency": Score(
        instructions=(
            "按 message 描述的业务影响评估紧急程度，"
            "不按措辞激烈程度。"
        ),
        criteria=[
            "普通咨询，可按队列处理",
            "业务受影响但仍有替代办法",
            "核心业务阻断且无替代办法",
        ],
    ),
}


def decide(result: SystemOneResponse) -> dict:
    team = result.choices["team"]
    human = result.nouls["human_requested"]
    urgency = result.scores["urgency"]
    if human.noul >= 0.8:
        return {"queue": "manual", "reason": "explicit_human_request"}
    if team.choice == "other" or team.confidence < 0.8:
        return {"queue": "manual", "reason": "uncertain_team"}
    priority = "normal"
    if urgency.confidence >= 0.6 and urgency.score >= 1.5:
        priority = "high"
    return {
        "queue": team.choice,
        "priority": priority,
        "reason": "routed",
    }


if __name__ == "__main__":
    try:
        with TypeSafeClient() as client:
            response = client.system_one(
                state=STATE, questions=QUESTIONS, model=MODEL
            )
        plan = decide(response)
    except TypeSafeError as exc:
        plan = {"queue": "manual", "reason": type(exc).__name__}
    print(json.dumps(plan, ensure_ascii=False))
```

程序先检查客户是否要求人工，再检查团队是否可自动接纳，最后根据紧急程度设置优先级。这些 0.8、0.6 和 1.5 都是示意策略，不能直接当成生产安全阈值。尤其是人工请求概率位于中间区域时是否也应复核，要根据漏接人工诉求的代价另行制定规则。紧急程度 confidence 不足时保留 `normal`，也只是本例的策略；漏接紧急事项代价高的业务，应将这类不确定结果转交复核。

在前面的明确工单示意中，人工请求概率为 0.05、团队 confidence 为 0.92、紧急程度 score 为 1.2，程序得到：

```json
{"queue": "billing", "priority": "normal", "reason": "routed"}
```

混合意图示意的团队 confidence 约为 0.227，则得到：

```json
{"queue": "manual", "reason": "uncertain_team"}
```

如果很确定地选中 `other`，仍然转人工；如果人工请求概率很高，优先走人工分支；服务调用失败，则产生调用错误对应的人工计划。失败不被包装成某个业务类别。

这段程序只输出路由计划，没有接入队列 API，更没有退款。下一层应用还要验证队列值、绑定可信客户和工单身份，再通过已有接口执行。若进一步增加财务操作，应在业务接口中检查资格、金额、审批与幂等。

离线验证把手工设计的四组响应送进 SDK 原生 JSON 解析路径，再运行同一个 `decide`：明确归属进入账单队列，混合意图、明确人工请求与候选外三组进入人工队列。这个结果说明数据结构与消费分支相符；模型是否会给中文工单返回这些概率，仍需真实样本验证。

## 拆问之后，要重新验证完整决策

把一个大问题拆成窄问题，能够使输入、选项与程序规则更清楚。但最终结果取决于这些问题怎样组合，不能把拆分本身当成准确率提升的证据。

开源原始评测项目 `jev-phishing-bench` 就能说明这个区别。直接让 Jev 给出总体判定，在 2,000 封合成正文邮件上报告了 62.6% 的准确率。另一项设置提取五类信号，再用一半标注样本训练逻辑回归，在留出的 1,000 封上报告 95.0%。这里同时改变了测试样本范围，并增加了有监督的下游训练。相同五信号设置下的 Haiku 对照为 93.2%，与 Jev 的差异未达到报告采用的显著性标准。它支持检验“模型特征加分类器”的完整方案，无法证明只把一个问题改成五问就会得到同样收益。

工单分流也应如此。固定问题描述、候选定义、模型版本和 `decide` 规则，准备单意图、混合意图、信息不足、候选外与对抗文本等样本，并标记正确归属及是否应该人工复核。先在影子模式记录实际输出和程序计划，再与规则或现有模型在同一批样本上比较。

至少同时观察三组结果：

- 自动接纳率：全部工单中有多少无需人工；已接纳决策准确率：自动接纳的部分有多少正确。提高阈值可能减少误分，也可能把大量工单转给人工。
- 概率校准：把预测概率相近的样本分组，比较实际发生率，并保留样本量。平均准确率不能单独说明概率是否校准。
- 每个正确接纳结果的成本：除 API 费用，还计入重复输入、重试、人工和误分补救。低单价只有在这些条件下才形成实际收益。

核查时列表价是每百万输入 token 0.042 美元，输出 token 免费。假设每天一万次判断，每次一千输入 token，单看模型输入是每天 0.42 美元。`state` 和问题描述都占输入，拆成多次请求还可能重复上下文；这个算式仅解释列表价，不能代表实际分流系统的总成本。

## 让确定性规则承担它擅长的部分

Jev 1.13 的官方已知局限列出了数字精度、日期排序、间接引用、长而无关的上下文、对抗内容以及选项顺序影响。这些边界可以直接指导设计：金额计算和日期比较交给代码，先筛出与工单相关的上下文，对候选顺序变化做回归检查。

同一个“把工单归到团队”的任务，可以按条件选择不同实现：

<div style="overflow-x: auto;" markdown="1">

| 条件 | 可优先考虑的实现 | 需要检验的部分 |
|---|---|---|
| 有可靠字段和明确条件 | 确定性规则 | 字段来源、规则覆盖与例外 |
| 标签稳定且有足够标注样本 | 专用监督分类器 | 训练分布、样本外误差与维护成本 |
| 候选或判断标准常变，需要自然语言定义 | Jev 等决策接口 | 问题边界、概率、接纳策略与目标域表现 |
| 同时需要生成答复、解释或复杂推理 | 生成式模型及相应工具链 | 生成内容、工具事实和执行过程 |
{: style="min-width: 720px;"}

</div>

这些是同一任务下的条件选择，不是性能排名。Agent 框架可以编排上述调用、工具和状态，属于外层组织方式；它与 Jev 可以组合。

让 Jev 进入现有系统的合理起点，是一个答案空间清楚、错误能够回退、且能拿到真实标签的窄判断。固定契约，在影子样本中同时确认接纳质量与处理成本，再让程序采用经过验证的那部分结果。候选、问题或版本变了，就重新检查整条决策链。
