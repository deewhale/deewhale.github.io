模型提出执行 `python hello.py` 时，程序还没有开始运行。必须有一段程序接住工具调用，找到装有 Python 的环境，在确定的目录下启动进程，再把输出和退出状态送回来。模型要根据结果修改文件时，下一次编辑和执行还必须落在同一个工作区。

**Agent Runtime 解决的核心问题，是为 Agent 的动作提供实际执行条件，并把环境变化变成下一轮决策可用的观察。** 对于能够读写文件、编辑代码和执行命令的 Agent，这包括工作区、工具执行接口、进程管理，以及运行身份、资源和生命周期。

Runtime 在不同项目中覆盖范围不同，有时也包含整个 Agent 循环。这里聚焦工具执行所依赖的环境层；模型推理服务负责生成响应，harness 负责组织模型调用、工具派发与停止判断，执行环境则让文件修改、命令和网络访问真正发生。这几部分可以组合部署，职责需要逐项接通。

## 一、沿一个官方示例看完整执行链

E2B 是提供远程沙箱环境及其管理接口的平台。Deep Agents 是基于 LangChain 生态组织 Agent 循环的框架；`langchain-e2b` 则把 E2B 沙箱接成 Deep Agents 可以使用的执行后端。

E2B 的 Deep Agents 官方示例给出的任务很简单：创建 `hello.py`，让程序打印 `Hello from E2B`，执行它，并展示输出。这个例子没有复杂业务背景，却包含了文件编辑型 Agent 最基本的工作过程。

调用端首先创建一个 E2B sandbox，取得代表该环境的对象，再用它构造 `E2BSandbox` 后端。创建 Deep Agent 时，将模型和这个后端一起传入。用户请求进入 Agent 后，接下来发生的是一条跨越多个组件的执行链：

1. 框架把用户消息和可用工具交给模型。模型可以提出写文件或执行命令的工具调用，参数说明要处理的路径、内容或命令。
2. 框架识别工具名称和参数，调用已经绑定的后端。模型接触的是工具定义，不需要持有云平台管理接口。
3. 后端把动作转换为沙箱接口请求。执行命令时，`E2BSandbox.execute` 实际调用 E2B 的 `commands.run`，同时指定工作目录和超时。
4. 沙箱中的执行服务启动真实进程。Python 解释器从该工作区读取 `hello.py`；写入和编辑工具也要修改这一环境中的文件。
5. 后端返回输出、退出码或执行错误，框架将它们作为对应工具调用的结果加入上下文。
6. 模型读取观察，再决定继续检查、修改后重跑，或者给出回答。结束时，由调用端负责交付所需文件和释放环境。

其中，Agent 的“思考”和程序的“执行”通过工具结果连接。代码缺依赖时，进程可能返回错误；工具结果让模型有机会识别错误并提出下一步动作。修复有没有生效，则要看后续执行读到的文件和环境状态。

这一官方任务也提供了直接的检查对象：工作区内是否存在 `hello.py`，文件内容是什么，命令有没有执行结束，退出状态与输出是什么。模型说“完成了”只是最终回答，文件与执行结果才让这句话有可检查的依据。

## 二、工作区让相邻动作能够接起来

要完成上面的过程，单独提供一个“运行命令”接口还不够。Agent 会先写文件，再运行，再读取报错并修改。每个动作必须指向相同的环境和约定目录，否则上一轮产生的变化无法成为下一轮的输入。

工作区可以从本地目录开始，也可以位于容器或虚拟机中。其关键是有稳定的环境身份和可持续访问的文件状态。应用在开始任务时创建或连接环境，保存环境 ID；后续工具调用通过这一绑定找到它。环境 ID 应由应用根据当前用户和任务解析，不能让模型自行指定一个任意环境就获得访问权。

文件工具通常需要读取、列目录、写入和编辑。写入适合建立新文件或替换完整内容；编辑更适合对已有内容做定位替换或应用补丁。无论工具名称叫什么，最终都需要将字节变化落实到同一文件系统。补丁若找不到目标上下文，应返回失败信息，让 Agent 重新读取后再修改，而不是宣称已经成功。

这些工具可以有不同实现。E2B 提供文件读写接口；Deep Agents 的 sandbox 后端也可以把文件操作转成在沙箱内执行的脚本。以其文本编辑为例，工具收到文件路径、旧文本和新文本后，后端在沙箱内运行 Python 程序，重新读取文件、查找旧文本，确认命中符合要求，再替换并写回。默认情况下，找不到旧文本或命中多处会返回错误；明确要求全部替换时才修改所有命中。结果中的替换次数或错误信息回到工具调用，让 Agent 知道这次编辑发生了什么。

OpenHands 则有专门的文件编辑与终端工具。**读写 API、补丁工具和 shell 都可能改变文件，环境提供的是共同落点，工具决定怎样表达动作和反馈结果。**

命令执行还需要明确三个条件：

| 条件 | 实际影响 | 实现时怎样处理 |
|---|---|---|
| 工作目录 `cwd` | 相对路径和程序入口从哪里解析 | 为工作区设定默认值，并允许受控选择子目录 |
| 环境变量 `env` | 程序怎样发现依赖、配置和外部服务 | 从受控配置生成，不让模型随意读取或覆盖平台凭据 |
| 运行用户 `user` | 进程能够读取、修改哪些文件 | 由环境配置决定，按任务需要授予权限 |

连续工作区也不意味着每条命令都共享一个 shell。通过独立进程运行的两次命令，通常不会自动继承前一次 `cd` 或 `export` 的结果。调用端可以每次显式传入目录和环境变量；确实需要交互式 shell 时，再使用持续终端会话。

OpenHands 当前终端实现体现了后一种选择：根据平台和可用工具使用 tmux、subprocess 或 PowerShell，并在终端会话中执行命令。这里的会话保存能力来自具体终端实现，不能由“文件仍在”推导出来。对大多数文件处理任务，先把目录、依赖和文件状态固定，已经能支撑连续的编辑与执行。

## 三、怎样把模型、工具和环境接起来

一套最小实现可以按三组职责组织。第一组是运行控制，决定何时创建环境、把它绑定给谁、何时回收；第二组是工具适配，接收框架动作并调用执行接口；第三组是环境内执行，真正读写文件、启动进程和收集结果。它们可以放在同一个服务，也可以分别部署。

![Deep Agents与E2B的执行关系：控制侧Agent循环经工具适配连接沙箱内文件与进程，观察结果返回模型；环境管理贯穿创建、绑定与回收](/assets/images/posts/agent-runtime-workspace-mechanism.png)

图采用 Deep Agents 与 E2B 的部署方式：循环位于调用端，实际命令在远程沙箱中执行。OpenHands 的远程 AgentServer 则可以把循环和工具一起放进工作区环境，通过 HTTP 与 WebSocket 接收客户端控制并返回事件。因此，图中的职责划分可以复用，部署位置要按实际方案确定。

### 先准备模板，再分配环境

环境首先需要能够执行目标任务。镜像或模板应包含基础操作系统、语言运行时、常用系统库和工作目录。代码任务可能需要 Python、Git 或 Node.js；浏览器任务需要浏览器及配套依赖。缺少这些条件时，工具接口即使调用成功，也只能得到程序不存在或依赖不满足的错误。

常用且稳定的依赖适合进入镜像，任务独有的依赖可以按锁定文件安装到环境中。前者减少重复准备，后者保留灵活性。依赖来源、版本和安装权限也决定环境能否重建，不能完全交给模型临时猜测。

应用随后通过环境服务创建实例，指定模板、资源限制、最长存活时间和网络规则。服务检查申请者身份与配额，安排计算节点启动环境，等待环境内执行服务可用，再把连接信息交给工具后端。OpenHands 的 `DockerWorkspace` 就会等待容器内 AgentServer 的健康接口，环境尚未就绪时不进入正常调用。

任务材料可以来自仓库检出、用户上传、数据库导出，或者从 S3、MinIO 等对象存储载入。它们负责提供工作区的初始内容；runtime 的执行模型不依赖某一种存储。材料就绪后，应用固定工作目录，开始接收 Agent 动作。

### 用现有沙箱接通最小闭环

E2B 官方集成示例的核心接线可以压缩成下面这段。它是接线节选，`model` 代表调用端已按模型提供商初始化的模型对象：

```python
from deepagents import create_deep_agent
from e2b import Sandbox
from langchain_e2b import E2BSandbox

sandbox = Sandbox.create(timeout=600)
try:
    backend = E2BSandbox(sandbox=sandbox)
    agent = create_deep_agent(model=model, backend=backend)
    result = agent.invoke({
        "messages": [{
            "role": "user",
            "content": (
                "Create hello.py that prints 'Hello from E2B', "
                "run it, and show the output."
            ),
        }]
    })
    print(result["messages"][-1].content)
finally:
    sandbox.kill()
```

调用端需要安装 Deep Agents、`langchain-e2b`、E2B SDK 及模型提供商依赖，配置 E2B 与模型访问所需的凭据。模型凭据供调用端请求推理服务，E2B 凭据供调用端管理环境；这个接线并不要求把两者写进工作区供生成代码读取。

这里最重要的配置是 `backend`。它使框架中的文件和执行工具指向已创建的 sandbox。`Sandbox.create` 负责分配环境，`agent.invoke` 进入模型与工具循环，`kill` 结束环境生命周期。实际任务若要交付文件，应在释放环境前通过文件接口取出成果；最终回答中的路径不会自动把远端文件复制回来。

该后端的执行入口把命令发送到 `sandbox.commands.run`，并带上后端配置的工作目录和执行超时。它将标准输出、标准错误合并为工具输出，同时保留退出码。因而模型看到的观察结构，既取决于环境原始接口，也取决于适配器怎样整理信息。

采用现成服务时，应用主要完成环境绑定、工具接线和任务生命周期。自建执行服务时，还要实现环境分配和环境内服务：前者管理实例、身份与资源，后者处理文件请求，启动子进程并采集结果。E2B 的控制 API、节点 orchestrator 与环境内服务，以及 Daytona 的 API、manager、runner 与沙箱内 daemon，都展示了这种分工。它们是可以参考的实现对象，不要求第一版就拆成同等数量的服务。

最小版本应先接通一条清楚的路径：创建环境，写入文件，在指定目录执行，取得结果，导出文件，再销毁环境。每一步都应能凭环境 ID 找回对应对象。等这一闭环成立，再引入排队、环境池和跨节点恢复，才能知道新增复杂性究竟改善哪一步。

## 四、把进程状态变成 Agent 能使用的观察

执行接口需要回答两类问题：命令是否还在运行，以及已经产生了什么结果。短命令可以等待结束后一次返回；长命令则应先返回进程句柄，之后支持读取状态、等待、获取输出和取消。

进程句柄至少要能定位环境中的那个执行者。应用保存环境 ID 和进程标识，才能在下一次请求中继续观察。E2B 的后台命令官方示例就是先启动进程，随后重新连接 sandbox，再通过 PID 连接已有命令。这种重连接回的是原进程；重新调用启动接口会产生另一次执行。

这个差异决定了断线后的动作。客户端失去连接时，应先确认原进程状态，再决定等待、取消还是重跑。立即重跑可能让两个进程同时编辑同一份文件，或重复发出外部请求。重试策略属于上层任务控制，但执行层必须提供足够状态，让上层作出判断。

### 分清等待时间、执行时间与环境寿命

它们限制的是不同对象：客户端愿意等多久，命令允许运行多久，整个环境可以保留多久。等待结束时，进程可能仍活着；进程被终止时，环境和部分文件可能仍在；环境被销毁后，进程和临时文件都会失去依托。

E2B 后台命令文档具体区分了启动与重连：`commands.run` 的命令超时会终止进程，`commands.connect` 的超时限制客户端等待。Deep Agents 的 E2B 适配器还有自己的命令默认值。接入时必须沿着实际调用入口检查参数，不能把外层等待时间误当作进程已经停止的依据。

取消也需要明确动作。停止读取输出、关闭页面和请求终止进程，分别改变不同状态。执行端应提供取消入口并返回后续进程状态；已发生的文件修改或外部请求则要继续按实际结果处理。

### 让反馈既可读，也足够完整

模型需要足以决定下一步的信息：执行了什么、是否结束、退出码，以及相关输出。完整日志可能很大，适合持久保存，再把末尾错误、相关片段或可继续读取的位置交给 Agent。输出被截断时，要让模型知道还有内容，避免把不完整信息当作全部结果。

原始 stdout、stderr 可以分别保存；某些终端和适配器会把它们合流。工具层应忠实反映所用接口，不给模型一个实现中不存在的精细分类。OpenHands 的动作与观察事件还会关联工具调用和动作标识，使一次输出能对应到发起它的动作，这比仅保留一段无来源的终端文本更适合排错。

进程成功退出后，任务仍需按目标检查。修改程序可以运行测试或检查补丁；生成文件可以解析或渲染。检查结果再次成为观察，决定继续修改还是交付。[Agent 评测体系设计](/posts/agent-evaluation-system-design/)进一步讨论了如何将执行成功、结果正确和任务目标分别评价。

## 五、隔离、权限和资源决定环境能做什么

环境可以执行模型生成的程序，也可能安装依赖、访问网络和处理敏感文件。因此，多用户服务从第一版就需要环境授权、资源限制与访问策略。这些配置直接决定程序可读什么、能连接哪里、最多消耗多少计算资源。

本地进程是最直接的起点，适合受信开发环境，但它会继承宿主的身份与文件访问条件。容器通过 namespace 隔离资源视图，使用 cgroup 限制资源，仍共享宿主内核；挂载目录、容器权限和暴露的宿主接口会改变实际边界。gVisor 增加用户态系统调用处理层，VM 或 microVM 则使用独立 guest kernel。选择哪一种，需要同时考虑要运行的程序、兼容性和隔离要求。

这些是隔离机制的比较。托管还是自建，是另一项运维选择：使用托管 VM 仍要配置访问规则，自建容器也不等于已经解决多租户管理。E2B 的 microVM、Modal 提供的不同沙箱后端，分别给出了可用实现；采用时应回到具体环境类别和配置判断。

文件系统隔离与网络访问还要分别处理。环境只能看到自己的目录，并不意味着其中的程序不能请求外部 API。应根据任务设置允许的网络目的地，限制运行身份与凭据范围。E2B 官方互联网访问文档明确提供出口规则；如果任务需要调用一个外部服务，就要同时配置可达性和该服务的授权。

凭据也不必全部进入环境。调用模型的密钥可以保留在控制侧；程序确需访问外部服务时，可以使用限定范围的短期凭据，或采用支持请求注入的代理机制。E2B 的 secrets 注入就是后者的一个实现：由环境外的代理在匹配请求上注入所需信息。这样，网络能力和秘密的持有位置可以分开设计。

资源策略至少覆盖 CPU、内存、磁盘和存活时间。大量输出会占日志空间，安装依赖会消耗磁盘，后台服务会持续占资源。环境服务需要记录占用并执行到期回收；仅在调用端正常结束时运行清理代码，无法覆盖客户端崩溃或进程失联的情况。

## 六、需要持久化时，先确定要延续什么

连续编辑需要跨工具调用保留文件；任务跨天继续，可能还需要保存依赖、进程和对话。这几种持久化分别作用于不同对象，应按任务需要选择。

| 要延续的内容 | 保存位置或机制 | 恢复后得到什么 |
|---|---|---|
| Agent 的消息、计划和工具事件 | 框架会话存储或任务记录 | 可以重新组织下一轮决策 |
| 源码、输入和中间文件 | 持久卷、文件导出或文件系统快照 | 可以读取原文件，再启动程序 |
| 内存变量与运行中进程 | 支持相应语义的内存快照或暂停 | 有条件地继续计算现场 |
| 已交付文件和补丁 | 独立成果存储 | 环境删除后仍可取得结果 |

E2B 的持久化文档区分保存内存与文件的模式，以及仅保存文件系统的模式。后者恢复后重新启动环境，适合保留目录与依赖再继续执行。Modal 的文件系统快照也展示了从保存的文件状态创建新 sandbox 的路径，挂载的 Volume 另有自己的寿命。

对以文件为中间结果的任务，导出文件、记录依赖、恢复时重新启动程序，往往已经满足需求。只有确实需要延续长时间计算的进程时，才需要进一步考察内存恢复。此时还要检查恢复后连接如何建立，外部授权是否仍有效，而不能只看接口是否叫 `pause`。

上层任务也要保存环境和进程的关联。任务可以重试，某次尝试可能换一个环境；一个环境也可能承接多轮动作。把任务 ID、环境 ID 和 PID 分开，才能解释“任务还在，但上一次进程已经结束”或“对话恢复了，但需要新建环境”。[Pi 的 Agent 循环与持久任务设计](/posts/pi-agent-runtime/)讨论的是与此相邻的上层恢复问题。

交付是这条生命周期的收尾：选出成果，执行目标所需的检查，通过下载或独立存储保留，再回收计算环境。已经交付的文件应有环境之外的读取入口，避免使用者拿到一个随着 sandbox 删除而失效的临时路径。

## 七、按动作需要决定第一版做到哪里

如果 Agent 只调用查询或业务 API，现有工具服务就可以承担执行，未必需要通用文件工作区。若要反复读代码、编辑、安装依赖和运行测试，就需要能够跨动作保留状态的环境。长时间计算或运行开发服务，进一步要求进程句柄、日志、端口访问和明确的取消方式。

实现路线可以从这些需求收敛。已有 Agent 框架、希望快速增加文件与代码执行能力，可以参考 Deep Agents 与 E2B 的后端接线；需要把 Agent 循环也放到远端工作区，则可以研究 OpenHands AgentServer 的部署。需要自己控制基础设施时，复用容器或 VM 管理能力，再实现环境授权、工具接口和回收，比一开始就设计全套快照平台更容易形成可检查的闭环。

第一版的完成条件应落在具体动作上：同一个环境能够被可靠找到；文件修改被下一条命令读到；执行状态和输出能够回到 Agent；成果在删除环境后仍可取得；越权请求和超限运行被确定的程序规则拦住。随后加入的浏览器、持久卷、后台任务或暂停恢复，都应对应已有任务的一项真实需要。
