给 Agent 一套可以读文件、写文件、编辑代码和执行命令的虚拟环境，再把 MinIO 中的材料载入其中，是一个很具体的工程需求。模型负责选择下一步操作，环境负责让操作真正发生：文件会被改写，依赖会被安装，进程会持续运行，成果还需要送回对象存储。

这里的 Agent runtime 指模型工具实际操作的**可执行工作区及其管理接口**。搭建它，既要回答“命令在哪里运行”，也要回答“这次运行读了哪份输入、断线后怎样继续、哪些文件已经交付”。这些问题连接起来，才是一项文件处理任务的完整生命周期。

## 一、执行环境持有什么，任务服务还要持有什么

先观察一次编辑循环：Agent 读取代码，运行命令，看到错误，修改文件，再次运行。后一轮必须读到前一轮的修改，命令也必须在预期目录和依赖环境中执行。因此，可编辑 workspace 的关键是连续的文件状态，以及可观察、可控制的进程。

E2B 的公开文件接口体现了这种连续性：`files.write` 把字节写入 sandbox 的路径，`files.read` 再把文件内容取出；命令接口则启动真实进程。官方上传示例既包含本地文件，也包含从 HTTP 获取字节流后写入 sandbox 的路径。这条公开路径展示了外部字节成为工作区文件的过程。

不过，操作发生的地方与任务完成的依据，需要分别保存。可以据这些公开接口，将状态拆成四类：

| 状态 | 具体对象 | 主要持有者 | 用来回答的问题 |
|---|---|---|---|
| Agent 决策状态 | 消息、计划、下一次工具调用 | Agent 框架 | 为什么选择这个动作？ |
| 执行状态 | sandbox ID、PID、工作目录、退出码 | 执行服务与进程管理器 | 命令是否还在运行？ |
| 文件状态 | 输入、修改后的代码、依赖、临时文件、产物 | workspace 文件系统 | 下一次操作实际读到什么？ |
| 交付状态 | 输入版本、尝试编号、输出对象、提交记录 | 上层任务服务 | 哪套成果可以交给使用方？ |

这是用于设计系统的分类，不是厂商内部数据库的字段说明。它能解释几种常见分歧：文件存在时，写文件的进程可能还没结束；进程退出码为零时，文件内容可能仍不满足任务要求；上传请求断线时，对象可能已经保存成功。

[Pi 的 Agent runtime 与持久任务设计](/posts/pi-agent-runtime/)讨论了运行循环和任务恢复。本文进一步向下看：循环触发的工具，如何操作进程、文件和外部对象。上层可以决定重试，下层仍需要告诉它哪些变化已经发生。

## 二、从 MinIO 载入材料，首先固定“这份输入”

对象存储提供 bucket 和 key，文件工具提供路径。将二者接起来的过程通常称为 staging：把选定对象物化到工作区，让命令和编辑工具通过本地路径处理。

显式 staging 的好处在于，控制方可以清楚记录哪份对象成为了哪份文件。对象 key 标识一个名字；如果同 key 会被覆盖，它并不足以固定一次任务的输入。启用版本控制并且目标版本仍被保留时，可以用 `versionId` 指定对象版本。未指定版本的读取则面向当前版本，重试时可能拿到更新后的内容。

MinIO Go SDK v7.4.1 的 `GetObjectOptions.VersionID` 会编码为请求中的 `versionId`。同一组选项还提供 `SetMatchETag`，生成 `If-Match` 条件。它们承担不同职责：版本选择决定读哪一份历史对象，ETag 条件检查所请求对象的 ETag 是否符合预期。

再加上内容校验，输入身份实际上有三个维度：

| 信息 | 作用 | 无法单独解决的事 |
|---|---|---|
| bucket、key、versionId | 定位本次指定的对象版本 | 不能代替下载后的字节检查 |
| ETag | 支撑条件请求和并发判断 | 不普遍等于整文件的 MD5 或 SHA-256 |
| size、明确算法的 checksum | 比较预期字节与收到的字节 | 不能代替身份授权或历史版本选择 |

尤其是 multipart 上传，ETag 不能直接按“全文件 MD5”理解。将版本、并发标识和内容摘要混为一个字段，会让恢复程序不知道自己是在判断版本变化，还是判断传输内容变化。

### 让输入清单与文件映射一起落地

参考设计可以先由任务服务生成输入清单，包含已授权的对象、指定版本、预期大小和内容摘要，再安排传输组件下载。清单中的 `local_path` 是服务确定的受控映射，Agent 只看到本次允许使用的工作区材料。

下面是字段关系示意，省略了实际值，不是运行回执：

```text
input manifest
  object: bucket + key + versionId
  integrity: size + checksum algorithm + checksum value
  workspace mapping: controlled local_path

staging
  read the selected object version
  write bytes to the mapped path
  verify received size and checksum
  mark this input ready for execution
```

每一步都有可观察对象：读取请求指定的版本、实际写入的路径、收到的字节数、校验结果。下载失败时，任务尚未进入执行；校验不一致时，应先检查版本选择和传输，而不是让 Agent 根据不完整材料继续推理。

E2B 官方文件示例提供了后一半的真实接口路径：控制方获取外部字节，再调用 `files.write`。MinIO SDK 提供前一半的对象读取。将二者连接，意味着控制方负责对象身份与授权，传输组件负责搬运，sandbox 文件接口负责落盘。这个组合没有要求 E2B 原生挂载 MinIO，也没有将 SDK 支持自定义 endpoint 当成兼容性已验证。

### 临时授权解决“能读什么”，路径解决“落到哪里”

可以由控制方签发精确对象的预签名 GET URL，再由传输组件取得字节；输出端则使用指定目标的上传授权。MinIO 的 `PresignedGetObject` 和 `PresignedPutObject` 分别签发对应方法的访问，使用附加签名 header 时还需检查 `PresignHeader` 等具体接口。

预签名 URL 在有效期内通常可以重复使用，不能按一次性凭证设计。使用临时身份签名时，身份到期还可能让 URL 提前失效。暂停后的环境保存着旧 URL，并不意味着恢复时仍有权限下载。

路径也需要服务端确定。对象 key 不天然是可信本地路径；若载入内容还要解包，解包后的条目同样要保持在允许目录中。这个约束直接决定文件身份是否仍然可信：Agent 应修改本次输入对应的文件，而不能借映射规则写到其他任务的材料里。

## 三、命令启动以后，观察的是进程，不只是一次 HTTP 响应

输入准备好以后，Agent 可以读取、编辑并执行。一个同步接口常让人形成直觉：请求成功返回，动作就已经完成。但长任务需要把“启动”和“等待”分开。

E2B 官方 background 文档给出了明确的参考路径：启动后台命令，保存 sandbox ID 和 PID；后续请求重新连接 sandbox，再连接这个进程，等待结束并读取文件。示例里的 `run-codegen` 是文档使用的占位命令，解释的是后台执行与重连接口，不代表一项真实代码生成业务已经成功。

把其对象关系写出来，就是：

```text
commands.run(..., background=True)
  → command handle，包含 PID

控制方保存 sandbox ID + PID + attempt ID

后续请求重新连接 sandbox
  → commands.connect(pid)
  → 对既有进程的 handle 进行等待与观察
```

`connect(pid)` 的含义是重新接入已有进程。它与重新调用 `run` 的差别，会在控制请求断线时显现：原进程仍可能运行，盲目重跑会创建第二个执行者，两者可能同时改写文件或上传成果。

E2B 稳定 2.62.0 的 Python 实现也支持这一解释。`commands.run` 将命令、工作目录、用户和环境变量传入进程配置，启动路径使用 `/bin/bash -l -c`；后台分支返回 handle，前台分支等待完成。因而工作目录与用户是运行输入的一部分，不能只记录一段命令字符串就假定复现条件完整。

### 三个超时约束三个不同对象

一次后台命令至少涉及三种时间限制：

- **请求与连接时限**限制传输建立或调用方等待，具体生效规则取决于接口。
- **命令执行时限**在启动命令的入口上限制任务运行；后台返回 handle 后仍需考虑它。
- **sandbox 生命周期超时**决定整个环境可以存活多久。

E2B 当前《Running commands in background》文档说明：`commands.run` 的默认命令超时为 60 秒，到期会终止进程，即使使用后台模式；`commands.connect` 的同名选项则只限制客户端等待时间。两次调用都可以用 `timeout=0` 取消相应限制。

在稳定 2.62.0 的 Python SDK 中，`timeout` 传给流式 RPC，约束整条命令连接流；签名里的 `request_timeout` 不单独应用于这个流式调用，连接建立还受传输层限制。理解生效位置，比把两个参数名当成两个独立开关更有用；sandbox 本身的生命周期时限仍然另设。

如果只是连接中断或重连等待超时，需要先查询已有进程；需要明确停止时，再调用 `kill` 并检查结果。如果命令已被终止，需要检查退出状态与部分文件；如果整个环境已释放，则应依靠外部记录判断能否从输入重建。将三者都处理为“再试一次”，会丢掉已经发生的状态变化。

### 日志要能追踪，也要有明确的留存位置

长任务需要 stdout、stderr、退出码和文件变化，但模型上下文不适合无限累积日志。控制方可以维护读取位置，将完整日志送到独立存储，只把与当前判断有关的片段交给 Agent，并注明截断。

E2B 2.62.0 的实际更新很能说明这个区别：`retain_output=false` 可以关闭客户端对输出的持续累积，同时保留相应流式接收路径。Python 后台 handle 应按该接口支持的迭代与等待方式消费输出，不能直接套用前台回调方式。接收到输出、客户端保存输出、任务服务持久保存日志，是不同动作。

这些观察也构成后续验收材料。[Agent 评测体系设计](/posts/agent-evaluation-system-design/)强调执行结果与过程约束分别验证；运行环境提供的轨迹，必须包含足够的输入和状态，才能支持这种判断。

## 四、文件生成以后，还要完成一次可解释的交付

命令结束后，先检查输出，再上传。退出码能反映程序如何结束，文件存在能反映某个路径已有内容；任务要求则需要格式、结构或内容验收来判断。对于文档，还可能需要打开或渲染；对于结构化文件，需要按目标格式解析。检查方法取决于真实任务，不能一律以“文件非空”代替。

导出也应有明确范围。由服务确定输出目录和允许的相对路径，避免直接上传 Agent 返回的任意绝对路径。上传之前，应确认对应写入者已结束，或者取得明确的稳定文件版本；否则校验时读到的内容与上传时读到的内容可能不一致。

接下来出现一个对象存储问题：一项任务可能产生多个文件，几个上传请求并不自动组成一笔事务。若消费者按照目录中“现在有哪些对象”读取结果，就可能读到一半成功、一半缺失的产物集合。

### 先保存尝试成果，再发布结果清单

一种参考设计是把每次执行称为一个 attempt，为其分配独立对象前缀。通过检查的文件先上传到本次 attempt 的对象位置；全部成功后，再提交一份小型 manifest，列出对外成果。

```text
attempt output objects
  每个对象有独立 key
  记录上传返回的 versionId / ETag
  记录与已校验文件对应的 size / checksum

committed manifest
  输入对象及版本
  被选中的 attempt
  输出对象的精确位置与校验信息
  任务验收结果
```

这些字段是设计示意。它们解释的关键关系是：**对象已保存与任务已发布分别有状态，消费者通过已提交 manifest 选择完整成果。** 未提交的 attempt 对象可以暂存，后续由恢复或清理程序处理。

若 manifest 保存在支持相应条件写的对象存储，可以用条件避免并发尝试互相覆盖。MinIO Go v7.4.1 的 `PutObjectOptions.SetMatchETagExcept("*")` 会生成 `If-None-Match: *`；`SetMatchETag` 则生成 `If-Match`。前者可用于仅在目标不存在时创建，后者可用于要求现有 ETag 符合预期的更新。实际服务端版本对这些条件的支持仍需要验证，不能从 SDK 能发 header 推出任意兼容部署都已具备同样保证。

这里的条件应放在真正竞争的发布位置。如果每次都向一个全新的 manifest key 写入，那么创建成功只能证明该对象首次创建，不能决定哪次 attempt 成为任务的唯一结果。设计还需一个按任务定位的提交记录，或者在数据库中协调被选中的 attempt。

如果任务状态在数据库、产物在对象存储，两个系统之间仍然没有因此出现全局事务。可以先让对象就绪，再通过受控提交状态对外可见，并用后台对账修复“对象存在但提交未确认”等中间态。消费者遵守提交入口，是这套设计成立的条件。

### 响应丢失和取消，分别怎样解释

上传请求发出后客户端断线，有两种可能：服务端未保存，或者保存成功但回执没有到达。独立 attempt key 让恢复程序有确定的检查位置；结合对象版本、大小和摘要，可以判断成果是否已经存在，再决定补传、提交或清理。若每次重试都覆盖一个没有版本记录的固定 key，判断依据就会弱得多。

取消也要沿状态逐层解释。E2B 的 `commands.kill(pid)` 请求强制终止进程，使用 SIGKILL；它不能保证程序有机会刷新缓冲或进行优雅清理，更不会撤销此前已经完成的 PUT。

对象上传自身也有清理路径。MinIO Go v7.4.1 发布说明修复了调用方取消后仍需中止失败上传的问题，对应 multipart 失败分支调用清理逻辑。这说明取消与清理是需要实现的动作。清理请求仍可能失败，因此未完成 multipart、未提交 attempt 对象和已发布结果，需要按各自状态回收，不能靠一次 cancel 全部抹掉。

由此，取消的任务可能仍有已上传对象；恢复中的任务可能尚未提交成果；已交付任务则可以释放计算环境。它们都能由 manifest 和 attempt 记录解释，而无需让 Agent 根据一句自然语言“我已经完成”重建事实。

## 五、暂停恢复时，先问要保存文件还是继续进程

工作区处理耗时材料时，通常希望暂停计算、保留进度。产品文档中的 pause、stop、snapshot 都与此有关，但保存的对象各不相同。

E2B 当前持久化文档区分 full 与 filesystem 模式：full 保存内存与文件系统，目的是恢复进程和变量；filesystem 模式保留磁盘，恢复时冷启动。前者适合需要延续计算状态的场景，后者适合保留已安装依赖、中间文件，再重新启动程序。

客户端连接仍需重新建立。最新文档还涉及特定自动暂停条件下的 filesystem fallback 和模式事件，SDK 的参数也不能证明所有团队、节点都已开放对应能力。因此，控制方应记录实际保存模式，而不是只记录一个布尔值 `paused=true`，随后假定旧 PID 必然有效。

Daytona 更需要按环境类别判断。研究时稳定客户端是 v0.226.1，官方生命周期表将默认 Container 与 Linux VM、Windows 等类别分开：Container 的 stop/start 与 archive 有文件保存路径，而 pause/resume 和 fork 的支持范围不同。stop 会清除内存、保留文件；Container archive 将文件系统移入对象存储。SDK 中存在 pause 方法，只说明有相应请求入口，不能让所有环境类别自动获得内存恢复能力。

Modal 的官方文件系统快照示例则从另一侧说明边界：先运行命令写入 `/test`，等写入进程完成，调用 `snapshot_filesystem`，再用返回的 Image 创建新 sandbox 并读取该文件。这个例子检查的是磁盘内容延续，无法推出原进程继续运行。其快照不包含挂载的 Volumes；内存快照是另外的 Alpha 能力，当前文档对 active exec、由 exec 启动的后台进程和重连都有具体限制。

| 要延续的对象 | 对应机制 | 恢复后应检查什么 |
|---|---|---|
| 工作区根文件系统 | 文件快照、stop/start、filesystem pause | 文件内容、依赖与工作目录是否符合预期 |
| 内存和运行进程 | 支持该语义的 full pause 或内存快照 | 实际保存模式、进程状态和连接重建 |
| 独立挂载文件 | Volume 或对象存储挂载 | 挂载是否重新接好、可见数据和访问语义 |
| 已交付成果 | 外部对象及提交记录 | 哪套输出已发布、哪些只是未提交尝试 |

该表比较保存对象，不能按品牌直接排列“谁更持久”。同一产品的不同环境与模式，就可能落在不同位置。

### 保存环境以后，外部世界仍会向前变化

恢复程序应把快照与原 input manifest 对照：仍然使用原版本的输入；短期授权过期时重新签发访问，而不是悄悄改为同 key 的最新内容。再检查哪些 attempt 对象已经存在、提交是否完成，最后判断需要接回进程还是重新执行。

内存快照保存不了一个仍然有效的外部会话。对端服务可能重启，URL 可能到期，权限可能改变；已经发生的上传和第三方请求也不会随着虚拟机恢复而倒退。持久工作流可以管理任务历史与重试，环境快照可以延续计算现场，两者必须通过外部副作用记录衔接。

对于单纯希望保留文件的任务，独立存储常比维持整个运行现场更直接。Daytona 的官方 Volumes 示例写入文件后删除 sandbox，Volume 仍保留，用来说明文件存储和计算实例的生命周期独立。它没有证明删除实例后进程仍在运行，也没有提供多任务并发写入的事务保证。

## 六、按工作负载选择，而不是先选一个“全能 runtime”

如果任务只是一次短代码计算，执行器返回结果就足够；需要反复编辑、安装依赖、排错和读取中间文件时，连续 workspace 才成为主要需求；需要长期等待或运行服务时，还要观察后台进程、管理连接和执行时限。

文件访问方式也要独立选择。显式 staging 把版本和字节边界放在载入、导出两处，适合希望清楚记录输入输出的任务。挂载则让程序按文件路径访问外部材料，但其语义取决于实际实现。对象存储不是天然的 POSIX 文件系统；随机写、重命名、缓存和并发更新，都应按所选挂载机制确认。

例如 Modal 的 CloudBucketMount 有 endpoint 配置，当前官方指南明确介绍 S3、R2、GCS，客户端也会序列化自定义 endpoint。这个事实不足以证明任意 MinIO 部署已完整兼容。若采用 MinIO，可以先按本文的显式传输路径建立清晰的数据交接，再根据实际文件访问需求验证挂载方案。

隔离同样需要落在真实环境上。E2B 以每会话 microVM 提供隔离环境；Daytona 提供不同 sandbox 类别；Modal 文档包含 gVisor 和 VM 等运行选择。它们说明执行边界有多种工程实现，采用时还应明确资源限额、运行身份，以及环境可以访问哪些网络目的地。程序要下载依赖、读对象或请求外部 API，这些能力都由网络和身份配置决定，不能只凭“sandbox”这个名称推断。

可以用一项真实目标任务检验采用方案：固定一份授权输入，观察它如何落盘；执行并编辑，确认第二次运行读到修改；中断客户端连接，确认能判断原进程状态；生成并检查产物，确认消费者通过提交记录取得完整输出；最后按选定模式暂停恢复，核对文件、进程和外部成果分别发生了什么。

这些步骤应验证所需机制，不必追求把每个厂商功能都测试一遍。如果只需要文件延续，就将验证重点放在文件和输入版本；如果必须延续进程，则应验证实际环境类别、保存模式与重连；如果交付多个成果，就要让部分上传失败与提交竞争进入验证。

E2B、Daytona 和 Modal 的公开接口已经表明，可执行工作区、文件交换、后台运行和生命周期管理是一组明确的产品能力。这能支持工程选型讨论，不能直接证明市场规模或需求增速。对于一套从 MinIO 载入文件的 Agent 系统，最有价值的采用判断是：**它能否让输入可追踪、修改可观察、交付可确认，并在环境变化后解释已经发生的事实。**
