Agent Runtime 为 Agent 准备和管理执行环境。模型提出读文件、编辑代码或运行程序以后，Runtime 将动作交给相应环境执行，并返回文件变化、输出与运行状态。为了承接这些动作，它还需要管理工作区、进程、权限、计算资源和网络。

这类 Agent 的工作往往跨越多轮决策。上一轮修改的代码要能被下一轮测试读到，长时间运行的程序要能查询和停止，成果要在计算资源回收后仍可取得。平台同时承载多个用户时，还要分开管理各自的数据、权限和资源。这些要求共同决定了 Runtime 的架构，而不仅是选择一种运行命令的接口。

不同项目对 Runtime 的覆盖范围有所不同，有些还包含 Agent 循环和任务调度。这里讨论执行环境及其管理：它向上连接 Agent 框架派发的工具动作，向下组织实际计算资源。理解这些职责怎样配合，才能判断一套实现需要提供哪些能力，以及怎样逐步搭建。

## 一、从工作方式导出运行要求

普通程序的部署通常已有确定入口。文件编辑型 Agent 的执行路径则由模型逐轮选择：先检查目录，再读取文件，随后可能修改、执行、安装依赖，或启动一个需要继续交互的服务。每个动作的结果都会影响下一个动作，运行环境因此成为推理过程的外部状态。

这类工作对 Runtime 有四项直接要求。

第一，**执行必须有连续的落点**。工具调用不能各自进入互不相关的临时目录。文件、依赖和服务需要在约定范围内保留，让相邻动作能够衔接。同时，环境归属于哪个用户、哪次运行，必须能够确定。

第二，**动作要产生可用的反馈**。文件编辑需要说明改了什么或为何失败；命令执行需要提供运行状态、输出和退出结果。反馈还要关联到发起它的工具调用，否则上层无法可靠地把观察放回对应的决策位置。

第三，**运行消耗和影响必须受控**。模型可能选择长时间运行的命令，也可能访问网络、读取凭据或修改文件。资源上限、运行用户和网络规则需要由应用配置并由执行系统落实。把限制写进提示词，不能替代实际权限检查。

第四，**环境与客户端具有不同寿命**。用户关闭页面时，后台进程可能还在运行；模型结束回答时，文件可能仍留在临时盘上；环境暂停后，恢复范围又取决于保存了哪些状态。Runtime 必须为这些变化提供明确行为。

模型推理服务根据上下文生成响应，[harness](/posts/pi-agent-runtime/) 再解析其中的工具调用并派发动作；Runtime 接收这些动作，找到相应工作区和进程接口执行。sandbox 是用于隔离执行的环境边界。将沙箱接入 Agent 应用，还需要绑定身份、返回工具结果并管理回收，这些工作由下面的管理和执行职责共同承担。

## 二、把环境管理与动作执行分开组织

环境的创建和回收，与已经就绪环境里的读写和命令执行，有不同的控制目标。前者决定资源属于谁、放在哪里、允许活多久；后者决定一个具体动作怎样运行、何时完成、返回什么。将这两组职责分开，可以避免每次工具调用都重新承担环境调度，也能让管理服务持续追踪脱离客户端的工作。

参考 E2B 与 Daytona 的管理和执行分工，可以组织出下面的通用架构。这里划分的是逻辑职责，实际实现可以先放在同一服务中。

![Agent应用框架连接环境管理面与工具执行接口；实际执行环境承载文件依赖、进程服务及权限资源，执行观察回到Agent循环](/assets/images/posts/agent-runtime-workspace-mechanism.png)

**环境管理负责把资源准备成可用环境。** 应用带着用户身份、环境配置和资源要求申请实例；管理服务检查授权与配额，选择执行节点，要求节点启动容器或虚拟机，记录环境身份和所在位置。环境内服务通过健康检查、工作区准备完成后，实例才可以交给 Agent 使用。

**工具适配负责把 Agent 的动作接到已有环境。** 框架注册文件与执行工具，适配器接收工具名称和参数，解析当前运行绑定的环境，再转换成具体后端的文件或进程接口。环境身份和用户权限来自应用保存的绑定关系。模型提供的路径和命令只是动作参数，不应直接决定访问哪个租户的实例。

**环境内执行负责改变实际状态。** 它在指定目录和身份下读写文件、创建进程、收集输出、报告退出，并提供查询和停止入口。文件变更发生在工作区；进程有自己的运行标识；较大的输出可以写入日志文件，再向上返回必要片段和读取位置。

管理服务记录环境是否就绪、何时到期、是否仍占用资源，工具接口则报告各次动作的输出与状态。应用异常退出后，管理服务仍要负责回收实例；环境仍然存活时，上层也需要通过执行接口判断内部命令是否已经结束。这两类状态分别支持资源管理和 Agent 的下一步决策。

### 创建完成，是执行端确认过的状态

E2B 的公开架构给出了一条具体创建路径：控制 API 先认证团队、解析模板并选择节点，节点 orchestrator 准备虚拟机的网络、磁盘与内存，恢复模板快照，再向环境内的 envd 发送 `/init`。envd 接收环境变量和访问令牌，完成初始化以后，orchestrator 才回复创建成功；控制 API 随后保存运行实例并返回环境 ID。客户拿到的成功响应，因而对应到环境内服务已经接收初始化的状态。

这条路径跨控制 API、节点与环境内服务，失败位置会影响重试。节点还没有接受任何创建时，换节点重试主要是在等容量；创建请求已经发出、响应却超时，就可能留下已启动的实例。当前 E2B 主线的 v2 创建接口据此区分可重试失败与结果不确定，未知结果不会被当作普通容量不足重建。启用对应幂等路径时，相同键和参数用于找回原请求；节点成功而运行记录写入失败，还会启动异步清理。

这也是管理服务不能只是一个 `create` 包装函数的原因：它要保留请求与环境的关系，在客户端已离开时继续核对资源。Daytona 则由控制面的 sandbox manager 持续对账，runner 从控制面领取创建、启动、停止等工作。两种实现的交接形式不同，都让环境的实际状态拥有持续的管理者。

逻辑分工也不要求 Agent 循环一定在沙箱外。Deep Agents 与 E2B 的组合把循环放在调用端，通过适配器访问远程环境。OpenHands 的 `DockerWorkspace` 可以创建带有 AgentServer 的容器，Agent 和工具在目标环境内运行，客户端通过 REST 与 WebSocket 控制会话、接收事件。部署位置改变后，仍然需要明确谁掌握环境管理凭据、谁调用模型、谁有权执行工具。

## 三、让工作区、工具与反馈形成连续执行

### 工作区保存相邻动作需要的状态

环境就绪后，还要决定 Agent 从什么状态开始。基础镜像适合提供解释器、编译器和系统库；仓库、上传文件或其他输入材料进入明确的工作目录。把常用依赖放入镜像，或通过锁定清单准备，可以减少每轮执行都重新建立依赖的工作，也使后续结果更容易解释。

应用应将文件工具和命令工具绑定到同一工作区。模型编辑的文件若位于一个后端，测试命令却在另一个目录运行，工具各自都可能返回成功，整个任务仍然无法推进。稳定的环境身份、工作目录和文件路径，是连接这两种动作的基础。

连续工作区保存什么，需要精确到对象。磁盘上的文件可以跨命令存在；独立启动的两次进程，通常不会自动继承前一次 shell 中的 `cd`、`export` 或内存变量。对于普通批处理，执行请求显式提供 `cwd` 和受控的 `env` 就比较清楚。需要交互、持续 shell 或终端程序时，再引入终端会话，并提供会话选择和中断能力。

OpenHands 的终端工具采用会话式执行，根据平台与可用工具使用 tmux、subprocess 或 PowerShell。它说明持续终端是一项具体执行机制，不能仅凭“工作区仍然存在”推断 shell 状态也被保存。

### 工具适配需要保留动作的真实含义

工具层向模型暴露的是可理解的动作，例如读取、编辑和执行。后端怎样实现这些动作，可以不同。文件接口可以直接读写，也可以把操作转成在环境内执行的程序；关键是结果能准确说明发生的变化。

Deep Agents 与 E2B 的同步适配路径提供了一个局部例子。模型提出 `edit_file(path, old_string, new_string)` 后，文件工具中间件把参数交给后端。后端在沙箱内运行替换程序：读取当前文件，查找旧文本，检查命中情况，然后替换并写回。默认情况下，找不到旧文本或命中多处会返回错误；明确选择全部替换时，才修改所有匹配位置。替换次数或错误通过对应的工具结果返回模型。

这里的检查让 Agent 能区分“文件已改变”和“定位条件不成立”。如果旧文本已经不存在，合理的后续动作是重新读取并调整编辑条件。它同时说明文件工具的成功应由实际变更决定，不能只因为收到了参数就报告完成。

这条实现没有锁或版本比较，读取与写回之间仍可能有其他进程修改文件。若多个 Agent 共同写一个工作区，设计上就需要串行化写入，或为它们分配独立分支与工作目录，再合并结果。唯一命中检查解决定位问题，并发写入需要另外安排。

命令执行同样要经过完整转换。`E2BSandbox.execute` 将命令、工作目录和超时交给 E2B 的 `commands.run`，沙箱内服务启动进程，结果再被适配成框架使用的返回类型。Deep Agents 随后将工具结果加入模型上下文，进入下一轮决策。模型提供的是工具参数；适配器持有后端调用入口，将这些参数交给指定环境。环境的创建、归属与权限仍由应用管理。

### 反馈同时服务模型和运行管理

面向普通命令，一个执行接口至少需要表达环境、命令、目录、环境变量和执行超时；返回结果需要区分仍在运行、已经退出以及执行端错误。长任务还需要稳定的进程标识，让后续请求能查询、等待或停止。

输出的形式也应由后端语义决定。普通进程接口可以分别收集标准输出和标准错误，终端会话则可能返回合并后的终端内容。Deep Agents 的 E2B 适配器会把输出合并到 `ExecuteResponse.output`，同时保留退出码。因此，统一工具接口时，要说明保留和转换了什么，不能假定所有后端都能提供完全相同的输出结构。

完整输出与模型上下文可以分开保存。模型通常只需要与当前判断相关的片段；完整日志则用于之后查询和排查。返回截断片段时，应同时说明截断及完整内容的位置，避免模型把看不到的部分当成没有发生。

进程退出码、文件变化和任务完成是三层判断。退出码为零说明该命令按自身规则成功结束；文件是否符合要求，要由相应检查确认；这些结果是否足以结束任务，则由上层依据目标判断。Runtime 提供可追踪的事实，harness 才能据此继续或停止。

## 四、用不同的对象寿命设计取消与恢复

一次用户任务可能经历多轮运行，一次运行可能使用多个环境，一个环境又可能承载许多进程。把它们都压成一个会话 ID，会使重试、续用和清理互相牵连。

可以参照前面的管理与执行分工，在应用中保存以下关系。这是一种设计分解，供应商接口未必使用同名对象。

| 对象 | 应保存的主要信息 | 生命周期上的意义 |
|---|---|---|
| 任务 | 用户目标、完成条件 | 目标可以在一次尝试结束后继续存在 |
| 运行 | 本次尝试、动作与事件、结束状态 | 区分重试前后的工作和结果 |
| 环境 | 镜像、资源、位置、工作区和权限 | 可跨动作续用，也可以按运行重新创建 |
| 进程 | 运行标识、退出结果、日志位置 | 环境存活时，进程也可能已经结束 |
| 成果 | 已导出的文件或补丁、归属和读取方式 | 交付之后可以独立于环境存在 |

客户端重连时，应用先根据原运行记录找到环境，再用进程标识查询状态。仍在执行的命令可以继续观察，已经退出的命令则读取已有结果；确认需要重跑后，才创建新进程或新运行。任务、运行、环境与进程分别有记录，应用才能作出这几种处理。

E2B 的官方后台命令示例展示了这一机制：启动后台命令，保存 sandbox ID 和 PID；另一客户端通过这些标识连接，再等待命令结束。原客户端的流式输出回调不会自动重播给后来连接的客户端，因此示例将日志写入文件，供重连后读取。重连标识解决“找到工作”，持久日志解决“看见已经发生的工作”，两者要配合。

超时也需要按对象分别设置。客户端等待超时，意味着调用方停止等待；命令执行超时，意味着执行端应按定义中止命令；环境最长寿命则约束实例整体何时回收。这些计时点和终止行为应在接口中明确表达。用户点击停止时，应用需要发出取消命令或终止环境的动作，并继续查询结果，不能只关闭页面连接。

网络错误还会留下结果不确定的状态：请求可能没有送达，也可能已经启动进程，只是响应没有回来。对于查询可以重新读取；对于启动和写入，管理侧应尽量保留请求与执行对象的对应关系，先查状态再决定重试。若命令已经向外部系统写入数据，重试安全性还依赖该业务操作的去重或幂等安排。环境隔离不能消除外部副作用。

### 从保存文件到恢复执行，有不同成本

恢复能力应从需要保留的状态倒推。只需要继续编辑文件时，可以保存工作区，使用相同镜像重新建立环境。需要保留解释器内存或后台服务时，则要考察内存快照和恢复条件。

E2B 的持久化文档区分保存内存与文件的暂停方式，以及只保存文件系统、恢复时重新启动的方式。Daytona 的管理文档也区分停止、暂停和归档；例如归档可以把已停止环境的文件系统移至对象存储并释放原磁盘。可见“保留环境”可能指不同状态集合，必须按后端确认恢复后还剩什么。

快照的名字同样不足以说明范围。Modal 的文件系统快照保存 rootfs，挂载的 Volume 不在这份快照里。即使采用包含内存的恢复方式，网络连接也可能需要重新建立。选择方案时，应具体列出文件、挂载数据、进程内存和外部连接分别怎样恢复，再决定是否值得承担更复杂的保存机制。

交付则应放在计算环境的寿命之外。应用从工作目录选择成果，将文件或补丁复制到独立存储，记录归属和读取方式，确认交付后再回收环境。对象存储、文件服务或代码仓库可以承担这个出口；它们的选择由输入输出需求决定，不定义 Runtime 的执行架构。

## 五、按代码信任程度选择隔离与权限

工作区和生命周期决定工作如何延续，隔离机制决定它在什么范围内发生。模型生成的命令最终会获得某个操作系统身份，并通过这个身份接触文件、内核接口和网络。选型应同时考虑代码来源、租户关系、系统调用需求和基础设施条件。

| 执行方式 | 主要边界 | 选择时需要承担的工作 |
|---|---|---|
| 本地进程 | 宿主用户和文件权限 | 限定受信代码与可访问目录，避免继承过大的宿主权限 |
| 普通容器 | namespace 提供隔离视图，cgroup 限制资源，共享宿主内核 | 配置挂载、运行用户、capability 与资源上限 |
| gVisor | 用户态应用内核承接 Linux 系统调用 | 检查所需 Linux 接口的兼容性及性能适配 |
| VM／microVM | 独立 guest kernel 与硬件虚拟化边界 | 准备虚拟化节点，并管理镜像、磁盘和网络 |

### 系统调用经过谁，决定隔离改变了什么

可以从同一段脚本的动作看这几条路线：读文件、创建进程或访问网络，最终都需要操作系统服务。普通容器中的进程向宿主Linux内核发出系统调用，namespace限定它看到哪些对象，cgroup分配资源，seccomp等机制筛选允许的调用。执行这些检查和提供服务的，仍是宿主内核；为了兼容更多程序而放宽允许范围，也会扩大不受信代码直接触达的内核接口。

gVisor把这条路径改为“应用调用→Sentry实现→受限宿主访问”。Sentry在用户态实现Linux接口；例如 `getpid` 直接查询它维护的进程表，返回沙箱内的进程标识。需要宿主协助时，再由Sentry及文件访问等配套组件发起各自受限的操作，应用调用并非原样逐条转发。租户代码首先面对另一份接口实现，宿主内核不再直接处理它提出的整套Linux调用。

microVM则让脚本先调用guest kernel。以Firecracker为例，guest内核处理文件、进程等请求，设备I/O再经过VirtIO设备模型与KVM虚拟化边界抵达宿主资源。每个Firecracker进程管理一个microVM，宿主还用jailer、seccomp和cgroup约束这个进程。平台由此要维护guest内核、镜像和虚拟设备，获得的是以独立guest为单位组织执行的方式。

三条路径的代价来自具体交接。普通容器直接使用宿主Linux接口，适合受信工具链或能够接受共享内核前提的工作；gVisor重实现接口，需核对所用运行库与系统调用支持，频繁文件、网络操作还会经过额外软件层。它的官方性能指南将这些成本区分为额外CPU与内存开销，可能影响延迟、吞吐或实例密度，不能只用启动速度判断。若程序依赖未实现的内核能力，就要调整程序、选择其他后端，或使用具有所需guest内核能力的VM。

对允许不同客户提交代码的平台，隔离单位还要对应租户边界。把多个互不信任客户放进同一个gVisor沙箱，会让它们共享沙箱内的文件和服务；官方因此建议分开沙箱。选择microVM时也应分别分配guest及其数据。隔离后端决定请求经过哪层内核与设备，挂载什么文件、提供什么凭据及开放哪些网络，仍由每个环境的配置决定。

这些是代码与宿主之间的隔离路线，托管平台和自建服务则是运维安排，两者属于不同选择。一个平台也可能提供多种后端，例如 Modal 同时提供 gVisor 与 VM。应根据实际运行方式判断边界，不能从品牌名称直接推定。

隔离机制需要与权限配置一起使用。容器如果挂载了宿主敏感目录或管理 socket，运行中的程序就获得了这些额外入口。E2B 将管理访问与环境内执行分成两次认证。管理 API 根据团队 API key 或身份令牌确定调用者；创建成功时返回 envd 的访问令牌，SDK 保存它，调用环境内的文件和命令接口时带上 `X-Access-Token`。直接绕过 SDK 调 controller，也要提供这份令牌，上传与下载另使用预签名地址。

应用可以据此绑定自己的用户和环境：先用服务端已认证用户查到获授权的环境，再由服务端持有对应连接信息并发起调用；环境 ID 负责定位，令牌负责访问。若把令牌交给浏览器或Agent，等于将相应执行能力交给它，应按产品的委托范围安排。当前 SDK 2.51.0 及以后始终创建启用 secure access 的环境，旧 `secure=False` 参数已被忽略；旧模板需要满足 envd 的兼容要求。

网络访问需要单独控制。程序下载依赖、调用业务 API 和读取云元数据，都经过网络路径，文件系统隔离不会替这些请求作授权判断。环境配置应明确允许的出口；业务凭据只授予当前任务所需范围，平台管理凭据由管理侧掌握。

E2B 提供通过出口代理在环境之外为匹配的 HTTPS 请求注入凭据的方式。这是减少明文凭据进入工作区的一种具体实现，但访问哪些目标、允许进行什么业务操作，仍要有相应规则。模型接收到“可以调用服务”的工具描述，与执行系统实际授予权限，应当是同一组能力的两种表达。

资源控制也要落到不同层次：单个命令有执行期限，环境有 CPU、内存、磁盘和存活时间限制，用户还有总配额。否则即使每个实例都受限，应用仍可能通过连续创建实例耗尽总体资源。面向多租户时，这些控制应与环境服务一起设计。

## 六、从需要保留的状态选择实现范围

第一次实现可以直接选用已有 SDK，先把一个固定环境接到文件和进程工具。需要留下的最小记录不是所有中间组件，而是“用户/运行—环境ID—工作目录”的绑定，以及命令启动后的进程ID和成果出口。应用用这份绑定把读写和执行落在同一个环境中，再从真实输出继续模型循环。Deep Agents 的 `E2BSandbox` 后端承担工具转换，创建与回收由调用它的应用安排。

管理服务是否需要独立部署，取决于工作是否超出一次请求寿命。只运行短命令且同步导出成果时，现有 SDK 加到期回收就能形成起点；客户端断开后仍须继续时，应保存环境和进程标识，将输出写入可重读的日志，再让持续服务追踪到期与清理。前面 E2B 的创建确认、未知结果和 Daytona 的状态对账，正是这层服务需要处理的工作。

下一项投入由状态需求决定。启动准备占主要时间，可以把依赖固化到模板；空闲占用太高，选择停止、暂停或归档；需要恢复运行现场，再比较内存保存与重建服务的成本。文件保留、进程存活、外部连接重建各有具体机制，应该按需要逐项引入。

多租户会改变这个起点的前提：应用自己的身份绑定、环境访问令牌、总体配额和网络出口，应在允许用户执行之前接通。计算环境结束后，成果从工作区导出到独立存储，交付因而不必依赖那台实例继续存活。
