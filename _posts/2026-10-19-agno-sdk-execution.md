Agno 是用 Python 构建 Agent 应用的框架。开发者提供模型、指令、工具和存储，SDK 将它们组织成能够接收输入、执行工具并返回结果的程序。它既能作为一个函数被应用调用，也能通过 AgentOS 以 API 服务的形式运行。

SDK 最重要的三个组织单元是 Agent、Team 和 Workflow。Agent 让模型选择下一步工具；Team 将工作委托给具有独立配置的成员；Workflow 用程序安排步骤、分支和数据传递。三者可以嵌套，区别在于谁持有控制权，而不是成员数量多少或回答长短。

Agno 官方的工具示例、双成员协调示例和内容规划 Workflow，分别展示了模型选工具、leader 分派成员和 Python 安排步骤的过程。

## Agent 把模型选择连接到实际工具

Agent 对象主要把四类配置放在一起：模型适配器决定请求送到哪家模型服务，指令说明要完成什么，工具提供可执行能力，数据库和上下文配置决定哪些过去的信息进入当前运行。

应用调用 `agent.run(input)` 后，Agno 根据这些配置组织消息和工具定义，请求模型。模型可以返回回答，也可以返回工具名与参数。SDK 查找已注册实现，校验并执行函数，将结果与对应调用标识一起交回模型。后者随后继续判断，直到产生回答或满足停止条件。

```text
应用输入 → 模型消息与工具定义 → 模型提出调用
                              ↓
应用取得 RunOutput ← 模型继续判断 ← Python 执行与结果回填
```

工具因此有两种对应形式：模型看到的名称、说明与参数 Schema，以及运行进程持有的可调用函数。普通 Python 函数可以通过签名、docstring 和类型提示转换为工具描述。SDK 注册实现以后，模型提出的调用才有地方落地；仅在提示词中提到一个工具名称不会提供它的功能。

官方 `HackerNewsTools` 是这条关系的具体对象。它将获取热门故事、读取用户资料等方法注册为工具。`get_top_hackernews_stories` 接收所需条数，工具实现通过 HTTP 取得故事数据，再把返回材料交给 Agent。模型决定是否查询、查多少以及如何使用结果；取得数据和处理网络响应由工具代码执行。

这也说明程序该检查什么。模型请求正确名称，只证明选择了一项已声明能力；工具成功返回，说明执行取得了某份材料；最终摘要是否忠实，则要对照这份材料。`RunOutput` 中的内容、消息和工具执行记录使应用能够检查这些不同对象。只显示 `content` 会省去运行细节，不能据此判断所有必需操作都已经发生。

异常处理同样属于循环的一部分。某些工具错误会作为观察反馈给模型，让它修正参数或选择其他动作；应用若规定失败必须停止，应在工具、运行控制或后面的流程层落实这个条件。把“必须先查”写成指令，仍然是在影响模型选择。

## Team 在成员之间建立委托关系

需要不同指令、工具集合或上下文时，可以把工作交给独立成员。Agno 官方 `01_basic_coordination.py` 定义 Planner 与 Writer，由一个 Team 协调它们，为一个小型编码项目形成三步规划。每个成员是独立 Agent，Team 自己也有模型和指令。

这个例子的作用是显露运行关系，不是证明两个角色比一个 Agent 的规划质量更高。在 coordinate 模式下，leader 的模型通过委托工具选择成员并形成任务。SDK 找到成员，启动成员运行，取得结果以后再回到 leader。成员内部仍可执行前一节的模型—工具循环。

```text
Team 输入 → leader 形成委托 → 成员独立运行
                ↑                  ↓
             继续判断 ← 委托结果返回
```

每次成员运行都要接收自己的任务与上下文，再将结果交还 leader。这增加了模型调用和交接，也让成员可以分别配置工具与指令。当成员只是在复述同一份材料时，这种额外组织未必值得。

信息交接是关键设计。`add_team_history_to_members` 和 `share_member_interactions` 决定某些团队历史与成员交互是否被传给成员，默认并非把所有内容共享给所有人。leader 给出的 `task` 因此应包含当前成员需要的目标和约束；未传入的材料，需要通过相应共享配置或其他已配置的获取方式补充。

在官方规划例子里，Planner 负责拆工作，Writer 负责表达。若最后的内容要保持某项范围，范围必须进入相关成员收到的任务或共享材料。leader 理解的条件不自动等于 Writer 理解的条件，独立上下文既是分工手段，也是信息可能丢失的位置。

Team 还具有多种模式。这里解释的是协调式委托：选择一个模式是在决定成员如何被调用和结果怎样流回，而不是为相同控制流换一个名字。研究具体应用时，应追踪所选模式的实际调用路径。

## Workflow 将必须遵守的顺序写进程序

Workflow 适合组织明确的步骤依赖。某些过程需要查询完成以后才能处理材料，某些条件不成立就不能进入下一步；此时由 Python 编排顺序，比让模型每轮重新决定是否遵守更直接。

Agno 既支持显式 Step 列表，也支持函数式执行。官方 `function_workflow.py` 是后者的具体例子：研究 Team 包含 Hacker News 与 Web 两类 Agent，执行函数先调用 `research_team.run()`，读取它的内容，再把原主题与截取的研究材料交给 `content_planner.run()`，最终返回规划内容。

这个例子里，研究是否先于规划由 Python 调用顺序确定；研究内部向谁委托由 Team 控制；成员怎样查询由 Agent 与工具循环控制。一项工作里因此同时存在三层决定。把所有层都称作“自主协作”，会掩盖真正需要修改的位置。

其中研究材料只取前 500 个字符，是示例自身的数据选择。它使研究输出进入规划输入，但也可能丢掉后面重要的事实。这个实现说明了数据怎样传递，并没有证明这种截断足够支持完整内容策略。实际应用应该按下一步的判断需要构造材料，而不把示例中的截取长度当作推荐值。

显式步骤使用 `StepInput` 和 `StepOutput` 传递数据。函数可以读取原始输入、最近输出，或按步骤名取得先前结果；Agent 步骤接收哪些前文取决于相应配置和结构。若最后一步同时需要请求、检索结果和校验意见，应明确组装它们，不能假设所有历史输出都会自动出现在模型上下文中。

`StepOutput(stop=True)` 可以表达后续停止，条件、路由、循环和并行结构则表达其他执行关系。对金额上限、字段有效性和审批结果等可明确计算的条件，函数适合落实强制判断；难以确定性编码的解释和判断仍可以交给 Agent。流程次序明确，模型生成内容仍需要它自己的质量检查。

## 数据保存与模型读取是两项配置

运行持续到多轮以后，Agno 需要处理几种不同的数据。它们可能共享底层数据库，却服务于不同问题：

| 数据 | 保存什么 | 怎样影响当前运行 |
|---|---|---|
| Session / runs | 会话及每次运行的消息、结果等记录 | 由历史配置决定哪些记录进入上下文 |
| Session state | 应用维护的结构化状态 | 工具通过 RunContext 等入口读取或更新 |
| User memory | 与用户相关的长期信息 | 按记忆机制更新，并选择用于后续会话 |
| Knowledge | 摄入并建立索引的外部材料 | 按当前问题检索，再加入模型材料 |

配置 `db` 让相关记录能够留下；开启 `add_history_to_context` 才会将选定历史加入请求，`num_history_runs` 等参数再决定范围。把数据持久保存与每次全部发送给模型分开，才能兼顾回查、费用和当前相关性。

结构化 state 适合记录应用需要保持的进度与选择。工具所需的 `RunContext` 由框架注入，不要求模型填写可信身份。用户记忆则需要相应的提取或管理配置，`user_id` 用于关联记录，实际认证与访问权限应由应用绑定。一个可任意填写的字符串不能提供身份保证。

Knowledge 还有摄入、索引与检索链路。保存聊天记录不会自动获得文档检索，配置向量存储也不会自动使每份回答有足够证据。应用需要检查检索得到的材料是否对应问题，原始来源是否仍可定位，以及模型如何使用这些材料。关于检索与原文阅读的架构可进一步看[知识库设计与治理](/posts/enterprise-knowledge-governance/)。

`output_schema` 则处理输出结构。Pydantic 类型等约束有助于解析结果，数字和引用仍要与来源对应。数据类型正确、来源一致、业务判断正确，是三个不同的检查目标。

## AgentOS 把执行组件提供为服务

前面的 Agent、Team 和 Workflow 已经能够被 Python 直接调用。需要供网页或其他应用使用时，AgentOS 将这些配置好的组件注册为 API，提供流式运行、会话、存储和追踪等服务入口。Control Plane 再连接这项服务，给人提供运行与观察界面。

服务层增加了部署、请求身份和资源管理。JWT 等认证配置确认调用者，工具与数据层检查其可访问范围。数据库保存运行记录。若要求中断后继续执行，还需要选择相应的持久执行路径；仅保存会话，无法确定任意一处中断应从哪里继续。

持续任务还要选择支持的队列存储并部署 worker。队列可以重新安排工作，外部工具已产生的写入则依赖目标 API 的幂等和查询能力。关于服务化与长期任务的取舍，见[Paperclip 与 Agno AgentOS 对比](/posts/paperclip-agentos-control-runtime/)。

## 按控制需求组合三种结构

工具域集中、下一步需要随观察变化的工作，可以先用单 Agent。需要独立能力和上下文时，引入 Team，并明确委托传递哪些材料。步骤顺序、门槛和数据依赖必须由应用保证时，使用 Workflow；其中需要灵活判断的一步仍可调用 Agent 或 Team。

选择不必从最复杂的组织开始。先画出输入、决策、执行与结果的关系：哪些决定允许模型提出，哪些条件必须由程序检查，哪些记录需要跨运行保存。Agno 的价值在于让这几种组织方式能够接在一起，而采用的依据是它们是否承担了应用真正需要的控制。
