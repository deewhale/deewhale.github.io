Pi 是面向编码工作的 Agent 系统。终端用户通过它与模型交互，读取项目、编辑代码、执行命令；应用开发者也可以通过 SDK 或 RPC 控制同一类编码会话。模型负责提出回答与工具动作，Pi 的 harness 负责组织上下文、执行工具、处理后续输入并保存历史。

当工作需要在多次交互与中断之间继续，harness 还必须决定保存哪些对象、从哪里重新推进。Pi 在这里提供两条不同路线：Coding Agent 的 AgentSession 管理交互式会话，Pi Durable 将模型生成、工具调用和等待关系变成持久任务。两条路线保存的状态不同，因而也以不同方式接续工作。

Pi 1.0 将原生 MCP 与 Code Mode 纳入稳定版，同时发布实验性的 Durable；持久 Code Mode 集成随后在 1.2 加入。下面按 `v1.4.0` 的具体实现解释会话与持久执行怎样组织，Durable 的 API 仍处于实验阶段。

## 从交互式编码到应用持续托管
交互式编码与应用持续托管有不同的控制目标。前者通常有人检查工作区、切换历史或继续提问；后者需要在客户端断开、执行实例替换以后，仍能辨认已接收输入、尚未完成的工具和子工作。两者都保存信息，但下一步由谁决定不同。

据此可以判断两条 harness 路线的适用范围：

| 状态责任 | Coding AgentSession | Pi Durable Harness |
|---|---|---|
| 主要工作方式 | 人参与的编码与探索，宿主可经 SDK/RPC 控制 | 应用持续管理输入、执行和多会话工作 |
| 核心持久对象 | 会话树与上下文相关记录 | entries、documents、submissions、tasks 与 checkpoint |
| 重启后依据 | 找回历史并组织继续交互 | 整理任务状态，再按检查点调度 |
| 子工作生命周期 | 由宿主或扩展组织 | 记录 ownership、等待和取消关系 |
| 采用所需工作 | 接好资源、工具、会话和宿主控制 | 进一步管理重放、兼容迁移、存储与外部效果 |

有人持续检查工作区并决定下一步时，编码会话提供了直接起点。请求需要跨客户端存活、子工作在重启后必须保持身份、界面状态需要与执行进度共同恢复时，Durable 的对象模型才对应上这些要求。



## Harness 如何组织模型、上下文和执行

一次模型响应可能只有文字，也可能包含若干 `toolCall`。模型给出工具名和参数，真正选择实现、验证参数、调用工具、保存结果并安排下一轮请求的，是 harness。于是模型的判断与运行时的执行之间，存在一条可以检查和改造的路径。

Pi 的实现把这条路径拆成不同职责。`pi-ai` 适配模型提供方；Agent 核心循环处理请求、工具回合与事件；Coding Agent 的 `AgentSession` 组织资源、会话操作、压缩和后续输入；SessionManager 保存历史；界面或 SDK 宿主呈现和控制过程。Durable 共享模型接入能力，采用另一套基于 Chord 的持久任务与存储机制。

这里有四类重要状态：模型当次能够看到的材料，已经记录下来的历史，运行时尚未完成的工作，以及工具接触的外部环境。它们之间有联系，却由不同对象负责。历史影响下一次请求，任务状态决定接下来调度谁，外部环境才持有工具产生的实际效果。

扩展点让宿主参与这些决定。准备阶段可以调整输入材料；调用前检查可以修改参数或阻止动作；结果阶段可以改变后续交给模型的内容。检查位置决定作用范围：结果转换发生在工具执行以后，能够改善模型接收的材料，已经发生的动作则需要由执行工具和外部系统处理。

Pi 的扩展在宿主进程中运行。对经过管道的调用作检查，是一项具体执行控制；扩展代码自身可以访问什么，还取决于宿主权限和执行环境。需要文件、网络、进程或多用户隔离的应用，应把这些要求落实到实际环境与身份配置上。



## 编码会话怎样从历史构造下一轮输入

先看成熟的 Coding Agent 路线。一段执行大体经过如下路径，具体准备细节由相应层处理：

```text
会话输入与资源
  → 组织系统信息、工具集合和当前历史视图
  → 上下文变换与模型消息转换
  → 请求模型，取得文本或 toolCall
  → 校验参数、调用前检查、执行工具
  → 保存 toolResult，用新观察继续请求
```

这条循环没有把自然语言目标编译成一份固定工作流。模型仍然决定尝试哪种工具和下一步方向，运行时负责让这些选择通过已定义的接口发生。参数符合 schema，只说明调用满足接口的输入要求；是否选对目标、取得足够证据，仍要依据具体任务判断。

固定版本默认允许同批工具并行执行，调用前检查依次进行，最终工具结果按模型原始调用顺序进入历史。这里区分了三种顺序：模型提出顺序，实际完成顺序，历史呈现顺序。结果排得整齐，不足以证明外部动作按同样次序发生。存在数据依赖的操作，必须让后一步读取前一步的实际结果。

SessionManager 保存带 `id`、`parentId` 的 JSONL 条目。当前叶节点选出活动分支，下一次模型上下文沿这条父链构造。因此历史存储可以保留多条尝试，模型请求使用的是其中一个活动视图。`/tree`、`/fork` 和 `/clone` 操作改变或复制会话关系；工作区文件由文件工具、版本管理或其他执行环境持有，切换历史分支不会自动重建工作区。

压缩同样是一种上下文投影。Pi 记录摘要与保留范围，用它们和后续条目构造模型输入，底层原历史仍然存在。保存完整记录与让模型一次读取所有记录，是不同的资源选择。涉及精确事实时，应让模型或工具重新取得相应原材料，而不是把摘要当成当前环境状态的证明。1.4 中，摘要生成使用模型的输出上限，`reserveTokens` 继续影响何时触发压缩，不再作为摘要输出的固定上限；触发预算与摘要容量分别影响不同阶段。

1.0 这一轮设计还让系统信息、工具等变化在 transcript 中具有位置。后续请求可以使用新的能力集合，历史记录则保留当时发生的变化。工具定义因此也属于会话演化的一部分，而非永远固定在对话之外的一份全局列表。

会话调度的范围比低层一次模型运行更广。自动重试、压缩或排队输入可能在一次 `agent_end` 后继续推进。SDK 与 RPC 宿主若要知道会话层工作是否已经收敛，应理解 `agent_settled` 的语义；接口接受输入、模型停止输出、应用目标达成，各有自己的观察对象。

到这里，编码 harness 能够找回历史、重建当前材料，并让用户或宿主继续工作。若希望程序自动决定一项中断的动作如何处理，还需要保存执行位置和恢复规则。Durable 正是在这层扩展状态模型。



## Durable 怎样把输入推进为持久工作
应用把输入提交到 conversation 后，Durable 先保存输入身份，再用持久任务推进模型生成。模型提出工具调用时，调用成为独立子任务；父生成等待结果，结果提交后才继续。存储保存的是这些衔接关系，重启后调度器因而能够继续安排已有工作。

一个输入可能触发多个生成回合。`GenerationTask` 请求模型，模型响应中有工具调用时，创建对应的 `pi.tool` 子任务；生成任务把自己转入等待，记录等待对象以及 `allSettled` 等策略。工具结果到齐后，再推进后续生成。模型响应、工具执行和下一次模型请求由此拥有明确的持久衔接点。


Pi Durable 没有把 SessionManager 的历史文件直接当作任务队列。它让 Conversation、Submission、Entries、Documents 与 Tasks 通过同一套持久存储协作。这些对象分别保存输入、历史、应用状态和待执行工作：

| 对象 | 持有的状态 | 为什么影响恢复 |
|---|---|---|
| Conversation | 一条工作对话的身份及相关关系 | 重启后继续定位同一对话 |
| Submission | 已接收的输入与回答状态 | 调用方可以确认输入是否接收、是否得到回答 |
| Entries | 用户、系统、模型、工具结果等记录 | 构造模型材料并检查已发生过程 |
| Documents | 应用与运行时的可变 JSON 状态 | 界面和工具可以读取已提交状态 |
| Tasks 与 checkpoint | 一项工作当前阶段、等待关系和终态 | 调度器据此选择从哪里继续 |

这些对象没有严格的一输入一运行关系。运行中的 steering 可以加入当前工作，后续输入也可以排队。Submission 主要说明输入的接收与回答，run 描述一段活跃模型工作，task 则是实际被调度的单元。用一个“任务完成”字段替代全部状态，会丢掉接收、执行和回答之间的区别。

Durable 的一次 mutation 可以共同追加 entry、更新 document、创建 task。提交成功后，这些变化一起可见。运行时因此可以将“模型已经提出这些调用”与“这些调用已经成为待执行任务”连接起来，也可以让界面状态跟随相同提交更新。模型输出不再只是等待另一段内存代码偶然读到的一条消息。

这条原子提交线覆盖内部存储。工具访问文件、远程 API 或其他服务的动作位于线外，需要自己的执行与结果核对机制。下面的 ToolTask 实现解释了这条边界如何被显式保存。



## ToolTask 怎样保存执行意图与结果

固定 v1.4.0 的 `packages/durable/src/harness/tool.ts` 是最直接的参考对象。`ToolTask` 定义了正常调用的 `call` 阶段，以及中断后恢复使用的 `execute` 阶段。正常执行与中断恢复分别从这两个阶段进入。

正常进入 `call` 时，运行时先找到调用记录和工具实现。模型发出的调用从 assistant entry 取得，嵌套调用从其持久输入取得。随后依次进行参数准备、校验、`beforeTool` hooks，以及对 hooks 修改后参数的再次校验。工具不存在、参数不合法或调用被阻止时，进入对应结果处理，不会继续执行目标工具。

参数最终确定后，运行时提交以下几项真实存在的检查点字段：

```text
status: running
checkpoint.phase: execute
checkpoint.arguments: 最终校验后的参数
checkpoint.replay: 当前工具的重放策略，缺省为 unsafe
```

这是依据源码字段整理的状态说明。它表达的事实是：这项工具已经通过本阶段的准备，恢复时应使用这份最终参数。`beforeTool` 可能改变输入，所以只保存模型最初给出的参数，不足以描述真正执行的动作。

提交完成后，正常 `call` 路径直接进入 `run` 调用工具实现；`execute` handler 是中断恢复的入口。执行结束，`settle` 提交结果与任务完成意图。对模型发出的调用，结果写入 `ToolResultEntry`；对嵌套调用，结果写入调用方对应的持久记录，以便调用方重新取得它。

如果仍有归属的前台工作尚未收尾，结果可以先提交，任务则停在 `completing`，保存待完成的 outcome；子树收敛后，再由后续提交进入真正的 terminal 状态并唤醒等待者。没有这类收尾工作时，结果与终态可以一起提交。结果已经产生，与整个归属工作已经结束，在这里具有不同的完成位置。

![依据 Pi Durable v1.4.0 ToolTask 实现绘制的参数准备、execute 检查点、工具执行及按 replay 策略恢复的流程](/assets/images/posts/pi-agent-runtime-mechanism.png)

图是固定实现的状态投影，重点在两个提交点之间：先提交执行意图，再产生外部效果，最后提交结果。内部存储能够保存“准备执行哪项调用”，却无法仅靠这份意图判断外部系统是否已经完成动作。这也决定了中断恢复必须显式处理不确定性。

同样的分界适用于 hooks。目标工具在意图提交后才执行；`beforeTool` 自己若访问了外部系统，其效果仍需由 hook 作者管理。不能把工具的检查点覆盖范围扩大到此前所有可执行代码。



## 中断后怎样依据检查点恢复

重新打开存储时，Durable 将此前处于 running 的任务整理回可调度状态，保留 checkpoint；等待中的工作保留等待关系，sleeping 任务继续保留到期时间。连续重启而没有新提交的任务还受重启次数保护。打开状态与推进状态属于两步，随后还要通过 `resume` 或相应提交、等待路径启动调度。

ToolTask 如果从 `execute` 阶段恢复，会直接读取已保存参数与 replay 策略。此时它不会重新走正常 `call` 的 `beforeTool` 链，因为执行意图已经提交；再次变更参数会让恢复动作偏离原记录。

固定实现按检查点与重放规则作出以下决定：

| 已持久化状态 | 固定实现怎样处理 | 读者应如何解释 |
|---|---|---|
| 工具已提交终态与结果 | 保留已有结果，不作为未完成工具重新预约 | 已有内部完成记录可供后续工作读取 |
| 位于 `execute`，保存策略和当前工具策略均为 `safe` | 以保存参数重新进入工具执行 | 作者允许这项动作在中断后重跑 |
| 位于 `execute`，不满足上述重放条件 | 结束为 interrupted 等相应结果 | 原动作可能部分执行，需要核对外部状态 |

这个表只解释本工具的检查点恢复。恢复还要求上层任务允许继续、所需定义可用，并且版本迁移成功。

最关键的判断是：检查点位于外部执行之前，结果记录位于之后。如果进程退出时只剩前者，运行时无法仅凭缺少结果断定工具未执行。因此默认 `unsafe` 不会自动重跑，而是报告中断可能已经部分运行。接入者要从外部状态、操作收据或工具专有的恢复接口取得进一步依据。

`safe` 表示允许重跑，工具作者必须保证这个声明符合动作性质。内部 task identity 帮助找回同一项工作；外部操作能否重复，则取决于工具与目标系统。需要去重时，身份必须传递到真正产生效果的位置，并由那里提供可靠的原子处理或可查询结果。运行时的任务记录不会自动让一个远程服务识别重复操作。

Submission 的 `requestId` 也有自己的范围：它对同一 conversation 中重复提交的输入作去重。它与 task identity、外部操作身份分别处理入口重试、内部恢复和外部效果。三者可以关联，保证范围需要分别建立。

恢复还依赖重新部署的代码。持久状态记录定义名称与版本，函数本身由 registry 提供。工具缺失、参数与新版实现不兼容或迁移失败时，任务可能被阻塞，应通过 `harness.inspect` 等途径检查原因。固定实现要求保存策略和当前策略同时为 safe，也是在避免仅凭旧声明执行已经改变含义的新工具。



## 等待时间与反复崩溃也需要进入任务状态

持久任务不仅等待子工具，还会等待重试退避或将来的某个时刻。Pi Durable 1.4 将这类等待保存为 `sleeping`，其中包含到期时间与下一阶段的 checkpoint。`sleepUntil()` 提交休眠后结束当前 phase，不占住一次内存 invocation；时间到达以后，从记录的下一阶段恢复。

这解释了为什么不能只在阶段内部调用普通 sleep：进程重启会从阶段开头重新执行，内存计时器和它后面的工作没有可靠衔接。官方 Reminder 原型把等待放在 `wait` 阶段，后续通知放在 `deliver` 阶段，并通过 checkpoint 指明下一步。通知本身的幂等仍由工具负责，保存唤醒时间不保证外部通知只出现一次。

宿主可以通过 `wake()` 与 `onWake` 取得当前是否有可运行工作以及最早唤醒时间，再设置自己的 alarm，唤醒后调用 `resume()`。官方 Cloudflare Durable Object 示例由宿主承担这一安排，使进程可以休眠；持久化层保存工作，宿主负责重新提供执行机会。

自动恢复也需要停止条件。固定版本默认将连续五次因崩溃等中断、且没有提交新状态的任务停放为 `restart_limit` 阻塞，供应用检查并显式 retry。否则确定性的内存或执行故障会在每次恢复后重演。正常关闭不按同样方式累计，新的状态提交会重新开始计数。

## 子任务归属如何保存等待和取消关系

单个工具能够恢复，还不足以管理长任务。一个工具可能派生子任务或子会话，父工作需要知道应该等待谁、取消影响谁、何时能够宣布空闲。若这些关系只存在于一组内存 Promise 中，重启以后就失去了生命周期依据。

Durable 保存 ownership 关系。它与历史父节点属于不同的关系：历史父节点决定上下文继承，执行归属决定工作由谁管理。子会话可以有自己的上下文，同时归属于某个父任务；这种归属不自动授予访问其他数据的权限。

任务结果已经决定，但仍有归属的前台子工作等待收尾时，任务可以停在 `completing`；没有活动 run 也不必然意味着 conversation 已经 idle，等待、阻塞或收尾中的前台工作仍然影响这个判断。取消也要沿相应归属关系处理，而非只停掉最外层一条模型生成。

官方 v1.0.0 的 `experimental/vacation` 是一个可以定位到源码的设计原型。原型使用预置搜索文本与不同延时来展示并行和恢复。对象之间的连接是：`research` 工具在同一次提交中创建 background 研究任务与 task-owned 子会话；研究任务的 `deliver` 阶段按 ownerTaskId 找到子会话，并用 `research:<taskId>` 提交输入；得到回答后保存报告和 `report` 阶段，再用 `research-report:<taskId>` 把报告提交回主会话。

这样，恢复中的 `deliver` 可以找到已有子会话与输入；恢复中的 `report` 可以复用已有投递身份。这里的去重仍发生在 Durable 自己的 conversation 提交中，不能推广成任意外部消息服务只投递一次。

background 改变等待与取消边界。后台任务仍有 owner，但普通 conversation 或 harness 的 idle 等待不会穿过这条边界等待整棵子树，普通 conversation abort 也不穿过；显式包含 background 的取消才继续传播。应用因此需要明确后台结果由谁最终接收。

调用方停止等待，也有可能只是取消当前等待，没有取消已提交工作。客户端断开后让任务继续，是持久应用的一种合理行为；若产品要求同时停止实际任务，就必须触发对应取消路径。任务终止后的文件恢复、远程补偿等动作仍需应用实现。



## Code Mode 的持久执行怎样接上工具恢复

普通 Code Mode 可以在一次脚本中组织多个工具调用。Pi Durable 在 1.2 加入可持久恢复的 Code Mode 集成，包括脚本 journal 重放及相应一致性检查；下面按固定 v1.4.0 的实现解释这套机制。这项能力不能倒推为 1.0 初版已经具备。

参考实现位于 `packages/durable/src/codemode/codemode.ts`。恢复方式是重新运行脚本，用 journal 重放已交付结果，并通过稳定的 nested-call key 附着到已有任务。结果先进入持久日志，再交给 VM，避免把已交付的观察只留在随进程消失的内存里。

它保存的对象解释了恢复方式。JavaScript 堆、调用栈和任意行号没有直接作为快照保存；脚本需要重新走过相同控制流，在对应调用位置取得相同的已提交结果。虚拟时间、带种子的随机性、固定时区等条件用于帮助重跑保持一致，稳定调用身份则防止重建出一批全新的内部工作。

外层程序重新运行，内层已完成任务仍可复用结果；内层尚处 `execute` 阶段的任务，继续依据自己的 replay 策略处理。所以脚本恢复和工具恢复是嵌套关系，后者的外部效果边界仍然存在。journal 没有把外部服务变成一个可回滚的事务参与者。

如果调用顺序、参数、模块版本或沙箱指纹与既有记录不相容，系统可以拒绝继续重放。拒绝说明新代码不能安全接到旧执行上，处理对象是代码兼容性、检查点和已发生动作。简单删除记录重新运行，会丢掉正是用来识别已有工作的依据。

journal 的恢复条件应以实际脚本和工具为对象验证，尤其要检查代码版本变化和外部写入。



## 应用怎样接管存储、版本与外部状态

Durable 的 documents 为应用可变状态提供了持久位置，可以与相关 entries 和任务变化共同提交。界面通过已提交状态及 watch/snapshot 更新，避免依赖某个终端是否一直连接。状态字段应该反映相应证据，而不是用“完成”两个字代替实际检查。

执行环境则确定工具究竟作用于哪里。conversation 配置、工作目录和相关 documents 可以参与环境构造，本地或远程工具仍然使用各自身份和权限。会话分支与应用文档能够重建内部视图，外部工作区是否与该视图一致，仍需从执行环境读取和核对。

持久存储也有部署条件。固定版本要求一个 storage 由单进程拥有，没有面向多个独立写入进程的跨进程锁协调。SQLite 与 JSONL 的数据组织、内存使用和故障条件不同；不能仅因接口可移植，就让多个 harness 共同写同一份存储。代码定义、检查点格式与执行环境需要随部署一起管理。1.4 的 SQLite 存储会自动迁移到 schema 2，迁移后不能交回 1.3 或更早版本打开；JSONL 虽无这项迁移，旧版本也不会继续新的 sleeping 任务。因此代码回滚需要与存储兼容性一同决定。

进入试点前，应能对真实工具回答四个问题：恢复使用哪份参数，在哪个提交点之后可能已有外部效果，什么条件允许重跑，谁负责确认最终结果。然后再固定兼容代码和单写者存储，对实际恢复路径作验证。这是把长期工作交给应用之前，需要由 harness 使用者接过的执行责任。
