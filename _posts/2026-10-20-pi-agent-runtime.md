收到“把服务的重试次数从 1 改成 3，并确认配置有效”这条任务，Coding Agent 会读文件、提出修改、调用工具，再解释结果。界面上短短几行记录，背后至少有三种状态：模型看见了什么，程序实际改了什么，以及下一次继续工作时能恢复什么。

Pi 把这些职责拆成可复用的组件。理解它，适合从一次任务沿着输入、工具和保存状态走下去：模型提出动作，循环中的代码校验并调度，工具改变目标对象，会话层保存历史并组织后续请求。终端界面呈现这段过程。选择 CLI、RPC 或 SDK，主要是在选择由谁管理进程、资源和会话。

以下以官方 Pi v1.3.0 为基线，资料核查截至 2026 年 10 月 20 日。上游仓库、对应发布版本与第三方界面各有自己的范围；这里讨论官方编码运行时。配置修复是教学情境，其中工具循环使用官方 Agent 执行过，模型响应由人工预设。

## 从命令行任务进入运行时

使用交互式入口时，安装官方 `@earendil-works/pi-coding-agent` 包，配置受支持模型所需的认证，在目标项目启动 `pi`，再输入修改要求。项目文件、用户指令和可用工具共同构成任务起点。模型认证只解决请求模型的条件；项目允许修改的范围、验收标准与执行环境仍需要使用者确定。

例如，任务可以明确为：读取配置，确认当前重试值，将它改为 3，再运行相应配置检查。这里的读、改、检查是一条合理的工作路径，具体调用顺序由模型与上下文决定，Pi 不会把这句话自动编译成固定工作流。

Pi 的四个常见包位于这条路径的不同位置：

| 组件 | 在同一次任务中承担什么 | 留给上层或外部的责任 |
|---|---|---|
| `pi-ai` | 适配模型提供方、请求和流式响应 | 哪些动作允许执行、怎样验收修改 |
| `pi-agent-core` | 管理低层 Agent 状态、推进循环、校验并调度工具 | 编码会话的完整存储与交互体验 |
| `pi-coding-agent` | 组合编码工具、会话、压缩、扩展和 CLI | 工作区及外部系统的业务正确性 |
| `pi-tui` | 提供终端界面组件与渲染 | 模型判断和工具执行 |

这些层可以组合使用。只调用模型接口，尚未获得工具循环；直接使用 Agent core，也尚未获得编码 CLI 的全部会话管理。已有一个常驻应用时，可以嵌入所需层，让应用继续拥有自己的输入输出与生命周期。

当用户提交任务，编码层准备会话与工具，core 将当前材料转成模型请求，再通过模型适配层取得响应。模型返回文本时可以直接展示；返回 `toolCall` 时，执行权转到工具调度路径。模型给出工具名和参数，程序才决定是否存在对应工具、参数是否有效、调用是否获准，以及怎样执行。

## 一轮工具调用怎样回到下一轮请求

把真实文件暂时简化成内存对象 `config = {retries: 1}`，注册一个 `set_retry` 工具，只接受 0 到 5 的整数。人工预设的第一条模型响应请求 `set_retry(value=3)`，第二条响应给出固定结束文字。这样可以单独检查循环，不把模型是否理解任务混入调度实验。

调用经过以下变化：

```text
用户消息：把 retries 设为 3
    ↓
模型响应：toolCall(name=set_retry, value=3)
    ↓
Agent 查找工具、验证参数并执行调用前检查
    ↓
execute 修改 config，返回内容与详情
    ↓
toolResult 加入历史，进入第二次模型请求
    ↓
模型产生最终响应，本次低层运行结束
```

参数定义和执行函数承担两项不同工作。整数范围检查可以挡住 `99`；它不会知道生产服务允许怎样的重试策略。业务规则需要放进调用前检查、工具实现或服务端。`execute` 返回成功内容，也只说明这个工具报告了什么；若目标是修复实际配置，还需要读取目标状态并完成验收。

v1.3.0 在 transcript 中声明系统信息和工具集合，工具变化也会通过系统消息表示。构造下一次请求时，还要经过上下文变换、模型消息转换和规范化。可执行工具集合、保存的会话记录与提供方最终收到的请求，因而是相关但不同的对象。

为了看清失败落在哪一层，离线例保留相同的两条预设响应，只改变一个条件。每一行都是一次重新创建的 Agent，初始 `retries` 都为 1：

| 条件 | `execute` 执行次数 | 最终 `retries` | 返回给下一轮的 `isError` |
|---|---:|---:|---|
| 参数为 3，调用获准 | 1 | 3 | false |
| 调用前检查拒绝 | 0 | 1 | true |
| 参数为 99，超出定义范围 | 0 | 1 | true |
| 进入执行函数后抛错 | 1 | 1 | true |

四条路径都产生了第二次模型请求，错误也作为工具结果进入其中。前两种失败在动作前被阻止，最后一种已进入执行过程。真实工具可能在抛错前已完成部分写入；这个内存例在写入前抛错，不能据此推导任何工具失败都会自动回滚。

实验使用官方 `pi-agent-core` 1.3.0 的 Agent 类、参数校验与调度代码，未调用真实模型或文件系统工具。它确认了表中的执行与错误回传，不能说明模型能自主选对工具。第二条预设响应在所有分支里都能结束，所以最终文字、低层 `agent_end` 与目标状态必须分开检查。

并发也属于调度层。在这个版本中，一批工具默认可以并行执行，调用前检查依次进行，最终工具结果按原调用顺序排列。实际完成事件可能先后不同。若两个工具都修改同一配置，把结果按顺序展示并不会消除写入竞争；需要选择串行策略或在工具内部协调共享状态。

## 会话保存的是历史树

完成第一轮以后，Agent 还要面对继续、改主意与压缩历史。Pi 的 SessionManager 用 JSONL 条目保存会话，条目的 `id` 与 `parentId` 构成树，当前叶节点决定活动分支。整份文件可以有多条尝试路径，下一次模型请求使用的是当前分支构造出的上下文。

假设配置修复走到共同节点 R，随后尝试 A，把重试数改成 5。用户回到 R，选择另一条解释路径 B，要求改成 3：

```text
R：确认要修改重试配置
├─ A：尝试设为 5 → 工具实际写入配置
└─ B：重新考虑，要求设为 3
```

选择 B 会改变后续会话沿哪条父链组织，A 的历史仍保留。分支操作移动的是会话叶节点，源码中的这条路径不负责恢复外部文件。A 已经写入的配置，因此需要按实际状态重新读取；使用 Git、备份或显式工具操作恢复代码，是另外一项工作。

这个区分直接影响扩展设计。若扩展要根据当前分支恢复自己的状态，应读取活动分支，而不能把全部历史条目一股脑重放。否则，另一条尝试中已经放弃的选择，可能被错误带回当前任务。

`/tree` 在同一会话文件中导航；`/fork` 从较早的用户消息创建新会话；`/clone` 复制当前活动分支。选择哪一种，取决于要保留同一棵探索树，还是将当前路线拆成独立会话。它们都不替代工作区的版本管理。

![AgentSession 协调输入，Agent loop 请求模型并执行工具，SessionManager 记录会话树与选中路径](/assets/images/posts/pi-agent-runtime-mechanism.png)

图中的两条线分别指向运行与保存。AgentSession 协调模型、工具、队列及扩展；SessionManager 保存历史，并为请求建立活动路径的视图。工具影响工作区的那条线还需要自己的检查，不能从历史恢复直接推导工作区恢复。

历史过长时，压缩会追加摘要及保留区间信息，原始条目仍在。构造请求时，系统结合当前分支上的压缩记录、摘要、保留段和后续条目生成上下文。磁盘中保留了细节，模型当次读到的材料却可能已缩减。

因此，摘要中的“配置已更新”与重新读取文件得到的当前值，证据来源不同。任务依赖精确版本或某个例外时，应让下一次行动取得相应原始材料。保存历史提高了可追溯性，摘要是否足以支持下一步判断仍要另行验证。

v1.3.0 还修复了恢复会话时活动工具集合丢失的问题，并支持 CLI 工具选项增量叠加。它影响的是恢复后哪些工具继续可用，不能延伸为对工具副作用或整个工作区恢复的保证。

## 集成方式决定谁管理生命周期

把 Pi 接入自动化程序后，最容易出错的是把“请求已收到”当成“工作已完成”。同一任务可以通过不同入口运行，但入口的完成信号和资源所有权不同。

| 入口 | 输入输出形式 | 适合的控制边界 |
|---|---|---|
| 交互式 TUI | 人在终端提交、查看并继续 | 人工编码与探索 |
| print | 一次输入，输出最终文本后退出 | 简单的一次性文字调用 |
| JSON 模式 | 一次运行，输出事件流后退出 | 需要解析过程和结果的脚本 |
| RPC | 常驻子进程，双向 JSONL 命令与事件 | 跨语言应用控制编码会话 |
| SDK | 同进程调用 AgentSession | 应用注入资源、存储并接管生命周期 |

RPC 中，提交 `prompt` 的成功响应说明请求已接受、排队或处理，不代表自动工作全部结束。低层 `agent_end` 表示一次运行结束；会话层还可能重试、压缩或处理排队的后续输入。宿主若需要等待这些自动工作稳定，应使用 `agent_settled` 的会话语义，并在提交任务前建立订阅，避免遗漏快速完成事件。

稳定下来仍不是业务验收。回到配置修复，自动化程序应检查最终状态和测试结果；使用 JSON 模式时，还要解析错误、取消与停止原因，不能只依赖进程是否零退出。print 模式与 JSON 事件流对失败的退出处理也不能混用。

SDK 允许宿主提供资源加载、模型运行与会话管理。它带来更大控制，也使宿主负责订阅、释放资源和更新会话引用。SessionManager 是最终模型上下文的权威来源；仅给 `agent.state.messages` 赋值，不等于改写了持续会话的存储历史。

CLI 的装配行为也不能原样套到 SDK。v1.3.0 的 SDK 默认不自动加载 `codemode`、`tool_search` 与 MCP；需要显式配置扩展工厂并绑定扩展。嵌入时应核对实际加载集合，再决定哪些能力向模型公开。

## 将确定规则放到合适的扩展事件

Skill 主要向模型提供操作知识，extension 则是在 Pi 进程中运行的 TypeScript 模块。扩展可以注册工具、命令和事件处理函数，也能参与上下文准备。两者作用不同：希望模型参考某项流程，可以提供说明；要求每次执行前都检查条件，需要对应的代码路径。

对配置修复，可以在 `before_agent_start` 补充目标与验收材料，在 `tool_call` 检查或修改输入、阻止某项调用，在 `tool_result` 调整返回给模型的内容。它们分别介入准备、动作之前和结果之后。结果变换只能改变后续可见材料，不能撤销已经发生的写入。

扩展事件各有自己的返回类型。某个通知事件没有阻断语义，在处理函数里随意返回 `block` 并不会获得阻止工具的能力。`tool_call` 处理函数抛错会阻断相应调用；工具自身执行抛错则转为错误结果。编写扩展时，应先确定要改变哪个阶段，再按该事件的类型实现。

持续连接也需要生命周期管理。可以在会话启动阶段建立资源，在关闭时幂等清理；会话替换或重载后重新绑定订阅。自定义持久条目和供模型阅读的消息承担不同作用，保存内部状态不必把每个字段写入模型上下文。

执行权限由另一层决定。扩展与 Pi 进程拥有相同的操作系统权限，能够访问该进程可访问的文件、网络和凭据。v1.3.0 没有内置覆盖文件、进程、网络及凭据的完整权限限制系统。工具调用拦截可以约束走这条路径的动作，加载的扩展代码仍可能直接访问资源；需要强制隔离时，应由容器、沙箱或其他运行环境机制提供。

例如，用 `tool_call` 检查只允许修改批准目录，是对已接入工具的明确规则。若未经审查的扩展本身可直接调用文件 API，这项检查就没有覆盖该路径。采用扩展时，来源、固定版本、实际代码和运行权限需要一起判断。

## 持久任务恢复需要单独的执行设计

对话历史能重新组织模型输入，长任务还可能需要保存步骤进度。Pi 提供实验性的 Durable API，将任务、模型轮次、工具调用与状态写入存储，重新打开存储后恢复调度。它是另一套任务执行设计，采用时需要接受实验 API 的变化。

关键边界在工具执行中途。Durable 会先提交工具意图；若进程在执行阶段中断，只有声明为可安全重放的工具才自动重跑，其他调用返回中断状态及已提交的输出。工具作者必须判断重复执行的后果。

读取配置通常容易重放，发送通知、扣款或提交外部变更则需要外部系统的幂等与核对机制。持久化调度记录不会自动让外部动作只发生一次。这里依据固定版文档与实现解释，未进行崩溃恢复实验。

选择 Pi 的入口，可以从控制需求开始：终端中的持续编码用 CLI；跨语言应用以子进程管理会话用 RPC；需要替换资源与存储、在同一进程内组合能力时用 SDK。只有当需求进入步骤持久化和中断调度，才进一步评估 Durable，并为每种工具确定重放策略。配置是否真的改对，最终仍回到目标对象与验收结果。
