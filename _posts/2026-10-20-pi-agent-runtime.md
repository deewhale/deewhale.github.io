一条配置修复请求已经被接收：读取服务配置，把 `retries` 从 1 改为 3，运行检查，最后报告结果。工具刚刚完成写入，进程却在保存执行结果前退出。重新启动以后，程序面对的不是一句“继续”就能回答的问题：文件可能已经改好，历史里却还没有成功记录；重新执行可能重复产生动作，直接跳过又可能遗漏工作。

这个故障点适合观察 Pi 的 harness 设计。模型决定下一步尝试什么，harness 则负责准备模型看到的材料、提供工具、执行与记录动作，以及安排下一步。把 Agent 接到一个聊天界面很容易；让它在上下文变化、输入排队、工具失败、进程中断以后仍有可解释的行为，需要的都是模型周围这套机器。

Pi 在 2026 年 10 月 1 日发布 1.0 时，同时展示了两条路线。成熟的 Coding Agent 面向有人参与的编码过程，原生 MCP、Code Mode、延迟工具加载等能力进入稳定版本。另一个项目 Pi Durable 则从持久状态出发，探索由应用接管长任务和多会话工作的 harness。Durable 仍是实验 API，采用前需要接受接口与迁移成本。

两条路线共享模型接入和可改造的设计取向，持有的恢复对象却不同。理解这种区别，才能判断自己需要的是更好的编码会话，还是一个能够在重启后重新调度工作的应用运行时。以下以官方 v1.3.0 的实现为依据，资料核查截至 2026 年 10 月 20 日；1.0 用来说明设计起点，后续能力分别交代版本。

## 一次任务里，harness 控制什么

先把配置修复拆成几项责任。使用者提供目标和验收条件；模型根据当前材料提出读取、修改和检查的调用；工具实现真正接触文件与进程；harness 处理这些参与者之间的信息与执行关系。

在 Pi Coding Agent 中，`AgentSession` 组织编码会话，底层 Agent 循环请求模型、调度工具，`pi-ai` 适配模型提供方。SessionManager 保存会话树，终端界面呈现过程。这些组件共同决定：当前有哪些工具，哪些历史进入请求，输入在运行中怎样排队，错误怎样返回模型，以及什么时候可以接受下一步工作。

沿着配置请求，执行路径可以写成：

```text
用户目标与项目材料
  → AgentSession 准备输入、工具和当前上下文
  → 上下文变换、消息转换与规范化
  → 模型返回文本或 toolCall
  → 校验工具参数，执行调用前控制
  → 工具读取或改变外部对象
  → toolResult 进入历史
  → 用新的观察继续请求模型
```

自然语言目标没有在这里变成一份预先固定的工作流。模型仍可能先读错文件、漏掉检查，或根据工具错误重新选择路径。harness 的价值，在于让这些选择通过明确的接口发生，并留下后续判断所需的记录。

例如，一个工具只接受 0 到 5 的整数，参数校验可以挡住 `99`；它不会据此知道这个服务该用怎样的重试策略。后一项规则要来自项目要求、调用前检查或工具的业务实现。模型最后说“已修复”，也需要与实际配置和检查结果对应。

v1.3.0 默认允许同一批工具并行执行，调用前检查依次进行，最终工具结果按模型原始调用顺序进入历史。结果排列整齐，并不意味着外部动作也依次发生。读取两个互不相关的文件可以并行；修改同一文件后再验证，存在前后依赖，必须让后一步观察前一步的真实结果。

Pi 的扩展点可以改变这条路径。`before_agent_start` 影响准备材料，`tool_call` 可以检查、修改输入或阻止调用，`tool_result` 可以调整后续模型看到的结果。选择扩展点时，应先问要改变哪个阶段：结果变换发生在执行之后，无法撤销已经完成的文件写入。

扩展与 Pi 进程拥有相同的操作系统权限。调用拦截能约束经过它的工具，扩展本身仍是可执行代码。需要限制文件、网络或进程访问时，宿主应提供相应执行环境。模型可见的工具集合负责组织能力入口，身份验证和系统隔离由具体运行环境与服务承担。

这些控制已经构成一个可用的编码 harness。接下来需要区分，它保存下来的内容能解决哪一种恢复。

## 会话历史怎样变成下一次模型输入

SessionManager 用带有 `id`、`parentId` 的 JSONL 条目记录历史。当前叶节点确定活动分支，模型请求沿这条路径构造。整份记录中可以保留多次尝试，模型每次读取的却只是当前上下文视图。

假设配置任务先走了 A 路线，把值改成 5；使用者回到较早节点，再开启 B 路线，要求改为 3：

```text
R：确认修改目标
├─ A：把 retries 改成 5，工具已写文件
└─ B：回到 R 后重新考虑，准备设为 3
```

切换到 B 会改变后续对话沿哪条父链组织，A 的记录仍在文件中。工作区配置此时可能还是 5。重新读取配置，才能知道 B 路线面对的实际起点。`/tree`、`/fork`、`/clone` 各自处理会话导航或复制，文件恢复仍需要版本管理、备份或显式工具操作。

这也解释了压缩的作用。历史过长时，Pi 保存摘要和保留范围，用摘要、保留片段及其后的条目重新构造请求，原始历史仍然存在。保存层拥有完整记录，模型当次看到的是选择后的材料。摘要中的“配置已经修改”与重新读取文件得到 `retries=3`，具有不同的证据强度。

1.0 支持在对话中调整系统信息和工具；对应变化记录在 transcript 中，影响后续请求。于是“这次模型可以做什么”也有时间位置：新加入的工具定义服务于后续判断，不能拿来解释过去一轮模型当时掌握的能力。

会话层还处理重试、压缩和后续输入队列，因此低层一次运行发出 `agent_end`，会话未必已经稳定。SDK 或 RPC 宿主需要观察自动工作是否结束时，应使用会话层的 `agent_settled` 语义。RPC 接受了 `prompt`，只说明输入进入处理流程；验收配置是否正确，仍要检查目标状态与测试记录。

到这里，普通会话恢复的范围就清楚了：它能够重建模型的工作上下文，让人或宿主决定如何继续。若进程恰好死在一次外部动作中间，仅有对话树还不足以回答这个动作应不应该重做。Durable 将这项判断所需的状态纳入运行时。

## Durable 怎样把一次输入拆成持久工作

Pi Durable 使用 `pi-ai` 接入模型，并基于 Chord 构建持久任务机制。它不依赖 SessionManager 把编码 CLI 的历史文件变成任务队列。应用可以通过网页、聊天入口或后台服务提交输入；运行时负责把输入、执行进度、应用状态和等待关系放在同一条持久提交线上。

回到配置修复，给这次应用请求一个标识 `job-42`。这是案例的业务编号，Pi 并没有一个叫 Job 的核心对象。运行时中实际涉及的对象如下：

| 对象 | 在配置任务中保存什么 | 后续谁使用它 |
|---|---|---|
| Conversation | 这条工作对话的身份及相关状态 | 输入入口、工具、界面和调度器 |
| Submission | 被持久接收的输入及其完成状态 | 调用方确认输入是否接收、是否已经回答 |
| Entries | 用户、系统、模型、工具结果及上下文变化记录 | 模型请求构造和历史检查 |
| Documents | 当前模型配置、应用状态、收件箱等可变 JSON 状态 | 运行时与应用代码 |
| Tasks 与 checkpoint | 正在做什么、停在哪个阶段、等待谁 | 重启后的调度器 |

Conversation 承载连续输入与历史。Submission 在这里指一次输入的持久接收与完成回执；运行时也支持被动写入记录的 submission。run 表示当前一段活跃的模型工作，可以经过多个生成 turn 和工具回合；运行中的 steering 输入可以加入当前 run，后续输入也可以排队，因此 run 与 Submission 不是严格一一对应。

任务才是实际被调度的单元。它可以创建子任务或子会话，ownership 记录这条归属关系，决定父工作要等待谁收尾、取消向哪里传播。比如主工具派生一个独立审查会话，即使两者各自保存对话，审查工作仍可归属于这个主工具。后面讨论任务状态时，父子关系指的就是这条执行归属。

这些对象的意义来自它们如何协作。应用接收 `job-42` 的输入，形成 Submission；GenerationTask 生成一次模型响应；响应包含工具调用时，生成对应 ToolTask；生成任务等待工具工作完成，之后才用结果进入下一轮生成。一个输入的回答过程可能包含多轮生成和工具工作。

```text
Submission：修复配置 job-42
  → GenerationTask：决定先读取配置
      → ToolTask：read_config
  → GenerationTask：根据当前值决定修改
      → ToolTask：set_config
  → GenerationTask：提出验证
      → ToolTask：check_config
  → GenerationTask：形成最终回答
  → Submission 完成
```

这是解释对象关系的示意路径，具体工具选择依模型与上下文发生。持久任务系统保存的是实际形成的工作，而非保证模型永远按上面这条理想路径行动。

一次提交可以同时追加 entry、更新 document、创建 task。提交成功后，这些变化才共同可见。例如工具完成验证时，可以在同一次 mutation 中保存检查结果，并把应用文档的状态改为 `verified`，使界面不会先看到“已验证”却还查不到相应结果。

原子性覆盖的是这条存储提交线。工具修改外部文件、调用 HTTP 接口或发送消息，发生在存储事务之外。否则一个慢网络请求会占据事务，而且普通外部服务也不能自动加入本地事务。Durable 的设计重点因此落在外部动作之前和之后分别保存什么。

## 检查点为何必须先于外部动作提交

一个 ToolTask 不会直接调用执行函数，再期待最后把所有东西一次保存。固定版本的路径先处理参数与调用前 hooks，保存最终参数和执行策略，再进入真正的工具执行。

```text
校验参数
  → beforeTool：可修改参数或拒绝
  → 再次校验最终参数
  → 提交 checkpoint：phase=execute、最终 arguments、replay 策略
  → 执行外部动作
  → 提交工具结果与 task outcome
```

中间的检查点相当于一份已持久化的执行意图。下面只展示其解释所需的概念字段，不是要求应用手工构造的完整存储格式：

```json
{
  "phase": "execute",
  "arguments": {"key": "job-42:config"},
  "replay": "unsafe"
}
```

如果进程死在意图提交之前，目标工具的 `execute` 尚未开始；调用前 hook 自己执行的外部动作需要单独管理。死在结果提交之后，已有完成结果；最难的是夹在两次提交之间。此时只能确定“这个工具可能已经执行”，无法单凭内部数据库知道外部系统完成到了哪里。

先保存意图没有消除不确定性，但它把不确定性精确定位到一项调用及其最终参数。恢复代码无需从一段自然语言摘要猜测“也许做过什么”，也不会把一个没有成功结果的工具自动当成未执行。

调度本身同样有持久状态。任务从 `pending` 被领取为 `running`；需要子任务结果时进入 `waiting`，等待对象和策略被保存，而不是只让一条内存 Promise 悬着。子工作满足条件后，任务从检查点阶段继续。例如父工具已经提交自己的正常结果，但它创建并拥有的审查子会话还没有收尾，父任务会处于 `completing`，待这部分前台归属工作结束后才进入终态。若父工具还在执行函数里显式等待子会话，此时则尚未走到结果已决定的 completing 阶段。

重新打开存储时，运行中的任务会被整理回可调度状态并保留检查点，等待中的任务保留等待关系。`Harness.open` 完成这项状态整理；真正推进工作还需要 `resume`，或通过提交、等待等路径启动调度。把数据库打开成功当成任务恢复成功，会漏掉后半段。

恢复也依赖代码。持久状态保存工具、模型与扩展的名字，不把 JavaScript 函数序列化进去。重启进程必须重新安装相应 registry 定义；定义缺失、保存的版本更新或迁移失败时，任务可能仍停留在 pending 或 waiting，并在调度检查中显示 blocked 原因。此时应检查 `harness.inspect` 给出的原因，补齐兼容定义或迁移，再决定是否继续。

因此，持久执行包含两个条件：状态能够找回，运行该状态的实现也必须可用。数据库留在原处、部署时却换掉了不兼容的工具，恢复并不会自然成立。

## 用进程中断看清 replay 与幂等

为了检验检查点真正影响了什么，可以选择一个比完整编码任务更小、但覆盖关键故障窗口的实验：注册 `record_change` 工具，把它的副作用写入独立账本；写入后立即终止进程，让 Pi 来不及提交工具结果；再由新进程打开原 SQLite 存储恢复。

实验实际运行官方 Pi Durable 1.3.0 的 ToolTask。模型调用由人工构造的 assistant 条目替代，没有向模型提供方发请求。这样可以观察“已保存执行意图以后，真实进程中断怎样恢复”，不把模型会不会选择正确工具混进结论。

完整代码与固定依赖可下载为[恢复实验附件](/assets/examples/pi-agent-runtime/durable/pi-durable-recovery.zip)，也可单独查看[源码](/assets/examples/pi-agent-runtime/durable/durable-recovery.mjs)和[运行说明](/assets/examples/pi-agent-runtime/durable/README.md)。解压到新目录，使用支持 `node:sqlite` 的 Node.js 24 与支持 POSIX 信号的系统，执行：

```sh
npm ci --ignore-scripts
node durable-recovery.mjs
```

脚本在临时测试目录创建数据库与账本，父进程启动工作子进程，并断言第一次确实被 `SIGKILL` 终止；然后启动另一个子进程恢复同一项任务。下面是执行函数中决定实验的节选，省略注册与父进程控制：

```javascript
execute: async (args, api) => {
  add(attemptsFile, {taskId: api.taskId, key: args.key});
  if (mode !== 'safe-idempotent'
      || !load(effectsFile).some(x => x.key === args.key)) {
    add(effectsFile, {key: args.key, value: 3});
  }
  if (stage === 'start') process.kill(process.pid, 'SIGKILL');
  return {output: [{type: 'text', text: 'retries=3'}]};
}
```

`attemptsFile` 记录函数进入次数，`effectsFile` 模拟外部账本，`load` 和 `add` 分别读取与追加账本内容。`safe-idempotent` 分支先检查 key 是否已有记录。完整定义在附件中；账本只用于单调用方的机制实验，生产系统需要由外部存储原子地实现去重。

三个分支保持相同故障点，只改变重放策略与外部去重：

| 策略 | 工具执行函数进入次数 | 账本实际副作用次数 | `beforeTool` 次数 | 恢复后的结果 |
|---|---:|---:|---:|---|
| 默认 `unsafe` | 1 | 1 | 1 | 工具错误，diagnostic 为 `interrupted` |
| `replay: 'safe'`，无外部去重 | 2 | 2 | 1 | 工具成功 |
| `replay: 'safe'`，外部按 key 去重 | 2 | 1 | 1 | 工具成功 |

第一行最容易被误读。工具没有被自动重跑，并不表示外部动作没发生。账本已经有一条记录，恢复结果却是错误，因为运行时无法确认中断调用是否完整结束。实际结果中的错误文字说明它可能部分运行过：`Tool record_change was interrupted and may have partially run`。程序应检查外部目标或操作收据，再决定补做、接受已完成结果，还是进入人工处理。

第二行说明 `safe` 的准确含义：工具作者允许恢复时重新执行。它没有让原来的动作消失，也没有自动将第二次调用变成同一次业务操作。结果虽然成功，账本已经多写一次。读取类工具通常更容易满足重放条件；写入类工具需要检查重复执行到底会产生什么。

第三行把两个层次接起来。Pi 重跑了同一工具，实验实现识别账本里已有的 `job-42:config`，跳过第二次追加，再返回固定成功文本。真实业务还应核对并返回已有操作的结果或收据。恢复能力来自运行时的再次调度，去重能力来自外部系统的业务身份，两者缺一项都会改变结果。

这里至少有三种不能混用的标识：

| 标识 | 识别什么 | 解决哪一种重复 |
|---|---|---|
| Submission 的 `requestId` | 同一 conversation 中已接收的输入 | 调用方重试提交同一请求 |
| task identity | 运行时中的一项工作及其检查点 | 恢复时找到已有执行位置 |
| 外部业务 key | 一次文件变更、消息发送或支付等业务操作 | 工具重跑时避免重复业务效果 |

在 conversation 内用 `requestId` 去重，不会自动让另一个 conversation 的同名请求也被去重；保存 taskId，也不会让第三方 API 自动认出同一业务操作。应用需要把相应身份传到真正执行副作用的位置。

实验中的 `beforeTool` 三组都只发生一次，是因为中断前已经提交 `execute` 检查点。该恢复阶段使用保存的最终参数，不重新走这条前置链。不能由此推广为任意 hook 在所有故障中都只运行一次。

固定版本还同时检查保存的 replay 策略与当前工具定义：二者都为 `safe` 才允许恢复重跑。部署后把当前实现改成 `unsafe`，或者相应工具不可用，都可能得到 interrupted。即使两边都保持 safe，新的实现也应兼容旧参数和重放含义。代码发布因此是恢复设计的一部分。

这三组中断实验验证了 SQLite 下的进程终止窗口和 ToolTask 恢复，没有执行完整 GenerationTask 链路，也没有模拟断电、存储损坏或并发写入。它的判别力在于三种策略产生了三种可检查的动作结果，不能扩成对所有运行环境的可靠性承诺。

## Code Mode 的恢复靠日志重放与子任务身份

当一项任务需要“读配置、修改、检查、提取结果”，Code Mode 可以把组合逻辑写成程序。正常执行时，脚本保存中间变量，等待工具结果，再决定后续动作。进程终止以后，这些 VM 内存变量都会消失，单独持久化工具调用仍不足以让整个脚本从任意一行继续。

Durable 在 1.2 加入自己的 Code Mode 集成；这里讨论的是固定 1.3 实现，不能将这项恢复能力倒推为 1.0 初版已经具备。它采用重跑脚本并重放已交付结果的方式恢复执行，而非保存一份 JavaScript 堆快照。

实现中记录脚本运行起点和终态，并用 journal 保存结果交付顺序。结果先进入持久日志，再交给 VM；嵌套工具通过基于 VM 调用标识的稳定 key 附着到已有任务。虚拟时间、带种子的随机性和固定时区等条件，帮助重跑沿着相同控制流前进。

可以沿一个明确的崩溃点推演：

```text
脚本：read_config → set_config → check_config → 输出

中断前：
  read 已完成，结果写入 journal
  set 已完成，结果写入 journal
  check 正在等待

重启后：
  从头启动脚本
  read 接收先前交付的结果
  set 接收先前交付的结果，附着已有终态任务
  check 找到对应任务，再按它的实际状态推进
```

已经完成并提交的 `set` 有稳定身份，不需要因为 VM 重跑就创建第二项写入任务。若进程恰好死在 `set` 外部动作之后、它的结果提交之前，这个任务仍落入前面实验展示的窗口：由自身 replay 策略决定是否重新执行，外部幂等仍然必要。

这段过程依据固定版源码与文档推演，前面的 SIGKILL 实验没有覆盖完整 Code Mode journal。两者放在一起，是为了说明脚本恢复与工具恢复怎样嵌套：外层恢复控制流，内层恢复具体动作，每一层都需要自己的身份和提交位置。

确定性也有条件。若脚本重跑时发出的调用次数、顺序或参数偏离 journal，或模块版本、sandbox fingerprint 与既存运行不兼容，系统会错误结束。相同稳定 key 被用于不同参数，也会被拒绝。这种拒绝避免了把新的程序路径悄悄接到旧副作用上；处理时应检查代码版本、检查点及已完成外部动作，不能简单清空记录重试。

它与 Coding Agent 中普通 Code Mode 的会话变量提交也有区别。普通脚本可以在一轮中编排多个工具；Durable 额外保存这段编排的执行关系，才有重启后重新附着工作的依据。采用 Code Mode 本身，并不会自动得到持久任务调度。

## 子任务归属决定取消与完成

长任务常需要派生一个子会话：主任务修改配置，另一个 Agent 独立检查差异。只在内存里写 `Promise.all`，可以让两个调用并发，却没有回答进程重启后谁拥有它们、主任务取消时该清理谁，以及同一个子工作是否已经创建。

Durable 将 ownership 保存为任务与会话之间的归属关系。这与历史父节点是两种边：历史关系决定继承哪些过去材料，ownership 决定生命周期和取消向哪里传播。一个子会话可以拥有自己的上下文，同时仍归属于发起它的父任务。

因此，构建可恢复 subagent 工具时，关键操作发生在创建阶段：在一次提交中，先按 `ownerTaskId` 查找已有 child；存在就复用，不存在才创建；给 child 配置独立模型、工具与环境，用稳定的输入请求标识提交，再等待结果。重启后再次进入工具，找到的应是同一子会话与同一输入，而非又创建一个新的 Agent。

这条流程是应用可以基于 Durable 实现的设计，官方提供构建示例，运行时没有预先替所有业务选好一套 subagent 分工。父工具声明 safe 之前，作者需要确认它的创建和提交操作能够按稳定身份复用。

这里的 idle 表示 conversation 没有活动 run，也没有沿归属关系等待收尾的前台任务。它比“模型不再生成文字”范围更广：waiting、blocked 和 completing 的前台工作都仍然活跃。普通归属工作会影响这个空闲判断。父任务准备结束但子树仍在运行时，生命周期需要先等子树收敛；取消或失败也沿归属关系处理子工作，再进入相应的收尾阶段。abort handler 可以由应用执行清理或补偿，框架不会凭任务取消自动退款、回滚文件或撤回消息。

后台工作还可以声明持久的 background 边界。它仍有 owner，但普通 conversation 或 harness 的 idle 等待不会穿过这条边界继续等待其子树；普通 conversation abort 也不穿过，显式包含 background 的取消才会继续传播。把任务放到后台，因此改变的是完成与取消语义，应用应明确谁负责最终核对它的结果。

同样要区分“等待被取消”与“工作被取消”。调用方不再等一个结果，可能只是断开了当前等待；已经提交的任务仍然存在。HTTP 客户端断线后让后台工作继续，正是持久任务应用的一种合理需求。若希望同时停止工作，需要明确执行取消动作。

## 应用状态、环境和部署怎样参与恢复

任务状态之外，应用还有计划、待办、审批、验收和界面状态。若它们分别写入几份无关文件，任务恢复之后，用户可能看到旧状态，或误以为一个没有完成的动作已经通过验收。

Durable 的 typed documents 为这类可变 JSON 状态提供了位置。应用可以把一次检查的结果 entry 与 `status='verified'` 放进同次提交；界面 watch 读取的是已提交状态，迟到的客户端可以取得 snapshot。把“verified”写入文档的条件仍应是检查证据满足要求，不能拿一个状态字段替代实际验收。

分支与应用状态也要一起考虑。documents 的历史和 fork 策略决定新分支使用初始、当前或某个时间点的值；会话分支选择依然不会自动回滚执行环境中的文件。运行时可以重建“当时认为自己做到了哪里”，工作区当前是什么仍要从环境读取。

长上下文处理也进入任务系统。摘要生成可以作为后台任务运行，到 turn 边界再插入上下文；接近阻塞阈值时才需要等待。旧 entries 仍保留，reset 或 handoff 可以改变模型上下文起点。历史可查询与模型当前记住全部细节是两回事，应用若依赖精确材料，应提供明确查询路径。

执行环境则决定动作在哪里发生。conversation 的 cwd 和已提交文档等状态可以用于构造本地或远程环境，控制面可以与真正运行工具的机器分开。NodeExecutionEnv 中的本地操作使用宿主进程权限；需要容器、VM、远程身份或多用户授权时，由宿主选择并接好对应环境。ownership 说明工作归谁管理，并不授予数据访问权。

官方还展示了 Cloudflare Durable Object 的宿主路线：一个对象承载一个 Pi Session，内部可以有多个 conversation；宿主负责重建视图，并把持久任务的截止时间映射到 alarm 等唤醒机制。运行时可移植，仍需要宿主在请求、休眠与唤醒之间接好生命周期。这里依据设计资料说明，未进行云端部署验证。

部署时至少要让三样东西保持一致：持久数据、重新注册的代码定义，以及工具接触的外部环境。每个 phase 解析并使用当次定义，正在运行的工具继续原有实现，后续阶段可能使用重载后的定义。旧检查点中的参数和新代码不兼容时，应通过显式迁移或停止恢复处理。

存储也影响采用方式。SQLite 按需读取工作集，JSONL 方案则会让全历史驻留内存并随记录增长。固定实现要求一个 storage 由单进程拥有，没有跨进程写锁协调。把多个独立 harness 进程指向同一份存储，不是扩大 worker 数量的可靠方法。SQLite 的进程崩溃恢复与主机断电下的持久性还有不同条件，选用时应按实际故障模型验证。

这些限制直接来自恢复路径：没有可用定义就无法执行 checkpoint，没有稳定环境就可能作用于错误目标，没有受控写入者就无法依赖同一条提交线。它们共同构成应用接管长任务的成本。

## 在两条 harness 路线之间作选择

把 Coding Agent 和 Durable 放在同一层比较，选择依据才清楚。CLI、RPC 与 SDK 是接入编码会话的不同形式，Durable 则调整应用持有的执行状态模型。

| 判断维度 | Coding AgentSession harness | Durable Harness |
|---|---|---|
| 主要使用方式 | 人参与编码与探索，宿主也可通过 SDK/RPC 控制 | 应用管理长期、多入口、多 conversation 工作 |
| 主要持久对象 | 会话树、上下文与相关设置 | entries、documents、submissions、tasks 与 checkpoint |
| 进程退出之后 | 重建历史，由人或宿主决定继续方式 | 整理持久任务状态，再由调度器恢复 |
| 子工作生命周期 | 由宿主或扩展组织 | 通过持久 ownership、等待与取消关系组织 |
| 外部动作 | 工具与宿主负责正确性 | 仍由工具与宿主负责，额外明确 intent 和 replay |
| 采用成本 | 成熟编码入口与扩展生态 | 实验 API、兼容迁移、幂等与存储管理 |

有人持续观察代码修改、可以检查工作区后再说“继续”，Coding Agent 的上下文和扩展机制通常已经提供合适起点。宿主当然可以在其外部继续建设恢复系统，但那部分状态与故障处理由宿主自己拥有。

当请求可能跨客户端存活、重启后必须找到同一子工作、应用状态需要与执行进度共同恢复时，Durable 的对象模型才开始发挥直接作用。进入试点前，可以用配置任务做一次明确准入：为每个外部工具分类 replay；为输入、内部任务与外部操作分配正确身份；固定可恢复代码版本；选择单写者存储；最后在“动作已发生、结果未提交”的位置注入故障。

恢复后应能解释每一次实际动作来自哪里、哪一条记录支持继续，以及哪些外部状态还需要核对。能回答这三项，应用才真正接过了这条长任务的执行责任。
