Agent Harness 是围绕模型组织任务执行的程序：它装配提示与上下文、提供工具、解释工具结果，并决定继续、重试或停止。相同模型放进不同 Harness，能够看到的材料、能够采取的动作和实际消耗都可能不同。Harness 因而也是一个可以被优化的对象。

自演化将这个优化过程自动化：用另一个 Agent 修改 Harness 的源码、提示或技能，运行任务检查修改，再根据测量继续生成后代。优化产物是一份程序版本，反馈是任务执行结果，模型权重可以保持不变。它适合研究工具处理和执行策略怎样改善能力，而不必把每次改进都转化为模型训练。

Salesforce AI Research 的 Beagle 负责运行和评估这些程序候选，内置的 DarwinX 算法根据任务结果选择父版本、提出修改并保留后代。候选之间的谱系还记录了哪些修改可以继续组合，而不只是留下总分最高的一份程序。

## 搜索对象是程序，任务负责提供选择压力

DarwinX 把被修改的 Agent 称为 evolvee，把提出修改的 Agent 称为 evolver。被测 Harness 有一个基线仓库和提交；提议者在实验副本中建立分支或独立工作区进行修改。每份候选有可重新执行的源码身份，不只保存一句修改说明。

代码变化能够改动实际行为。论文中的演化技能包含工具使用、结果检查和交互处理等策略；它们改变模型在某类任务中会读到什么、何时执行下一步。修改提示可以影响选择，修改工具适配与控制流还可以直接改变执行过程。记录候选时因此要包括源码和配置，不能只记录模型名称。

任务给这场搜索提供方向。每个任务定义输入、环境与验证条件，被测 Agent 在其中完成工作；任务自己的执行框架给出轨迹和结果。Beagle 将这些评测接到统一调度，DarwinX 再使用结果选择下一次从哪个版本出发、尝试修复哪些失败。

为了把改善归因于 Harness，同一实验应固定被测模型、供应方、推理投入、每题预算和基线提交。提议者使用哪个模型则是另一个配置。一次演化可能调用许多次模型，但这些调用是在生成与测试程序，不等于更新被测模型的参数。与权重优化的区别可结合[模型后训练与 RLVR](/posts/rl-post-training-environments/)理解。

当前公开配置将这一系统分成 `run`、`evolvee`、`evolver`、`algorithm` 与 `data`：运行基础设施、被测程序、编辑者、搜索规则和任务池分别配置。这样的划分使一次失败能够追到环境、编辑器还是被测程序，而不是全部记成“自演化无效”。

## 一次分支演化怎样真正改出候选

一轮分支搜索从已有谱系中选取父节点，再领取该节点尚未解决的任务。任务不应只是随意列出的愿望：先运行基线，才能知道哪些失败存在可优化空间，以及哪些已通过任务可用于检查回归。

提议者先读取失败轨迹，结合允许修改的文件与已有经验分析原因，再编辑父版本的代码，由运行器执行修改后的程序。失败时，它可以继续分析和修订，直到这条编辑流水线（pipeline）达到迭代上限。整条流水线结束后才形成一个候选节点，其中可能已经经历多次修改。

官方配置中的 `n_failure_tasks` 控制一条 pipeline 领取多少失败任务，`max_loop_iters` 控制这条 pipeline 内分析、实现与检查的次数。失败任务更多，能够暴露共有原因，也扩大了修改目标；迭代更多，给编辑者修正机会，也增加搜索费用。这两个参数影响产生候选的过程，不能替代整场搜索的节点预算。

编辑者需要能够从失败摘要回到原始动作。`trace_qc` 先寻找每次trial保留的 `trajectory.jsonl`，将流式记录规范化成按回合组织的消息，再生成带问题定位的摘要。摘要中的 `#N` 指向规范化消息序号，实现同时保存相应 messages sidecar，让编辑者按序号钻回具体回合。默认规则路径在本地处理；显式开启语义分析时，还可以调用模型补充规则难以识别的失败。缺少兼容轨迹或分析器时，这段材料为空，提议继续使用原有失败信息。

跨节点经验走另一条路径。启用 `collective_knowledge` 后，pipeline 从整个campaign的task experiences汇总“哪些改动有效、哪些应避免”，注入下一次分析提示。另行启用推理判定时，已拒绝候选也可留下 `lesson` 与 `next_directive`，分别说明为何失败及下一次尝试方向，再进入近期经验块。前者供编辑者找失败位置，后者使新分支不必重复走完旧分支的试错。

需要比较同题成败时，`bestof2_contrast` 读取重复运行中的成功与失败尝试；若全部成功或全部失败，就没有这种成败对照。

新代码重新运行后，结果与源码版本一起进入谱系。后续提议者取得的因此不只是一个分数，还包括造成这些成败的程序和轨迹，可以继续修改同一版本，也可以从其他分支寻找不同修法。

接入用户自己的提议Agent时，需要实现编辑接口，并让修改落到本轮候选工作区。编辑者的文字建议只有被写入仓库、记录为源码版本，并确实进入下一次运行，才成为搜索中的程序候选。

## 保留与扩展分别在哪里落实

每个候选需要面对两项不同要求：保留已知有用的行为，并解决父节点尚未完成的任务。若只对当前失败题优化，一个专门绕过它的补丁也可能获胜；若完全禁止共享路径变化，又可能堵住可迁移修正。

DarwinX 的 `preserve_extend` 将已解和未解任务写进编辑者收到的目标；实际执行检查则由 guard、候选评分与后续确认承担。提示中的要求影响提议方向，运行过的任务才提供保留证据。`guard_enabled` 会选择父节点已解任务作 canary 检查，`guard_strict` 决定相应失败是否直接拒绝候选。

当前驱动默认每节点检查一个父节点已解任务。这个检查能及早发现部分退化，不能代表所有历史能力都重新测过。`preserve_extend.py` 的集合差检查也明确要求，先把保留集合与实际评估范围相交；没有执行的任务既不是通过，也不能直接记成失败。

`require_extension` 进一步要求候选带来测量到的新增能力。它避免搜索把只改写解释、没有改善结果的版本不断提升。范围检查与 `anti_cheat` 则处理候选是否越过允许修改的对象、是否篡改评估等问题。验证器需要独立于可编辑程序，否则分数可能因测量被修改而提高。

提议范围先限定允许怎样改，任务执行再测量改后的行为，提升规则最后决定这个候选是否值得继续扩展。要判断保留了多少能力，应回看实际执行的任务范围，而不是只看 `preserve_extend` 是否开启。

## 种群与谱系，让互补能力有机会重组

始终从当前最高分版本继续修改，会把搜索集中到一条路线。一个总分较低的候选可能解决了其他版本一直失败的任务，丢弃它就丢掉了后续重组可用的程序片段与策略。

DarwinX 通过谱系记录保留这些差异。默认 `mixed_high_score` 先筛出当前任务子集下有评分依据的可选节点，包括允许继续探索的归档节点，再按谱系收益排序。节点相对父节点新增解决的题数减去退化题数，得到本次净收益；沿祖先链相加，得到累计净收益。

采用增量而非单个节点的绝对解题数，有一个设计原因：候选常在各自领取的失败题与guard子集上评测，完整跑过大量题的根节点，绝对通过数天然更大。只按这个数排序，搜索就会反复从根出发，难以积累多代改进。

一个明确的数学例子是：A相对根新增3题、退化1题，累计净收益2；A的子节点B再新增2题、退化0题，累计为4。即使B当前那批题的绝对通过数少于根，它仍能凭累计改进成为优先父节点。数字只是对选择规则的复算，不是论文成绩。

实现用pipeline ID的哈希低位决定两条选择路径，大致各占一半。两条都先比较累计净收益、收缩奖励和当前评分；一条接着直接哈希破同分，另一条在同层得分相同后优先选择子节点更少的父节点，再破同分。因此“扩大分支”发生在同等排序层内，并不会任意抽取一个低收益节点。`llm_first` 则让模型读档案卡片选父节点，调用失败时回退到这套确定性规则。

重组实际从代码合并开始。运行器先在主父节点的commit上建立子工作区，再对第二父节点执行Git merge，同时记录两侧修改文件、重叠文件、各自独有成功题、共同失败题和应保留的谱系能力。

Git能干净合并时，程序先记录合并提交；若冲突只在可做确定性并集的技能注册对象，专门处理器尝试组合这些对象；其他冲突交给编辑Agent。编辑提示包含主次父节点、工作区、Git输出与前述行为要求，要求在目标程序中解决冲突，评测框架保持独立。编辑后仍要运行候选检查和必要修复。即使Git没有文本冲突，两份改动也可能对同一工具结果作不同假设，行为验证仍然必要。

成功题集合在这里用于规定要检查什么。它帮助编辑者看到应保留两侧哪种能力，而子节点是否真正同时拥有这些能力，要由合并后的程序重新执行决定。

`merge_every` 设置按节点数触发重组的节奏；有足够互补候选之后才有意义。过早启用，搜索可能只是在近似相同的代码之间付费合并。合并节点也消耗整场预算，失败合并不能从费用记录里消失。

质量多样性档案 `qd_archive` 则允许一种重要的探索状态：候选解决了新的任务，却丢失某项 guard 能力，仍可作为专才入档，供未来重组使用，但不因此成为交付的最佳节点。搜索档案和可交付版本具有不同标准。允许搜索保留有缺陷的材料，并不意味着允许直接将其上线。

## 增长、剪枝与整合，处理程序不断变大的代价

如果每次成功都只增加一条补丁，长期搜索会使程序充满分支和技能。某个条件越写越窄，既增加模型阅读负担，也增加共享路径相互影响的机会。自演化因此还需要决定哪些修改可以删、哪些旧结构可以重写。

当前配置在提议之前先确定允许的编辑方式。ADDITIVE 默认增加内容；PRUNE 只允许删除当前谱系新增的部分，保留演化前的基线；CONSOLIDATE 可以整合并改写演化前的代码，因此还要配置计算复杂度的源码范围。三种方式提出的修改，都要经过任务测量和相应回归检查，再判断是否保留。

剪枝率、最小谱系深度与整合触发决定这些编辑何时发生。在短实验中，即使开了 prune，也可能因深度条件和抽样没有产生剪枝节点。配置某个功能，与已经观察到它实际参与候选生成，应当分别记录。

论文还研究了跨任务主题和共享记忆，让早先修复提供可复用线索。这与单任务中“做完后写反思”的区别，在于这些材料进入了后续程序提议，并有新的执行结果检验。共享经验如果只是不断追加文本，却不能改善提议和测量，也会成为另一种增长负担。

## 搜索分数怎样成为采用证据

模型采样和环境执行都有噪声。同一候选恰好通过一次，不足以说明它比父节点稳定。Beagle 提供小范围重复筛查与完整集合确认，应按基线波动配置重复次数，并固定聚合方式。

平均成功和 best-of-N 回答不同问题。前者描述一次尝试的表现，后者允许多次尝试中有一个成功；若实际系统只执行一次，不能用更多尝试得到的分数替代单次交付能力。当前实现中，完整集合 `avg` 路径使用驱动默认的五次，而 `fullset_eval_n_attempts` 控制 `best` 路径，两者不能从同一个参数名推定。

候选很多时，每节点全量测量昂贵。延迟全量评估可以降低搜索成本，但要使用固定评测面板，保证节点比较的是同一批题；最后选出的候选再按报告口径确认。面板越小，越容易围绕其特征定向优化，因此确认集还需要独立于搜索选择。

DarwinX 论文分别研究了基准内适配、未见任务、合成到真实和跨基准迁移。这些关系的证据范围不同：在搜索池内提升说明程序适应了可见测量；未参与编辑和选择的任务，才进一步支持迁移判断。公开实现也提供可选的跨基准和混合回归门，必须实际配置、标定并触发后才能作为采用依据。

总成本应包含所有候选的提议、编辑、运行、被淘汰的检查和最终确认。`total_steps` 计算所有非根节点，不只成功保留的节点；并发工作可能越过协调停止目标。最终程序每次执行便宜，与找到它的整场搜索便宜，是两项需要分别测量的结论。

## 将它用于可测量的 Harness 改进

开始试验前，先确定可编辑仓库、固定模型和任务预算，运行一份可重建基线。任务池既要有可靠失败，也要保留稳定通过的能力；搜索外任务不要参与提示修订、候选选择或阈值调优。

随后先跑通一个候选：任务能被启动，失败轨迹能被编辑者理解，修改能被记录成提交，新程序确实进入下一次执行，验证结果回到谱系。确认这条路径后，再根据任务噪声增加重复和 guard，根据候选互补性增加档案与重组，根据代码增长增加剪枝与整合。复杂度应由观察到的问题引入。

最终交付的是明确的程序提交、模型配置和测量结果。采用前以同样预算检查未参与搜索的任务，同时确认延迟、成本与关键规则；生产回退则保留旧版本及流量切换安排。搜索过程可以探索有代价的分支，承担真实任务的版本必须满足预先定义的采用条件。

Harness 自演化的适用前提，是失败中存在可被程序改变的部分，而且任务结果能够独立检验。验证器无法判断目标、环境噪声主导分数，或任务池已经没有有效差异时，自动增加修改不会自然产生改进。先建立可靠的反馈，再让程序版本沿反馈演化，才是这条路线的工程基础。
