一个命令执行 Agent 能处理短输出，遇到很长的日志却漏掉关键错误。模型收到的可能只是被截断后的开头；把提示写得更严肃，仍然看不到已经丢失的内容。另一些任务失败于临时工具错误：模型本来能够完成，执行程序却在第一次失败后结束。

这些问题都发生在模型周围的程序里。程序决定调用什么工具、把多少结果交回模型、何时重试，以及什么条件下结束。修改这些决定，可以在不改模型权重的条件下改变任务结果。

Harness 自演化把这种修改组织成自动搜索：提出一个外层程序候选，执行任务，根据结果保留或淘汰，再从已有候选继续搜索。**关键工程问题是确定哪些修改值得进入下一轮，以及什么证据足以支持采用。**

Beagle 是评估和演化 Agent Harness 的开源框架，其中包含 DarwinX 的实现。下面结合论文和实现解释搜索机制，再用一组手工设定结果的日志任务演示筛选。

## 被搜索的是外层程序的版本

一次普通任务运行，模型根据提示和工具结果选择后续动作。一次演化运行，则由另一个过程观察失败轨迹，修改执行这类任务的程序。前者交付任务结果，后者交付候选程序。

例如，原 Harness 把命令输出原样附进上下文，并在工具报错时直接终止。演化提议可以改为按段读取日志、保留错误附近的内容、给临时故障增加有界重试，或者调整工具返回格式。候选因而可能同时包含提示、解析器、工具适配、技能文件和控制流的变化。

这与只搜索一句提示的范围不同。程序修改可以改变模型能看见哪些观察，以及哪一次工具调用会实际发生。也因此，一份候选源码值得单独版本化：只记录最终提示，无法重建解析、重试和退出行为。

它与模型后训练的更新对象也不同。这里固定底层模型，改变调用模型的程序；模型权重是否更新属于另一条优化路径。两者可以组合，但若同一次比较同时更换模型、提高推理预算并修改 Harness，就很难说明收益来自哪项变化。

DarwinX 的配置把被演化程序、使用的模型与供应方、推理设置和任务预算分开描述。试验需要固定这些测量条件，同时声明哪些仓库文件允许编辑。固定模型名字还不够：模型每题可用的动作次数、输出长度或推理投入变化，同样会改变结果与成本。

## 提议、执行与评分分属不同角色

可以把一次候选生成拆成五个对象：

| 对象 | 负责什么 | 留下什么证据 |
|---|---|---|
| 演化提议者 | 阅读失败轨迹，提出程序修改 | 修改说明与代码差异 |
| 被测 Harness | 使用固定模型执行任务 | 工具调用、观察、退出结果 |
| 任务环境 | 提供初始材料与执行条件 | 环境版本、输入、运行记录 |
| 验证器 | 按任务规则判断结果 | 任务得分与失败原因 |
| 搜索控制器 | 分配候选和任务，选择父节点与保留版本 | 谱系、测量记录和选择结果 |

模型可以提出“增加重试会解决问题”，验证器需要检查重试后任务是否完成；控制器还要判断它是否损害原来能完成的任务。把这几步都浓缩成“Agent 反思后提升”，会丢失决定结果的控制边界。

假设一次失败轨迹包含完整命令输出、实际交给模型的截断内容，以及最后遗漏的错误。提议者据此新增“提取错误行”的处理。下一轮执行使用修改后的代码重新跑任务，评分应来自任务结果，不能只接受候选对自身修改的解释。

提议者能否编辑评分器也需要明确。若它可以改掉判定失败的测试，分数提高就可能来自测量变化。一个合理的试点设计会把可编辑执行代码与评分规则分开，将后者固定在独立边界，并保留候选真正运行的版本。

## 保留旧能力需要先定义可见集合

搜索最容易接受的候选，是修好了当前失败任务。但当前失败只是一个观察窗口。把长日志直接压缩成固定长度，可能通过长输出任务，同时删掉原来正常 JSON 里的字段。

DarwinX 的保留与扩展逻辑关注两件事：父节点已解决的任务是否丢失，候选是否解决了新的任务。这种判断要以实际评估过的任务为范围。未运行的旧任务不能算已保留，也不能因没有失败记录而算通过。

这里有两个经常被混淆的动作。提议者收到“保留原有能力”的要求，是编辑约束；系统真正运行回归任务并拒绝退化候选，是执行筛选。把要求写进提示，并不会使修改自动满足要求。

在核对的实现中，guard 可以选择父节点已解任务作为 canary，即用来预警回归的小样本；严格 guard 才会因这些检查中的失败而拒绝候选。检查一个 canary，只能说明这一个样本的结果。需要全量已知回归保证的采用流程，还要实际覆盖相应集合，并决定允许哪些波动。

假设可见任务分成两部分：原来已通过的短输出、正常 JSON、无需重试任务，以及尚未通过的长输出、临时工具错误任务。候选的新增能力与丢失能力可以直接记为集合差：

```text
lost   = 父节点已解集合 − 候选实测已解集合
gained = 目标集合 ∩ 候选实测已解集合
```

这要求候选确实跑过被比较的任务。若只运行当前失败题，再拿它的结果与父节点全量结果做差，`lost` 会把“没测”混成“失败”。更稳妥的记录应分别保存任务是否被评估与是否通过，再对共同测量范围解释结果。

## 谱系档案与交付候选有不同用途

只保留当前最高总分的版本，容易让搜索集中到一种处理方式。另一个候选也许总分稍低，却能处理最高分版本一直失败的一类输入；它可能提供后续重组所需的不同方案。

DarwinX 保留候选谱系，并提供在得分与谱系广度之间选择父节点的方式。谱系记录的不只是一个分数，还包括候选从哪里来、改变了什么、在哪些任务上获得和丢失能力。后续提议可以从不同父节点继续，而不是永远修补同一份代码。

保留多样性也意味着“在档案里”不能直接解释为“可发布”。配置中的质量多样性档案模式，允许丢失某些 guard 能力却获得新能力的候选成为搜索材料；这类节点不会因此被当成交付的最佳版本。另一些模式还允许在核心与外围任务之间进行有界取舍。

因此，采用条件应该与搜索策略分开写。搜索可以探索有回归的分支，以保留解决新问题的线索；交付版本则按明确的稳定性与成本要求选择。否则用户看到“候选被保存”就自动上线，会把研究过程的探索状态混进实际服务。

运行出错也需要单独归类。候选没有存活下来，可能只是没有产生有用修改；执行流程失败，可能来自环境初始化、工具调用或基础设施。把这些情况全部记成零分，会使父节点选择同时受到能力和环境可用性的干扰。

## 一组小样本演示筛选改变了什么

以下是作者设计的教学数据。三个候选的任务结果与成本均为手工指定，只用于检查筛选规则；成本单位没有对应实际金额或模型调用次数。

| 候选 | 可见任务结果 | 单候选成本 | 搜索结果 |
|---|---|---:|---|
| 无差别截断 | 保留短输出并通过长输出，丢失正常 JSON 与无需重试任务 | 2 | 有回归，拒绝 |
| 有界重试 | 保留全部基线任务，新增临时工具错误处理 | 4 | 进入候选集 |
| 输出处理加有界重试 | 保留全部基线任务，并新增两类目标能力 | 7 | 进入候选集 |

这里设置一个“单候选可接受成本上限”。上限为 8 时，后两个候选都满足成本条件，按已解任务数量优先、成本次优的规则，选择第三个。上限降为 5 时，第三个超出限制，第二个成为搜索结果。

这并不表示整场搜索只花了 8 或 5 个单位。所有候选的编辑、执行和被淘汰前的评估都需要成本；该上限只是在最终选择中约束一个候选的预设成本。

再给被选版本一次独立检查，使用未参与前述选择的 Unicode 输出与永久工具错误任务。教学数据中，第三个两项都通过；第二个只通过 Unicode，因而不能满足采用条件。预算收紧选出了可见任务上合法的赢家，仍然可能没有得到可采用版本。

核心判断可以用一个独立的集合例子复算：

```python
baseline = {"short", "json", "no_retry"}
targets = {"long", "temporary_error"}
holdout = {"unicode", "permanent_error"}
candidates = [
    ("truncate", {"short", "long"}, set(), 2),
    ("retry", baseline | {"temporary_error"}, {"unicode"}, 4),
    ("output_retry", baseline | targets, holdout, 7),
]

def choose(limit):
    eligible = [c for c in candidates
                if baseline <= c[1] and targets & c[1] and c[3] <= limit]
    if not eligible:
        return None, False
    winner = max(eligible, key=lambda c: (len(c[1]), -c[3]))
    return winner[0], holdout <= winner[2]

assert choose(8) == ("output_retry", True)
assert choose(5) == ("retry", False)
```

这组预设结果显露了选择规则：通过搜索检查、符合预算、通过最终检查，是可以得到不同答案的三个判断。

如果看到第二个失败，又根据它的留出结果调整搜索，再从同一留出集挑版本，这个集合就已经参与优化。下一轮需要另外保留检查材料，才能继续把结果解释为搜索外证据。

## 测量口径会改变“最好”的含义

真实模型有采样波动。一个版本每题运行一次恰好通过，另一个运行五次只通过三次，不能凭单次成功就确定前者更好。试验需要记录每个任务尝试了多少次，以及最终指标怎样聚合。

平均成功与多次尝试中至少一次成功回答的是不同问题。前者接近随机选一次运行的可靠性，后者包含额外采样预算带来的机会。若服务只能执行一次，用更大的 best-of-N 与基线单次结果比较，会把更多计算混进程序改进。

Beagle 的配置区分完整集合的平均测量和最佳尝试等口径。在核对版本中，平均测量的重复次数与某些 best 模式参数并非同一个开关。采用前应检查实际被执行的路径，不能只看到一个名为“尝试次数”的字段就推断全部测量都受它控制。

DarwinX 论文也区分同一基准内适配、未见任务、合成到真实、跨基准迁移等验证关系。同基准搜索可以显示程序找到了适应该基准的策略；跨任务结果才对更远的采用范围提供额外证据。它们不能拼成一个不带条件的生产效果结论。

搜索预算还包含失败尝试。候选编辑、模型推理、容器运行、重复验证和最后全量检查都应该计入。核对实现中的总节点步数包含保留与丢弃的非根节点；并发任务在协调停止时仍可能产生额外工作。只统计最后成功版本执行一次的费用，会遗漏找到它的成本。

## 从可以搜索到值得搜索

一个可行试点先需要可靠验证器和可重复的失败。若同一版本在同一任务上波动很大，先增加必要的重复测量，判断究竟是程序问题还是采样与环境噪声。若基线已经通过全部可见任务，继续搜索也缺乏新增能力的有效信号。

随后固定模型、任务版本和每题预算，圈定可编辑文件，保留初始程序与候选提交。给搜索提供能改变处理策略的失败轨迹，并为重要旧能力设置实际回归检查；预先决定哪些回归只允许入档，哪些条件允许成为交付候选。

采用版本还需要搜索外证据，以及清楚的退回路径。保存旧提交和配置可以重建旧版本，但生产流量是否能平滑回退、外部副作用如何处理，仍需服务本身设计。程序搜索得到一个版本，不会自动完成上线工程。

当失败主要发生在工具反馈、上下文组织和执行控制上，而且任务结果能被独立检验时，Harness 搜索才有明确的可优化对象。让系统自动提出更多修改只是开始；决定某一份修改能否承担下一批任务，仍要回到固定条件下的测量与最终接受标准。
