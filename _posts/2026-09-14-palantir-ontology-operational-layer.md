Palantir Ontology 是企业数据、业务逻辑与操作之间的一层公共模型。它把来源系统里的记录组织成可查询的业务对象和关系，并把允许执行的变更定义成 Action。不同应用、分析程序和 Agent 因而可以围绕同一批对象工作，复用其身份、属性、权限和动作。

企业系统中的数据和操作规则往往分散在不同位置：数据平台保存记录，业务应用定义用户能做什么，模型又在另一处形成建议。若三者各自解释“客户”“设备”或“订单”，每次应用建设都要重新连接数据和操作规则。Ontology 让多个消费者复用同一组对象定义和 Action，减少这部分重复。

它的建设成本也由此产生。团队需要确定对象身份、来源关系、可写字段及动作规则，并持续维护这些定义。理解其架构，重点是看这份公共模型怎样承接读取和操作，哪些职责因此复用，哪些跨系统问题仍由集成设计处理。

## Ontology 在 Foundry、AIP 与既有系统之间的位置

Foundry 承担数据接入、处理和应用建设，AIP 将生成式 AI 接入数据与业务流程；两者使用 Ontology 的对象、关系、逻辑和动作连接业务数据与应用。Apollo 则负责软件部署与持续交付。

关系可以概括为：来源数据经过接入与处理，映射为 Ontology 对象；查询和函数读取这些对象；应用或 Agent 根据结果形成操作；经过许可的 Action 修改对象或调用外部系统；更新再次进入查询视图。这里是职责关系，具体数据源可以使用不同接入和更新方式。

因此，对象查询并不等于每次都直连 ERP。Ontology 后端维护面向应用的索引与查询状态，原业务系统也可以继续拥有相应交易的权威记录。对象上的变更、外部系统的接受，以及新数据重新可见，需要按集成路径区分。

这一层对纯报表任务可能显得偏重。它的价值在多个消费者需要反复使用相同的业务定义、判断和受控操作时更明确：一处定义被多个应用复用，规则修改也有集中的治理位置。

## 对象模型连接业务含义与数据来源

可以沿官方“航班更换飞机”的例子理解模型。`Flight` 和 `Aircraft` 是对象类型，分别定义航班和飞机有哪些属性；某个具体航班和候选飞机则是带主键的对象实例。两者通过分配关系连接，后续换机操作改变的是这个关系。模型先把“哪一班”“哪一架”“当前分配给谁”表达出来，操作才有明确目标。

字段的数据类型负责表示值，Object type 把这些值组织成有身份的业务对象。同一架飞机可以被列表展示、函数读取，也可以作为 Action 的参数，无需每个应用重新解释一串来源字段。

Object type 的数据源映射把来源列接到主键和属性。主键回答“它是哪一个对象”，属性回答“目前知道它什么”。如果来源系统的两个编号表示同一个实体，或相同编号在不同范围内重复，组织必须先完成身份建模；增加一张对象类型不会自动消解歧义。

Link type 再定义类型之间的关系，具体 Link 连接对象实例。关系可以由外键或单独的数据源表达。上层应用由此可以从一个对象找到相关对象，而无需在每个界面重新拼接来源表。

这个模型还有两种复用方式。Shared property 统一跨类型字段的定义和元数据；Interface 描述多种对象类型共同具备的属性和能力，使代码能按共同形状操作。是否需要抽取这些公共定义，取决于真实消费者是否需要共享语义。过早统一仅仅同名、实际含义不同的字段，会把歧义集中到平台里。

定义了对象、关系和属性以后，同一对象既能出现在列表中，也能被函数读取、计算，并成为 Action 受控变更的目标。上层不必为读取与操作分别建立一套身份映射。

## 后端将定义、索引和读取分开

对象类型和 Action 定义之外，后端还要把来源变化写入可查询状态，让应用在权限范围内读取对象。官方后端架构将定义管理、索引和读取分为几项职责：

| 部件 | 保存或处理的对象 | 对应用的意义 |
|---|---|---|
| Ontology Metadata Service | 对象、关系、Action 等定义 | 决定可用的类型和能力 |
| Object Data Funnel | 来源数据与用户编辑的索引输入 | 将变化送入对象查询状态 |
| Object databases | 已索引的对象数据、查询与编辑相关状态 | 为业务访问提供执行基础 |
| Object Set Service | 对象集合的搜索、过滤、聚合与加载 | 给消费者提供统一读取入口 |
| Functions on Objects | 面向对象与关系的计算 | 将复用逻辑接到公共模型 |

一项来源变化如何进入查询，可以沿官方 OSv2 分工追踪。数据源保存新记录，类型映射确定这些列对应哪个对象主键与属性；Funnel 读取来源数据及 Action 产生的编辑，将它们索引到 object databases；消费者再通过 OSS 搜索、筛选和加载对象。OMS 保存的是类型和关系定义，而非每条实例变化的查询结果。

按这一职责关系推演，飞机运行状态已经在来源中改变，而对象查询仍返回旧值时，应检查来源变化是否已进入索引，再检查查询范围；若映射把状态列接错属性，则反复刷新也不会修好模型。来源、映射、索引与读取分别提供排查位置。

Object Set 是理解读取方式的关键。静态集合保存对象主键清单，成员不会因为来源属性变化自动替换；动态集合保存筛选定义，数据变化后，满足条件的对象随之改变。两种集合表达的是不同业务意图：前者固定“选中了谁”，后者固定“按什么条件选”。

沿关系查询、聚合后再加载对象，与先把全部记录搬到客户端计算，也有不同的成本。查询设计宜先明确范围和筛选，再读取真正需要的属性与关联。具体执行可能使用存储下推、内存或其他计算路径，应用不应把某一种内部路径当成永久的性能保证。

由此，平台排错也有自然顺序：先确认类型和主键映射，再查来源与编辑是否已索引，最后检查集合定义与读取权限。界面中缺少一个对象，可能发生在这三层中的任何一层。

## Action 让应用复用允许的业务变更

Action type 定义一组对象、属性和关系变更，以及可选副作用。用户提交参数，平台根据 Action 配置及权限判断能否执行，再应用相应规则。它让应用复用的是一个有业务含义的操作，而非让每个消费者自行获得任意写表权限。

回到航班换机，Action 参数给出目标航班与候选飞机，配置规则负责改变相应分配关系。提交条件分别读取两种上下文：`Current User` 取得提交人的组成员关系，`Parameter` 从候选 `Aircraft` 对象取得运行状态。前者用集合包含判断操作者是否属于指定组；后者用精确相等判断运行状态是否为 `Yes`。两项都通过后，才允许提交。

这使业务规则与界面控件分开：候选下拉框帮助用户选择，提交条件仍针对本次提交的身份和参数计算。换一个应用调用同一 Action，检查仍有相同定义；飞机运行状态变了，当前参数条件也随之改变。某架飞机可被看见、可被选择，与这次换机是否获准，分别由读取、参数和提交条件决定。

读取到某架飞机，只说明操作者在当前读取范围内可以看见它。能否修改关系，还取决于 Action 的提交条件和相关对象的编辑配置。配置人员修改 Action 定义的权限，与业务人员应用 Action 的权限，也分别管理。

Functions 可先查询和计算候选，Agent 或其他应用再选择对象，将参数交给同一个 Action。复用的位置是对象身份与操作规则：调用者改变，仍以它的身份执行已配置条件。

这里的复用不要求所有变更都人工审批。哪些条件能自动检查，哪些操作需要人批准，应由组织按后果设计。平台提供实施位置，业务含义仍由负责该规则的人确定。

## 外部写回将系统边界重新显露出来

当操作只修改 Ontology 对象时，平台可以管理该范围内的编辑。需要改变 SAP、Salesforce 等外部系统时，Webhook 把动作材料交给外部接口。每个必填输入可以映射到同类型的 Action 参数、静态值或参数对象的属性；也可以由 Function 沿关联对象取值，返回符合 Webhook 输入结构的数据。这样，业务对象先转换成外部请求需要的字段，外部返回又可以供后续规则写回对象。官方区分两种执行时序。

Writeback webhook 在其他规则及对象变化之前执行。外部请求失败，后续 Ontology 修改不会应用，用户能收到失败。它适合外部接受是平台内变更前提的路径。

Side-effect webhook 则在对象修改之后运行，用户可能先看到成功；多个副作用没有固定执行顺序。它适合通知或尽力而为的投递。选哪种时序，实质上是在选择先让哪一侧面对失败。

官方明确保留了一种 Writeback 故障窗口：外部请求已经成功，Ontology 的后续变更却失败。面对这种窗口，集成方需要让外部写入对应到可识别的业务请求，超时后查询其结果，并安排来源更新重新进入读取视图。稳定请求身份与幂等需要由接受请求的系统或集成层实现。

同样，Ontology 页面显示的更新不能独自证明原系统完成了交易。若某字段由外部系统持有最终权威，完成判定应回到该系统的结果和后续读取。否则，公共模型容易把“已请求”“已写入平台”和“外部已确认”合成一个模糊状态。

对账与恢复需要分别关联 Action 提交、外部执行结果和后续读取状态。Action 提供受控操作入口，跨系统结果不一致时，集成方仍需判断应查询、重试还是补偿。

## 治理围绕共同定义及其变化展开

Ontology 被多个应用复用后，模型变更会影响更大的消费者集合。字段含义、主键、Link 和 Action 参数的调整，都需要考虑现有应用依赖。治理的工作因而同时包含来源质量、模型演进、动作权限和操作追踪。

### 用分支同时检验模型与消费者的变化

Global Branching 给共享定义的修改提供了独立开发位置。官方示例先在同一个分支上修改数据流水线的输出逻辑和字段，再在 Ontology Manager 中调整由该数据集支持的对象类型。来源结构和对象映射可以一起检查，不必先改动主分支，让现有消费者面对一份尚未配套完成的定义。对已迁入项目权限、并启用保护的对象类型、Link 或 Action 等资源，修改必须先存到分支，再经过 proposal 合并。

消费者也要进入检查范围。以官方支持的 OSDK React 应用集成为例，应用、Ontology 资源和源码使用同一个 global branch；定义或资源集合变化后，在分支生成 SDK，安装更新后的依赖，再运行应用或 PR 预览。应用拿到的类型与它实际读取的分支由此对应起来。验证 Action 之前，还要先完成它会编辑的所有对象类型的分支索引；测试产生的对象编辑留在分支，不随定义一起合入主分支。Webhook 默认不在分支执行；测试时需显式启用，启用后仍使用已配置的外部目标。

开发期间主分支继续变化，包含 Ontology 修改的分支需要手动 rebase：先载入主分支更新，再逐资源处理与本分支的冲突。准备交付时建立 proposal，合并检查先检查资源是否能够合入，具备相应批准权限的审查者再按资源与项目政策审核变更。检查和批准满足后，合并 Global Branching proposal，才会推进 Ontology 的合并。

这套过程把定义修改、消费者测试与接受修改连在一起。合并使共享定义进入主分支，应用发布仍有自己的步骤：官方 Developer Console 流程要求在源码默认分支另行创建 release，才部署生产网站。Global Branching 负责开发期间的隔离与协同，跨开发、测试和生产环境的版本交付则由 release management 处理。因而，复用同一模型的团队既要审查定义是否正确，也要安排依赖它的应用何时采用。

### 运行追踪与规则责任

官方提供的 Action log 将成功提交记录成对象，帮助回答谁在什么上下文作了什么决定。它与编辑历史、失败指标各有范围：失败调用要看 Action metrics，绕过 Action 的其他编辑也不会自动生成 Action log 对象。选择观察工具应从需要回答的问题进入。

读取安全与写入传播同样需要分清。当前 Permissions 文档说明，行列读取控制过滤调用动作时能看到的数据，但不能因此推断相同控制会自动保护写出的全部结果。数据标记和分类授权等机制承担下游保护，具体写入仍要检查 Action 的授权配置。

模型和操作既然是共享资产，就应有明确负责人：谁确认来源权威，谁批准类型演进，谁维护 Action 规则，谁处理外部结果不一致。公共建模减少各应用重复实现，也提高了这套共同定义的维护责任。

## 哪些系统值得引入这一层

只读分析首先需要稳定数据口径和查询能力。对象数量少、操作路径单一的内部工具，可以继续通过现有 API 和工作流实现。引入 Ontology 的理由，应来自跨应用反复复用业务对象、关系和动作，而非企业想增加一个知识图谱。

当多个团队、应用和 Agent 需要共同查询并操作同一组业务对象时，公共模型能减少身份映射、参数解释、权限规则和界面逻辑的重复。相应成本是模型治理、平台接入和跨系统集成；来源事实混乱时，平台会把混乱暴露出来，组织仍需作出裁决。

一个合适的起点，是选择已有来源、明确身份、实际有多个消费者的一组对象，先跑通读取，再开放少量后果清楚的动作。判断是否扩大时，看新增消费者是否真的复用了对象和操作定义，以及异常能否被追到来源、Action 或外部系统。这样，Ontology 承担的是一层可治理的业务能力，系统选择也有可观察的依据。
