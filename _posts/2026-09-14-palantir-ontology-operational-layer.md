假设生产订单 `PO-DEMO-042` 遇到缺料。企业资源计划系统（ERP）保存着计划开工日，制造执行系统（MES）显示前序工序尚未结束，库存系统报告关键物料不足，供应商数据给出的到货承诺又晚于计划。四套记录可能都没有错，因为它们回答的是不同问题；但任何一套都不足以决定订单是否改期。

这里的 Palantir Ontology，是 Palantir 提供的一层业务建模与操作机制。它把来源数据映射为有身份的业务对象，用关系连接对象，让查询与逻辑消费这些对象，再把允许发生的变更封装成受控命令。它承担的是统一业务语言和操作边界，不是把 ERP、MES 和库存系统搬进同一个数据库。在这个假设架构中，ERP 仍然对订单计划日期拥有最终确认权。

理解这层机制，先要拆开四种容易被一个“成功”混在一起的状态：第一，带来源与时效的观测；第二，根据观测算出的改期候选；第三，获准向生产系统提交的受控命令；第四，由 ERP 确认、并被平台重新读取的业务结果。看见缺料不等于应该改期，建议了日期不等于允许执行，命令被平台接受也不等于 ERP 已经改完。

这笔订单需要经过以下步骤：

```text
观测 → 改期候选 → 受控命令提交 → ERP 确认结果 → 重新读取并对账
```

## 先确认四套记录说的是同一笔订单

`PO-DEMO-042` 进入 Ontology 后，首先成为一个 **Object（业务对象）**。Object 是对实体或事件的带身份表示：`object type` 规定某一类对象有哪些属性，`object instance` 表示其中一个具体实例。本文假设建立 `ProductionOrder`、`Material`、`Supplier` 和 `SupplyRisk` 四种类型；这些名字服务于缺料案例，不是 Palantir 自带的行业模板。

每个 Object 都要有在其类型内唯一的 primary key（主键）。数据源中的列可以映射为主键和 property（属性）：例如把 ERP 订单表的 `order_id` 映射为订单身份，把 `planned_start_date` 映射为计划开工日。这个映射建立的是访问契约，不会自动修复主数据。如果两个工厂重复使用同一订单号，或者 MES 中的编号指向不同粒度的工单，团队仍要设计带命名空间的规范标识、维护对照关系，或隔离无法确认的记录。

身份对齐后，**Link（关系）**才有意义。Link type 规定对象类型之间如何关联，具体 Link 则把实例连起来。订单可以通过物料标识连到所需 `Material`，供应商和物料的多对多关系可以通过含两端主键的关联数据建立，`SupplyRisk` 再指回触发它的订单与物料。Link 证明“谁与谁相关”，不证明两端同时更新，也不承诺某次查询看到的是同一时刻的快照。

因此，对象属性不能只剩一个值。要让缺料判断可追责，本文建议同时维护来源、业务 owner（责任人）、观测时间或版本，以及冲突处理规则。这些是生产建模建议，不是 Ontology 强制提供的固定字段。

| 属性 | 本例中的权威来源 | 进入判断的条件 | 冲突时怎么做 |
|---|---|---|---|
| `planned_start_date` | ERP 与生产计划负责人 | 对应 ERP 当前有效版本 | 版本不明则停止改期判断 |
| `available_quantity` | 库存台账与库存运营负责人 | 不早于本轮排程使用的库存批次 | 与预留量冲突时标记异常，不取较大值 |
| `promised_arrival_date` | 经确认的供应商承诺与采购负责人 | 承诺仍在有效期内 | 未确认或多份承诺并存时转人工 |
| `SupplyRisk.severity` | 本轮输入和排程规则 owner | 与输入快照属于同一批次 | 来源变化后重算，不覆盖来源字段 |

至此，Ontology 中出现的是可追溯的订单观测。它仍不是新的生产事实：ERP 日期可能刚被别人修改，库存批次可能已过期，供应商承诺也可能撤回。对象模型的价值是让这些差异能够被指出和归责，而不是把差异抹平。

## 观测经过计算，只能先成为候选

接下来要从众多对象中选出与 `PO-DEMO-042` 有关的那一组。Palantir 把一次查询选中的对象集合称为 **Object Set**；Object Set Service 负责搜索、过滤、聚合和沿 Link 查找周边对象。它读取已被索引的对象表示，产出某个读取时点的集合，不会因此创造一条新的 ERP 记录。

查询从有效观测窗口内的 `SupplyRisk` 开始，只保留指向 `PO-DEMO-042` 的风险，再沿 Link 取得订单计划日期、短缺物料、库存和供应商承诺。要避免让结果在计算途中失去语义，集合需要携带或能够追溯到输入版本。否则，候选日期即使算法正确，也可能基于已经失效的库存或承诺。

Palantir 的对象后端会把已配置的数据源和部分 Action 编辑索引成可查询对象；查询的物理执行可能随规模、表达式复杂度和资源变化。调用者不应依赖固定执行路径或固定延迟。对这笔订单，工程上更重要的不是猜测底层使用哪种引擎，而是尽早按订单与有效期过滤，避免先加载大量无关对象再做业务判断。

**Function** 是在运行时业务上下文中执行逻辑的能力。本文假设一个改期 Function：只有物料缺口仍成立、且已确认到货日晚于计划开工日时，才建议把开工日移到“到货日加业务缓冲期”。算法和缓冲期都是案例设定，不是 Palantir 内置的排程规则。

平台上的 Function 可以生成 Ontology 编辑（edits），但本文刻意不在这里写生产状态。它只产出 `CAND-PO-DEMO-042-01`，其中保存订单、风险、物料与供应商身份，输入版本，当前与建议日期、原因和逻辑版本。本文把这种结果称为 **Decision Proposal（决策候选）**；这不是固定的 Palantir 资源类型（resource type），而是一道作者设计的隔离边界。

隔离候选有两个直接后果。其一，输入变了就能废弃并重算，不必先撤销一次生产写入；其二，候选可以接受业务审查，却还没有调用 ERP 的资格。订单路径因此从“可追溯观测”前进到“可解释建议”，仍未跨入生产变更。

## Action 只授予尝试改变状态的资格

`CAND-PO-DEMO-042-01` 若要继续，必须进入 `RescheduleOrder` **Action**。Action 是预先定义的对象属性、Link 修改与外部副作用契约，同时规定输入和提交条件。它读取候选和当前对象状态，产出一次受约束的提交记录（submission）；它不是界面上的普通按钮，也不是可以执行任意请求的接口。

这个假设 Action 只面向 `ProductionOrder/PO-DEMO-042`。输入包括候选标识、当前日期或版本、建议日期、原因和操作者；允许修改的范围只有 `planned_start_date`，不能顺手改变订单状态、物料关系或其他 Link。提交条件（submission criteria）先根据参数和当前可读对象，检查候选是否仍指向同一订单、输入版本是否过期、建议日期是否满足业务规则。这只是平台内检查。真正写入 ERP 时，还应由 ERP 的更新接口把预期版本与更新操作绑定，在版本不匹配时拒绝修改；具体可以使用该接口支持的条件写入或等价机制。若 ERP 没有这种能力，平台内再读一次也不能消除并发覆盖窗口，此时需要业务侧互斥流程或人工处置，不能承诺候选不会覆盖新值。

这套参数、范围和检查是本文对案例的设计。Palantir 提供 Action type、编辑与副作用等产品机制，却不会替团队决定“什么日期合理”“谁应批准”或“覆盖冲突是否可接受”。人工审批也不是所有 Action 的固定前置；是否增加审批，应由变更后果、自动检查覆盖和失败可恢复性决定。

权限要分层看。操作者能否看到 action type，只是入口；运行时还要有权读取相关对象与数据源，提交内容要满足 submission criteria 和底层编辑策略，日志对象也有自己的权限。读取过滤约束 Action 能看到什么，却不能单独证明写出安全。真正的写边界来自允许修改的字段、提交规则、编辑策略、外部服务授权和必要的审批共同作用。

因此，Action 提交被接受，只能证明一次受控命令通过了平台这一侧的入口检查。它没有证明 ERP 接受了新日期，更没有证明更新后的日期已经重新进入 Ontology。订单路径到这里是“获准尝试”，不是“改期完成”。

## 写回顺序决定故障落在哪一边

`RescheduleOrder` 通过入口检查后，还要选择平台内修改与 ERP 调用的顺序。Palantir Action 支持两类 webhook，也就是动作过程中调用外部系统的回调；两种方式都留下跨系统失败窗口。

| 方式 | 先发生什么 | 仍可能留下什么裂缝 |
|---|---|---|
| writeback webhook | 先调用 ERP；ERP 明确失败会阻止后续 Ontology 修改 | ERP 已改期，随后平台内修改失败 |
| side-effect webhook | 先修改对象，再调用 ERP | 平台已显示新值，ERP 失败或结果未知 |

writeback 提供的是有限事务性，不是跨系统原子事务。外部请求成功后，平台内规则仍可能失败。side-effect 的外部调用还可能晚于用户看到成功提示；配置多个 webhook 时，它们之间也没有顺序保证。它更适合通知等尽力而为（best-effort）的副作用，不适合用“页面成功”证明 ERP 已接受改期。

两种顺序只是让一侧暂时领先另一侧。它们都不提供跨系统 ACID，也就是不能把平台与 ERP 的改变视为一个不可分割、失败后整体回滚的事务。选择哪种方式，应看哪一侧可以暂时领先、是否存在不可逆操作，以及团队能否发现并修复不一致。

最棘手的状态不是明确失败，而是超时。ERP 可能没有收到请求，也可能已经完成改期，只是响应丢失。此时重新点击或生成新请求，会把网络不确定性变成重复副作用。本文建议为命令建立稳定业务幂等键，例如由订单、候选和目标日期共同决定；这不是 Palantir 自动生成的固定字段。

超时后先用同一个键或 ERP 业务键查询实际结果（outcome）。确认未受理，且 ERP 或前置集成服务确实持久化幂等键时，才使用同一键受控重试；查到成功就记录外部交易号；仍无法判断则把订单置为 `unknown`，冻结再次提交并转人工。若外部接口不支持幂等键，只有在副作用落地处存在可验证的唯一业务约束或等价去重机制时，才可能安全重试。串行化同一订单的命令可以减少并发冲突，却不能单独解决响应丢失后的重复执行；无法确认旧请求结果时，应继续保留 `unknown` 并转人工，不能仅凭平台内保存过一个键就再次发送请求。

这套查询、幂等和 `unknown` 分支是本文的恢复设计，不是 Action 自动提供的业务保证。它让订单路径在外部结果不明时停住，而不是把“Action 提交成功”冒充“ERP 已生效”。

## ERP 确认后，还要重新读取一次

一次 `RescheduleOrder` 会留下多种记录。Palantir 的 **Action log** 是可配置的成功 Action 提交日志：它不记录失败提交，也不覆盖绕过 Action 发生的编辑。日志里出现这次 Action，只能证明一项被配置为记日志的提交成功；它不是完整编辑历史，不是 ERP 交易总账，更不是最终业务结果库。

要把四种状态串回同一笔订单，本文建议保存下面的关联链：

```text
candidate_id
  → action_submission_id
  → external_transaction_id
  → outcome_status
  → reindexed_object_version/time
```

这些字段不是 Palantir 自动提供的固定字段结构。`outcome_status` 应表达 accepted（已受理）、committed（已生效）、rejected（已拒绝）、unknown（未知）等业务语义，不能拿传输成功或 webhook 执行结束代替 ERP 终态。关联链的作用，是让值守人员能从候选追到命令、从命令追到外部交易，再确认当前读取看到的是不是那次交易之后的状态。

对账，也就是 reconciliation，会比较候选目标、Action 提交、ERP 交易和当前权威日期。若 ERP 已成功而 Ontology 仍是旧值，应修复摄取或索引并重新读取；若平台先改而 ERP 明确失败，要根据业务政策恢复平台状态；若两边都发生了部分变化，则由业务 owner 决定接受现状还是执行一个纠正动作。

这种纠正动作称为 compensation（补偿）：它针对已经发生的副作用再做一次业务操作，不是可靠回滚。把 ERP 日期改回去可能再次失败，也可能与下游排程冲突。订单一旦已被车间或采购流程消费，逆转甚至比接受现状更危险。因此，补偿需要自己的授权、记录和结果确认，不能由自动化执行者（Agent）在异常后临时发挥。

已配置数据源更新后可以重新索引为 Ontology Object，但延迟取决于摄取和索引配置，不能假定实时。最终确认必须同时看两处：ERP 的权威交易结果，以及重新读取的 `ProductionOrder`。新计划日期一致，读取版本或时间又足以证明看到的是更新后状态，`PO-DEMO-042` 才从“结果待确认”进入“改期完成”。不一致时，它仍是待对账任务。

这一步把失败定位变得具体：候选可能不合理，Action 可能被拒绝，ERP 调用可能失败，外部交易也可能成功但索引尚未追上。只看 Action 提交数量，会把业务正确性、外部可靠性和数据新鲜度揉成一个没有诊断价值的成功率。

## 是否采用完整 Ontology，取决于谁愿意长期负责

走完 `PO-DEMO-042`，Ontology 的边界已经清楚：它可以拥有对象、关系与 Action 契约，提供查询、逻辑和治理挂点；它不自动拥有来源字段真伪、跨系统标识对齐、ERP 终态、跨系统原子性和业务风险接受。

这些空缺都需要 owner。Data owner 解释来源、版本和时效，Object owner 维护身份与关系，Action owner 负责参数、规则和副作用语义，App 或 Agent owner 约束消费者行为，Security owner 管访问与写出边界，运行团队承担异常对账。角色可以由同一人兼任，责任不能留给平台名称。

如果需求只到统一指标、检索关系或辅助人工判断，没有生产写回和结果确认，就停在只读层。先把业务标识、来源、时效与冲突规则做清楚，比预建一套可能用不到的 Action 体系更有价值。

如果对象和动作很少，只有少数应用使用，而现有接口、工作流、授权、审计与对账已经成熟，轻量对象接口加既有工作流通常更直接。代价是团队继续自行维护对象合同、幂等、权限、失败恢复和结果关联，而不是这些问题消失了。

只有当多个团队、应用、操作者与自动化消费者反复使用同一组对象和受控动作，副作用需要统一治理，而且组织愿意长期维护上述 owner 边界时，完整 Ontology 路线才可能产生复用价值。复用的是业务契约与控制面，不是把所有权威状态搬到一个地方。

合适的试点应是一项后果明确、结果可观察、失败可处置、操作者清楚的窄 Action。先让 `PO-DEMO-042` 只读地走通身份、时效和冲突处理，再开放受限改期；同时在平台外保留可读的业务标识、数据合同、动作规范、测试、审计导出与外部交易关联。这样能降低退出成本，但不等于可以无损迁移。

回到这笔订单，判断是否闭环不需要记住所有产品名。只要连续回答四个问题：观测来自哪里、何时有效；候选依据哪一版输入；Action 获准改变什么；ERP 结果是否与重新读取一致。Palantir Ontology 可以承载这条运营契约，但谁拥有真相、谁允许改变、谁确认结果，仍必须由组织回答。
