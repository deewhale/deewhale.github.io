Paperclip 是一个用来组织 AI Agent 工作的应用。把它部署起来，打开的是网页工作台：可以建立组织、给 Agent 配置岗位与执行程序、分派任务（Issue），再查看进展、产出和费用。真正读文件、修改代码、调用模型的，可以是接入的 Claude Code、Codex 等程序。Paperclip 将这些执行者放进共同的工作流程。

Agno 则从写 Agent 开始。开发者安装 Python SDK，选择模型，提供指令和工具，定义一个 Agent 怎样完成工作。AgentOS 将这些 Agent，以及多 Agent 的 Team、预先编排的 Workflow，作为 API 服务运行；Control Plane 是连接该服务的网页界面，供人发起运行、查看会话和执行记录。三者分别对应编写程序、提供服务和操作服务。

这解释了两者为什么容易被放在一起，又为什么不能直接按功能名称打勾比较。Paperclip 首先让人组织一群执行者；Agno 首先让人构建可调用的执行组件。不过，Agno 的 Company 也开始保存产品、项目和长期任务，任务执行之后还要审查交付物。比较的交集因此扩大到了：**已有 Agent 之后，一项工作如何被提出、交给执行者，最终由谁确认完成。**

要理解这条交集，先分别走一遍它们让用户开始工作的路径。

## Paperclip：先配置谁来工作，再让工作进入看板

Paperclip 的官方首次使用教程从建立组织开始。运行 Paperclip 服务后，用户进入工作台，建立组织，再到 Goals 中补充目标。这里得到的是一个保存工作关系的地方：目标解释为什么做，项目归集相关工作，任务记录具体要做什么，Agent 则承担角色和分工。

教程接着创建首个 CEO Agent。“CEO”是这个 Agent 在组织中的角色，它负责读目标、提出策略，并向其他角色分派工作。创建这一角色不意味着 Paperclip 生成了一个新模型。用户仍需选择实际执行程序，并准备该程序能够使用的模型账号或凭证。

例如，选择 Claude Code adapter，意思是让 Paperclip 按该适配器的方式启动 Claude Code；选择 Codex adapter，实际执行者就换成 Codex。adapter 负责连接 Paperclip 保存的角色配置与真正运行的程序，处理启动所需参数，以及相应的运行信息。岗位、模型和执行程序因此可以分别选择：同样一个工程角色，可以由不同模型和程序承担；使用同一种执行程序，也可以配置多个职责不同的角色。

在这一步，用户要做的决定很具体：这个角色用什么执行者、在哪个工作环境里运行、能拿到哪些材料和工具、遵守什么指令。选择 adapter 并测试连接，解决的是“能不能把它启动起来”。任务描述和岗位指令则告诉它“启动后该做什么”。二者缺一，组织图上的名字都不会自动变成有效劳动力。

配置好以后，Paperclip 通过一次次唤醒让 Agent 工作。界面的 Run now 可以立即触发一次运行，也可以配置 heartbeat 定时唤醒。heartbeat 在这里是一次工作机会：执行者读取当前目标、分派和上下文，决定下一步动作，完成后回报。它不要求每个 Agent 一直保持一个正在推理的进程；下一次唤醒可以继续处理尚未结束的工作。

官方 Watching Agents Work 教程用这条路径展示第一轮协作：CEO 先读取目标和指令，提出策略，用户审查策略，再让后续工作进入任务看板。这个流程把人放在方向确认的位置，将具体拆分和后续分派交给 Agent。能否形成有用的任务，仍然取决于执行者的判断和它收到的材料；Paperclip 提供保存与推进这些决定的工作环境。

任务进入看板后，用户可以分派给某个 Agent，也可以让有相应职责的 Agent 建立子任务和安排交接。执行者领取分派，查看任务及其讨论，在自己的环境中处理工作，再通过 Paperclip 的接口更新进展、补充评论或提交产物。官方随项目提供的 Paperclip skill，就是给执行者的操作指引：怎样查找分派、领取任务、说明阻塞和回报结果。

这与让人盯住几个独立终端有一个直接区别：任务即使经历了多次运行、换人处理或被退回，仍有自己的记录。人在任务页看工作要求、讨论和产出，在 Agent 的 Live Run 或 Runs 中看某次执行。前者回答工作推进到了哪里，后者回答某次启动具体发生了什么。执行日志能帮助排查过程，交付物与审查结果才说明这项工作有没有达到要求。

因此，Paperclip 的“协作”首先落实在角色之间的任务分派和交接：工作被保存为共同对象，不同执行者围绕它领取、回报和继续推进。模型在单次运行中怎样选择工具，则由接入的执行程序负责。

## Agno：先定义怎样执行，再把执行提供给应用

Agno 的默认入口是 Python 程序。开发者构造 Agent 时选择模型，写入指令，并提供它可以调用的工具。工具可以是函数，也可以连接数据库、搜索或其他系统。模型判断要调用哪个工具及其参数，SDK 负责实际调用、把结果放回上下文，再让模型继续，直到返回答案或达到相应停止条件。

这时已经可以在 Python 中直接运行 Agent。若要让网页、业务后端或其他服务调用它，AgentOS 会把这些配置好的执行组件注册成运行 API，同时接入会话、数据库和其他运行设施。

官方 Run Your First AgentOS 的例子构造了名为 Agno Assist 的 Agent，使用 Claude 模型和 SQLite 存储，然后交给 AgentOS。去掉安装与启动部分，关键关系是：

```python
from agno.agent import Agent
from agno.db.sqlite import SqliteDb
from agno.models.anthropic import Claude
from agno.os import AgentOS

db = SqliteDb(db_file="agno.db")
agent = Agent(
    name="Agno Assist",
    model=Claude(id="claude-sonnet-4-5"),
    db=db,
)
agent_os = AgentOS(agents=[agent], db=db)
app = agent_os.get_app()
```

这个官方示例先只注册一个能够对话的 Agent。模型由外部供应商提供，Agent 对象保存它的调用配置，数据库保存会话，AgentOS 生成对外的应用接口。要让它搜索或编辑文件，还要在 Agent 配置中提供相应工具及访问条件；把程序注册成 API，并不会凭空增加工具。

按教程准备依赖和模型凭证，启动文件后，用户得到的是一个可接收 API 请求的服务。它的 API 文档可以查看请求方式，运行信息接口可以查看注册组件。应用向 Agent 的运行接口发送消息，AgentOS 找到对应组件，由 SDK 推进模型和工具调用，再返回结果或流式事件。后续请求携带相应会话信息，才能在已有上下文上继续。

Control Plane 让这套服务有了网页入口。用户在网页中添加 OS，填写自己运行的 AgentOS 地址，连接成功后就能看到注册的 Agent、Team 和 Workflow，再从界面测试它们、查看会话与运行数据。会话、知识和追踪等内容，取决于服务端实际启用了什么。浏览器连接服务，并不把执行进程自动迁移到网页提供方；AgentOS 运行在哪里、能访问什么，仍由部署决定。

这条路径可以扩展到多个执行者。Agno 的 Team 将成员组合起来，在协调模式下由 leader 根据输入选择要委托的成员，并利用成员返回的结果继续处理。成员有各自的指令和工具；leader 决定分工，并不等于所有成员共享一个没有区分的上下文。Workflow 则把步骤和控制流写进程序，由预先定义的流程安排函数、Agent 或 Team 的执行。前者把一部分分工决定交给模型，后者把关键顺序和分支交给流程定义。

两者最终都可以注册到 AgentOS。调用者面对的是一个可运行组件，内部可能有一次工具循环，也可能有成员委托和多步处理。更细的差异见[《Agno SDK：Agent、Team 与 Workflow 的执行机制》](/posts/agno-sdk-execution/)。

这也建立了与 Paperclip 的第一处区别：Paperclip 中，用户先定义角色和工作，再接入负责执行的程序；Agno 中，开发者先定义执行组件，再让应用或用户调用它。两者都有界面和运行记录，但起步时要求准备的东西不同。

## Company：让一次执行成为一项可以审查的长期工作

一个 AgentOS 接口正常返回，只能说明这次执行得到了结果。工作属于哪个项目、当初接受了什么要求、结果需不需要修改，这些信息需要比一次请求活得更久。Agno 的 Company 就在已有运行服务上补上这一组工作对象。

Company 需要显式启用。它用 Product 表示持续负责的产品，用 Project 组织一组工作，再用 Task 记录具体要求、执行者、工作状态和结果。一个 Task 可以经历多次执行和审查；它与某次运行的关系，类似持续存在的工作单与一次具体处理过程。

官方 `06_execute_tasks.py` 提供了一个足够具体的示范：建立名为 SDK 的 Product，在其中建立 Release 项目，再创建 Draft release notes 任务，要求整理经过审查的变更。与此同时，程序注册一个 ID 为 `draft` 的 Workflow，作为这个任务的执行者。

这里有一个重要设计：示例中的 Workflow 只包含确定性函数。函数读取 Task 传入的上下文，并返回待审文本，用来展示工作如何接入运行服务。发布说明的质量判断并不由这个函数承担。这个安排把“工作记录怎么流转”单独显露出来，读者可以清楚看到每一步由谁触发。

首先，示例创建 Task 并写入 brief 和证据引用。接着，把工作转为 `ready`，同时绑定已注册的 `draft` Workflow；这一步明确接受的是哪项工作，以及交给谁处理。然后请求开始一次运行。AgentOS 将任务材料交给对应 Workflow，通过持久队列安排 worker 执行，并保存 Task 与这次运行的关联。

Workflow 正常返回后，运行结果是完成，Task 则进入 `in_review`。这两个状态没有冲突：程序已经做完它被要求执行的步骤，但交付物还在等待接受。后续审查通过，工作才进入 `done`；需要修改时，工作记录保留，后续处理仍能关联到原来的要求和已有结果。

任务为什么不能直接等同于一次运行，在这里就很明确了。一次正常返回不能替代交付审查；一次调用失败也不意味着项目中的这项工作不存在了。把工作要求、执行和审查分开保存，才能回答“上次做到了哪里，这次为什么又要做”。

Company 还需要满足相应执行路径的条件：任务绑定的是运行层能够解析的已注册组件，任务运行使用持久队列，需要配置支持的存储和 worker。官方示例将 Company 记录与队列存储分别配置，队列使用 PostgreSQL。这些是将长期工作真正交给执行层的接线工作，而不是在网页上多建一张任务表就能完成。

因此，Agno 已经可以进入与 Paperclip 相似的工作管理范围。比较时应把 Company 纳入，而不是停在“一个管理任务，一个只能调用模型”。但 Company 也只是 Agno 的一部分：构建问答接口、运行一个 Workflow，并不要求先建立 Product 和 Project。

## 同样组织 Agent 工作，分派与协作发生在哪里

现在可以回到同一个需求：已经有可执行的 Agent，希望把工作持续交给它们，并知道结果是否完成。差异首先体现在分工发生的位置。

Paperclip 的组织关系主要跨越任务和多次唤醒。CEO 可以提出策略、创建工作并分派给不同角色；具体角色处理后，在任务中回报结果或继续交接。组织中的成员可以使用不同执行程序。人看到的是角色对哪项工作负责，以及工作在这些角色之间怎样推进。

Agno Team 的成员协作首先发生在一次组件运行内部。协调者按当前输入委托成员，再处理成员结果。应用不必为每次成员委托创建一张长期工作单。若要保存跨运行的产品责任、任务要求和验收记录，再由 Company 承担。Team 与 Company 可以配合：一个 Task 交给一个 Team，Team 内部再决定由谁完成哪一部分。

这两类协作可以服务于相似目标，但不能只按“都支持多个 Agent”归为同一种机制。前者先建立角色与工作之间的持续关系，后者先组织一次请求中的成员执行；加入 Company 后，Agno 才把执行组件与持续工作进一步接在一起。

接入方式也有相似的交叉。Paperclip 用 adapter 连接不同执行程序；Agno 除了自己构造 Agent，也提供外部 harness 的接入。Agno `v3.1.11` 已允许 ClaudeAgent、CodexAgent 进入 Team 和 Workflow，因此现有 Claude Code、Codex 能力并非必须全部重写成原生 Agent。具体能否用于 Company 的某条任务执行路径，还要满足该路径对注册组件和队列的要求；支持一种组件，不代表所有入口都接受完全相同的对象。

| 要完成的事 | Paperclip 的典型入口 | Agno / AgentOS 的典型入口 |
|---|---|---|
| 确定由谁工作 | 建角色、选 adapter、配置执行环境 | 定义或接入 Agent，再组合 Team、Workflow |
| 提交一项工作 | 在组织的任务中写要求并分派 | 直接调用运行 API；需要长期跟踪时建立 Company Task |
| 多个 Agent 分工 | 角色之间拆任务、分派和交接 | Team 内委托，或由 Workflow 安排步骤；Company 保存长期工作 |
| 查看处理过程 | 任务讨论、产物与对应的运行记录 | Control Plane / API 中的会话、运行和追踪；Company 关联任务结果 |
| 确认工作完成 | 按任务的交付与审查规则处理 | 普通运行返回结果；Company Task 另经过交付审查 |

这张表比较的是已经走过的动作。真正影响选择的，是团队先需要组织现有执行者，还是先需要开发一个可嵌入应用的执行服务，以及长期工作是否已经由 Company 覆盖。

## 接单、批准和预算，会改变真实的使用结果

工作开始自动推进以后，有几个细节会直接改变人对进度的判断。它们应沿执行过程理解。

第一，接单成功和交付完成是两个时刻。Paperclip 的通用 HTTP adapter 可以把请求发给远端服务，但远端返回成功响应，可能只是表示作业已入队。若远端还要继续运行，集成就需要保存远端作业标识、查询进展、取得结果，再回报工作状态。否则看板上的进展可能领先于真正的执行。较深的 CLI 或会话集成可以提供更多运行信息，不能用一个 HTTP 入口概括所有 adapter。

取消也沿同一条关系处理。停止等待 HTTP 响应，远端作业仍可能继续；把任务改成不再进行，也不会自然终止已发出的工具操作。需要核对的是实际执行者是否收到取消、是否停止，以及已经发生的外部写入怎样处理。AgentOS 的持久队列保存待执行工作和运行关联，有助于请求进程退出后继续处理，但队列重试可能重新执行一次 run。已经成功的外部操作仍需靠操作标识、幂等处理或结果查询避免重复。

第二，批准方向、批准动作和接受交付发生在不同位置。Paperclip 首次使用教程中的策略审查，是人决定后续工作方向；任务的 execution policy 可以要求交付先经过 review 或 approval，再完成状态变更。它约束的是任务怎样结项。若执行者此前已经对外部系统完成了写入，事后的交付审查不能撤回那次操作。

Agno 则还提供工具调用前的确认与审批机制：在被保护的工具执行前暂停，等待相应处理，再继续运行。Company Task 之后仍可以进入 `in_review`，由人判断产出是否合格。一次工作里，两种检查可以先后发生：先允许执行某个动作，再审查整份交付物。选择平台时，应该明确自己要约束的是哪一步，而不是只问“有没有审批”。

第三，费用控制依赖执行者把消耗回报回来。Paperclip 的预算参与开工控制，包括运行前预留和后续费用记录；但远端执行者没有回传的费用，不会因为任务出现在看板上就被完整计入。通用 HTTP adapter 的响应不会自动提供完整的模型 usage 集成。采用时应把所用 adapter 的成本回报、预算检查和在途消耗一起看。

Agno 的 usage、metrics 和并发配置分别帮助观察消耗与限制同时运行的工作。这与向组织角色分派月度额度是不同的操作。若费用额度是关键条件，应按目标部署实际支持的预算流程判断，不能将运行监控直接当作相同的组织预算管理。

这些差异说明，产品界面中相同的“运行”“批准”“预算”，需要追到真正生效的动作：哪一步才算做完，哪一步能拦住操作，哪一步能阻止继续花费。

## 按已有资产选择入口，组合前先确定工作归谁管

已有多套 Claude Code、Codex 或其他 Agent，主要困难是任务分散、分工不清、交付难追踪，Paperclip 的进入方式更直接：接入执行者，配置角色和工作环境，再将工作集中到任务记录中。采用的主要投入，是把 adapter、账号、工作区和回报方式配置完整，以及确定谁分派、谁审查、怎样处理阻塞。

要把 Agent 能力嵌入应用，希望应用通过 API 调用一个有明确输入输出、工具和会话的组件，Agno 的 SDK 到 AgentOS 路径更直接。开发者能控制组件内部如何执行，再选择 Team 或 Workflow 组织协作。采用的投入在组件定义、服务部署、存储与访问控制；需要持续工作时，再配置 Company 的任务和审查流程。

执行组件已经在 AgentOS 中，Company 也能覆盖项目与任务要求时，应先判断它是否足够。增加 Paperclip 的价值，通常来自还要统一组织其他执行程序、角色或工作流程。反过来，Paperclip 已经承担跨执行者的工作管理，而某项能力适合做成专门的 AgentOS 服务，两者也可以组合。

组合需要明确一项工作的主要记录放在哪里。如果 Paperclip Issue 负责要求、分派和验收，AgentOS 可以承担一次或多次具体执行。连接层保存 Issue、Paperclip 运行与 AgentOS run 的关联，持续取得结果、错误和费用，再回报任务。仅把一个 URL 填进 HTTP adapter，还没有完成这条回路。

如果 Company Task 也独立保存相同要求和验收，两边就可能分别改派、退回或重新执行。此时必须规定哪一边可以决定工作范围，另一边怎样跟随，并明确重试是查询已有执行，还是发起新的工作尝试。共同的标题无法代替明确的关联记录。

Paperclip 与 Agno AgentOS 的选择，因而可以落在两个实际起点上：是先把已有执行者组织起来，还是先把执行能力构建成服务。长期任务管理让它们产生直接交集；谁来定义工作、谁推进执行、谁接受交付，则决定这份交集究竟已经满足需要，还是值得承担两套系统连接的成本。
