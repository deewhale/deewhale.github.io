团队安装了一个文档生成包。审查者读过 `SKILL.md`，步骤看起来只是整理内容、运行渲染器、输出 PDF。一个月后更新版本，包里增加了上传 Hook 和一个 MCP 服务启动项。文档生成的目标没变，执行对象与联网能力已经变化。

Agent 配置的供应链需要沿这段变化审查。文件里既有影响模型选择的文字，也可能有将被执行的脚本、宿主事件触发器和工具服务声明。只有把来源、精确版本、客户端加载方式与实际权限连起来，才能判断安装和更新会使什么行为发生。

这里以一个自拟文档生成包为例，拆开配置进入运行的过程。资料核查截至 2026 年 10 月 20 日；所用清单是教学模型，只比较数据，没有安装、启动或执行第三方包。

## 配置进入了几条不同的路径

先把包中的对象分开。指令文件告诉模型怎样理解任务、使用哪些步骤；Skill 组织一项能力的描述、说明与附属材料；脚本提供可执行程序；Hook 把宿主事件与动作关联；MCP 配置指定 Agent 可以连接或启动的工具服务。它们可能在同一个发行包里，却不由同一机制生效。

Agent Skills 规范允许包中包含 `scripts`、`references` 与 `assets`。这解释了为什么只检查主体说明不够：一个简短的说明文件可能指向更多材料，其中既有供模型阅读的文本，也有由工具执行的程序。

读取通常也有阶段。客户端可以先用名称和描述发现 Skill，在激活后读取主体说明，额外资料按需取得。这个过程有助于减少无关内容进入上下文，但它不是安全审查流程。某份文件暂时没有被读入模型，不表示附属程序已经经过检查。

要追踪文档生成包，可以依次问：哪个客户端识别它，怎样激活，读取哪份指令，指令是否要求调用脚本，以及脚本由哪个执行工具启动。每一步都需要具体对象，不能把“安装了 Skill”当作全部动作已经发生。

| 包内对象 | 它改变的部分 | 需要进一步核对 |
|---|---|---|
| 指令 | 模型得到的任务说明和行为建议 | 加载顺序、作用范围及冲突处理 |
| Skill 描述与主体 | 能力发现及激活后的材料 | 客户端实现、附属文件与脚本 |
| 脚本 | 实际程序行为 | 参数、读取范围、写入位置与网络 |
| Hook | 某个宿主事件触发的动作 | 注册位置、触发条件与移除条件 |
| MCP 启动项 | 工具服务及其依赖 | 来源、版本、启动方式和继承权限 |

这张表中的审查项不代表所有客户端都有相同文件名和加载语义。配置研究需要对具体产品取证。一个客户端承认的 Hook 配置，换到另一个客户端可能不会加载；一个客户端的权限规则，也不能直接按名字迁移。

## 从文件存在到实际执行

假设第一版包包含排版说明与 `render.py`。用户请求生成文档，模型在读取 Skill 后选择调用渲染脚本，执行工具启动程序，程序读取工作目录中的输入并生成输出。行为发生的必要条件，包含模型选择、工具支持与执行权限。

现在第二版增加一个“生成后上传”的 Hook。以 Claude Code 的公开文档为例，Hook 由宿主的特定生命周期事件触发，注册与移除还受其所在配置或 Skill、子 Agent 生命周期影响。它与“模型看完说明后决定运行”是两条不同路径。

因此，审核第二版时应知道 Hook 由谁注册、哪个事件触发、执行什么命令。不能笼统说所有 Hook 都每轮执行，也不能说一段文字只要存在就能自行启动程序。实际行为取决于客户端语义和用户启用条件。

MCP 启动项又引入另一层。客户端或 Agent 按配置连接服务，服务暴露工具，之后工具调用进入服务实现。若配置使用未固定版本的启动包名，安装时读到的配置可以一直相同，后续启动解析得到的程序版本却发生变化。要审查的对象因此包含服务本身及其依赖解析方式。

把三条路径合在一起看：模型通过指令作选择，宿主按事件触发 Hook，工具服务在自己的进程内执行。运行时有效权限决定它们能读取和改变哪些资源。配置描述表达意图，实际后果还需要穿过这些执行环节。

图中四类检查承担不同职责。固定版本稳定被审查对象，检查加载语义说明它何时生效，授权决定哪些请求被接受，隔离约束程序实际可访问的资源。某一项通过，不会自动完成其他三项。

## 扫描结果主要描述声明

2026 年 9 月修订至 v3 的研究《Scanning the Harness: Configuration Exposures in AI Coding-Agent Supply Chains》，将指令、Skills、Commands、Hooks、子 Agent 与 MCP 配置一起作为分析对象。这个视角有助于把通常分散的文件纳入同一来源和更新链路。

研究样本包含 3,171 个公开仓库，区分 2,660 个使用配置的 setup 与 511 个分发集合。作者在 setup 中识别出 409 个、约 15.4%，含其定义的三类版本或宽执行预批准声明之一。分母、分类和样本来源决定了这个数字能说明什么。

它描述的是所选公开样本中的配置暴露，不是整个生态的恶意率，也不是发生攻击的比例。一个宽泛声明是否转成有效权限，还要看客户端怎样解释、用户是否启用、执行环境能访问什么资源。扫描器能把复核工作集中到相关位置，不能仅凭命中给一个包定性。

尤其要区分三个证据层次。文件中写了一个匹配规则，是声明证据；对应客户端把它解释成什么授权，是实现证据；某个调用在实际环境里成功执行，是运行证据。把第一层直接写成第三层，会使风险结论超过测量覆盖。

研究 v3 还修正过对 `find` 通配授权的共同误判，涉及客户端对特定危险动作的另行处理。这项修正说明，两个检查实现相互一致，仍然可能共享同一项平台语义错误。交叉检查应回到客户端的实际规则，而不只比较两个扫描器给出的标签。

## 行为指引与执行权限各自生效

Skill 可以写“只读取当前项目”，但这段要求首先是模型接收到的行为指引。执行工具是否只能读取当前项目，需要看操作系统隔离、工具实现和有效授权。若启动程序继承了更广的文件权限，文字要求并没有改变这些权限。

开放 Skill 规范中的 `allowed-tools` 目前仍是实验字段，支持情况取决于实现。不能把它作为跨客户端统一强制的授权机制，也不应反向断言所有客户端都会忽略它。审查时需要针对目标客户端确认它是否识别、怎样解释及与其他规则怎样组合。

Pi 的内置 MCP 可以说明配置选择与运行授权的区别。以 v1.3.0 为例，客户端先读取用户级服务配置，获得项目信任后再读取项目配置。同名完整定义会替换用户级定义；没有启动命令、地址或类型的项目条目，只能覆盖是否启用、工具暴露方式及逐工具规则，其余启动参数和凭据仍来自用户配置。逐工具规则表会被整体替换，审查新增一条规则时也要查看哪些旧规则随之消失。

暴露方式决定工具从哪个入口到达模型：直接声明、经搜索加载、供脚本调用，或在该客户端中隐藏。Pi 的项目信任控制配置加载，工具调用仍使用进程和服务的有效权限。审查时因此要分别确认加载了哪份配置、当前允许哪些工具入口，以及服务凭据和运行环境实际准许什么。隐藏一个工具不会撤销同一凭据在其他客户端的访问能力。

命令匹配也有自己的粒度。Claude Code 文档区分命令规则和沙箱：前者围绕调用文本匹配允许、拒绝或询问，文件系统与网络的强制边界需要相应隔离机制。拒绝某个命令拼写，并不等于从系统层撤销相关资源的全部访问路径。

回到文档包。第一版只需读取输入和写出 PDF，可以把执行目录、输出目录与必要依赖限定清楚。第二版新增上传动作后，目的地、发送内容和凭据使用都成为需要决定的对象。如果团队接受上传，应明确接受哪个目标与哪些材料；如果不需要这项功能，应选择不激活该路径或在运行权限层阻止它。

判断重点是能力与用途是否相称。新增网络连接可以是合理功能，也可能与原任务无关。来源可信可以提高审查起点，但不能替代对具体行为的判断。

## 用两版清单检查能力增量

为了比较更新前后，给这个假设包整理一份审查清单。以下字段是教学设计，不是 Skill、Hook 或 MCP 的官方配置格式。它们把分散文件中需要审查的对象汇总到一起：

```python
v1 = {
    "revision": "release-1",
    "executables": {"script:render.py"},
    "network": set(),
    "mcp": set(),
}
v2 = {
    "revision": "release-2",
    "executables": {"script:render.py", "hook:upload.py"},
    "network": {"upload.invalid"},
    "mcp": {"demo-doc-server@latest"},
}

for field in ("executables", "network", "mcp"):
    print(field, sorted(v2[field] - v1[field]))
```

代码只做集合差异，已离线执行。它会列出新增 Hook、虚构联网目的地以及未固定版本的 MCP 启动包。程序没有访问该域名，也没有解析或运行这个包。

差异给审查者一个入口：先读新增 Hook 源码，查清它何时触发；再核对它发送哪些文件、发送到哪里；最后查看 MCP 启动对象的来源与精确版本。`@latest` 使后续解析仍可能变化，固定文档包版本并不能自动固定这一层。

清单也有不足。`render.py` 名称不变，内容仍可能改变；因此完整复核还需要比较被固定版本的源码或摘要。仅比较新增项适合定位能力范围变化，不能替代现有执行对象的内容审查。

教学程序最终给出的合理状态是“需要复核”，而不是“已发现恶意”。它没有模拟客户端加载、权限组合和网络执行，无法对这些环节作实测声明。审查者据此开始具体调查，而不是把清单输出当作安全认证。

## 更新应重新绑定版本、来源与权限

第一次批准的对象应当明确：来自哪个仓库或发行方，具体哪个提交或发布版本，包含哪些执行文件，由哪个客户端以怎样的权限加载。只有这些对象固定，下一次更新才有可比较的基线。

自动更新省去了寻找新版本的操作，也缩短了“旧版本已知内容”与“新版本即将执行内容”之间的审查时间。团队可以根据能力变化决定更新路径。纯说明修订、渲染脚本改动、增加联网 Hook 和引入新的工具服务，对执行的影响不同，没有必要采用同一种粗略判断。

对例子中的第二版，一次有用的升级 PR 应同时展示文档包版本变化、新执行对象、启动包版本和权限变化。将这些变化拆到彼此看不见的多个配置层，审查者就难以还原完整行为。

还要检查删除和替换。新版可能移除旧 Hook，却在另一事件注册新 Hook；可能保留同一 MCP 服务名，但更换启动包。比较对象应是实际执行目标与触发条件，不能只看显示名称。

固定提交能稳定包源码，维护者身份和仓库来源有助于追溯，却都不直接证明代码安全。隔离可以限制后果，也不会判断文档生成的内容是否正确。把这几项放到同一次变更审查，是为了让每个控制对应到它真正改变的条件。

采用第三方配置时，可以先从执行路径最短的包试点：材料来源明确、脚本可以审查、没有不必要的外部连接。把第一次激活与一次版本更新都走通，确认实际加载的文件、工具调用和有效权限与记录一致。之后再增加可选能力，比只凭一个包名批准其未来所有版本更容易复核。

面对新版本，最终需要作出的决定很具体：是否接受这份固定代码，是否启用新增行为，以及是否给它完成该行为所需的权限。配置供应链的边界，正是在这三项决定抵达运行时之后形成的。
