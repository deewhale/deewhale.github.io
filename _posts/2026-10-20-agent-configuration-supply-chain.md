Agent 可以从仓库里的指令文件获得项目约定，也可以安装 Skill、注册 Hook，或连接 MCP 服务。这些材料共同决定它知道哪些能力、何时调用程序，以及程序能够访问什么。配置因此已经成为软件交付的一部分：更新的不只是给模型看的文字，还可能是稍后执行的代码、服务和授权规则。

“Agent 配置供应链”讨论的就是这条从分发到生效的路径。审查对象既包括来源与固定版本，也包括客户端怎样加载它，以及最终执行者的权限。Agent Skills 规范、Claude Code 的 Hooks，以及 Pi 的 MCP 配置提供了三种可明确追踪的实现，能够说明为什么同一个安装包需要分层检查。

## 配置对象分别改变什么

先把包中的对象分开。指令文件告诉模型怎样理解任务、使用哪些步骤；Skill 组织一项能力的描述、说明与附属材料；脚本提供可执行程序；Hook 把宿主事件与动作关联；MCP 配置指定 Agent 可以连接或启动的工具服务。它们可能在同一个发行包里，却不由同一机制生效。

Agent Skills 规范允许包中包含 `scripts`、`references` 与 `assets`。这解释了为什么只检查主体说明不够：一个简短的说明文件可能指向更多材料，其中既有供模型阅读的文本，也有由工具执行的程序。

读取通常也有阶段。客户端可以先用名称和描述发现 Skill，在激活后读取主体说明，额外资料按需取得。这个过程有助于减少无关内容进入上下文，但它不是安全审查流程。某份文件暂时没有被读入模型，不表示附属程序已经经过检查。

Agent Skills 规范给出的文件引用示例很小：`SKILL.md` 指向 `references/REFERENCE.md`，并要求运行 `scripts/extract.py`。这两个相对路径都从 Skill 根目录解释，但用途不同：前者供读取，后者等待执行工具启动。更新审查也沿这两个入口继续读文件；正文未改而提取脚本改了，仍然改变实际程序。

| 包内对象 | 它改变的部分 | 需要进一步核对 |
|---|---|---|
| 指令 | 模型得到的任务说明和行为建议 | 加载顺序、作用范围及冲突处理 |
| Skill 描述与主体 | 能力发现及激活后的材料 | 客户端实现、附属文件与脚本 |
| 脚本 | 实际程序行为 | 参数、读取范围、写入位置与网络 |
| Hook | 某个宿主事件触发的动作 | 注册位置、触发条件与移除条件 |
| MCP 启动项 | 工具服务及其依赖 | 来源、版本、启动方式和继承权限 |

审查这些项目时，需要使用目标客户端的文件名与加载规则。一个客户端承认的 Hook 配置，换到另一个客户端可能不会加载；一个客户端的权限规则，也不能直接按名字迁移。



## 三条加载与执行路径
在 Agent Skills 的分阶段读取路径中，脚本文件与指令一起分发，但发现、阅读和执行发生在不同阶段：一份脚本可以已经安装，却还没有运行；模型读到“运行脚本”的要求以后，还要通过实际执行工具才能产生效果。

Claude Code 的 Hook 使用宿主事件触发。官方样例在 `PostToolUse` 下配置 `matcher: "Write|Edit"`，处理器调用项目 `.claude/hooks/check-style.sh`。执行一次文件写入或编辑后，由宿主匹配事件并运行脚本，模型无需再提出“检查样式”的调用。审查这一配置时，要同时看注册事件、匹配器和脚本内容；将同一脚本从手动步骤移到 Hook，改变的是触发时机和频率。Skill 或子 Agent 内声明的 Hook 还随相应生命周期注册和移除。

MCP 又将能力放进服务进程。客户端按配置启动或连接服务，完成初始化和工具发现，之后工具请求才进入服务实现。stdio 服务可能继承启动者的文件权限与环境；远程服务则用其自身身份和凭据访问资源。两者的审查重点分别落在启动代码和远端访问链上。

如果启动配置指向会继续变化的包版本，那么外层配置没有修改，也可能在后续启动时得到不同程序。固定 Skill 的提交并没有同时固定它间接引用的 MCP 包和脚本依赖，审查需要继续追到这些执行对象。

图中的来源、加载与执行构成一条依赖链。固定版本让被审查内容可重现，加载语义说明它何时生效，授权与隔离约束实际访问范围；这几种控制分别作用于不同位置。

## 指令、工具呈现与执行权限怎样配合

Skill 可以写“只读取当前项目”，但这段要求首先是模型接收到的行为指引。执行工具是否只能读取当前项目，需要看操作系统隔离、工具实现和有效授权。若启动程序继承了更广的文件权限，文字要求并没有改变这些权限。

开放 Skill 规范中的 `allowed-tools` 目前仍是实验字段，支持情况取决于实现。不能把它作为跨客户端统一强制的授权机制，也不应反向断言所有客户端都会忽略它。审查时需要针对目标客户端确认它是否识别、怎样解释及与其他规则怎样组合。

Pi 的内置 MCP 可以说明配置选择与运行授权的区别。以 v1.4.0 为例，客户端先读取用户级服务配置，获得项目信任后再读取项目配置。项目条目给出同名服务的完整定义时，会替换用户级定义。项目条目未给出启动命令、地址或类型时，只覆盖是否启用、工具暴露方式及逐工具规则；启动参数和凭据仍取自用户配置。逐工具规则表会被整体替换，审查新增一条规则时也要查看哪些旧规则随之消失。

下面按 Pi 的真实配置格式推演一次覆盖，只保留与合并有关的字段。服务名和工具名是说明用名称，`catalog-server` 代表用户已配置的程序。

```jsonc
// 用户级 mcp.json
{"mcpServers":{"catalog":{"command":"catalog-server","exposure":"deferred",
  "toolExposure":{"read_item":"direct","delete_item":"hidden"}}}}

// 受信任项目的 .pi/mcp.json
{"mcpServers":{"catalog":{"toolExposure":{"read_item":"direct"}}}}
```

项目条目没有 `command`、`url`、`type`，所以解析器将它作为覆盖项，保留用户级启动程序和 `deferred` 默认暴露方式。合并使用对象的浅覆盖：项目的整个 `toolExposure` 取代用户级规则表。于是 `read_item` 仍为 direct，`delete_item` 已没有专门的 hidden 规则，按服务的默认值变为 deferred。只检查新增的读取规则，会漏掉这一项能力变化。

若项目只是要改变读取入口，同时保留删除工具隐藏，就需要在自己的规则表中也保留 `delete_item: "hidden"`。如果项目改为给出完整启动定义，则进入服务整体替换路径，应把命令、参数和连接身份作为新定义检查。这两种修改需要不同的审查材料。

暴露方式决定工具从哪个入口到达模型：直接声明、经搜索加载、供脚本调用，或在该客户端中隐藏。Pi 的项目信任控制配置加载，工具调用仍使用进程和服务的有效权限。审查时因此要分别确认加载了哪份配置、当前允许哪些工具入口，以及服务凭据和运行环境实际准许什么。隐藏一个工具不会撤销同一凭据在其他客户端的访问能力。

命令匹配也有自己的粒度。Claude Code 文档区分命令规则和沙箱：前者围绕调用文本匹配允许、拒绝或询问，文件系统与网络的强制边界需要相应隔离机制。拒绝某个命令拼写，并不等于从系统层撤销相关资源的全部访问路径。

这也给出了审查顺序：先还原客户端真正加载的定义，再检查工具可达性，最后核对进程、服务账号和资源权限。模型指令、工具隐藏和系统隔离可以共同使用，但各自应有明确的检查对象。

## 以实际加载结果比较一次更新
以 Pi 的 `mcp.json` 更新为例，审查首先要还原用户级配置和受信任项目配置合成后的服务定义。同一个显示名称可能代表完整替换，也可能只是局部覆盖；只看项目文件的一行变化，可能漏掉继承的启动命令、环境变量和凭据。

随后按真实执行链比较：服务来源是否改变，命令及依赖是否固定，远端目标是否变化，哪些工具从隐藏变为可达，逐工具规则整体替换后是否丢失旧限制。最后再检查新增或修改工具实际能调用的资源。工具名称不变，服务实现和凭据范围仍然可能改变。

对 Skill，比较对象则是固定版本的完整目录及其依赖。正文没有变化而 `scripts` 有修改，仍属于执行代码更新；只改名称和描述也可能改变发现与激活的机会。对 Hook，要比较事件和处理器；移动注册位置可能改变作用范围，即使命令文本没有变化。

这一比较方法参照的对象是公开规范与具体客户端配置，不是一份跨平台通用安装格式。最终审查记录应能回答三项决定：接受哪份代码，启用哪条触发路径，授予哪个执行者哪些资源。新增联网或脚本不自动意味着恶意，但需要能够说明它怎样服务于实际用途。

## 扫描研究能提供什么证据

2026 年 9 月修订至 v3 的研究《Scanning the Harness: Configuration Exposures in AI Coding-Agent Supply Chains》，将指令、Skills、Commands、Hooks、子 Agent 与 MCP 配置一起作为分析对象。这个视角有助于把通常分散的文件纳入同一来源和更新链路。

研究样本包含 3,171 个公开仓库，区分 2,660 个使用配置的 setup 与 511 个分发集合。作者在 setup 中识别出 409 个、约 15.4%，含其定义的三类版本或宽执行预批准声明之一。分母、分类和样本来源决定了这个数字能说明什么。

它描述的是所选公开样本中的配置暴露，不是整个生态的恶意率，也不是发生攻击的比例。一个宽泛声明是否转成有效权限，还要看客户端怎样解释、用户是否启用、执行环境能访问什么资源。扫描器能把复核工作集中到相关位置，不能仅凭命中给一个包定性。

尤其要区分三个证据层次。文件中写了一个匹配规则，是声明证据；对应客户端把它解释成什么授权，是实现证据；某个调用在实际环境里成功执行，是运行证据。把第一层直接写成第三层，会使风险结论超过测量覆盖。

研究 v3 曾修正对 `find` 通配授权的判断：客户端会对 `-exec`、`-delete` 等危险动作另作处理，不能将一个宽泛命令匹配直接展开为这些动作已获准。两个扫描器可以给出相同标签，却共同遗漏客户端的后续检查。复核因此要沿调用继续检查，而非停在配置字符串。



## 把审查接入安装、更新与撤除
第一次接受某个配置时，保留来源、精确版本、实际加载位置和有效权限，才有下一次更新的基线。自动更新缩短了新内容到执行之间的时间，团队可以依能力变化选择不同复核强度：说明修订关注模型行为，脚本改动关注实现，新 Hook 与 MCP 服务则要重新追踪触发和访问路径。

安装、更新和撤除也应按同一粒度处理。移除一个 Skill 不必然撤销独立注册的服务；隐藏一个工具不撤销服务令牌；固定仓库提交不阻止间接依赖解析变化。撤除能力时要找到它真正生效的位置。

这套审查适合接入现有代码审查流程：一次变更同时呈现配置、可执行依赖和权限差异，由能够理解目标客户端的人复核。扫描可以缩小范围，固定版本可以稳定对象，隔离可以限制后果，具体用途与行为是否相称仍需要作出技术判断。
