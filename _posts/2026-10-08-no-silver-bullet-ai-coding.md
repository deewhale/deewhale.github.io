三组数字摆在一起，很难讲成一个简单的“AI 提效”故事。

| 研究观察到的结果 | 测量对象 |
|---|---|
| 完成标准化 JavaScript HTTP 服务快 55.8% | 95 名开发者、边界清楚的单一任务 |
| 完成熟悉仓库中的真实维护任务慢 19% | 16 名资深开源维护者、246 个任务 |
| commit 活动的增幅远高于项目和 release | 超过 50 万名开发者的观察性数据 |

第一个数字说明，意图清楚、反馈快速时，候选实现可以便宜很多。第二个数字提醒我们，熟悉成熟系统的人原本就很快，核查建议和处理隐含约束会吃掉收益。第三个数字则把观察点移到交付链：代码写出来之后，还有评审、集成、发布和运营。

我的判断是，AI 编程最重要的变化并非简单消灭某一类困难，而是把一部分本质工作从“亲手构造”改成“生成候选、作出选择并完成验证”。构造成本下降了，选择权和结果责任仍要有人持有。这正是 Fred Brooks 在《没有银弹》中留下的框架今天仍有解释力的原因。

## Brooks 的原意和边界

Brooks 所说的本质困难，是构造软件的概念结构：数据及其关系、功能与算法、边界条件，以及它们怎样组成一个自洽系统。规格、设计和测试困难，源头都在这里。

附生困难来自表达和实现这套结构所用的媒介。汇编、批处理周转、内存紧张和贫乏的工具曾经吞掉大量工程时间。高级语言、分时系统和集成环境逐步削减了这些成本。这里的“附生”表示它依附于实现媒介，并不表示工作量很小或可以忽略。

“没有银弹”也有明确范围：Brooks 讨论的是未来十年里，任何单项技术或管理方法能否独自带来数量级改善。他没有否定局部任务出现十倍提速，也没有排除多种改进长期累积出巨大的生产率变化。1995 年的回顾还进一步说明，本质困难能够缓解；工具进步只是不会自动替团队完成概念工作。

绘画的类比依然直观。更好的笔刷、透视辅助、素材库和撤销功能降低落笔摩擦；画面表达什么、元素为何在这里、观众应该感受到什么，仍需在作品层面决定。生成式 AI 又往前走了一步：它能给出构图草案、比较风格、快速生成原型，已经参与“画什么”的探索。它交付的是可供选择的画面。创作意图和验收标准来自作品之外。

软件也是如此。Agent 可以搜索仓库、修改多个文件、运行测试、调试失败，还能在需求讨论中提出方案。把这些工作统统归进附生劳动，会低估它已经触及概念设计的程度。更准确的描述是：AI 扩大了探索空间，并压低了产生一个可检验方案的成本。

假设任务写成“把订单时间统一为 UTC”。Agent 可以很快找到日期字段、生成迁移、修改序列化代码并补齐单元测试。真正改变系统含义的选择仍在任务之外：历史数据保存的是门店当地时间还是服务器时间？夏令时重叠的一小时怎样解释？已经把旧字段缓存下来的消费者何时切换？回填失败后以哪份记录为准？AI 可以搜索调用方、列出方案和构造反例，从而参与回答；最终采用哪种时间语义，却要与业务历史和迁移责任一起确定。编译通过只覆盖表达工作的末端。

## 本质工作转向选择和验证

候选变多之后，复杂性首先出现在选择上。一个实现与数据模型、权限边界、部署拓扑和历史兼容承诺之间会发生什么，仍需要被理解。过去团队可能因为写代码昂贵而克制功能和抽象；现在生成十个变体很轻松，审查十个变体与系统其他部分的关系依旧昂贵。

迁就性来自软件必须服从的外部世界：税制、组织权限、客户流程、旧接口、数据约定和监管规则。模型能处理写进上下文的规则，隐含约束则要先被组织发现和表达。这里的 conformity 更接近“迁就现实”，不是代码风格的一致。

变化最大的是可变性。实现成本降低后，“顺手再加一个”的提议更容易进入开发队列；低成本原型也会带来更多真实反馈。两者都有价值，却会共同提高变更吞吐。需求澄清、架构治理和发布能力若保持原速，团队看到的结果通常是更多在制品，而非同比例增加的用户价值。

不可见性也换了位置。Agent 可以为一次任务建立局部代码地图，却很难自动把它变成团队共享的系统模型。代码已经提交、测试已经通过，仍可能没人能解释控制流跨过了哪些边界、异常时应该看哪里、下一次修改应该落在哪一层。

我不认同“AI 代码天然会制造技术债”这种概括。2026 年发表的一项预注册维护性实验，让开发者继续演化 AI 协作或纯人工产生的 Java Web 应用；在任务耗时、代码健康度和测试覆盖等指标上，研究没有得到清晰、稳定的优劣差异。更可靠的风险判断是：当生成规模持续超过规格、审查和验证能力时，未理解的变更会累积。问题在容量失衡，而非代码带着某种神秘的 AI 污染。

## 生产率数字的测量位置

55.8% 来自标准化的绿地任务。三家公司的随机试验覆盖 4,867 名开发者，在考虑实际采用后，估计助手让每周完成任务数提高约 26%。这些结果支持 AI 在清楚任务和真实企业环境中都可能产生收益，但“完成任务”仍位于软件交付链的中段。

METR 在 2025 年初测的是另一种工作：资深维护者在自己长期熟悉的成熟仓库里解决真实问题。当时的工具让他们平均慢 19%，参与者事后却仍主观认为自己变快。METR 后来公布的晚 2025 年数据出现了加速信号，不过样本选择和多 Agent 并行计时已经使实验难以可靠估计当前幅度。这组结果的价值不在于宣布一个永久的负数，而在于显示仓库熟悉度、隐含约束和核查成本足以改变答案。

超过 50 万名开发者的 NBER 观察性研究又换了尺度：AI 对 commit 活动的影响显著高于项目和 release。它无法给某个团队提供因果 ROI，release 也不等于用户价值，但它指出了测量位置的重要性。

| 测量位置 | 能看见什么 | 仍需另算什么 |
|---|---|---|
| 候选实现 | 首稿、样板、迁移和局部修改速度 | 需求与方案是否适合系统 |
| 工程变更 | 任务、PR、commit 和测试通过 | 评审返工、集成冲突、认知负担 |
| 软件交付 | 前置时间、部署频率 | 故障、回滚、恢复和运维成本 |
| 产品结果 | 用户任务成功、采用或收入变化 | 机会成本、长期约束和错误方向 |

因此，我会把代码行数、生成 token 和建议接受率当作过程诊断，而不会把它们当作生产率目标。越接近最终结果，指标越慢、噪声越大，也越接近团队真正承担的后果。

## 两条坐标决定自动化程度

判断一项工作适合怎样使用 AI，我更看重两个变量：成功条件是否明确，错误能否被便宜地发现。

| 任务状态 | 验证便宜 | 验证昂贵 |
|---|---|---|
| 目标清楚 | 高度自动化；Agent 自跑检查，人抽查结果 | 生成候选，人主导审查；限制改动范围并先写关键不变量 |
| 目标模糊 | 制作可丢弃原型，让用户比较行为 | 人主导问题定义；AI 用于列备选、反例和未知项 |

左上象限未必技术简单。一次跨仓库 API 迁移可能涉及很多文件，只要旧接口、新接口和回归检查明确，自动化程度仍可以很高。右下象限的错误只能在真实资金、法规、用户或长期运行中暴露，把整项实施交给 Agent 会同时放大方向错误和验证债务。

AI 也能帮助任务移动象限。原型让模糊需求接受具体反馈；模拟环境、历史回放和属性测试则降低错误发现成本。这与 Brooks 提出的快速原型和有机生长相通：先让概念结构接受反馈，再扩大实现。

## 概念负责人

如果只能保留一道人工门禁，我会把它放在“谁拥有这个变更的概念结构”上。每项进入主干或生产的变更都需要一名概念负责人。这个人可以不手写每行代码，但要能回答五个问题：

概念负责人承担解释权，也承担停止权。需求仍在摇摆、关键约束没有来源、验证成本超过当前预算时，他应把任务退回探索阶段。模型、提示词和执行 Agent 可以随工具升级而替换，这个责任接口要一直存在；否则团队拥有的是一批代码产物，而非一项可以继续维护的系统能力。

1. 用户最终获得了什么行为？
2. 哪些不变量必须保持？
3. 最可能的失败方式是什么？
4. 团队怎样观察和撤回它？
5. 下一次需求变化应该修改哪一层？

回答不出这些问题，任务仍停在“候选实现”阶段。回答得出，AI 写了多少代码反而只是实现细节。
