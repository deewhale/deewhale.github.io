假设一个 Coding Agent 正在改造支付回调。支付回调是支付平台在交易状态变化后发给业务系统的通知；这里的 Coding Agent，是能够读取代码库、调用工具并修改代码的模型驱动执行者。代码库已经出现改动，进度记录写着“实现完成”，结构化账本却仍把任务标为 `running`。它还调用过支付平台的管理接口，但响应没有来得及保存。进程就在此时消失。

新实例面对的不是“从哪一行继续写”，而是几种互不相让的记录。相信进度文字，可能漏掉没有落盘的代码；只看账本，可能重复已经发生的动作；只看仓库，又无法知道支付平台是否接受了注册请求。它们记录的是不同种类的事实，不能靠多数票选出真相。

某一轮交给模型的有限输入称为 context，其中可以包含指令、代码、工具返回和历史摘要。context 能帮助当前一轮推理，却不是耐久状态。把旧对话全部塞给新模型，也只能告诉它“记录声称发生过什么”，不能证明代码已经持久化、命令执行到底，或者外部系统完成了业务动作。

因此，长运行不是一个小时数。只要任务会跨过不能依赖模型内部记忆的边界——进程崩溃、context 更换、执行环境重建或人工暂停——它就需要可交接的协议。负责装配 context、路由工具、记录事件并推进持久状态的模型外控制层，本文称为 Harness。它不替 Agent 写代码；它负责让新执行者知道从哪里恢复、什么可以相信，以及凭什么宣布完成。

支付回调事故会沿一条控制循环处理：先分清各类状态的权威范围，再对中断现场做对账；实现形成固定候选后，由与候选绑定的证据决定能否晋升；外部结果未知时先查询而不是盲目重放。可恢复性来自权威分离，完成性来自证据绑定。

## 中断后，先承认五种不同的事实

先把工作收窄成一个 work item，也就是能够独立领取、实现和验收的最小工作单元。这个 work item 要验证支付回调签名、避免重复通知造成重复入账，并保持原有支付路径不回退。它需要五类状态，每一类只回答自己的问题。

| 状态 | 有权回答什么 | 不能证明什么 |
|---|---|---|
| task spec | 要完成什么、按哪个版本验收 | 目标已经实现 |
| work ledger | work item 处于待办、运行、待验证、通过还是失败 | 代码和外部环境符合记录 |
| artifact | 当前实现具体是什么，通常是可定位的代码版本或构建产物 | 实现满足需求，或外部调用成功 |
| evidence | 某个 revision 按某版规格通过了哪些检查 | 能替另一个版本作证，或修改验收目标 |
| ephemeral state | 当前进程、context、临时文件和工具会话正在发生什么 | 中断后的唯一事实来源 |

task spec 是版本化的任务规格。假设当前为 `spec_version=3`，它同时写明目标、非目标和验收约束。需求改变时应产生版本 4，不能让执行者放宽测试后继续沿用版本 3 的“通过”。work ledger 是结构化生命周期账本，不是长篇工作日记。它即使写着 `passed`，只要找不到对应实现和证据，状态也必须降级。

artifact 是实现产物，revision 是可定位的产物版本，checkpoint 是可以返回的落点。Git 能保存代码差异和历史，却不知道支付平台是否注册了新回调，也不能证明需求已满足。evidence 是可重跑的验证证据，必须说明自己检查了哪个 work item、哪版 task spec、哪个 revision，以及依赖什么环境前提。`passes=true`、一张截图或一段测试摘要都缺少完整的证明对象。

ephemeral state 则是临时现场：模型此刻记得什么、未提交工作区有什么、子进程是否仍活着。它能帮助执行，却不能承担跨中断交接。开头那句“实现完成”也属于线索，不能单独把账本从 `running` 推到 `passed`。

这不是五份记录的可信度排名，而是字段所有权。规格定义验收目标，仓库固定实现，账本记录生命周期，证据说明某个版本通过了什么，临时现场只属于当前运行。小团队可以把它们存进同一个数据库或目录，但语义不能合并。否则，Agent 修改一份 Markdown，就可能同时改需求、宣布实现完成，再给自己补一条通过记录。

以支付回调为例：若账本显示通过，但代码已经从被验证的 revision 继续变化，旧证据仍是有效历史，当前 work item 却应回到待验证；若规格升到版本 4，版本 3 的代码和证据也不能继承为新目标下的完成证明。冲突处理不是挑一份“最像真相”的记录，而是把结论降到仍能证明的层级。

## 接管不从“继续工作”开始

中断现场里，ledger 仍是 `running`，仓库却多出一个 revision，最近的 evidence 指向更早的代码，支付平台注册调用只留下“请求已发出”。恢复完整对话不会消除这些矛盾。新实例的第一项工作应该是对账，而不是编码。

本文建议为每次任务领取分配 `run_id`，关联该轮账本更新、revision、证据和外部动作；再给领取设置有期限的占用权，也就是 lease。lease 防止消失的实例永久占住 work item，但过期只表示现在可以核查和回收，不表示旧动作没有发生，也不保证重跑安全。`run_id` 和 lease 是本文的协议设计，不是某个开发工具已经提供的固定字段。

Harness 先只读取得当前 spec version、ledger、revision、最近 evidence 和必要的持久事件，然后执行 reconciliation，也就是找出多种存储之间的部分更新，恢复引用关系，并把不能证明的状态降级。支付回调事故中的检查顺序很具体：旧 lease 是否过期；新 revision 是否属于旧 `run_id`；证据是否绑定同一 revision 和 spec version；工作区是否仍有未提交改动；支付平台注册是否处于结果未知。

如果代码已经落盘而证据缺失，任务进入待验证，不必重新开发。证据指向旧 revision 时，它保留为历史，却不能抬高当前状态。`running` 找不到任何持久产物时，可以回收到待处理，但要记录原因，不能假装旧执行从未存在。未提交工作区若能与旧 `run_id`、工具事件和目标文件对应，可以先保存为隔离 checkpoint；来源不明或混入多个 work item 时，不能直接并入新候选，也不应默认删除。

对账得到可解释的 revision 后，再运行 baseline：在继续改动前，对已知能力做一次短而稳定的重验。这个案例可以检查项目能否启动、原有签名校验是否工作、无效签名是否仍被拒绝。baseline 没有通用清单；它只需覆盖这次改动最可能破坏的旧能力。若此时已经失败，Harness 应记录既有故障，而不是让新的 work item 背负来源不明的红灯。

只有现场完成降级并留下 baseline 结果，Harness 才分配新的 `run_id` 和 lease。交给 Agent 的 context 不需要倾倒全部历史，只需包含当前规格、相关代码、失败证据、环境约束和停止条件。lease 仍需底层存储用条件更新处理续租和并发抢占；它并不提供 exactly-once，也就是不能保证每个动作恰好执行一次。

到这里，系统只取得了一个可解释的恢复点。支付回调代码是否完成、平台注册是否成功，仍然都没有得到证明。

## 完成只能授予一个固定候选

Agent 在新 lease 内补全幂等处理，让同一回调重复到达时只产生一次业务效果，并跑完类型检查和单元测试。即使它再次写下“完成”，ledger 也不能直接进入 `passed`。实现者能报告做过什么，完成证明必须回答最终留下了什么结果。

实现开始前，应冻结与当前 spec version 对应的 validation contract，也就是完成条件和允许的验证方式。本文为支付回调设定四个条件：合法签名只处理一次；重复回调不重复入账；无效签名不改变订单；原有支付路径不回退。这些是本文的案例设计，不是任何厂商的默认测试。若条件本身需要修改，应由规格所有者生成新的 spec version，说明变化原因，再把受影响的 work item 送回验证；执行者不能为了让当前实现通过而静默放宽门槛。

实现结束后，Agent 只能提交不可变的 candidate revision，也就是等待验证的候选版本。类型检查、单元测试和局部集成测试是候选的随附材料，不是晋升决定。候选送验后若代码或测试变化，就必须生成新的 revision，否则验证对象会在检查过程中漂移。

这里还要区分 transcript 和 outcome。transcript 是运行过程的交互记录，说明 Agent 调过什么工具、看到什么输出；outcome 是运行结束后环境里真正留下的结果。对支付回调来说，“测试命令返回成功”是 transcript 中的事件；数据库只产生一笔入账、无效签名没有写入，才是要检查的 outcome。

检查 outcome 的规则或执行角色可称为 grader；由独立角色承担时，本文称为 Evaluator。它不一定是另一个模型，也不会因为独立就天然正确。可以编码的条件优先使用确定性断言，例如状态转换次数、唯一键和响应码；端到端测试从真实入口穿过处理逻辑和持久化边界；难以编码的质量条件，才交给用人工样本校准过的模型评分规则。这个验证顺序是本文的协议设计。

Anthropic 公开的长运行编码实验观察过“一次做得过多”和“过早宣告完成”，并曾用功能清单、进度文件和代码版本帮助后续运行接手。另一项全栈应用实验让 Evaluator 检查界面、应用程序接口和数据库，也出现过发现问题却仍宽松放行的情况。这些是公开实验观察，能支持“交班工件有用、独立验收仍需校准”，却没有直接给出本文的 `run_id`、lease、状态机或支付回调协议。

本案例的一份 evidence 至少要能回答下面这些问题；字段只是概念示例，不是厂商配置语法。

```text
work_item_id: payment-callback-idempotency
spec_version: 3
revision: candidate-7
run_id: run-18
environment_assumptions: test database schema 12, payment stub profile 4
checks: signature, duplicate delivery, database write count, regression path
result: pass or fail, with rerunnable artifacts
```

环境前提不能只写“测试环境”。数据库 schema、依赖版本、功能开关、测试数据种子和外部替身配置，都可能让同一 revision 得出不同 outcome。凡是会改变结论的条件，都应进入 evidence 或指向可重建配方。证据的价值不是日志越多越好，而是下一轮能重构同一个问题，并判断差异来自代码、规格还是环境。

最小状态路径是：

```text
pending → running → needs_verification → passed
```

硬条件失败时，`needs_verification` 转为 `failed`；spec version、revision 或关键环境前提改变时，原有 `passed` 退回 `needs_verification`。禁止从 `running` 直接进入 `passed`。只有同一规格、同一候选和覆盖 outcome 的证据仍然对应，candidate 才能晋升为 verified revision，ledger 随后标记通过。

反过来看，如果 Agent 声称完成，测试摘要也显示通过，candidate revision 却没有持久化，账本就不能前进。没有可找回的被验对象，证据无法复验，也无法在下次中断后恢复。它最多证明某个已经消失的工作目录曾出现过绿色结果。

## 未知的外部结果不能靠重试消掉

代码侧恢复为 verified revision 后，接下来处理的仍是开头那次没有保存响应的平台注册请求，并不是再发起一次注册。崩溃前 Harness 已经发出请求，持久事件却只有“开始调用”；外部平台是否新增订阅仍然未知。此时直接标记成功会掩盖漏注册，原样重跑又可能创建第二个订阅。

仓库、事件记录和外部服务通常不共享一个事务，所以 `unknown` 是必须保留的业务状态。恢复后的第一个动作是查询 outcome，而不是重放命令。系统可以用商户、回调用途和 spec version 组成稳定业务键，再查询外部对象是否已存在并指向预期配置。这个键的组成只是本文示例，实际设计必须服从外部服务的唯一性语义。

若对象已经存在且内容一致，查询结果可以补记为 evidence；若明确不存在，并且服务支持幂等键，才使用原键重试。若出现重复或半成品，而服务提供可验证的撤销动作，则执行 compensation，也就是用另一个可观察动作补救此前结果，再次查询终态。有些服务既不能按业务键查询，也不保证幂等，更没有可靠补偿接口，这时只能保留 `unknown/manual_review`，暂停自动推进，由人工查账或业务负责人裁决。

补偿不是数据库回滚。撤销订阅本身可能失败，退款可能产生新的账务事件，删除工单也可能破坏审计链。每个补偿都应拥有自己的业务键、结果查询和失败状态。若业务不允许自动撤销，应提前把人工审批写进状态机，而不是等异常出现后让 Agent 自行判断风险。

“先查询 outcome，再选择幂等重试、补偿或人工处理”是本文针对失败窗口给出的工程建议。Harness 不能赋予外部接口原本没有的幂等性，也不能用自己的日志证明对方已经落账。它能做的是拒绝把未知压成成功或失败。

## Harness 控制推进，但不拥有所有真相

支付回调事故现在已有两类恢复对象：仓库中的代码 revision，以及支付平台中的订阅 outcome。如果控制逻辑、工具环境和事件记录又全部困在同一进程，中断后仍然无法判断丢失了哪一部分。需要分开的不是产品菜单，而是可以独立失效、重建和核验的职责。

Anthropic 的 Managed Agents 参考架构给出过一种职责形状：Session、Harness、Sandbox 和 Model 分开。下面沿用这些名字解释边界，但不把它们当成唯一部署方案。

大写的 Session 是 Harness 外部的追加式事件记录。Harness 从中读取必要事件，调用模型和工具，再把新事件写回。Session 可以保存“支付平台注册请求已发出”，却不拥有 task spec、代码内容或外部业务结果；事件可读取也不表示模型或外部系统能够确定性重放。

Harness 是控制循环。它读取规格、ledger、revision、evidence 与必要事件，决定何时对账、领取、验证、降级或暂停。它不替 Model 生成代码，也不替支付平台确认订阅。Harness 自身崩溃时，新实例从持久记录重建控制位置，再次核对引用关系。

Sandbox 是命令和工具的执行环境。它接收指定 revision 与环境配方，产出编译、测试和工具调用结果。Sandbox 可以按标准配方重建，但未持久化文件、内存状态和进程内响应默认已经丢失；环境重建成功也不能代替 baseline 或外部 outcome 查询。

Model 在给定 context 内推理、生成修改和选择工具动作。它不拥有耐久历史，也无权批准自己的完成状态。于是故障后的事实位置可以明确回答：规格与生命周期在持久任务状态，代码在 revision，验证结论在与版本绑定的 evidence，工具现场在 Sandbox，事件轨迹在 Session，支付平台注册结果仍以支付平台查询到的 outcome 为准。

这组分工直接决定恢复方式。Session 丢失会削弱过程解释，但只要 ledger、revision 与 evidence 尚在，仍可能从可验证落点继续；Sandbox 丢失就按配方重建并重验；Harness 丢失则由新实例重新对账；Model 更换时重新装配 context。反之，如果规格、candidate 或外部业务键只存在临时进程，再完整的事件回放也救不回来。

凭证也应遵循相同边界。Git 凭证可在 Sandbox 初始化时绑定到仓库；支付平台令牌可放在专门的凭证存储，由代理按本轮授权代为调用，使 Agent 和生成代码不直接持有原始 token。代理仍要检查目标服务、动作范围和调用主体，并采用最小权限。这只能缩小凭证暴露面，不能消除提示注入、越权工具调用或原本过宽的授权。

## 稳定协议，不固化临时脚手架

支付回调能够跨中断恢复，依赖的是几个不变量：目标有版本；work item 有生命周期；领取可以回收；实现先成为 candidate；evidence 绑定 spec version 与 revision；外部结果允许未知；每次接管先 reconciliation。至于 context 怎样装配、是否设置负责拆分工作范围与依赖的 Planner、是否保留独立 Evaluator、是否并行执行，都是可替换策略。

context reset 是结束旧 context，再用持久状态重新装配输入；compaction 是压缩既有历史，以摘要维持当前会话。两者改变的是 context 行为，不解决状态一致性。Anthropic 在应用开发 Harness 的实验演进中，曾从 reset 转向自动 compaction，后来又取消固定实现阶段，并把 Evaluator 调整到完整应用构建完成之后。这些变化只能说明模型行为改变后旧脚手架需要重验，不能推出 compaction 永远优于 reset，也不能推出 Evaluator 已经无用。

是否保留一种机制，应从可复现失败决定。如果连续 context 反复导致过早收口、忽略新证据或偏离目标，就在同一任务集和当前模型上比较 reset 与 compaction，并观察成功率、返工、墙钟时间、人工介入和 token 成本。范围经常缩水或依赖遗漏时，Planner 才值得保留。实现者反复放宽标准、遗漏 outcome，而且校准后的复核收益高于成本时，独立 Evaluator 才有价值。不能删除的是模型外验收；可以删除的是“必须再放一个模型验收”的组织形式。

并行 Agent 的门槛更高。工作必须能够拆分，每部分拥有隔离产物和验收边界，合并冲突可检测，共享瓶颈又不会让多个实例重复撞向同一故障，并行才可能有净收益。否则，它只会增加 lease 竞争、context 分叉和 reconciliation 成本。角色数量与并行度都不是成熟度指标。

整项支付回调改造的完成证明，比单个 work item 更严格：所有必要 work item 都在当前 spec version 下通过；每项能定位到 verified revision 和可重跑 evidence；ledger 中没有遗留 `running`、过期 lease、悬空 candidate 或未知外部结果；组合后的系统还要做一次整体验收。签名验证、幂等写入和回调注册可以分别通过，组合后仍可能因路由配置、数据库约束或部署顺序失败。最终 evidence 必须绑定组合 revision 与部署前提，不能只是汇总三张绿色卡片。

若整体验收失败，局部证据仍可保留，但整体状态必须停在未完成。这种“晋升”只是协议语义，并不暗示 ledger、Git、Session 和支付平台完成了一次原子提交。

这套协议也有成本。任务很短、失败后可以廉价重跑、没有不可逆副作用，而且人工能快速核对 outcome 时，一个受约束的 Agent 加简单脚本通常足够。任务一旦跨 context、进程或执行环境，需要多轮接管，或者会产生不能盲目重试的外部副作用，分离状态权威与 candidate、verified 的区别才开始抵消记录和校准成本。

回到最初的中断现场，新实例不需要猜旧 Agent 的真实意图。它回收过期 lease，核对 revision 与 evidence，查询支付平台的订阅 outcome，按同一 validation contract 重验，并把所有无法证明的结论降级。可靠性不要求 Agent 永不中断，也不要求 context 永不丢失；它要求中断之后，未经证明的状态不能继续前进。
