Agent 连续工作几天，听起来像是一次思考被拉得很长。真实情况恰好相反：它往往由许多次短执行拼起来。真正困难的不是让某个模型永不停止，而是它停下来之后，下一次执行还能不能接得上。

这使长运行 Agent 更像一支换班的工程团队。交班材料含糊，接班人就会重复调查、误判进度，甚至把半成品当成完成品。上下文窗口再大，也只是推迟交班，并没有消灭交班。

## 长运行，先解决“换班”

Anthropic 在 2025 年的[长运行 Agent 实验](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)里观察到两个很具体的失败：Agent 喜欢一次做太多，做到上下文耗尽时留下一个无法解释的半成品；后续会话看到项目已经有些内容，又容易过早宣布完成。自动压缩上下文能延长单次会话，却不能保证压缩后的信息足以让下一次执行准确接手。

他们采用的办法并不神秘。第一次运行由 initializer 把需求展开成结构化 feature list，所有功能先标为失败；之后每次只处理一个功能，结束前提交 Git，并把进展写入文件。下一次执行先读功能清单、进度记录和提交历史，再继续工作。

这里最有价值的不是 JSON、Git 或某一种 Agent SDK，而是状态归属发生了变化：**项目状态不再寄存在模型的“脑子”里，而是落在模型之外、下一位执行者也能读取和验证的工件中。**

一份最小的交班材料，大致只需要这些东西：

```text
goal.md          目标、边界与非目标
features.json    可逐项验收的功能清单
progress.md      已完成、正在做、下一步、已知问题
git history      可恢复的工作状态与变更原因
test results     环境是否真的达到预期
```

“记住更多”不是第一目标。减少下一次执行必须猜测的东西，才是。

## 不要相信 Agent 说“做完了”

长任务的另一个坑，是把进度理解成一段自然语言总结。模型写下“功能已经完成”，只说明它生成了这句话。

Anthropic 在[Agent 评测方法](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)中专门区分了 transcript 和 outcome：前者是模型说过什么、调用过什么工具；后者是环境最终变成了什么。订票 Agent 的最后一句可以是“预订成功”，真正的 outcome 却是数据库里是否存在那张订单。

放到 Coding Agent 上，单元测试通过也未必够。页面能否打开、按钮能否完成真实流程、数据是否正确落库，都需要从系统外部验证。Anthropic 后来的[三角色 Harness 实验](https://www.anthropic.com/engineering/harness-design-long-running-apps)加入 planner、generator 和 evaluator，让 evaluator 用 Playwright 操作实际页面。结果并不浪漫：未经调校的 evaluator 会发现问题，又说服自己问题不重要；它同样需要清晰的验收合同和针对性约束。

所以，多一个 Agent 并不会自动带来可靠性。可靠性来自两件更朴素的事：完成条件能被环境观察，验收者不能随意改写标准。

## 固定接口，而不是固定脚手架

Harness 很容易越做越厚。某个模型会在上下文接近上限时匆忙收尾，于是系统加入 context reset；模型升级后这个行为消失，reset 反而浪费时间。Anthropic 在 2026 年的实验里就记录了这种变化：对 Sonnet 4.5 有用的上下文重置，在 Opus 4.5 的版本中被移除，改由连续会话和自动 compaction 处理。

这件事提醒我们：Harness 本质上编码了“模型目前做不到什么”。模型变化，这些假设就会过期。

相对耐用的是接口。Anthropic 在 [Managed Agents 架构](https://www.anthropic.com/engineering/managed-agents)中把系统拆成三部分：session 是追加式事件记录，harness 负责调用模型和路由工具，sandbox 提供执行环境。三者可以分别失败、替换和扩缩容。容器挂掉时，不需要抢救那台“宠物”服务器；重新准备一个 sandbox，再把仍然存在的 session 和工作目录接上即可。

这里比“保存完整内存快照”更实用。生产系统首先需要回答的是：哪个状态必须活下来，哪个组件可以直接丢掉重建。通常任务目标、事件记录、代码、产物和验收结果必须持久；某个模型进程、某个容器、一次临时工具连接不应该成为单点依赖。

## 一套够小的长任务 Harness

如果任务确实会跨越多个上下文，我会先做四件事。

第一，把“完成”写成可执行或可观察的条件。不要只写“做一个好用的后台”，而要写用户能完成哪些路径、数据落在哪里、失败时看到什么。

第二，把工作切成能独立验收的小块。每轮只推进一个边界清楚的单元，开始前跑一遍基线测试，结束后留下可回退的提交。

第三，让进度文件只记录事实：改了什么、验证了什么、什么还失败。背景知识可以另存，但不能用长篇总结淹没下一步。

第四，把评估放到主观声明之外。能运行的测试就运行，能检查的环境状态就检查；涉及视觉或交互，就让验收工具真正走一遍用户路径。

并不是每个 Agent 都需要这套东西。十分钟能结束的任务，引入任务账本、事件日志和多角色评估只会增加摩擦。即使是长任务，也应该从单 Agent、外置工件和真实测试开始，直到证据说明某个环节需要独立 planner 或 evaluator，再增加角色。

长运行不是让 Agent 一直醒着，而是允许它随时停下、换人、换模型、换机器，工作仍然能够继续。把这一点设计好，才谈得上“跑几天”。
