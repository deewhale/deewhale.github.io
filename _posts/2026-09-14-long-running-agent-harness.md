长运行 Coding Agent 面对的是跨越多轮模型调用、多个上下文窗口，甚至执行进程重启的软件开发工作。目标不只是让模型持续写代码，还要让未完成的实现能够被接手，让后续改动保留已有功能，并让完成判断对应实际软件。

Harness 是模型周围的执行控制层：准备上下文、推进模型与工具循环、保存过程，并组织检查。它与 IDE、模型和沙箱可以分别实现。对于长任务，最重要的架构决定是把工作状态留在哪里，以及怎样让一个新的执行者理解和验证这些状态。

Anthropic 的长运行编码实验提供了两组具体材料：早期 Autonomous Coding 示例用项目文件和 Git 跨会话交班，后续应用开发实验进一步安排规划、生成与评估。两组设计的共同点是让过程形成可继续读取的工件；角色数量和上下文策略则随任务与模型变化。

## 从连续对话转向持续存在的开发工作

早期实验观察到两类失败：Agent 尝试一次实现过多功能，留下难以接续的半成品；下一轮只看到部分结果，又过早宣布整个项目完成。对话窗口里的计划不能稳定承担全部项目状态。

官方 Autonomous Coding 原型把首次初始化与后续编码分开。initializer 从 `app_spec.txt` 形成 `feature_list.json`，建立启动脚本、项目结构和 Git 基线；后续 coding session 再按功能逐项推进。外层 `agent.py` 创建新的客户端和上下文，选择对应提示，工作目录中的文件和提交则继续存在。

这里恢复的是开发工作所需材料，而不是上一轮模型内部状态。新会话读取规格、功能清单、进度和 Git，再检查项目。程序能够重新开始一段模型运行，能否正确接上已有开发仍依赖材料质量和验证。

这些工件各有任务。规格描述要做什么；功能清单将要求变成可检查项目；进度记录解释当前判断和待办；Git 保存候选代码。把它们合在一份自由改写的总结里，要求、实现与检查便容易互相覆盖。

| 官方原型中的材料 | 为下一轮保留什么 | 仍需继续检查什么 |
|---|---|---|
| `app_spec.txt` | 项目目标和范围 | 本轮工作是否仍对应要求 |
| `feature_list.json` | 功能描述、测试步骤和通过标记 | 标记是否与当前实现相符 |
| `claude-progress.txt` | 已做事项、问题和后续建议 | 这些说明是否被后续改动改变 |
| Git 提交 | 可定位和比较的代码版本 | 当前工作区与候选提交是否一致 |
| `init.sh` | 环境启动方式 | 依赖、服务和数据是否就绪 |

这些文件使交接有对象可读。它们不是天然的访问控制：提示词要求只能修改通过标记，执行器若仍能任意写文件，就需要额外程序或审查确保要求不会被悄悄缩小。

## 新会话先验证已有工作，再增加功能

官方 coding prompt 的顺序很明确：先辨认工作目录、阅读规格和进度、查看 Git，再启动服务，复验少量已经标为通过的核心功能，随后才选择一个未完成项。这个顺序把“知道上次写了什么”与“确认现在仍能工作”分开。

复验的意义是建立当前基线。代码已经提交，不代表服务能够启动；某个功能上轮通过，依赖或后续代码变化后也可能失效。若基线失败，直接增加功能会把旧故障和新改动混在一起，让后续诊断更困难。

一次编码 session 应留下可接手的候选：有明确范围的改动、相应检查、代码提交和更新过的进度。原型通过提示要求这些动作；更强的自建系统可以把“提交候选”和“标记完成”设计成独立入口，由控制层检查提交与证据是否对应。

规格、功能清单与 Git 已经提供了这种关联的基础：进度中的完成说明，可以回到对应要求、代码和检查记录核对。只有进度说“完成”，却没有对应代码或可重复检查，下一轮就应把它当作待核实说明。

工作区也应单独看待。未提交改动可能有价值，接管时先保存并检查差异，再决定是否并入候选。切换会话、摘要或 Git 分支都不自动解释这些文件属于哪项工作，来源含糊的改动需要保留并厘清。

## 把“完成”连接到可观察的软件行为

长任务还会逐渐改变完成标准。模型在实现过程中可能缩小范围，也可能把部分测试通过解释为全部成功。因此完成检查要绑定要求和候选实现，而不是仅询问执行者是否满意。

Anthropic 后续的应用开发实验增加 planner、generator 和 evaluator。planner 将工作形成规格，generator 构建应用，evaluator 用明确标准检查交付，失败再返回修复。三个角色分别负责定义目标、实现软件和检查交付。

评估标准需要能影响接受决定。界面任务不仅看服务器返回成功，还看实际页面与交互；全栈任务既检查功能路径，也检查持久数据和已有行为。模型可以辅助检查难以编码的质量，确定性的状态、计数和权限条件则适合程序断言。

评估者本身也要校准。该实验报告过 evaluator 找到问题以后仍宽松通过的情况，研究者通过分析轨迹和调整标准改善这一行为。增加一名复核 Agent 不会自动形成独立、稳定的完成判断。

对自建 harness，可把一份检查结果关联到三项对象：它依据的要求、受检代码版本、运行环境与测试配方。代码变化或标准变化后，旧结果仍可保留为历史，当前组合需要重新检查。这样，完成状态表达的是“这个版本在这些条件下满足要求”，而非永久贴在任务上的绿灯。

这种关联也帮助恢复。若代码已保存而检查结果尚未保存，下一轮可以从候选重新验证；若结果指向旧提交，就不能沿用到新提交；如果环境已经丢失，还需要依赖、启动与数据准备方式才能复跑。

## Session、Harness 与 Sandbox 分离后怎样接管

Anthropic 的 Managed Agents 架构把 session、harness 和 sandbox 分离。session 是可追加事件历史，harness 调用模型并路由工具，sandbox 运行代码和编辑文件。这个划分使模型循环与执行环境能够分别替换。

分离的原因来自故障与演进：沙箱可能损坏或需要扩缩资源，harness 可能升级，模型配置也会变化。工作记录若与它们共同困在一个临时进程里，替换其中一部分就可能丢掉全部状态。

| 需要替换的对象 | 应从外部找回什么 | 接管后先做什么 |
|---|---|---|
| 模型上下文 | 当前规格、历史、相关材料和未完成项 | 重建本轮输入，确认已有事实 |
| Harness 实例 | 事件和工作状态、产物关联 | 核对当前执行和待处理动作 |
| Sandbox | 固定代码与必要数据、环境配方 | 重建环境并复验基线 |

日志和文件要分别持久化。历史记录保存了一个产物路径，并不意味着对应文件已经存到耐久介质；事件显示启动了命令，也不表示进程仍然存在。恢复需要读取实际环境，对照内部记录。

多执行者共同领取工作时，还要明确谁能推进同一任务。领取、租期与过期写入拒绝可以在支持条件更新的存储中实现；它们解决内部所有权，无法单独阻止外部 API 的重复副作用。只有实际存在并发接管需求时，才值得承担这项协调成本。

## 外部写操作要保留独立身份与恢复路径

编码工作可能包含提交远程变更、调用部署接口或修改生产配置。此时失败后的代价已超出重跑测试。请求发出以后丢失响应，harness 不能从缺少成功事件推断外部动作未发生。

调用以前保存业务操作身份，重试时沿用目标 API 支持的幂等规则，并提供权威查询，是处理这种窗口的基本条件。若接口不能确认结果，接管者应保留未知状态并停止危险重发。具体工具设计可参照[Stripe 退款工具的授权、重试与查询](/posts/agent-tool-contract-refund/)。

操作授权也应落在执行位置。模型提出写入，可信程序核对主体、目标和范围；需要人工批准时，批准应绑定具体动作。Managed Agents 公开设计使用外部凭证存储和代理处理特定工具凭据，体现的是将原始凭证与生成代码隔离的思路。凭证管理、操作审批和结果确认分别承担不同工作。

因此，代码验收通过与整项交付完成可能是两个时刻。候选实现可以已经通过测试，某个外部动作仍待核对；任务状态应保留这种差别。把最后一句自然语言写成完成，无法补齐外部证据。

## 随模型升级检查哪些机制可以删除

持久记录、产物定位和验收入口属于长期职责；Planner、固定阶段、上下文 reset 与额外模型复核，则是可调整的策略。模型能力和任务分布变化后，策略需要重新评估。

Anthropic 的实验呈现过这种变化：对较早模型有用的上下文重置，在后续模型上可能增加重复交接；固定 sprint 和评估时机也随实验调整。它支持的是定期检验当前策略，不能推出所有模型都该连续运行或都该强制重置。

自建系统可以用同一批真实任务做消融：固定输入、环境和验收，逐项关闭策略，比较合格完成、返工、人工介入、耗时与成本。任务应分层，不能让大量廉价小改动掩盖少数复杂迁移的失败。

Planner 要看是否减少范围和依赖遗漏；Evaluator 要看查出的缺陷与误报、额外修改；并行要看任务是否真正可分。Anthropic 的 C 编译器工程报告中，多 Agent 在不可分解的阶段会围绕同一问题相互干扰，后来借助已知编译器的对照拆分工作。并行数量不能代替任务结构。

## 以恢复代价决定建设规模

可廉价重跑的短期代码修改，可以从单 Agent、Git 和现有 CI 开始。跨上下文持续开发时，先建立规格、功能状态和进度的关联；执行环境会消失时，补上环境重建与产物保存；存在并发接管时，再引入所有权协调。

进入生产写操作之前，应先具备权限限制、审批和结果查询。暂时不能做到时，将交付限定为只读调查与候选代码，人执行外部动作，仍是有明确价值的系统。

可以用三项恢复演练确定建设顺序：更换上下文能否接手，替换沙箱能否复建并验证，在外部响应丢失时能否查明结果。哪一类人工恢复代价已经不可接受，就先建设对应职责。长运行能力由这些可以重现的接管行为构成，保持进程一直活着只是其中一种运行方式。
