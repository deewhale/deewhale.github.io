```text
# 支付回调改造：假设进程中断后留下这些记录
progress.md     实现完成，下一步交付
work-ledger     task: payment-callback; run: run-18; status: running
git log         c7d4e2a Add callback deduplication [run-18]
events          run-18 register_webhook: started
```

接班的 Agent 应该相信哪一份？

提交已经存在，任务还在运行，进度文件宣布完成，支付平台的调用却连返回值都没留下。四份记录各自都可能准确：进程恰好停在了几次写入之间。让新实例接着旧对话推理，会把本该由存储和验证回答的问题交给它猜。

Harness 是模型外负责装配上下文、调度工具和推进任务状态的控制层。长任务跨过进程重启、上下文更换或人工暂停时，它要让接班者找回工作，并分清下一步该实现、验证还是停下来查证。我更关心这项能力能否留在系统里：换一个模型，甚至删掉规划和复核角色，已有任务仍然接得上。

以下支付回调案例、`run_id`、lease、状态机与验收字段，是我为讨论交接而设计的协议；Anthropic 的公开实验和架构会另行标明来源。

## 五类状态的所有权

这次改造要完成三件事：校验支付回调签名，避免重复通知造成重复入账，保持原有支付路径工作。最省事的记录方式，是让 Agent 在同一份 Markdown 里维护需求、进度和测试结果。它也有一个危险的便利：改动一份文件，就能缩小需求、宣布实现完成，再给自己补一条通过记录。

我会先拆开这些记录的写入权。文件数量可以很少，责任需要清楚。

| 状态 | 回答的问题 | 写入与使用规则 |
|---|---|---|
| task spec：任务规格 | 交付什么，按什么条件验收 | 规格所有者维护版本；实现者提出修改建议 |
| work ledger：工作账本 | 谁在做，处于哪个阶段 | 控制层根据领取、提交和验证结果推进 |
| artifact：代码或构建产物 | 本轮留下了哪个实现 | 执行者提交可定位的版本，保留来源关联 |
| evidence：验证证据 | 哪个版本通过了哪些检查 | 验证程序或复核角色生成，绑定规格和产物 |
| 临时运行态 | 工作区、进程和本轮上下文里还有什么 | 接管时检查、保存有用现场，按需重建 |

开头的 `status: running` 属于工作账本。它负责指向 `run-18`，解释任务由谁领取；代码内容以 `c7d4e2a` 为准。进度文字适合补充“为何选这个实现”和“接下来查什么”。支付平台是否注册成功，则要向支付平台确认。

这一区分也改变了权限安排。如果所有记录仍允许实现者随意覆盖，表格只是文档。我的设计会让 Agent 提交候选代码和测试材料，由控制层校验引用关系、推进状态；修改验收目标走独立的规格变更入口。小团队可以先用单进程脚本、受控文件和 Git 实现这条边界，规模扩大后再迁移到服务与数据库。

例如 `spec_version: 3` 约定重复投递同一支付事件时，数据库只增加一笔入账。执行者发现某种旧订单缺少事件编号，可以把它记录为规格问题，交由负责人决定兼容规则。若决定改变规则，就产生版本 4，并重新确认受影响的检查。这样，测试放宽和需求修改会留下同一条可追溯记录。

代码演进也遵循类似规则。版本 A 通过的证据保留为历史；版本 B 加了一次数据库迁移，即使账本曾显示通过，B 仍要重新验证。恢复时最有用的往往是这个具体差异，而非一份更流畅的工作总结。

如果只能先做一件事，我会把“任务—规格版本—代码版本—测试结果”的引用链存下来。原因很实际：下一轮拿到它，就能复验已经付出成本的工作；只有摘要时，接班者往往还得重新判断哪些工作值得保留。规划角色、记忆检索和并行调度都可以晚一点加入。

Anthropic 在 2025 年的长运行编码实验中，观察到一次做得过多、交班留下半成品，以及后续实例过早宣布完成。它用功能清单、进度文件和 Git 帮助新会话接手，还要求开始新功能前检查已有能力。这些工件提供了一个很小的起点：先让下一轮能辨认手里的代码和目标，再考虑让它做更多事。

## 接管时的对账顺序

`run-18` 领取任务时，控制层给它分配一个有期限的 lease。期限到达后可以发起回收检查；续租、抢占和账本写入都通过底层存储的条件更新处理。新执行者取得所有权后，旧执行者提交的过期写入要被拒绝，否则一个迟到的结果就可能覆盖新的进度。外部调用另按业务接口处理，lease 的作用限于任务所有权。

接管入口先只读收集现场：当前规格、账本、Git 历史、工作区差异、最近证据和调用事件。随后依据记录之间的关系，决定保留什么、重验什么。

| 现场状况 | 接管处理 |
|---|---|
| lease 已过期，旧执行者状态待确认 | 核查活动实例，条件更新所有权；保留旧 run 的事件 |
| 新提交能关联到旧 run，缺少对应测试证据 | 保存提交，任务转入待验证 |
| 测试通过，但证据指向旧提交或旧规格 | 保留历史结果，对当前组合安排重验 |
| 工作区有未提交改动，来源清楚 | 先保存隔离副本，检查差异后形成候选 |
| 改动混入多个任务，来源有冲突 | 隔离现场，暂停合并，由人或专门流程厘清 |
| 账本仍在运行，找不到持久产物 | 记录丢失范围，再决定重做或人工接管 |
| 工具事件停在外部写请求发出之后 | 保留结果未知，按原业务标识查询 |

这里最容易做错的是“恢复到最新提交”。最新只描述顺序。若提交属于另一个任务，或者包含两项未完成修改，直接把它交给新 Agent，会把隔离问题伪装成实现问题。对账首先确认提交与任务的关系，再决定从哪里继续；来源不清的改动应保留下来调查。

对已经找回的版本，我会跑一次短基线检查：启动项目，验证既有支付路径，再触发一个合法和一个无效签名请求。它的用途是记录新一轮改动之前的状态。红灯若已存在，任务先处理这个故障；绿灯则给后续差异一个对照。基线应短到每次接管都愿意运行，完整回归仍在交付前完成。

这之后交给模型的输入可以很小：当前规格、相关文件、刚才的基线结果、尚待解决的失败和停止条件。详细历史留在可检索的存储里，按需读回。把所有日志重新装进上下文既增加开销，也让“当前已确认的状态”淹没在旧建议和失败尝试中。

实现恢复逻辑时，我会专门在几处切断进程：代码已提交但账本未更新，测试已结束但证据未保存，证据已保存但通过标记未写入。重启后检查是否沿同一个提交继续，是否重复开发，是否错误地沿用旧结果。正常退出时写一份完整摘要很容易；这些半完成的写入更能检验交班协议。

## 验收绑定代码与环境

接管找回了 `c7d4e2a`，验收程序接下来需要一个固定对象。送验时保存 candidate revision，并锁定对应测试与环境配方。Agent 修复失败后提交新版本，再开始新一轮验证。测试过程中继续修改工作目录，会使“这次绿灯对应哪份代码”重新变得含糊。

支付回调的完成条件可以直接写成可观察结果：合法请求被处理；同一事件重复投递后只留一笔入账；无效签名请求保持订单和账务不变；原有支付路径继续通过。这份验收合同与规格一起版本化，在实现开始前确认。它给执行者留出设计空间，同时固定交付边界。

一份可交班的证据记录如下：

```yaml
work_item_id: payment-callback
spec_version: 3
revision: c7d4e2a
run_id: run-18
environment:
  database_schema: 12
  payment_stub_profile: 4
  fixture: duplicate-delivery-v2
checks:
  valid_signature: pass
  repeated_event_write_count: 1
  invalid_signature_write_count: 0
  regression: pass
artifacts:
  recipe: checks/payment-callback.yaml
  report: results/run-18/report.json
result: pass
```

这张记录让接班者能够定位代码、构建环境和复跑检查。数据库 schema、替身配置、依赖锁定版本、功能开关和数据种子，会影响验证结果；会改变结论的条件都应进入环境配方。`revision` 固定了代码，配方固定了怎样运行它，两者配合才有可比较的结果。

Anthropic 的 Agent 评测方法把交互轨迹称为 transcript，把试验结束后的环境状态称为 outcome。落到这个例子，“运行测试命令”属于轨迹，重复投递后的入账条数属于验收目标。Evaluator 可以是确定性检查程序，也可以包含复核模型：条数、状态转换和响应码先用代码断言；从入口穿过处理逻辑到数据库的路径用端到端测试；难编码的交互质量再交给经过样本校准的复核。

我不认同用“多放一个模型复核”替代验收设计。两个角色若共享模糊标准，花更多轮次也可能一起放行。Anthropic 的全栈应用实验就出现过 Evaluator 发现问题后又宽松通过，研究者需要读日志、调整 QA 提示来校准。应先明确测试会拒绝什么，再判断增加复核模型能补上哪些漏检。

状态转换可以由很短的规则控制：

```text
pending → running → needs_verification → passed
                         └─ 硬条件失败 → failed

代码、规格或关键环境变化：passed → needs_verification
修复重试并提交新候选：failed → running → needs_verification
```

控制层在写入 `passed` 前核对任务、规格、提交和证据仍然匹配；中途任一对象更新，当前结果留下作历史，最新组合重新送验。通过后的提交标为 verified revision。这里需要持久化的是证据及其引用关系，详细日志可以单独保存；把整份终端输出塞进账本反而会妨碍恢复程序检查。

一个支付功能还可能由签名校验、去重写入、路由配置几项工作组成。各项通过以后，组合版本仍要走一次整体验收，覆盖接口连接、数据库约束和部署顺序。最终记录绑定组合提交与环境配方，必要任务全部通过，影响交付的外部动作也已有确定结果。整体验收失败时，局部证据继续保留，用来缩小排查范围。

## Agent 写操作的授权位置

`register_webhook: started` 还提醒了一件 Agent 特有的事：动作由模型选择，授权和凭证却应由模型外的系统控制。我会把测试环境内的代码与数据操作交给受限工具，把生产回调地址变更、凭证轮换和不可自动撤销的动作放在人审之后，审批绑定具体对象与动作。Anthropic 的 Managed Agents 公开架构采用外部凭证存储和专用代理处理自定义工具的 OAuth 凭证；自建 Harness 也可以沿这个边界检查调用主体、目标服务和权限范围，让生成代码接触不到原始 token。遇到中断，先按事先保存的业务标识核对外部结果，再依据该接口的幂等、补偿能力选择后续动作；查证条件不足时暂停自动推进。凭证隔离、操作授权和结果查询分别由对应机制负责，避免接班模型凭一句旧的“已经批准”继续写入。

## 持久化底座与可替换组件

我会把研发投入分成两本账。一类是更换模型后仍要维护的职责：状态保存、产物定位、环境重建、权限检查和验收入口。另一类是为了改善当前模型表现而增加的策略：如何裁剪上下文、谁先规划、何时复核、一次派几个 Agent。前一类适合做成稳定接口，后一类适合配置成可以逐项关闭的策略。

这不要求一开始就拆成很多服务。单进程也能先把读事件、调模型、执行工具和保存结果分成清楚的接口。重要的是，当模型停止响应或沙箱损坏时，任务记录仍在可读取的位置，替换执行者有明确入口。

Anthropic 的 Managed Agents 将日志、控制循环和执行环境拆开，分别称为 Session、Harness 和 Sandbox。把 Model 一并放进来，可以看出稳定接口围住的是什么：

| 组件 | 稳定职责 | 允许替换的部分 |
|---|---|---|
| Session | 在 Harness 外保存可追加的事件历史 | 事件存储实现与读取方式 |
| Harness | 调用模型、路由工具、记录事件 | 调度顺序、角色安排、上下文组织 |
| Sandbox | 执行命令和保存待持久化产物 | 容器实例、计算资源、运行配方 |
| Model | 根据本轮输入提出实现与工具动作 | 模型版本、提示、推理配置 |

这种分工最直接的价值是故障处理。Sandbox 故障时换环境、取回固定提交并重跑基线；Harness 故障时由新实例读持久记录接管；更换 Model 则重新装配上下文。对于源码、规格和验证报告，仍要保留各自的耐久存储。日志里的路径可以帮助找文件，文件本身也必须确实保存过。

事件历史与模型上下文分离后，还有一个选择权：恢复时可以先读失败前后的几条记录，遇到含糊处再向前追溯，而无需接受旧摘要对历史作出的所有取舍。原始事件值得保留多久，取决于调查、合规和存储成本；把摘要策略写死在唯一的历史副本中，会让以后更好的恢复方法失去输入。

我倾向于优先保住这些输入和引用关系，而让 Harness 的执行实例轻一些。原因是上下文策略会反复调整，状态格式却要承接已经运行到一半的任务。升级时可以先用旧任务演练恢复，再切换调度策略；如果每次换模型都得迁移所有任务进度，策略和持久状态就耦合得太深。

## 脚手架的消融检验

把 Planner、Evaluator、固定阶段和上下文重置全部列为必备组件，很容易把某一代模型的弱点永久写进架构。

Anthropic 的应用开发实验提供了一个具体对照：Sonnet 4.5 接近上下文上限时会提前收尾，研究者通过清空上下文并交班来处理；换到 Opus 4.5 后，这种行为减弱，便改用自动 compaction 维持连续运行。到 Opus 4.6 的实验，固定 sprint 被移除，Evaluator 改在完整构建后检查，发现问题再进入修复循环。删除机制与补强机制一样，都在改变 Harness。

我会把“定期尝试删除”纳入升级流程，而非把架构图上的每个框都当作资产。为同一组真实任务固定输入、环境和验收条件，先跑现有配置，再每次关闭一项机制。每种配置重复运行，记录完成率、验收后漏检、返工、人工介入、墙钟时间和成本。改变模型、提示和任务范围时也留下版本，避免把几项变化的效果算到同一个组件头上。

对上下文策略，比较的是故障形态。reset 用一次明确交班换取干净输入，可能丢掉尚未写入工件的判断；compaction 保持连续性，也可能让摘要中的误判跟着后续运行。若连续运行经常过早收口、忽略新证据，值得试 reset；若反复重置使 Agent 一再探索同一段代码，连续运行可能更合适。验收结果和重复劳动一起看，比单看 token 数更能解释取舍。

Planner 的价值主要看范围和依赖是否经常遗漏。上游已经提供细致规格时，可以先由单个执行者工作；输入只有几句产品愿望时，单独规划更可能有用。Anthropic 的该项实验在移除 Planner 后出现过范围缩水，所以保留了它。对自己的任务，应把“少做了哪些必需功能”记成失败，再比较规划步骤是否真正减少了这类失败。

Evaluator 则要检查净收益。先保存一批人工确认的缺陷样本，看它能找回多少、误报多少，以及反馈会引起多少无效修改。模型升级后，旧的缺陷可能已能稳定自修，复核可以后移或降低频率；高风险路径和新任务类型仍保留更强检查。验收入口始终在，是否由另一个模型跑一遍，则由任务难度和漏检成本决定。

我会最后才增加并行。可拆分的失败集合、隔离产物和可检测的合并冲突，是它值得尝试的前提。Anthropic 的 C 编译器实验曾在编译 Linux 内核时遇到多个 Agent 修同一故障、覆盖彼此修改，后来通过与已知可用编译器对照，把问题重新切成可并行诊断的部分。瓶颈在任务划分时，多开实例会增加协调工作。

删除也需要范围明确。某种配置在例行缺陷修复上表现稳定，可以用于这组任务；跨仓库迁移、陌生框架改造和生产操作仍进入各自的评测。把所有任务混成一个成功率，会掩盖最需要复核的少数类别。团队要保存的是“在哪些条件下可以省掉这一环”的结果，方便下次任务分布变化时重新检验。

## 按恢复成本选择实现规模

一个只改本地文件、失败后可以廉价重跑的短任务，我会从受约束的单 Agent、Git 提交和已有测试开始。新建任务数据库、租约服务或模型评审链路的维护成本，很可能高于重跑成本。已经有成熟 CI 的团队，也可以直接复用现有的构建和验收入口。

需要跨会话保留未完成工作时，再补上规格版本、任务账本和证据引用；需要在环境丢失后接班时，加上持久事件和环境配方；存在多个执行者抢占同一工作时，才落实领取、续租和过期写入拒绝。每一项新增设施都对应一个能重现的恢复故障。

如果任务带有外部生产写入，却缺少可限制的工具权限、明确审批或结果查询，优先补齐这些接口。更复杂的规划和重试策略可以等待。对这类任务，先开放只读调查与候选变更，让人执行生产动作，是一个完整且有用的交付范围。

选择前可以用三次演练定规模：丢掉模型上下文后是否能接班；删去临时执行环境后是否能重建并复验；提交外部动作后失去响应，是否能查明结果并停止危险重试。哪一项超出了团队可接受的人工恢复成本，就先建设对应的那一层。
