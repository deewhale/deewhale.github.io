Agent Client Protocol（ACP）是编辑器等客户端与 Coding Agent 之间的通信协议。客户端提供交互界面和项目入口，Agent 提供模型与工具驱动的执行过程；ACP 让双方使用共同的消息表达会话、工具进度、权限选择和取消，而不必为每个编辑器与每个 Agent 单独设计一套交互。

接入之后，编辑器可以把用户尚未保存的文本交给 Agent，展示它准备修改的文件，并在执行前收集权限选择。Agent 在处理用户输入的同时，也能向编辑器请求文件等能力；这些反向请求使工作能够接上编辑器当前持有的状态。

## 客户端与 Agent 分别负责什么
ACP 的典型两端是编辑器客户端和独立 Agent 进程。客户端把用户输入交给会话，Agent 在执行过程中发回更新，遇到所需客户端能力时也可以反向请求。JSON-RPC 请求有对应响应，通知用于单向更新。用户提交的 prompt 向 Agent 发送；执行中需要编辑器文件时，文件请求则沿相反方向发送。

![编辑器与 Agent 进程双向交换 ACP 请求和会话更新，Agent 再通过工具连接访问服务器](/assets/images/posts/agent-client-protocol-session-mechanism.png)

图的左侧是客户端与 Agent 的交互边界，右侧是 Agent 访问工具或资源的路径。ACP 传递客户端与 Agent 的交互消息；MCP 可以连接 Agent 与工具服务。多成员分工或工作流则由 Agent 内部另行组织。

编辑器最少需要维护会话视图、待处理请求和工具状态。Agent 最少需要维护执行上下文、工具调用记录与取消状态。双方通过消息关联这些状态，各自持有的内存或持久化记录仍由实现负责。



## 连接协商决定可以使用哪些能力

在 v1 的标准输入输出传输中，客户端启动 Agent 子进程。双方通过 UTF-8 JSON-RPC 消息通信，以换行分帧。Agent 的诊断日志应写到标准错误流，避免混进承载协议消息的标准输出。

启动进程只说明通信对象存在。客户端还要发送 `initialize`，确定协议版本，并告诉 Agent 自己支持哪些客户端方法：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": 1,
    "clientCapabilities": {
      "fs": {"readTextFile": true, "writeTextFile": true}
    }
  }
}
```

这里的文件能力表示 Agent 可以向客户端请求相应操作。编辑器因而能通过自己的文件服务提供文本，或把写入与缓冲区协调起来。它没有改变 Agent 进程本来拥有的操作系统权限：Agent 若另行执行本地工具，是否能访问文件，取决于进程和工具的运行边界。

Agent 的初始化响应则声明自己的能力：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": 1,
    "agentCapabilities": {"loadSession": false}
  }
}
```

相同的 JSON-RPC `id` 把响应对应到初始化请求。`loadSession: false` 表明客户端不能据此启用“加载已有会话”路径。未声明的可选能力也应按不支持处理，不能靠“另一款 Agent 有这个按钮”推断当前连接具备同样功能。

如果 Agent 返回的协议版本不在客户端支持范围，客户端需要终止不兼容连接。继续把字段按自己理解解析，可能到敏感操作时才暴露错位。网站所标的协议 v1，与 Schema 1.27.0、Rust Crate 1.13.0 这类发行版本属于不同编号：后者新增兼容能力，并不意味着线上消息的 major version 已变为 2。

初始化之后，若实现需要认证，再完成对应认证路径。随后 `session/new` 提供会话工作目录 `cwd` 和 MCP 服务器列表 `mcpServers`，Agent 返回 `sessionId`。工作目录要是绝对路径；客户端需要把它绑定到用户选定的项目，而不能把任意输入当工作区授权。



## 请求、会话与工具有不同的身份

以规范消息结构表达一次配置编辑请求，客户端向 `session/prompt` 发送 `sessionId: "s1"` 和文本内容块。Agent 在这个会话中调用模型、读取配置，并决定下一步动作。

后续更新沿 `sessionId` 归到正确会话，工具调用另由 `toolCallId` 区分。同一个会话可能有多次工具调用；同一次工具调用又会收到多个阶段的更新。JSON-RPC 请求 `id` 则用于把需要响应的一次方法调用与其响应配对。

这三个标识处理三种关联：请求往返、会话归属和工具生命周期。只拿工具名称作关联键，会在同一时间出现两次 `read_file` 时混淆状态；把会话 ID 当用户身份或访问凭据，又会把消息路由混成授权判断。



## 工具执行怎样变成编辑器中的可见进度

Agent 可以通过 `session/update` 发送工具通知。下面是会话 `s1` 中工具 `t1` 的初始状态；为突出消息内容，后续示例只展示方法参数，省略 JSON-RPC 外层：

```json
{
  "sessionId": "s1",
  "update": {
    "sessionUpdate": "tool_call",
    "toolCallId": "t1",
    "title": "修改重试配置",
    "name": "edit_file",
    "kind": "edit",
    "status": "pending"
  }
}
```

`title` 供人阅读，`name` 表达工具名，`kind` 帮助客户端按操作类型呈现。客户端收到后，可以先建立一张尚未完成的工具卡片。通知是状态报告，不是客户端必须执行文件修改的命令。

工具开始和结束时，Agent 继续使用相同 `toolCallId` 发送 `tool_call_update`，把状态推进到 `in_progress`，再到 `completed` 或 `failed`。更新还可以包含输出、差异和位置，让编辑器展示此次操作的材料。

这比在聊天文本里搜索“已经完成”更明确：客户端按结构化字段更新一个对象。但 `completed` 仍然属于工具生命周期。它可能说明编辑操作完成，不代表配置正确、测试通过或用户任务已经达成。

在配置编辑中，完成后还应核对实际文件及相关验证。若工具只成功写入了另一个文件，协议通知仍可能形状合法，业务结果却不成立。呈现差异有助于用户发现这种问题，不能替代读取实际结果。

### 文件内容怎样经过客户端

协商文件能力以后，Agent 可以发送 `fs/read_text_file`，参数包含 `sessionId`、绝对 `path`，以及可选的起始行与行数。客户端在响应的 `content` 中提供文本。由于读取由编辑器实现，它能够提供未保存的缓冲区内容，Agent 可以基于用户正在编辑的版本工作。

修改也可以走这条路径。`fs/write_text_file` 携带目标路径和完整 `content`，客户端负责写入，成功时返回空结果；文件不存在时，规范要求创建。Agent 随后通过工具更新通知展示差异和状态。文件方法执行写入，diff 内容帮助呈现变化，二者在消息里各有位置。

这组 v1 文件参数没有提供一个通用的“仅当版本仍为v时写入”字段。假如 Agent 读取后用户又编辑了文件，客户端怎样接受整份新内容、保护未保存修改，需要由编辑器实现处理。接入时应确认读到的版本来自哪里，以及写入期间是否还有其他修改者。

Zed 的公开问题 #49162 展示了另一种具体冲突：报告者先经 ACP 读文件，再让终端命令改磁盘，随后再次读取时仍取得旧缓冲区。磁盘变更被文件监听器处理前，下一次读取可能已经发生。这个报告可用来设计接入测试：同时覆盖缓冲区内编辑和终端外部修改，再检查后续读取及diff是否对应最新工作材料。它提供的是具体故障线索，是否已在目标版本修复须由该版本验证。

## 权限消息怎样约束实际执行

对需要授权的操作，Agent 可以发送 `session/request_permission`。它携带工具信息及当前可选动作，客户端显示给用户，或依据用户已设定的策略作出选择。

```json
{
  "sessionId": "s1",
  "toolCall": {
    "toolCallId": "t1",
    "title": "修改重试配置"
  },
  "options": [
    {"optionId": "allow-1", "name": "仅允许本次", "kind": "allow_once"},
    {"optionId": "reject-1", "name": "拒绝", "kind": "reject_once"}
  ]
}
```

用户允许本次时，响应参数为：

```json
{"outcome":{"outcome":"selected","optionId":"allow-1"}}
```

这里两层 `outcome` 有不同结构位置。外层是响应字段，内层说明结果属于 `selected`；`optionId` 指向此请求提供的具体选项。若用户选择拒绝，仍然可以用 `selected` 返回 `reject-1`。因此，看到 `selected` 不能直接理解为已批准。

接收方至少需要把响应对应到原请求，确认会话与工具仍然有效，查到这个选项代表的行为，再决定是否执行。一个应用层判断可以表示为：

```python
offered = {option["optionId"]: option["kind"] for option in request["options"]}
outcome = response["outcome"]
if outcome["outcome"] == "cancelled":
    decision = "stop"
else:
    option_kind = offered.get(outcome.get("optionId"))
    decision = "execute" if option_kind == "allow_once" else "stop"
```

这是针对上述两个选项的示意片段，省略了请求登记、异常处理和其他权限种类。它展示必要的关联判断：`not-offered` 即使是字符串，也不应当成为可执行决定；未知 ID 应作为无效响应处理。

按响应定义，`selected` 需要 `optionId`；但单条响应即使形状有效，仍可能引用未提供的选项。单条响应 Schema 不知道先前请求究竟提供了哪些选项，应用层必须补上跨消息关联。

规范定义了权限请求与选择的消息形式，是否在某次工具调用前请求批准，仍由接入实现决定。Agent 何时请求、客户端怎样应用已有偏好、执行器是否确实遵守拒绝，都是接入验证需要检查的路径。



## 取消如何影响会话和已发生的动作

用户在权限框里取消时，可以返回：

```json
{"outcome":{"outcome":"cancelled"}}
```

如果取消的是整个会话中正在进行的操作，客户端还可以沿 `session/cancel` 路径通知 Agent。实现需要让取消状态影响后续等待、工具分派和结果呈现。

一个容易出错的时序是：用户点取消时，文件写入已经完成，检查命令还没结束。客户端可以停止等待或显示任务已取消，实际文件却不会自动恢复原值。工具进程的停止、已写文件的保留或恢复，以及外部请求的后续处理，需要由执行实现决定。

因此，取消验证不能只检查 UI 按钮变灰。至少要分出等待授权前、授权后尚未执行、执行中、已产生副作用几个位置，观察是否仍启动新操作，已经完成的改动是否清楚呈现。若应用支持回滚，还要检验其具体动作，而不能从 ACP 的取消通知推断存在通用回滚。

工具失败也要回到同一状态关联。`t1` 写入失败，就应在该工具记录中呈现失败与相应内容；会话最后一句自然语言回答可以解释失败，但不能用“任务完成”覆盖结构化错误。用户需要能据此决定重新执行、调整输入还是保留当前文件。



## 会话加载与可选更新

会话历史的重新呈现由 `loadSession` 能力控制。Agent 声明支持后，客户端才能请求加载；Agent 负责取得保存的会话并发送相应更新。历史消息为用户和后续执行提供材料，执行进程与文件则由各自的运行环境管理。

持续工作还可能产生上下文压缩、提示性通知或子任务状态。采用时只启用双方稳定实现的更新：本文参照的 Schema 1.27.0 已稳定工具名称、session notices 与 compaction，子 Agent 更新仍在不稳定Schema。v1的相应扩展能力按规范对象声明，缺省时不发送该类更新。

当前网站同时提供 v1 与 v2 草案，初始化字段及部分工具安排已有差异。客户端与 Agent 应沿同一条版本路径完成协商；本文消息采用 v1。

## 接入验收同时检查消息与实际结果

试点前，先列出这个编辑器和这个 Agent 的版本及必需能力。对于“修改配置并检查”的需求，可以形成如下验收表：

| 需要的行为 | 双方必须明确的选择 | 应观察到的结果 |
|---|---|---|
| 建立会话 | 协议版本、认证与项目目录 | 不兼容时停止；成功时取得会话标识 |
| 展示工具 | 工具通知与更新支持 | 同一调用按 ID 持续更新 |
| 批准写入 | 何时请求、选项含义、决定如何落实 | 允许才执行；拒绝和未知选项不会执行 |
| 呈现修改 | 文件操作路径、diff、缓冲区协调 | 展示与实际文件相符的变化 |
| 取消操作 | 等待与执行阶段的取消处理 | 不启动后续动作，已发生变化仍可辨识 |
| 加载或扩展 | load、压缩、通知及草案能力 | 缺省能力不被擅自调用 |

先运行允许和拒绝两条路径，再加入取消、工具失败与未知能力，能比只跑一次成功演示更早暴露边界错位。接入时应在编辑器与 Agent 进程之间观察消息时序和文件结果，检查载荷之外的实际行为。

如果需求只是在编辑器里展示最终文字，启动一个命令并收集输出可能已经足够。需要持续工具进度、权限交互和多客户端接入时，ACP 才提供更完整的公共表达。是否采用，最终应由这张行为表与实际互通结果决定，而不能只由产品页面上“支持 ACP”的标签决定。
