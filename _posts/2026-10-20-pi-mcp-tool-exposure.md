Pi 是一个可在终端使用、也能通过 SDK 嵌入应用的 Coding Agent。它接收用户目标，组织模型调用，并通过工具读取文件、执行命令和修改代码。外部系统越多，工具接入便同时涉及两件事：模型怎样找到接口，多次调用怎样组合成一项工作。

Pi 1.0 将原生 MCP 和 Code Mode 一起纳入稳定版，围绕这两项工作调整了工具系统。MCP 让外部服务暴露能力，工具呈现机制决定定义何时进入模型上下文，Code Mode 则让模型提出程序，由解释器推进循环、并发和结果处理。三者接成一条链，才构成这轮更新的设计意义。

下面先解释连接、发现和执行的整体组织，再用官方 Linear 与 Jev 会话重放分析一次组合任务。具体机制参照 `v1.4.0`，历史演示与当前接口的差异在相应位置说明。

## 工具接入与工具组合分别解决什么

Pi 此前可以通过扩展接入 MCP。官方重新考虑原生支持时，关注的是更普遍的组合问题：服务提供了工具，并不意味着多个工具已经可以顺畅协作。许多 MCP 服务将接口设计成“调用一次，返回一段给模型阅读的文本”，后续取字段、循环查询和汇总又要回到对话里完成。

命令行工具有另一种使用习惯。调用者可以把查询、过滤、连接和排序接成程序，中间材料留在程序中，只输出需要查看的结果。Pi 希望在结构化工具上获得类似能力，因此把 JavaScript 解释器放在 harness 侧，由它通过受控桥接调用已经注册的工具与模型。

这个位置有实际意义。工具执行环境可能是本地工作区，也可能是远程容器；协调 Agent 的进程则持有会话、服务连接和模型接口。Code Mode 在后者组织能力，不要求所有远程服务都先变成工作区里的一条 Shell 命令。同一段程序因而可以取得 MCP 查询结果，再交给分类模型处理。

仅增加一个解释器仍不够。工具注册以后，模型未必需要立即读取完整定义。Pi 用 exposure 安排工具从哪个入口可达，用 namespace 组织发现范围，并以输入输出描述帮助调用者构造请求、读取结果。这轮更新因此同时调整了工具定义、呈现与嵌套执行的接口。

0.99.0 已经引入相关内置实现，1.0 是稳定发布的汇合点。把变化理解成“增加 MCP 开关”，会漏掉可组合性；把它理解成“所有工具都改用 JavaScript”，又会漏掉 Pi 仍然保留的直接调用与按需加载。



## 工具怎样从 MCP 服务进入会话

接入时，需要先理解工具怎样进入 Pi。固定版本支持 stdio 与 Streamable HTTP 两类 MCP 连接。前者启动一个服务进程并交换协议消息，后者连接 HTTP 服务；需要认证的服务还要完成对应登录。不能从演示中的 `mcp__linear__list_issues` 反推出某个当前可用的服务地址、凭据或接口定义。

Pi 读取用户级 `mcp.json` 与受信任项目的 `.pi/mcp.json`，连接服务，完成初始化并取得 `tools/list`，再把服务接口转换成会话工具。配置已读取、服务已连接、工具已注册、工具已向模型声明，是连续但不同的状态。连接后台进行；初次提示主要等待 direct 服务，默认等待预算为 10 秒，间接入口则可在使用相关服务时继续等待。

CLI 可以用 `pi mcp list` 查看服务，交互会话通过 `/mcp` 查看连接和认证状态，通过 `/reload` 重载配置。这里首先要确认工具目录确实进入运行时，再检查呈现方式。把“模型没列出这个工具”直接归因于服务连接失败，会混淆这两层。

SDK 的接入入口可以直接看官方 `examples/sdk/14-codemode-mcp.ts`。它先把 Code Mode、Tool Search 和 MCP 三个扩展工厂交给 `DefaultResourceLoader`，再调用 `reload()` 加载资源。此时得到的是会话将要使用的扩展定义；MCP 连接由会话开始事件推进。

例程随后把 `defaultTools` 增补为 `+codemode`、`+tool_search`，把资源加载器和设置传给 `createAgentSession`。这里的加号保留其他默认工具：若改用限制整个工具集合的 `tools` 配置，反而可能把 MCP 工具排除在外。Code Mode 与搜索工具也可以随相应 exposure 的服务自动激活。

会话创建后，例程先 `session.bindExtensions({})`，再发出 `session.prompt(...)`，最后 `dispose()`。`bindExtensions` 触发 `session_start`，MCP 扩展才开始后台连接。把加载、建立会话和触发生命周期分开看，就能解释为什么‘工厂已经放进数组’还不足以说明工具可用。

脚本发现并调用工具，需要以下描述：namespace 缩小服务范围，名称和说明表达用途，输入定义说明参数，输出定义说明返回材料。对 Linear 演示，脚本需要的是“查询 issue”与“取得某条 issue 评论”的接口，而不是靠猜测注册名称和字段拼接请求。

Code Mode 提供异步的 `searchTools`、`describeTool` 和 `describeNamespace`。搜索帮助找到候选，定点描述帮助取得参数与返回说明。固定实现使用 BM25，默认返回八项候选，主要依据名称、描述、参数等词项排序。它不能被当成对任意中文表达都有可靠理解的语义搜索。服务描述越具体，发现过程越容易区分查询与修改、单条与批量等能力。

发现也存在两种不同效果。模型使用 `tool_search`，命中的延迟工具会在下一次模型请求中加载完整声明；脚本使用 `searchTools`，取得的是供程序选用的候选与接口信息。后者不会因此把所有候选变成模型当前的直接工具声明。需要减少定义常驻上下文时，这个区分很关键。



## direct、deferred 与 Code Mode 如何分配控制

下面的官方任务先取得一组 Linear issue，再用每条 issue 的标识查询评论，将线程文字交给 Jev 按同一标准分类，最后筛选结果。这里有两项不同依赖：取评论需要 issue 标识，分类需要实际评论。三种工具方式都能完成这些调用，差别是定义何时出现、谁保存中间集合并推进这些依赖。

在 direct 路径中，相关工具从一开始向模型声明。模型调用 issue 查询，根据返回材料决定取得哪些评论，再安排后续分析。独立的评论查询可以在同一条 assistant 消息里批量提出，运行时也支持并行，因此不能假定每条 issue 都必然多消耗一轮模型推理。中间工具结果进入模型历史，后续组合取决于模型提出的动作。

deferred 先隐藏完整定义，模型需要时调用 `tool_search`，命中声明在后续请求中出现。工具加载以后，调用与结果路径同样是原生工具调用。它主要处理大工具目录对请求的负担，不会自动把评论结果变成一份已经筛好的分类表。

Code Mode 由模型提出程序，解释器推进“取集合—限制并发—取评论—调用分类器—聚合输出”。worker 的领取规则和先后依赖由代码表达，中间数组、概率与评论留在程序和相应模型调用的处理路径里。协调模型最终取得程序选择呈现的材料。

| 同一维度 | direct | deferred | Code Mode |
|---|---|---|---|
| 完整工具定义何时出现 | 初始请求中声明所选接口 | 搜索命中后在后续请求声明 | 按需发现供脚本使用的接口 |
| 后续动作由谁推进 | 模型继续提出调用 | 加载后由模型提出调用 | 模型提出程序，解释器执行其控制流 |
| issue 与评论中间值 | 进入模型工具历史 | 进入模型工具历史 | 可先留在脚本中处理 |
| 独立查询如何并行 | 模型可批量提出 | 同 direct | 程序明确并发上限与依赖 |
| 内部工具执行 | 会话共同管道 | 会话共同管道 | 通过嵌套桥接进入共同管道 |
| 最直接解决的问题 | 少量接口直接可用 | 大目录按需声明 | 确定的多步操作可编程组合 |

这三条路径可能发出相同的外部查询。Code Mode 增加了程序生成、发现、执行和结果说明的工作，收益条件在于被程序接管的中间转换足够明确，且不必把所有原始数据交给协调模型。公开案例没有提供可用于推导通用耗时、token 或费用降幅的对照测量。

MCP 的 `codemode` exposure 与 `deferred` 还有重叠的间接可达性，差异包括自动启用的发现入口。`hidden` 则限制当前客户端的入口。实际配置可以按工具混用这些方式：常用的小接口直接声明，大目录按需发现，明确的批处理使用脚本。呈现方式负责安排能力如何被找到，服务端身份与授权负责允许它产生什么动作。



## 官方 Linear 与 Jev 任务怎样组合查询和判断
Earendil Engineering 在 2026 年 9 月 29 日《“You Said No MCP!”》中公开了浓缩会话重放：从团队的 Linear issue 里筛选情绪明显不满的讨论，再用 Jev 分类器组织判断。这是一次公开的工具组合演示。

![官方 Linear 与 Jev 演示中，模型生成脚本，Linear 提供 issue 及评论，Jev 分类，脚本保存并筛选结果后交回外层模型](/assets/images/posts/pi-mcp-tool-exposure-mechanism.png)


官方会话请求寻找 issue tracker 上最不满的人，展示的程序却以 **issue 线程** 为单位处理。这个差别决定了输出能支持什么判断。

程序先调用 Linear 的 `list_issues`，参数是 `team: "Pi"`、`state: "open"`、`limit: 250`。返回的 `issues` 成为后续处理集合。展示代码没有翻页循环，所以分析范围是这一次查询得到的记录。它随后取得类型为 `classifier`、provider 为 `cloudflare-workers-ai`、标识为 `typesafe/jev` 的模型。

Jev 的判断目标被明确写成一个 choice 问题：根据发言者的情绪语气，在 `none`、`mild`、`high` 三项中选择，并忽略 bug 本身有多严重。中性地报告严重故障，与愤怒地讨论一个小功能，可能属于不同情绪类别。这项标准由调用者提供，模型负责将具体文字归入标准，而问题严重程度或修复优先级并没有因此被算出来。

整个处理过程可以沿官方代码中的实际对象追踪：

| 阶段 | 实际输入与动作 | 产物与用途 |
|---|---|---|
| 取问题 | Linear `list_issues` 查询 Pi 团队的 open issues | `issues` 数组，确定本轮处理集合 |
| 取讨论 | 对每条记录以 `issue.identifier` 调用 `list_comments` | 该 issue 的评论，与 issue 本身组合成分类输入 |
| 判断情绪 | Jev 读取组合后的 `state` 与 `questions.frustration` | `answers.frustration` 中的类别和类别概率 |
| 保留身份 | 将 issue ID、title 与分类值写入结果行 | 后续仍能回到原线程检查 |
| 聚合筛选 | 统计类别，筛掉选中类别为 `none` 的行，再按分数排序 | 一组需要优先阅读的 issue 线程 |
| 保存与呈现 | `store("frustration", results)`，输出总数、计数与标记项 | 后续可以继续追问已有结果，而不必从头查询 |

这份程序最有解释力的部分，是把模型判断与确定性处理放在了不同位置。评论的情绪需要分类器推断；取下一条记录、并发上限、计数、过滤和排序，则由 JavaScript 明确执行。协调对话模型提出组合程序，harness 推进程序，Linear 服务提供数据，Jev 完成受问题定义约束的分类。

并发方式也很具体。程序启动四个 worker，共用一个递增索引。每个 worker 领取一条 issue，先等待该 issue 的评论，再等待分类结果，然后领取下一条。因此最多有四条 issue 处理链同时推进。单条链中，分类必须等待评论；不同 issue 之间则可以重叠等待。这里的“四”是官方程序选择的并发上限，公开材料没有给出它相对于其他上限的性能比较。

筛选阶段采用的分数为：

```text
排序分数 = 0.5 × mild 的概率 + high 的概率
```

程序先保留选中类别不为 `none` 的行，再按此分数降序排列。这意味着“是否进入列表”与“进入后排在哪里”使用了不同规则：前者看选中类别，后者看概率加权值。分数表达这段程序的排序偏好，不能直接当作人的真实情绪强度，更不能转成修复优先级。

官方浓缩重放展示了 167 条记录，156 条选为 `none`，11 条选为 `mild`，最后返回 11 个 issue ID 与标题。总数可以由类别计数核对，ID 可以定位待检查的讨论；这些数字没有提供人工标注对照，因而不能说明分类准确率。代码也没有按评论作者聚合、身份去重或建立个人排名，结果应解释为“本次材料中被标记的讨论线程”。

从这份结果采取的下一步应是阅读这些线程，检查分类所依据的评论，再决定跟进方式。一次情绪筛选可以缩小阅读范围；若目标改为找出具体用户、衡量长期满意度或安排工程优先级，还需要相应的数据处理和判断标准。



## 从历史演示迁移到当前返回接口

9 月 29 日的公开脚本直接从工具返回中解构 `issues` 和 `comments`。固定 v1.4.0 的 MCP 适配器则向脚本提供 `CallToolResult` 外包装。真实服务的结构化业务数据位于其中的 `structuredContent`，另有 `content` 和 `isError` 等字段。因此历史程序适合作为设计对象，不能原样作为当前版本的可运行教程。

对应实现位于 `packages/coding-agent/src/extensions/mcp/tools.ts`。适配器构造返回定义，转换 MCP 结果，供脚本取得的结果去掉 `_meta`，保留业务内容及错误标记。理解这层包装后，接入者应根据当前发现的返回定义取值，而非将旧演示里的解构方式当成所有服务器的共同格式。

迁移评论查询时，脚本先取得 MCP 返回外包装，检查 `isError`，再从当前接口定义指明的位置读取业务数据。参数校验、拦截或调用失败也可能使 Promise rejected，两条错误路径都应进入该线程的失败记录。只有取得对应评论以后，才调用分类器；查询失败时将空对象继续送去分类，会改变被判断的材料。

Code Mode 的脚本并发还要受宿主 worker 资源控制。1.4 在 worker 满载时让新脚本排队等待空位，`PI_CODEMODE_MAX_WORKERS` 可调整进程内上限；这与脚本自己限制 issue worker 的数量是两层并发。脚本内部的四条处理链不等于占用四个 VM，也不能据此估算所有会话的资源上限。

分类模型也有独立的结果状态。固定版本的 `models.classify` 在 provider 失败时不一定抛出异常，应先检查 `stopReason` 是 `stop`、`error` 还是 `aborted`，必要时读取 `errorMessage`，再使用 `answers`。MCP 的 `isError` 与分类器的状态属于不同接口，不能用一项检查代替另一项。模型标识还依赖 provider 与账号可用能力，当前接入应先发现可用分类器，历史演示里的标识不代表任意账号今天都能调用。

分类结果失败时，也应保留对应 issue 的失败身份，而不是记成 `none`。这样聚合得到的类别计数与失败计数共同覆盖本轮集合，后续才知道哪些线程需要重试查询或分类。这是沿当前返回接口导出的接入处理。

内置 Code Mode 通过 `ctx.executeTool` 调用会话工具，使嵌套操作进入共同执行管道。参数检查、`tool_call`、`tool_result` 和已配置的扩展规则仍然参与；事件还可以保留父调用标识，帮助宿主把一次编排与内部调用关联起来。若宿主只使用底层沙箱库并直接调用某个 `execute` 函数，需要自行接好这条桥接，不能把不同集成方式的检查范围混用。

结果从哪条路径交给模型，也影响可见内容。普通 MCP 长文本在模型侧有截断处理；脚本可以先取得结构化结果，再选择输出。于是程序能够保留 ID、类别和短证据，暂不把全部评论写入协调模型的工具历史。Jev 仍须读取用于分类的文字，服务请求也仍须传输数据；这里减少的是某些中间材料经过协调对话模型的需要。



## 数据复用、执行恢复与权限分别落在哪里

官方演示将分类行写入 `store("frustration", results)`，使后续追问能够复用结果。这里保存的是数据。普通 Code Mode 每次调用会启动新的 VM，上一段程序的局部变量不会自然保留；成功脚本的 store 写入作为 `codemode-store` 条目进入会话，并沿当前分支恢复可见值。

这个设计适合保存结果索引和适量结构化材料。下次追问可以按 issue ID 找到分类结果，再查询原评论；新的 VM 从保存数据继续计算。固定实现有单值及总量预算，因此应保存后续真正要复用的字段。

脚本对外部世界的动作则具有自己的生命周期。一次写操作完成后，脚本可能在 store 提交以前失败。下一次没有找到进度值，只能说明这次数据没有成功保存，不能推出外部动作尚未发生。因此批量读取与批量修改需要不同的重试考虑；一段程序可组合工具，并不意味着这些工具被包在同一个可回滚事务中。

QuickJS 对程序直接使用宿主文件、网络和进程接口作限制。它注入的工具仍然可能读写外部系统，权限由服务令牌、工具实现、宿主扩展规则和执行环境共同决定。把接口改成隐藏，不会撤销令牌；允许脚本调用工具，也不等于给脚本任意操作宿主的入口。

若要求进程中断后接续在途工具，需进一步保存任务身份、检查点与重放关系，具体见[Pi Durable 的持久恢复设计](/posts/pi-agent-runtime/)。本篇的 store 用于后续读取已有结果，外部写操作仍按目标服务的请求身份与查询规则恢复。



## 按数据依赖选择调用方式

接口很少、结果很短、下一步需要模型重新理解新材料时，直接调用容易观察和调试。接口目录很大，但仍希望由模型逐步决策时，deferred 可以按需提供定义。循环、并发、连接、筛选与聚合已有清晰规则时，Code Mode 才能把这些规则落实成程序。

Linear 与 Jev 的官方演示符合后一个条件：每条 issue 都需要取得评论、按同一情绪标准分类，再按同一规则汇总。模型判断仍然存在，只是被放到一个明确问题上；数据调度与分类后的处理则交给代码。程序选错材料、遗漏分页或把线程结论写成人物画像，仍然会改变任务含义，执行成功不会修正这些选择。

服务作者也要为这种组合方式提供材料。描述要让调用者区分操作目的，输入定义要足以构造请求，结构化输出要保留稳定身份、错误状态与可回查依据。只将文本压短，却丢掉记录 ID 或失败项，会让后续程序更难验证自己处理的是哪一份对象。

采用 Pi 1.0 的工具设计时，可以先找一项已有实际操作记录的任务，画出输入依赖与结果去向：哪些接口需要发现，哪些步骤需要模型判断，哪些步骤可以按确定规则推进，最终必须保留哪些证据。能够把这几条关系写清，才有依据决定直接声明、延迟发现与程序编排各放在哪里。
