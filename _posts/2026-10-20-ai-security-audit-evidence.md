安全审计需要判断可疑代码在实际条件下能否造成安全影响。本文关注低信任输入如何进入程序、经过哪些检查，最终能否影响本不应受其控制的资源。危险函数、模型置信度和报告条目只是调查线索；支持修复决定，还需要把入口、约束、资源和证据连成一条可复核的路径。

Cloudflare 的 security-audit-skill 是一套交给 Coding Agent 使用的审计工作方法。用户提供目标仓库和审查范围，主 Agent 组织源码侦察、分工搜寻和候选验证，最终交付覆盖记录、机器可读的 findings 与报告。它运行在已有 Agent 工具环境中，模型承担查找和推理，脚本约束记录格式，操作系统沙箱限制验证代码的权限。

这套设计值得研究的地方，是怎样把“模型认为可疑”推进为“工程师有依据采取行动”。它给出的答案分为两条相互关联的线：覆盖记录管理还需要查哪里，候选验证管理一条判断凭什么成立。

## 审计范围先落到身份、资源与入口

仓库中不同代码的安全意义并不相等。一个内部转换函数是否构成漏洞，取决于谁能把什么输入交给它，以及它最终能影响什么。因而侦察先建立产品和权限模型，再组织源码检查。

官方 `RECONNAISSANCE.md` 将这项工作拆为几种互补视角：产品用途和本地运行方式；身份、授权与权限变化；低信任输入的入口、转换和敏感操作；能在隔离条件下运行的现有测试及缺失的部署事实。各视角返回带源码位置的材料，由主 Agent 合成后续搜索范围。

这里的“信任边界”有具体含义：低权限主体提交的数据，进入了能够读取其他资源、调用更高权限操作或改变其他主体状态的代码。HTTP 参数、归档文件、插件、CI 输入、模型上下文和本地 IPC 都可能是入口。是否构成越权，要继续追踪资源归属和实际检查。

覆盖台账把入口、信任边界、子系统与攻击类别分别保存为可追踪的源码引用。官方文档用路由 `src/router.ts#POST /users/:id`、授权函数 `src/authz.ts#requireOwner`、包 `packages/api` 和 Access control 类别说明记录形状。这里是台账格式示例，实际运行要从目标仓库找出对应对象。

这四项确定“检查哪个入口，沿哪项授权边界，按哪类攻击解释查什么”。`starting_paths` 给搜寻者起点，`reviewed_paths` 记录真正读过的代码，`local_checks` 留下检查依据，`result_fingerprints` 连到候选；缺失材料进入 `unresolved`。同一路由若经过不同边界，或要查另一种攻击类别，就有不同单元。一个文件读过一次，不能关闭所有相关单元。

主流程将规范引用按UTF-8百分号编码后拼成 `coverage_id`；标签、审查轮次、行号与结论不进入身份。显示名称改变不会让一个未查问题消失。单元先为 `planned`，分派后写入检查；发现候选时与候选记录关联，阻塞时则留下原因。后续批评者重开单元，会归档上一轮依据，分配新的检查，而不是覆盖过去记录。

例如，官方侦察要求分别区分“源码能确认的控制”和“依赖未观察到的部署条件的控制”。身份检查写在源码里，可以查调用路径；某路由是否对外开放、服务实际使用什么云权限，则可能需要系统所有者提供材料。覆盖台账据此保留待查和阻塞项，而不把材料缺口算成已完成。

## 覆盖驱动搜寻与候选验证是两种任务

搜寻者的任务是提出值得检查的解释。它需要指出低信任输入怎样传播、哪项约束可能缺失、哪个主体的资源会受到影响，并给出当前源码位置。函数名或通用漏洞类别无法替代这条路径。

覆盖管理则从全局检查有没有漏掉重要区域。若所有 Agent 都沿最容易找到的问题继续扩写，候选数量可能增长，尚未触及的边界仍然不变。覆盖批评环节回看剩余单元，要求补查或明确记录为何不能继续。预算不足也是覆盖状态，而非可以省略的空白。

候选验证在这之后进行。官方 `VALIDATION-AND-REPORTING.md` 要求把每条独特候选交给没有参与发现的验证者。验证者重新读取当前源码，主动寻找最强的反证：入口是否真的可控，身份是否已绑定，框架是否先做规范化，下游是否再次授权，运行方式是否使声称的路径无法成立。

验证者可以读取发现者的证据，但不能继承其结论。源码中的上游检查足以推翻候选时，应结束这条判断；缺失事实仍具有决定性时，应保留缺口；能在规定环境下取得最小观察时，才把观察与源码解释合起来评价。

这一步可以用官方侦察要求中的授权关系理解。设低权限主体 P 请求资源 R，调用路径经过入口 E、授权检查 C，再到读取 S；这只是源码权限分析的抽象模型。搜寻者若只读到 E→S，会提出缺少授权的候选。验证者接着查 C 是否在所有能抵达 S 的路径上执行，C比较的究竟是P与R的归属，还是只有登录状态。前一种检查能切断所声称的越权路径；只有登录检查则仍需追踪资源范围；C是否启用取决于未知部署配置时，记录具体阻塞。

因此反证不是再给一次同意票，而是寻找足以改变路径可达性的事实。只有检查到当前源码或取得有界观察，结论才前进。

![覆盖台账产生候选，独立验证后分为已确认、待验证与已反证三个状态](/assets/images/posts/ai-security-audit-evidence-mechanism.png)

搜索提出的攻击路径，需要经过验证才能分流：源码与实际观察支持它，记录为确认；决定性事实仍缺失，记录为待验证；上游检查或其他证据切断路径，记录为反证。尚未验证的候选继续留在台账。

## 三种结论保留了不同的知识状态

官方报告模型为 `confirmed`、`needs_validation` 和 `rejected` 定义了不同字段。三者之间的区别，直接决定接手人员需要做什么。

| 结论 | 依据 | 下一步工作 |
|---|---|---|
| `confirmed` | 当前源码路径与独立验证者在指定环境、输入和权限下取得的观察相互支持 | 根据根因修复，并检查正常行为和边界回归 |
| `needs_validation` | 源码支持疑点，但决定性事实尚未取得 | 取得明确列出的材料或观察，再重新判定 |
| `rejected` | 当前源码或证据切断了候选声称的路径 | 保存反证理由，避免反复处理同一误报 |

已确认记录保存 intended behavior、root cause、trace、evidence、conditions、execution、remediation，以及与证据相称的严重性和置信度。这里既要说明本来允许谁做什么，也要说明实际哪条路径违背了这个规则。

未决记录采用 claimed root cause、blockers 和 validation plan，不携带已确认记录的严重等级。这样，缺少部署身份材料的疑点不会仅凭措辞进入高危修复队列。验证计划应明确需要系统所有者核对的事实，接手者才能知道怎样结束这项工作。

已反证记录也保留原先声称的根因、路径与 reason。它记录的是某条攻击解释为何不成立，不能被扩张为整个产品安全。

三种结论用 `fingerprint` 关联同一个源码根因。它与按固定维度编码的 `coverage_id` 不同：报告 Schema 只约束其非空、字符形式与跨状态稳定的要求，没有从源码自动算出语义相同根因的算法。主 Agent 合并候选时依据根因保持标识，验证者若认为确实是另一个根因，才提出更换；最终报告每个标识只留一条记录。

文件移动后，需要重新核对控制与路径是否仍对应同一根因，再延续标识；只改描述而没有改变根因，不应重建记录。稳定身份在这里依赖调查者的源码判断和流程核对，格式脚本负责发现重复或结构错误。

## 验证的权限由环境控制

安全审计需要执行代码时，审计对象也会成为执行环境的攻击面。构建脚本、测试、文档夹具和浏览器内容，都可能由目标仓库控制。仅在提示词里要求“安全运行”无法限制这些进程。

官方方法把执行前提放在操作系统沙箱：禁外网，使用白名单环境变量，目标与工具链只读，只允许指定 scratch 目录写入，并限制 CPU、内存、进程数、文件大小、磁盘和运行时间。需要本地客户端与服务交互时，网络也限制在隔离回环命名空间。

这些条件决定证据取得方式。缺少必要控制时，验证停在源码与现有材料，把缺失能力记为阻塞；不能为了生成一个 confirmed 而在共享环境里试探目标。验证只做支持当前判断所需的最小动作，不把局部观察扩展为持续利用。

还有一处容易忽视的边界：目标程序写出的结果文件也不天然可信。官方流程让验证者写入临时区域，再由可信主流程按照预先允许的路径、文件类型和体积限制提升最小证据。源目录、目标目录的路径穿越和符号链接检查，都属于这条取证路径的一部分。

因此，审计环境保护的不只是被审系统，也保护证据仓库本身。让目标代码直接写入最终报告目录，会使待验证对象获得修改验证依据的机会。

## 机器可读报告检查记录，证据检查结论

`report-schema.json` 将 trace 明确拆成 entrypoint、propagation 与 sink，要求文件、正行号、范围和解释。evidence 指向可复核材料；conditions 说明结论生效条件；execution 记录决定性观察的取得方式。结构化记录使下一位工程师能够从结论返回源码和材料。

配套验证脚本检查记录格式及其证据引用。漏洞是否成立，仍由前面的源码追踪与候选验证判断；脚本让接手者找到这些依据。

交付前还要复核记录是否忠实表达了已经形成的结论。受影响身份写错、运行观察被夸大，或生效条件丢失，都可能使正确调查导向错误修复；这一步检查调查结果怎样被写进报告。

对采用者而言，评估这类工具应先看可行动结果：覆盖记录是否能定位未查边界，确认项能否追到当前源码与最小观察，未决项是否有可结束的验证计划，被反证的问题是否保留原因。候选总量只说明发现工作产生了多少输入。

适合交给 AI 扩大的，是源码搜索与解释空间；需要流程保住的，是每条判断的来源、权限和变化。只有这些材料能够被接手者重新检查，AI 审计才能进入真实的修复、回归和风险接受流程。
