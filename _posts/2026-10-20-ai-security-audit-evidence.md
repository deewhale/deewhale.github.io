模型在审计结果里写下“路径穿越，高危”。负责修复的工程师接下来仍要确认：哪个身份能调用哪个入口，用户输入经过哪些检查，最终读到了哪份原本无权访问的文件。

如果这些问题没有答案，发现数量再多，也难以转化成修复顺序。AI 审计的交付物需要包含一条从源码到观测的证据链，同时说明审过哪些边界、哪里还没有足够条件下结论。模型负责发现和分析，确定性程序与隔离验证负责检查其中一部分，部署事实还需要从系统本身取得。

Cloudflare 开源的 security-audit-skill 提供了一种组织方法：先建立覆盖范围，再搜寻候选，交给独立角色反证，最后生成结构化记录和报告。理解它的价值，可以沿一个文件下载疑点，看证据怎样改变判定。

下文的下载函数、虚拟文件和审计记录是一组教学示例，用来说明候选问题怎样经过验证形成结论。

## 覆盖记录先定义“找过哪里”

假设应用提供租户文档下载。处理逻辑接收租户名和相对文件名，从该租户目录中寻找文件。应保持的安全条件可以写成一句话：当前身份只能取得其获准租户目录内的文件。

审查不能只搜索 `../` 或统计读了多少个文件。这个条件涉及入口、身份、路径处理及读取操作。文件名可能先经过路由解码，租户可能来自登录会话，也可能来自未经验证的请求参数，路径检查可能发生在另一层。需要把相关代码组织成一条可追踪的路径。

Cloudflare 的侦察材料将入口、信任边界、子系统和适用攻击类别组合成覆盖单元。对下载功能，一个单元可以是“外部用户进入下载路由，跨过租户文件访问边界，检查路径与身份约束”。覆盖的对象是这组关系，代码文件是寻找关系的材料。

台账可以把这个单元记成已检查、待检查、因缺少材料而阻塞，或者范围外。范围外项仍值得留下：它说明没有把某个部分纳入结论。假如存储层属于另一套服务，而本次没有其源码，那么“下载入口已读完”不能扩展成“文件访问链路已审完”。

| 台账内容 | 对下载例子的具体含义 |
|---|---|
| 入口 | 下载路由，接收文件名和租户信息 |
| 信任边界 | 用户可控输入进入文件定位逻辑 |
| 需追踪对象 | 当前身份、租户目录、规范化路径、最终读取目标 |
| 检查结果 | 有效约束、候选缺陷或决定性阻塞 |
| 未覆盖部分 | 未取得的外部存储或部署路由配置 |

这份表不能直接转换成安全覆盖百分比。一个入口是否检查充分，与它占源码行数多少没有简单比例关系。台账的作用是让下一位审计者知道结论适用的范围，并能找到还没有完成的工作。

重新审查也应绑定源码版本。旧报告可以提供线索，但源码改变、入口重构或未决条件仍存在时，需要重新核对。继承一个“检查过”的标记，不能代替检查标记所指向的实现。

## 候选的工作是提出可被推翻的解释

假设发现者看到如下逻辑：先拼接租户根目录与文件名，再读取结果。它可以提出一个候选解释：“相对路径能跳出指定租户目录，读取其他位置的文件。”

发现者应写清推断所依赖的对象：文件名是否可控，拼接后是否规范化，最终是否检查目录包含关系，以及读取发生在哪个权限下。只列出危险函数名，验证者还不能知道要反证什么。

验证阶段有三类可能改变结论的事实。第一，输入可能在上游已经被严格限制。第二，下游读取程序可能再次检查真实目标。第三，可疑代码可能只用于受信任的内部数据，攻击者根本无法进入这条路径。每种事实都对应一个需要查找的源码位置或运行条件。

Cloudflare 的标准流程让未参与发现的角色重新读取当前源码，并尝试推翻候选。它不应只是把发现者的措辞变得更流畅，而要主动寻找先前遗漏的限制。发现者提出的路径越具体，反证越容易落到决定性事实。

独立角色并不等于两次结论在统计上独立。若双方使用相同模型、同一份错误摘要或同样误读的平台语义，仍然可能一致犯错。真正需要保留的是反证过程：查了哪条约束、怎样判断它生效，以及哪里仍有未知条件。

## 用虚拟文件检查路径边界

为让这条关系可以复算，构造一个纯内存文件表。目录和内容都不存在于实际文件系统中，`DUMMY_INTERNAL` 是虚构标记。下面程序只做字符串路径规范化与字典查询：

```python
import posixpath

FILES = {
    "/docs/acme/report.txt": "PUBLIC",
    "/docs/internal/note.txt": "DUMMY_INTERNAL",
}


def target(tenant, name):
    return posixpath.normpath(f"/docs/{tenant}/{name}")


def unsafe_download(tenant, name):
    return FILES.get(target(tenant, name), "MISSING")


def guarded_download(tenant, name):
    root = posixpath.normpath(f"/docs/{tenant}")
    path = target(tenant, name)
    if posixpath.commonpath([root, path]) != root:
        return "DENIED"
    return FILES.get(path, "MISSING")


assert unsafe_download("acme", "report.txt") == "PUBLIC"
assert unsafe_download("acme", "../internal/note.txt") == "DUMMY_INTERNAL"
assert guarded_download("acme", "../internal/note.txt") == "DENIED"
```

程序已按这一思路离线执行：正常请求返回 `PUBLIC`，不受约束的版本返回虚构内部标记，增加目录边界检查的版本拒绝越界请求。

这组观察支持的是教学程序里的具体结论：单纯拼接并规范化不会自动保持租户目录约束，而这里的目录包含检查阻止了给定越界输入。真实文件访问还需根据系统处理符号链接、真实路径与检查执行之间的变化，并把租户目录绑定到经过验证的身份。

正常路径同样要检查。若只测越界输入被拒绝，修复版本完全禁止所有下载也会看起来成功。这里保留公开报告返回值，是为了同时观察正常功能与边界。更完整的回归集应来自真实业务允许的文件名和目录规则，而不是无限增加随机字符串。

## 三种判定对应三种后续动作

Cloudflare 的材料将验证后的结果区分为 `confirmed`、`needs_validation` 和 `rejected`。这些状态要求的证据与交接方式不同。

`confirmed` 需要完整源码路径与有界观测。观测可使用目标适用的库调用、文件夹具或渲染后的策略，并不等同于对真实部署完成利用。应用到虚拟程序，可以确认输入进入 `target`，路径跨到 `internal`，随后字典返回内部标记。结论范围限定在这段程序及给定输入，修复对象是缺少目录边界检查的读取路径。

`needs_validation` 表示决定性条件尚未取得。例如，源码中的下载函数存在越界行为，但未拿到部署路由及身份校验逻辑，无法判断外部用户能否到达。应记录具体阻塞：“下载路由是否把未经约束的文件名传入该函数”，并给出取得哪份代码或哪项观测后可以继续。材料要求这类未决项不附已确认严重等级。

`rejected` 要留下反证理由。若当前实现先把规范化后的读取目标限定在租户目录，再执行读取，而候选此前忽略了这项检查，那么给定攻击解释已被推翻。反证针对的是当前源码与这条候选路径，不意味着整个下载系统不存在其他缺陷。

| 判定 | 下载例子中的依据 | 合理交接 |
|---|---|---|
| 已确认 | 完整调用路径与越界返回观测一致 | 修复边界并添加正常、失败回归 |
| 待验证 | 本地逻辑可疑，缺少入口可达性事实 | 精确列出阻塞及下一项验证 |
| 已反证 | 有效约束切断此前声称的路径 | 保留反证理由，结束这条候选 |

未经独立验证的候选继续留在候选台账中，不应自动成为最终发现。否则，报告使用者很难区分“值得检查”与“已有足够依据修复”。

## 结构化报告负责可交接性

完整报告需要记录候选对应的入口、源码位置、触发条件、执行观察和证据引用。Cloudflare 的 schema 对已确认和未决记录使用不同字段：已确认项要求轨迹、证据、条件及执行信息；未决项需要被声称的根因和阻塞。

结构化校验能发现记录缺字段、状态与内容不一致，或者未决项混入不应有的已确认属性。但程序接受一份 JSON，不会自动证明其中写的源码路径真实存在，或某个输入确实能产生声称的结果。验证器需要分清自己检查的是格式、引用关系，还是实际执行。

可以把一条简化交接记录理解为以下四句话：

```text
对象：下载函数中的租户目录边界。
观察：给定越界文件名，不受约束版本返回虚构内部标记。
条件：只验证内存教学程序，未验证真实部署入口。
下一步：对真实实现核对身份、路径解析与最终读取目标。
```

这不是官方 schema 的完整实例，而是说明每项字段应该提供什么信息。公开报告的关键证据也应能够让读者理解，不依靠审计会话里某次没有保存的模型判断。

标准流程在候选验证后，还有结构化记录与独立记录复核，再生成最终报告。所查 `quick` profile 会合并候选与记录复核环节；不能把较完整流程的两次分工描述为所有模式必有的保证。选择模式时，应明确自己减少的是哪项检查及其成本。

## 验证环境决定可以执行到哪一步

审计对象中的构建脚本和测试同样是目标控制的代码。验证者为了复现问题而运行它们，可能先把自己的执行环境交给目标程序。Cloudflare 材料要求在操作系统层隔离环境中执行，禁外网、清理环境、限制资源，并约束可写位置；相关控制缺失时不执行目标代码。

这些要求解释了审计与普通读源码的边界。阅读可以定位候选，运行可以增加观测，但运行权限不能由待审仓库的说明决定。所需隔离条件无法建立时，应交付一个具体的待验证项，而不是虚构执行结果或把源码猜测改写成已确认。

本文的示例选择纯内存程序，避免把机制解释扩展为真实目标审计。它证明了路径边界与三种判定怎样对应，没有验证 Cloudflare Skill 的全流程、模型发现能力或真实漏洞准确率。采用这个工具时，仍要对目标范围、源码版本和执行条件作自己的记录。

预算也应沿证据链分配。若候选已经很多，继续生成更多标题往往不能帮助工程师决定先修哪项。可以先完成关键边界的可达性分析与候选反证，再扩展覆盖；这是一项以可行动结果为目标的工作选择，不能据此声称固定的效率提升。

对于源码齐全、能提供受控验证环境的项目，这种流程适合作为审计辅助。对于依赖部署身份、外部服务配置或复杂运行状态才能判断的问题，应把未取得的决定性事实写清，并配合专业审计和动态测试。最终可采用的报告，应让另一位工程师知道该修哪里、依据是什么，以及哪项结论还需要什么事实。
