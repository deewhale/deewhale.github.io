一个 Coding Agent 交来三层修改：先定义带币种的金额类型，再写旧接口的适配器，最后改调用方。把三层都放进一个 PR，审查者得同时理解类型设计、兼容规则与业务行为。拆成三个 PR 后，如果比较基线都指向 `main`，后两个 PR 又会重复展示前面的修改。

PR 数量变多，审查单元仍然没有分开。这里缺少的是代码依赖与比较基线之间的对应关系。

**Stacked PR 把有顺序的改动组织成依赖链，让每层审查自己的增量。** 底层接受修改后，这条链还需要重新排列、重新检查，并按依赖顺序进入主干。AI 加快了候选代码的生成，这些关系因此更值得显式管理；审查者仍然要判断每一层承担的行为变化。

下面以三层金额接口迁移的假设案例，解释 Git 的比较和重排，以及它们怎样接入 GitHub 的审查与合并。

## 每层的比较基线决定读者看到什么

假设旧接口只返回整数 `100`，新接口返回 `{"amount":100,"currency":"USD"}`。迁移需要三个有依赖的增量：

| 分支 | 本层改变 | PR 比较基线 | 本层应回答的问题 |
|---|---|---|---|
| `types` | 引入金额结构与币种定义 | `main` | 类型能否表达需要的金额，边界如何检查 |
| `adapter` | 把旧整数输入转换成新结构 | `types` | 兼容路径的默认币种与转换是否正确 |
| `client` | 调用方改用适配器 | `adapter` | 返回的新结构能否被业务正确使用 |

三条分支依次包含前一条的提交。调用方能编译，依赖于类型和适配器已经存在；这也是分层依据。按改动行数切成三份，却让每份同时涉及全部职责，仍会把审查者的理解成本留在原处。

Git 的三点比较 `git diff A...B` 从双方的共同祖先到 B 展示变化。在这条简单依赖链中，`main...client` 展示完整迁移；`adapter...client` 只展示调用方这一层。PR 选择正确的 base，才能让审查者先接受下面的前提，再专注本层新增的决定。

![main 之后依次为类型、适配器和调用方三个 PR，每层指向下一层的比较基线](/assets/images/posts/stacked-pr-review-flow-mechanism.png)

图中的箭头表示代码和审查的依赖。上层引用下层分支作为基线，并不会把下层尚未确认的设计变成既定事实。审查者可以提前阅读调用方，也可以因为底层接口尚在变化而暂缓批准。

GitHub 的 `gh-stack` 将这种顺序记录为 stack，并在提交 PR 时为各分支设置相邻层的 base。官方扩展要求 GitHub CLI 2.0 及以上、Git 2.36 及以上。准备好远程仓库与 GitHub 身份后，可以通过 `gh extension install github/gh-stack` 安装扩展。

对于已经按顺序建立的三条分支，入口如下。命令用法来自官方 README：

```bash
gh stack init --base main types adapter client
gh stack push
gh stack view
gh stack submit
```

`init` 按给定顺序登记分支，以 `main` 为主干；存在的分支会被采用，缺失的分支会被创建。因此先确认拼写与分支历史，避免把误输名称建成新层。`push` 推送分支，`view` 检查 stack 关系，`submit` 才为每层创建并关联 PR。工具保存的本地 stack 元数据也不能替代远程 PR 的审批与检查状态。

这一区分在多人或多个 Agent 同时工作时尤其直接：一方更新了远程 PR，另一方持有的本地记录可能仍然描述旧链。操作之前需要确认分支、父层和远程状态，而不能仅凭 PR 编号推断当前依赖。

## 下层修改会改变上层增量的落点

第一次审查发现默认币种应当是 CNY。类型层从 USD 改成 CNY，而适配器层曾把同一处定义改成 EUR。此时，`adapter` 还基于旧的 `types` 提交，`client` 又基于旧的 `adapter` 提交。

目标是保留适配器自己的增量，把它移到新的类型层上；随后保留调用方自己的增量，把它移到新的适配器上。这个操作需要知道旧父层停在哪里。

可以把最初的关系写成：

```text
main — T0 — A0 — C0
       types adapter client
```

类型层审查修改后，`types` 指向 T1，A0 和 C0 仍在旧路径上。重排后的目标是：

```text
main — T0 — T1 — A1 — C1
             types adapter client
```

A1、C1 是原有增量在新父层上的重新应用结果，提交标识通常会变化。它们还可能因为解决冲突而拥有新的内容。

Git 的 `rebase --onto` 可以明确表达这三个对象：新父层、旧父层、需要移动的子分支。在修改底层前保存旧边界，随后从下往上重排：

```bash
old_types=$(git rev-parse types)
old_adapter=$(git rev-parse adapter)
# 在 types 上完成审查修改并提交后：
git rebase --onto types "$old_types" adapter
# 处理 adapter 冲突并确认业务内容后：
git rebase --onto adapter "$old_adapter" client
```

这里保存的是提交标识。重排之后分支名会移动，若再把移动后的分支名当旧边界，选中的提交范围就可能变掉。工具替用户管理这些边界的价值，在于减少重复操作和漏层；审查者仍需要理解它正在移动哪一组增量。

如果上一层通过 squash 进入主干，主干中的提交身份还可能不同于原分支。过期的父层记录会让后续重放混入已经合并的祖先。社区对早期工具版本有此类报告，但不能由旧版本报告推断当前版本必然复现。实际排查应检查合并方式、原父提交与新主干，而不是反复执行同一个重排命令。

## 冲突解决还要检查业务假设

类型层与适配器层同时修改币种定义，Git 可以报告文本冲突。但类型层改了字段含义，适配器的某段代码刚好位于别的文件时，Git 可能顺利应用全部提交。两种情况都需要重新理解适配器的输入和输出。

例如，最终类型定义已经接受 CNY，适配器却仍然返回：

```python
def adapt(n):
    return {"amount": n, "currency": "EUR"}
```

只消除类型定义文件里的冲突标记，不能消除这个不一致。重排成功意味着提交已经落到新位置；它没有证明 EUR 是正确默认值。修正应当同时覆盖定义和转换逻辑：

```python
def adapt(n):
    return {"amount": n, "currency": "CNY"}
```

随后，调用方的检查也要以新的组合运行。这个例子的最小调用是：

```python
from adapter import adapt

result = adapt(100)
assert result == {"amount": 100, "currency": "CNY"}
```

实际离线验证先构造了 `main → types → adapter → client` 四条分支。完整比较显示 `schema.txt`、`adapter.py`、`client.py` 三个文件，顶层与相邻父层比较只显示 `client.py`。在底层修改币种后，重排确实产生冲突；解决文本冲突、调整适配器并继续重排，调用方最终输出 CNY，祖先关系也恢复为类型层、适配层、调用层的顺序。

这个结果支持两件事：比较基线能缩小本层展示范围；沿旧父边界重排可以把增量移到新位置。GitHub 是否保留审批、CI 是否通过、仓库是否允许合并，需要在远程系统分别检查。

检查对象也应沿层次变化。类型层验证字段与约束，适配层验证兼容路径，调用层验证组合行为。如果只有每层自己的测试，却没有最终组合检查，下面的语义变化仍可能从缝隙中穿过。

## 审批与测试绑定的是不同事实

Stack 重排经常只改变提交身份，内容差异可能保持不变。GitHub 的 2026 年 10 月 GA 说明中，未改变差异的 rebase 可以保留审批。这个条件有助于减少纯历史调整造成的重复批准。

审批保留需要放回它所能说明的范围：审查者曾接受这份差异。底层即使改变了行为，上层的文本差异仍可能相同。调用方原来在 USD 环境下接受的逻辑，放进 CNY 环境后是否仍满足业务要求，要根据依赖变化判断。

因此可以把一次底层反馈分成三个问题：

| 变化 | 可以沿用什么 | 需要检查什么 |
|---|---|---|
| 只调整历史，层内差异与依赖行为均未改变 | 已有审查结论可能仍适用 | 当前 PR、检查状态与仓库规则 |
| 层内差异改变 | 尚未涉及变化处的解释 | 新差异的代码审查与相关测试 |
| 层内文本相同，但父层语义改变 | 这层代码原有意图 | 对父层假设、组合测试与业务结果 |

这里的判断不能完全交给“文件是否变化”。一个函数仍叫 `adapt`，它返回的数据单位或默认值已经变化，上层使用方式就需要复核。反过来，只因提交 SHA 改变就要求重读所有未变代码，也会消耗本来希望节省的审查时间。

合理的审查说明应该标出下层反馈改变了哪项前提，以及上层据此重新检查了什么。比如“默认币种改为 CNY，适配器和调用方组合测试已改用 CNY”，比“已 rebase，全部正常”更能帮助下一位审查者定位变化。

## 合并顺序把局部审查接到主干

上层 PR 单独通过，不意味着它可以先进入主干。GitHub 的 stacked merge 路径要求从最低的未合并层开始，选择连续的一段；相关下层审批、检查以及主干保护条件都要满足。

例如，类型层和适配层已经完成，调用方还需调整，可以先合并前两层。上方剩余层随后需要以更新后的基线继续工作。若只尝试合并调用方而跳过尚未落地的类型层，主干就缺少它依赖的定义。

启用合并队列的仓库还要考虑整组进入队列后的变化。官方说明把 stack 组织为一个 merge group；其中一层被移出队列，上方依赖也会受影响。队列能组织检查与依赖，不能把业务发布、数据库迁移或外部服务切换变成自动原子操作。

金额迁移即使代码通过，也可能需要兼容仍在运行的旧客户端。这属于应用发布设计。Stack 可以清楚展示“先提供新结构、再兼容转换、最后迁移使用方”的代码依赖，但是否允许逐层上线，仍由每层的兼容行为决定。

GitHub 的发布说明与当前文档对部分自动合并能力存在推出时点差异。采用流程可以先依赖明确的审查、检查和手动提交合并路径；若团队要依赖自动合并，再核实账户与仓库当前支持。把尚未验证的自动化行为当采用前提，会让整个工作方式依赖一个可能未开放的分支。

## 让 Agent 提交可解释的一层

最适合开始试点的改动，是依赖顺序稳定、每层都有独立验收对象的迁移。给 Agent 的任务可以限定为：“这一层只引入金额类型；说明字段约束并提供测试，暂不修改调用方。”下一层再以这个结果作为明确输入。

这种分工减少审查者同时持有的假设，也让反馈更容易定位：类型设计有误时修改底层，兼容规则有误时修改中间层，业务使用有误时修改顶层。Agent 每次更新下层时，应同步说明受影响的后续层，而不是把所有上层冲突留给合并时处理。

能直接进入主干且彼此独立的两项修改，更适合各自开 PR。一个尚在频繁改写的接口，也不宜急着叠上许多调用方：底层一次变化就要沿链传播，层数增加会放大维护成本。先收敛共同前提，再拆有意义的增量，审查才有稳定对象。

是否采用 stack，可以落在一次具体检查上：每层能否用一句话解释新增行为，能否指出它依赖的父层，底层变化后能否重新验证最终组合。满足这些条件，再交给工具维护提交和 PR 关系；无法说明这些关系时，继续增加 PR 数量也难以形成清楚的审查路径。
