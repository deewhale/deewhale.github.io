Agent 的工具接口要把自然语言中的意图转换成应用能够执行和检查的动作。只读查询与资金写入的差别在这里尤其明显：退款除了需要正确参数，还要维持客户身份、授权、重试与最终状态之间的关系。

Stripe 的 Refunds API 提供了一个具体参照。它以原 Charge 或 PaymentIntent 创建退款，允许在可退额度内多次部分退款，返回独立的 Refund 对象，并提供查询。API v1 的幂等机制再为请求重试提供身份。把这组接口封装给 Agent，需要保留这些业务关系，不能只给模型一个 `refund(order_id, amount) → success`。

下面讨论的是基于这些公开接口的工具设计，重点是哪些决定应留在可信应用，哪些材料应交给模型，以及工具返回以后系统能够确认什么。

## 先建立退款对象与业务权限的关系

原支付与退款是两个有关联但独立的对象。原支付限定退款来源和可退范围，一笔支付可以对应多笔部分退款，每笔退款有自己的标识和后续状态。工具若只保留订单号与成功布尔值，会丢掉这项操作的可查询身份。

应用中通常还存在订单、租户、客户与客服权限。它们与 Stripe 对象之间的映射由业务系统维护。模型可以帮助理解退款诉求、整理原因；订单归属与可退额度则通过当前身份和支付记录取得。

因此，提供给模型的参数应从它真正需要决定的部分开始。应用已经知道当前订单和原支付时，可以在工具实现中绑定这些对象；确实需要用户选择时，再提供经过授权的候选。OpenAI 的 function calling 指南同样用已知订单 ID 的退款举例，建议把应用已掌握的参数交给代码处理。

金额用最小货币单位等明确表示，币种从原支付关系中校核；服务端在真正提交时重新核对权限与剩余可退额度。输入 Schema 可以要求字段、类型和范围，授权判断则需要结合当前用户和业务状态。

## 把评估、提交和查询分成可解释的动作

基于 Stripe 的创建与查询接口，可以在应用层分别提供退款评估、提交和状态查询。评估决定能否提交，提交产生退款对象，查询跟踪后续状态；这是一种应用层拆分方式。

评估入口读取当前支付和业务规则，返回是否可申请、金额依据及是否需要人工批准。它可以让 Agent 向用户解释条件，尚不产生退款。提交入口接受应用保存的意图与审批引用，重验条件后创建退款，保留返回的退款 ID。查询入口按该身份读取权威状态。

可以把这个拆分落实为两份应用记录。退款意图保存当前租户、订单与原支付的关联、最小货币单位金额、币种、参数版本和幂等键；审批记录引用这份意图及其参数版本，记录批准主体和批准范围。它们是封装层的设计，Stripe 接收的仍是原支付、金额等创建退款参数。

提交工具只接收意图引用和审批引用。服务端先用当前登录身份查找本租户意图，再检查审批是否指向同一版本、是否覆盖该金额；随后从支付系统重新检查原支付和可退额度。通过以后，用意图中保存的参数及幂等键创建 Refund，将返回的 ID 关联回该意图。金额需要调整时先产生新参数版本并重新取得所需批准，避免沿用旧批准偷偷扩大操作。

这也说明为何审批和幂等分别存在：审批限制可以尝试的操作，幂等键识别网络上重复传输的同一请求。两个并发的不同退款意图仍可能竞争剩余额度，最终创建是否接受还要以支付端的判断为准。

| 入口 | 可信程序负责什么 | 模型可以利用什么 |
|---|---|---|
| 评估 | 身份、归属、额度和规则检查 | 条件、原因与下一步要求 |
| 提交 | 审批范围、参数、幂等身份和外部调用 | 已受理或拒绝的具体结果 |
| 查询 | 找到同一 Refund，读取状态与更新时间 | 按当前证据解释处理进度 |

这组职责允许分别设置权限。只读 Agent 可以评估并准备材料，有提交权限的执行器才调用资金接口。人工批准绑定具体对象和金额，不能只是一条供模型引用的“已同意”。审批以后余额或权限变化，提交仍需要重新检查。

工具描述也应采用这个尺度。一个只能提交申请的工具，返回“渠道已接受申请”即可；若名称和文案声称完成，就需要能够读取相应完成依据。较少的工具数量可以减少选择负担，合并到一个入口以后仍必须保留这些状态差异。

## 重试需要固定业务身份

Stripe API v1 接受幂等键，在端点开始执行后保存首个请求的状态码与响应体，同键重试返回已保存结果，包括错误响应。参数不一致会被拒绝；键的保留也有范围，文档允许至少 24 小时后移除旧键，再次使用已清理键会成为新请求。

这组语义决定了封装方法。应用在发出写请求以前，先保存一次退款意图及对应幂等键；因连接问题重试时，复用同一身份和参数。模型工具调用的 `call_id` 只关联一轮调用与返回，一次重试可能产生新 `call_id`，不能把它直接当成业务去重身份。

如果每次超时都重新生成键，即使参数相同，也会被当作不同请求。反过来，也不能把同一个键用于金额已经改变的新意图。应用应把意图、原支付、金额和参数版本保存在一起，重试前检查它们是否仍然对应。

依 Stripe API v1 的规则，记已保存的键为 K、固定退款参数为 P，可以比较以下请求怎样被识别：

| 发出的请求 | 提供方怎样识别 | 应用怎样处理 |
|---|---|---|
| K + P，首次已开始执行 | 保存这次请求的状态码和响应体 | 将返回对象与意图关联 |
| K + P，再次发送 | 在键仍保留时返回首个已保存响应，包含相应错误响应 | 接续同一操作；取得 Refund ID 时查询状态，错误响应按其类别处理 |
| K + 改过金额的参数 | 与原参数不一致，拒绝复用 | 新金额先走新的意图与审批 |
| 新键 + P | 作为另一次请求处理 | 仅在确实需要另一笔退款时使用，仍受可退额度限制 |

参数校验失败或与并发请求冲突、尚未开始端点执行时，Stripe 不保存这一幂等结果；这类请求允许按规则重试。应用记录因此同时保存传输情况与实际返回，不能仅用“曾发出K”判断提供方已有结果。

MCP 的 `idempotentHint` 只描述服务对工具行为的提示。它不会替支付后端保存幂等记录，也不会扩大提供方键的保留时间。Agent 看到提示以后可以减少某些不必要询问，真实重复执行的控制仍在应用与目标 API。

长时间中断以后，恢复策略要结合键的保留和外部记录。不能在原键可能失效时无限自动重发，也不能因为没收到响应就认定退款未发生。

## 超时与失败需要不同处理

写请求有一个典型的不确定窗口：外部系统已经接收，响应没有抵达调用方。本方此时知道“请求发出”，却不知道它是否执行。网络超时描述传输观察，不等于退款失败。

应用能够找回退款 ID 时，应查询同一 Refund；尚未得到 ID 时，可以在所支持的幂等重试范围内按同一请求取得原结果。操作记录要保留参数、时间、键与可用的外部引用，供后续核对。若现有查询和重试条件仍不足以确认，就保留结果未知并进入受控查证。

恢复时，本方意图用来找回参数和幂等键，Refund ID 用来查询提供方状态。将两份记录关联后，接管者才能决定继续等待、处理失败还是查证未知结果。

这些检查可以落实在工具结果结构中：操作身份、提供方状态、观察时间、错误类别和允许的下一步。模型据此组织解释，界面上的资金状态最好由程序消费这些字段生成，避免让自然语言覆盖结果未知。

## 完成语义要跟随提供方状态

Stripe Refund 有 `pending`、`requires_action`、`succeeded`、`failed`、`canceled` 等状态。创建请求得到正常响应，不意味着每次都直接进入成功；读取状态也要保留后续处理的可能性。状态名应按实际接入版本映射，而不是把所有非错误响应压成成功。

| 观察对象 | 可以支持的判断 |
|---|---|
| HTTP 或工具调用正常返回 | 这次接口交互产生了可处理结果 |
| 得到 Refund ID 与提供方状态 | 已定位到具体退款，能够继续查询 |
| 提供方仍为处理中或要求进一步操作 | 继续处理相应步骤，不能报告终结 |
| 提供方确认成功 | 报告 Stripe Refund 状态为成功；客户银行的显示仍需对应记录确认 |
| 客户银行显示、商户账务核对 | 由对应系统记录分别确认 |

MCP 的 `isError` 为假，说明没有按该字段报告工具执行错误；模型函数调用格式正确，说明输入满足相应结构要求。它们都不负责定义资金何时到达客户银行。退款通知应准确表达当前已确认的范围，并保留可回查标识。

若产品还要求商户账务完成核对才能结束工单，应该把它作为独立完成条件。退款对象、账务核对和客服工单可以关联，但不应仅因为其中一个 API 返回就同步标为完成。

## 用外部状态检验工具设计

退款工具的评测应覆盖正常流程与会改变处理决定的反例：订单不属于当前用户，额度在评估后减少，审批金额不足，权限被撤销，提交响应丢失，以及重复传输。每次既检查工具轨迹，也核对测试环境中的支付与退款对象。

Anthropic 的 Agent 评测方法区分 transcript 与 outcome：前者记录模型、工具的交互，后者是运行后环境里的状态。对这类写工具，“模型说已经退款”属于交互；只有一笔授权正确、金额正确且没有重复的退款对象，才是相应结果依据。评测不应只搜索回答中的“成功”。

采用工具接口的程度应跟随后端能力。能够稳定检查归属与余额时，可以先开放评估；具备审批绑定、持久意图与真实幂等处理后，再开放提交；提供可回查的状态以后，才能让 Agent 持续解释进度。每一步都扩大了可承担的工作，也增加了必须由模型外程序维护的事实。
