![一张发票依次经过结构、业务与来源证据三层检查](/assets/images/posts/structured-output-invoice-validation.jpg)

```json
{
  "invoice_total": 8420,
  "currency": "CNY",
  "purchase_order": "PO-1847"
}
```

这段 JSON 没有解析错误。金额是数字，币种来自允许列表，订单号符合规定格式；必填项齐全，也没有多余属性。假设源发票上的应付金额其实是 8,240 元，采购订单号是 `PO-1842`，抽取服务已经把两个关键值都写错了，应用却仍能顺利反序列化。

如果流水线只检查 JSON Schema，这张发票已经“成功”。如果下游把“成功”理解成可以入账，错误就从模型输出变成了财务事实。

结构化输出确实解决了一个长期存在的接口问题。模型不再随意夹带解释、漏掉括号，或者把数组写成自然语言。但它保证的是某个值可以出现在某个位置，不是这个值确实来自发票上的正确位置，也不是这些字段放在一起构成一笔真实、可接受的交易。

因此，一条可靠的文档抽取管线至少要过三道彼此独立的门：接口合规、业务一致性和源证据绑定。任何一道失败，都不能用另外两道的成功抵消。

## Schema 只控制模型能写出什么

普通 JSON mode 主要防止输出变成不可解析的文本；严格的结构化输出再向前一步，让结果匹配指定的字段、类型、枚举和嵌套关系。常见实现会在生成每个 token 时，根据当前已经生成的内容计算下一步仍然合法的 token，并把其余候选屏蔽掉。OpenAI 公开的实现把 Schema 转成上下文无关文法；XGrammar 则展示了另一套文法执行与缓存优化方法。

这类约束很重要。它把“模型有没有正确闭合 JSON”“字段名是不是约定值”从概率问题变成了接口层可以强制执行的问题。应用不必再靠正则修补括号，也不该在解析失败后悄悄猜测模型原意。

但约束解码只会问：`invoice_total` 后面能不能出现一个数字。8,240 和 8,420 都是合法数字，解码器没有理由屏蔽后者。`PO-1847` 也完全可能匹配订单号的正则。OpenAI 的官方说明明确保留了这条边界：结构化输出仍可能把 JSON 对象里的值写错；拒答、输出被截断和只支持部分 JSON Schema 关键字，也需要由调用方单独处理。

2026 年发布的一项结构化输出预印本把这类差异分开测量。在它的测试中，21 个模型几乎都能保持很高的 Schema 合规，但最底层字段值（leaf value）的最佳精确匹配率在文本、OCR 文档和音频上分别只有 83.0%、67.2% 和 23.7%。这些数字不能直接当成发票系统的生产准确率：图像组只有 209 条记录，输入还经过 OCR 和文本归一化，论文也仍处于预印本阶段。它真正有用的地方，是证明“结构对了”和“值对了”必须是两项指标。

接口门的输出因此不应叫 `validated_invoice`。更准确的名字是 `schema_valid_candidate`：一个能够被程序稳定接收、仍等待事实校验的候选。

## 入账需要字段之间互相约束

假设候选里还有以下字段：未税金额 7,292.04 元，增值税额 947.96 元，应付金额却是 8,420 元。每个字段单独看都满足类型、精度和取值范围，放在一起却不成立。把前两项相加即可得到 8,240 元。

成熟的电子发票规范通常把这类关系写成独立业务规则。Peppol BIS Billing 的规则会检查行项目净额合计、单据级折扣与附加费、未税总额、税额、含税总额、预付金额、舍入金额和最终应付金额之间的等式。它还把能够查找相关采购订单、合同或交付记录列为发票验证需要支持的能力。Peppol 面向特定电子发票生态，不是中国企业的法定实现模板；这里值得借用的是规则的形状：字段存在和跨字段成立是两件事。

对开头的候选，业务门至少要做三类确定性检查。

第一类是单据内部不变量。行项目数量乘单价，结合行级折扣和费用，应得到行净额；各行合计经过单据级调整，应得到未税金额；未税金额、税额、预付与舍入再共同决定应付金额。计算要使用十进制定点数和明确的舍入规则，不能把二进制浮点误差当成模型错误。

第二类是代码与格式之外的主数据约束。`PO-1847` 虽然长得像订单号，却可能不存在，可能属于另一家供应商，也可能已经关闭。采购系统应按供应商、法人、币种和订单状态查询，而不是只验证字符串。供应商银行账户发生变化、新供应商首次开票、发票号重复，也都需要由各自的权威系统判断。

第三类是业务时点。订单在模型读取后可能已经关闭，收货数量可能刚被调整，税务或付款状态也会变化。抽取结果必须携带校验时使用的主数据版本或时间；入账前若关键状态已变化，就重新校验，不能拿旧查询结果为新交易作证。

业务规则擅长发现矛盾，却也有明显盲区。如果模型把未税金额、税额和总额一起从错误列读取，三者可能算得严丝合缝；一张伪造发票甚至可以做到内部完全自洽。业务门能证明候选满足已编码的不变量，不能证明它忠实于输入文档。

## 每个关键值都应带着来处

第三道门不是再问模型一句“你确定吗”，而是要求关键字段携带可复核的来源记录。文档解析系统已经能返回这类基础信息：原始文字片段、规范化后的值、页码、文本区间、页面坐标和抽取置信度。Google Document AI 的数据模型就是一个公开实例；它把 `mentionText`、`normalizedValue`、`textAnchor` 和 `pageAnchor` 分开保存。

对发票金额，一条最小记录可以表达为：原文是“¥8,240.00”，规范化值是十进制 `8240.00`，位于第一页“价税合计”右侧区域，并记录产生它的解析器版本。订单号也应保留自己的原文和位置。复核界面据此可以直接高亮模型看到的区域，而不是让财务人员在整张扫描件里重新找一遍。

原始值与规范化值必须分开。把 `2026/10/08` 变成 `2026-10-08` 是可解释的格式归一化；根据供应商知识库补出文档上不存在的地址，则是 enrichment，也就是外部补全。两者都可能有用，却不能共享一个“来自发票”标记。否则，系统会把推断或主数据补全伪装成文档原文。

来源绑定也不自动等于正确。OCR 可能把框画在错误数字上，表格中的邻近关系也可能被误解。它提供的是可定位、可复核和可重新处理的证据接口。真正高风险的字段——应付金额、收款账户、供应商身份、订单号——可以要求同时通过原文锚点、跨字段规则和外部主数据匹配；低风险的备注字段则不必使用同样昂贵的门槛。

置信度也只适合做路由信号。0.97 不是“有 97% 概率正确”的通用承诺，更不能跨字段、文档类型和解析器版本直接比较。团队需要用自己的标注集，分别观察金额、日期、订单号和银行账户在不同阈值下的误放率与人工量，再决定哪里允许自动化。

## 失败原因决定下一步

三道门的意义不只是多做几次校验，而是让失败落到可处理的位置。

| 失败位置 | 典型现象 | 合理动作 |
|---|---|---|
| 接口门 | 拒答、截断、字段缺失、Schema 不兼容 | 不进入业务系统；按明确错误重试或更换兼容 Schema |
| 业务门 | 金额不平、订单不存在、币种冲突、重复发票 | 硬拒绝自动入账；返回具体规则与相关字段 |
| 证据门 | 关键值无原文锚点、多个候选位置、低置信或归一化歧义 | 送字段级人工复核，不要求整张单据从头录入 |
| 风险策略 | 新供应商、收款账户变更、金额超过授权范围 | 即使前三门通过，也进入额外审批或外部验证 |

这里不应让模型自行“修好”所有错误。金额算式失败时，系统可以计算期望值，却不能擅自决定哪一个原字段错了；订单不存在时，也不能生成一个更像真的编号。自动修复只适用于可逆、无歧义的表示转换，例如去掉千位分隔符或把已确认的日期格式规范化，而且仍要保留原值。

人工复核则应以失败字段和证据为单位。界面同时展示候选值、原文高亮、触发的业务规则和相关主数据；复核结果回写为带操作者与时间的更正记录。这样，人处理的是机器无法裁决的差异，而不是替一条没有门禁的流水线兜底。

## 评测要落到入账决定

如果测试集只统计“多少响应能被 JSON parser 读取”，结构化输出会显得近乎完美，生产风险却没有被测到。JSONSchemaBench 已经把约束解码的效率、Schema 关键字覆盖和输出质量分开；业务系统还要继续向下拆。

一套可用于上线决策的评测至少包括：字段级精确匹配，金额等关键字段的加权错误率，业务规则拦截率，错误候选被自动放行的比例，人工复核率，以及复核后仍然错误入账的比例。对“缺失”与“填错”也要分别计数：系统主动留空会增加人工量，凭空补出一个合法值则可能直接污染账务，二者代价不同。

测试样本要保留真实分布中的困难部分：扫描模糊、表格跨页、中英文混排、负数与红字、多个金额区块、历史模板和供应商版式变化。每次更换模型、提示词、OCR、Schema、归一化代码或业务规则，都要用同一组冻结样本回放。评测对象不是单独的模型，而是从文档输入到入账决定的整个版本组合。

自动入账的条件可以写得很朴素：输出结构完整；所有硬业务规则通过；关键字段都有可接受的证据；相关主数据在同一校验时点仍有效；风险策略允许自动处理。缺少任何一项，状态都应保持为 `needs_review` 或 `rejected`，而不是降级成“可能成功”。

回到开头那张发票，Schema 的确完成了自己的工作：它交付了一份机器可读的候选。金额等式会拦下 8,420 元，采购系统会指出 `PO-1847` 不属于这家供应商，原文锚点则让复核人员看到正确的 8,240 元和 `PO-1842`。三道门各自负责一种事实，谁也不替谁作证。

结构化输出把模型接进了软件接口。只有业务不变量和源证据继续把候选接进现实，系统才有资格把 JSON 变成账。
