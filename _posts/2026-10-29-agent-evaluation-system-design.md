Agent 评测体系负责为系统变更提供可复核的质量证据：给定一批任务，让固定版本的 Agent 在确定的条件下运行，保存行为与结果，再据此判断能力、成本和退化。与单轮回答评分相比，Agent 还会检索、调用工具、修改外部状态；评测因此必须同时观察回答和执行。

这项工作的产物不止一个分数。开发者需要知道失败发生在哪里，发布负责人需要知道新版本改变了什么，领域人员需要确认评判标准是否符合实际目标。一套可用体系，要让这几种判断共享同一次执行证据。

monday Service 团队使用已经解决并脱敏的真实 IT 工单建立基础集，先检查运行健康、输出结构、状态持久化和工具调用，再增加检索、政策冲突、调用顺序等专项测试。他们把离线实验接入 CI，也对多轮线上会话评分。这项由 monday.com 团队公开的实践显示，系统每承担一种工作，就需要留下能够判断这项工作是否完成的证据。

答案评分检查回复内容；检索评测还要核对来源；工具评测需要读取环境变化，并确认必要操作发生在获授权之后。系统持续更新版本时，还要重复运行同一任务，观察这些行为是否稳定。评测体系因此逐步增加不同种类的证据，而不是把所有判断都交给一个总分。

LangSmith、Braintrust 等成熟产品，把数据集、实验、执行轨迹、人工复核和线上反馈组织起来，减少了维护这些证据的成本。但平台不能替应用方决定什么叫成功，也不能仅凭一次 experiment 给出可靠发布结论。要判断一套体系是否成立，需要沿着一次任务，从输入和初态一直看到最终结果、评分依据与后续动作。

## 先组织任务、执行、评分与实验四层

评测的第一层是任务资产：输入、初态、成功条件以及禁止行为。第二层是执行器：准备环境，运行指定 Agent，保存消息、工具动作、终态和产物。第三层是评分器：读取这些证据，按规则、模型裁判或人工标准得到分项判断。第四层是实验管理：把同一批任务上的新旧版本逐题比较，保留结论与发布决定。

职责这样分开，是为了让不同修正有不同入口。任务标错，需要修题；环境没有重置，需要修执行器；有效结果被误判，需要修裁判；证据充分而行为失败，才应修改 Agent。若执行、评分与汇总揉成一个不透明调用，这几类错误都可能表现为同一个低分。

这几层需要共享的记录可以按下表组织。这是依据公开基准与产品对象整理的参考设计，各平台的具体字段会不同。

| 记录对象 | 至少固定或保留什么 | 它使哪种判断成为可能 |
| --- | --- | --- |
| 任务版本 | 用户目标、初态、工具与数据定义、成功及禁止条件、任务类别 | 检查测的是不是同一问题 |
| 系统与运行版本 | 模型和参数、执行框架提交、工具实现与权限、索引或记忆快照、模拟用户配置、预算 | 追查分数变化对应哪些系统变化 |
| Trial 证据 | 实际观察、工具参数和结果、终态、原始产物、停止原因、耗时与调用量 | 区分行为失败、运行故障与证据缺失 |
| 评分记录 | 规则、judge 模型与提示版本，评分输入、分项结果和理由，人工修正 | 复核分数，或在修正裁判后重新评分 |

沿图中的记录关系，维护者可以从一次实验的分项结果找到对应 trial，再取得当时的输入、初态、工具动作与产物。评分记录保留采用的规则和材料，便于判断失败来自执行本身，还是对执行结果的判定。下层的线上反馈则为后续数据集补充需要验证的任务。

## 从答案检查到检索诊断，增加的是故障定位能力

只有固定输入和唯一输出时，评测很直接：比较答案，或者检查输出是否符合 schema。分类标签、结构化字段、格式约束，都适合由程序判断。开放文本允许多种正确表达，字面一致性就不够了，需要明确评分标准，判断它有没有回答问题、有没有遗漏必要信息。

检索增强生成（RAG）又增加了一层因果关系。最终答案错误，至少可能有三种来源：没有找回所需材料，找回了但生成阶段没有正确使用，或者忠实复述了本来就错误、过时的材料。一个总分无法区分这些情况，修复动作却完全不同。

《Ragas: Automated Evaluation of Retrieval Augmented Generation》（arXiv 2309.15217v2）把检索上下文、生成忠实性和生成质量分别评估，价值就在这里。检索相关性关注拿回来的证据，忠实性关注回答是否得到这些证据支持，答案质量再看是否满足用户问题。它们可以同时改善，也可能彼此背离：回答完全忠实于上下文，仍可能因为来源已失效而答错。

引用检查也有类似层次。程序可以确认文档 ID 存在、页码有效、引用格式正确；要证明一句结论得到引用支持，还必须比较结论与原文内容。一个引用标记出现了，只说明结构检查通过。对通过树导航或其他检索方式取证的系统，这个区分同样成立。[PageIndex 的检索原理分析](/posts/pageindex-document-retrieval/)说明了结构导航怎样回到原页；这里需要进一步验证的是，取回的原页能否支持当前回答。

monday 的案例把这种分层带进了真实应用。基础检查先排除系统没有运行、结果格式不对、状态未保存等问题；检索与政策专项再追问内容有没有依据、行为是否符合要求。好处是一个样本失败后，可以沿分项证据找原因，不必把所有低分都解释成“模型不够强”。

当工具开始写入外部系统，文本诊断仍然不够。Agent 说“已经处理”，和系统里确实完成处理，是两件需要分别检查的事。

## 工具改变环境后，任务结果需要由执行来证明

公开基准提供了两种清楚的参考。SWE-bench 从真实 GitHub issue 和代码修改构造编程任务，把候选补丁应用到仓库，再执行测试。OpenAI 的《Introducing SWE-bench Verified》（2024-08-13）区分了 `FAIL_TO_PASS` 与 `PASS_TO_PASS`：前者检查目标问题是否由失败变为通过，后者检查原来通过的行为是否仍然通过。

这使“补丁能应用”“问题被修复”“已有行为没有发生已测出的回归”成为三个可观察判断。测试覆盖仍然限制结论的范围，但它已经把验收依据从模型解释转向实际产物及执行结果。

另一个参考是 2024 年的 τ-bench。它研究带工具和政策约束的多轮交互：用户模拟器与 Agent 对话，工具操作环境，任务给出应达到的状态与必要输出。论文 Figure 2 的零售任务包含退货、换货和金额比较，Agent 需要结合政策与用户偏好完成选择。这是研究者构造的公开模拟任务，并非真实客户订单。

这里必须区分四个对象。**任务（task）**定义用户目标、初始环境和成功条件；**一次执行（trial）**是 Agent 从该初态出发完成任务的一次尝试；**轨迹（trace）**记录消息、工具参数和返回等过程；**结果（outcome）**是最终环境状态与交付产物。只拿最终回答评分，会丢掉后两者之间的差异。

在 τ-bench 提交 `59a200c6d575d595120f1cb70fea53cef0632f6b` 中，`tau_bench/run.py::run` 为每个任务的每次 trial 创建独立环境，再调用 Agent 求解。`tau_bench/envs/base.py::Env.reset` 重载数据库、清空操作记录并初始化模拟用户；`step` 将回复交给模拟用户，将工具调用交给对应实现，由工具改变环境。

结束后，`Env.calculate_reward` 取得候选执行的终态，再重载初态，重放标注动作，得到目标终态；随后比较状态哈希，并检查必要的输出内容。标注动作在这里用于构造目标状态，不是要求候选逐步模仿标准轨迹。有效的替代路径，或多做一次无害读取，不应仅因步骤不同而被判错。

这个设计把状态的归属说清了：模型提出动作，工具实现执行动作，环境保存变化，评分器读取证据。模型自己宣告完成，不能替代工具结果和终态验证。政策写进提示词，也不能自动变成不可绕过的程序限制；需要由工具或权限层强制执行的约束，必须检查相应实现。

终态正确仍有盲区。τ-bench 论文第 3 节明确指出，即使状态和输出的奖励达到 `r=1`，Agent 仍可能没有获得用户明确确认就执行操作。状态比较记录了“最后变成什么”，却可能漏掉“在什么授权下发生”。因此，过程检查应该针对必要约束：确认是否发生在写操作之前、禁止调用有没有实际执行。它不意味着把所有路径都锁死成一条参考序列。

这也解释了 monday 团队为何在工具是否调用之外增加调用顺序和政策冲突检查。需要守住的是业务要求允许的行为集合。检查太宽，会漏掉违规；检查过窄，会拒绝本来有效的方案。

截至 2026-10-29，τ-bench 官方已经把旧任务标记为过时，并指向后续仓库中的 τ³ 任务与维护修正。这里借历史论文和固定源码解释机制；选择今天的测试任务时，应核对当前版本，历史分数不能与新版本直接混用。

## 实验可比较，依赖版本固定与环境复位

四层都有了记录，仍需要控制比较条件。上次使用旧知识库，这次使用新索引；上次工具权限更小，这次评分提示也改了。即使分数提高，也无法判断改变来自哪里。

LangSmith 的《Manage datasets》文档提供了基础能力：example 的新增、修改和删除都会产生数据集版本，可以按时间或 tag 读取历史状态，再用于评测。这里解决的是“每次测的题不同”。但名为 `prod` 的 tag 仍可能移动；实验需要留下实际解析出的版本，才能知道当时用了哪批内容。

monday 团队进一步把 Vitest 与 LangSmith experiment 关联，让 CI 中的检查能对应到一组具体运行及逐条结果。这样，代码变更与评测证据可以一起审查，失败也有可回看的位置。实验记录的意义由此超过汇总分：它应当允许维护者找到某个任务当时的输入、调用、结果与评分理由。

其中最容易被低估的是环境。前一个 trial 的写操作、共享缓存或账户状态，如果进入下一个 trial，后者就不再从同一初态开始。一次成功可能依赖前次留下的东西，一次失败也可能是其他并发任务造成的。

Inspect 的《Sandboxing》文档支持按样本配置隔离的文件系统与工具执行环境，同时区分工具调用所在的主进程和真正执行工作的 sandbox。容器本身不会复位远端数据库、共享服务或账户余额。涉及这些状态时，还需要独立测试租户、快照、命名空间，或可审计的模拟环境。模拟环境适合受控比较，其结果只能说明该环境中的行为。

随机种子也只固定可控制的随机源。外部模型服务、工具数据、并发调度仍可能变化。合理目标是保存足够的条件与证据，让结论能够被复核，并能在明确条件下重新执行比较。不能把设置 seed 当成逐字复现的保证。

对于希望采用开放部署路线的团队，Arize Phoenix 的《Datasets》与《Annotations》文档展示了另一套实际对象：带版本的 example、独立的 experiment，以及 span 或 document 上的标注。线上片段可以经过标注进入数据集，文档级标注还可以定位单条检索证据的问题。选择这条路线时要区分 Phoenix 与商业托管产品 Arize AX；数据和追踪对象可复用，环境复位与成功条件仍需应用方实现。

## 裁判需要校准，分数才能进入版本比较

证据保存完整，只解决了“看得见”。评分器也可能把有效方案判错，或者放过缺少关键步骤的结果。Agent 评测通常需要组合三种判断，各自承担适合的部分。

确定性的格式、测试结果、状态条件和禁止调用，优先由代码检查。开放语义，例如回答有没有曲解证据、是否完整响应用户需求，可以使用 LLM judge；judge 是根据评分标准阅读证据的模型裁判。人工则用于定义成功、核对边界和处理分歧。规则和模型一致仍可能共同漏掉一项要求，不能把一致本身当成正确性证明。

judge 的输入范围尤其重要。只有最终回答的裁判，无法知道实际工具调用是否成功；没有政策和权限条件的裁判，也难以判断一次操作是否允许。评分标准应拆成可解释维度，并允许在缺证据时返回“无法判断”。否则，评测系统只是把未知强行变成一个数字。

《Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena》（arXiv 2306.05685v4）识别了位置、冗长和自偏好等偏差。它研究的是开放对话，不能把其中的具体一致率直接当成 Agent 裁判准确率；可迁移的是对偏差进行检查的必要性。

实际校准可以从应用自己的样本开始：由领域人员给合格、不合格和边界结果标注理由，再让 judge 评分，逐条检查分歧。如果比较两个候选答案，还应交换 A/B 顺序，观察结论是否受到位置影响。误放不合格结果与误拒合格结果的代价可能不同，需要分别统计；只看总体一致率，容易被数量最多的一类掩盖。

LangSmith 的《Use annotation queues》提供了组织人工复核的入口。《Evaluation types》则区分离线数据集评测与线上监控：线上往往没有参考答案，自动评分更适合作为异常信号。将分歧放入队列、核对评分标准、锁定 judge 版本后再比较实验，是可以基于这些对象建立的工作流；队列本身不会自动产生正确标签。

monday 的实践在这一点上继续向前：他们把 judge 定义存入代码，并在部署中同步 prompts 和 rules、清理废弃配置。这让评分变更也可以被审查和追踪。但同步与清理是该团队自建的部署工具，不能据此声称 LangSmith 默认向所有用户提供完整 GitOps 流程。

更换 judge 后，可以重新读取旧轨迹和产物，检查新的评分标准怎样判定同一结果。更换工具实现则改变了 Agent 可能采取的行为，通常需要重新运行，才能取得这份实现产生的证据。实验记录要区分重评分与重跑，版本差异才有可解释的来源。

## 重复运行测的是稳定性，任务数量测的是覆盖面

固定了条件与裁判，单次成功仍不足以描述 Agent 的交付能力。模型可能在多轮对话中选择不同路径，工具等待和用户模拟器也会改变后续观察。LangSmith SDK 的 `Client.evaluate` 提供 `num_repetitions` 参数，可以让每个样本重复运行；但多运行几次，不会自动得到正确的统计结论。

首先要决定产品问题。允许尝试多次并从中选出一个可用结果，与要求同一任务每次都成功，关注的是两种能力。τ-bench 论文第 3 节用两个容易混淆的指标表达这个区别：

| 指标 | 回答的问题 | 使用前提与限制 |
| --- | --- | --- |
| `pass@k` | 同一任务尝试 k 次，至少一次成功的概率有多大 | 真正部署还要付出尝试成本，并有办法识别、选择成功结果 |
| `pass^k` | 同一任务执行 k 次，全部成功的概率有多大 | 描述给定任务与条件下的一致性，不能直接当成生产 SLA |

如果线上只运行一次，`pass@k` 不能冒充其成功率。即使离线评测知道 k 个候选中有一个正确，没有可用的验证与选择机制，线上系统也未必能交付那个候选。

估计时应先以任务为单位。对某个任务运行 n 次，其中 c 次达到严格的二值成功，且 k 不大于 n。可以从这 n 次中等可能地抽取 k 次：至少一次成功的比例，是 `1 − C(n−c,k) / C(n,k)`；全部成功的比例，是 `C(c,k) / C(n,k)`。`C(a,k)` 表示组合数，a 小于 k 时为零。随后对任务级估计求平均。

把这些组合比例用于估计重复尝试的成功概率，需要在所定义条件下独立同分布的试验假设。共享环境故障、前次缓存泄漏、执行期间模拟用户配置变化，都可能破坏假设。不同任务难度也不相同，因此不能先算全体平均成功率，再取 k 次方来代替任务级 `pass^k`。平均部分得分与“整项任务成功”的比例，同样需要分开报告。

这里存在两个样本量：独立任务数，以及每个任务的 trial 数。增加重复，主要帮助观察同一任务的运行波动；增加有代表性的任务，才能扩展对工作负载的覆盖。把少数熟悉任务反复执行，不能获得更多独立业务场景。也不存在“N 达到四次就稳定”的通用门槛；需要多少数据，取决于希望识别的变化、可接受的不确定性和失败代价。

报告应保留每题试验次数、各类任务数量和不确定性。单一、近似独立的二值比例可以参考 NIST/SEMATECH e-Handbook 第 7.2.4.1 节的比例区间方法；任务内多次执行存在聚类结构时，就不能把所有 trial 当成完全独立样本。一个可采用的比较设计，是固定任务并逐题配对新旧版本，以任务为单位做重采样来估计差异；这是统计设计建议，需要结合实际采样方式选择。

缺失 trial 和异常也会改变解释。τ-bench 固定版本的 runner 在异常时写入零奖励，同时保留错误和堆栈。因而单看零分，不能知道 Agent 做错了，还是运行器或服务失败了。某题未完成计划次数、只选择性重跑失败题时，也不能原封不动套用平衡试验的聚合方式。

可审查的结果应同时呈现计划与实际次数、能力成功或失败、环境异常、评分错误和无法判断。超时属于运行结果的一部分，但是否计入任务失败、是否允许重试，需要事先定义；删掉异常后只报剩余样本成功率，会让可靠性看起来高于实际交付情况。

## 从 CI 到线上反馈，让失败改变下一次测量

版本比较得到的是各类任务上的变化，发布负责人还要据此决定：哪些改善足以采用新版本，哪些退化必须阻止上线。这个决定需要保留分项结果，不能只看一个汇总分。

monday 的 CI 与 experiment 关联解决了“代码变更后能否持续得到检查结果”。他们的多轮线上评测进一步处理会话边界：什么时候认为会话已经完成，哪些会话进入评分，采样比例和成本怎样控制。若在任务尚未结束时评分，会把正常进行中的工作误判成未完成；若只观察最后一条回复，又会丢失前面的行动与约束。

这些设置把离线与线上连接起来，却不能让两个场景共享同一种真值。离线实验用于在固定任务下比较候选变更；线上追踪记录实际发生了什么。用户满意度、投诉或自动 judge 都可以提供信号，但满意不必然代表执行正确，没有投诉也不说明没有失败。

Notion 的公开实践补上了另一段链条。Braintrust 的客户访谈《How Notion evaluates AI at scale across 70 engineers》中，AI Modeling Lead Sarah Sachs 描述了多语言 workspace 中语言选择不符合期望的失败类别。团队搜索并收拢这类实例，建立专项 dataset，用于后续回归。这里可迁移的动作很具体：把线上发现的一类错误，变成下一版必须面对的固定任务。

这解决了总体平均分容易掩盖局部退化的问题。一个版本整体改善，仍可能对某种语言、某类权限或某段工具链更差。专项集合让维护者单独看到这些变化，而不是等待它们在总分里占到足够权重。

该访谈还区分 regression eval 与 frontier eval：前者守住已有能力，后者探索新模型能否支撑新能力。一个长期接近满分的回归集，适合阻止已知问题重现，却可能无法区分候选方案的上限。因此可以保留不同用途的集合：日常开发诊断集、固定版本回归集，以及未反复参与调参的验收或新鲜样本。这个划分是工程建议，并非所有产品强制采用的三套结构。

线上样本进入回归前，需要经过确认、脱敏并保留必要条件。任务当时的知识版本、用户权限和初态如果无法恢复，就只能作为观察证据，不能声称已经得到可重演任务。同时还要采集代表性的新样本：只收投诉和失败，会使数据集逐渐变成故障目录，无法估计当前工作负载的整体表现。

回到一次具体版本变更，发布判断适合保留多个维度：任务完成、关键规则、运行错误、延迟与成本。加权总分可以辅助排序，但更好的文字质量不应抵消关键越权行为。门槛应来自业务风险与已有基线；成本要计入失败和重试，端到端延迟要包含工具等待，judge 的评测开销则应明确另列。样本不足时，尾延迟分位数也不能充当精确的服务承诺。

当实验未通过，下一步应由证据决定。目标与标注冲突，先修任务并建立新基线；环境复位失败或服务限流，先修运行层；裁判拒绝有效方案，先校准并重评分；证据确认是 Agent 行为错误，再修改模型、提示、执行框架或工具，并重新运行受影响的任务。这样的分流能避免团队用更复杂的提示词去修一个错误的评分器。

发布后再通过受控灰度或 A/B 观察真实任务完成情况，核对离线改善是否延续到实际人群。人群、时间和工具版本的差异仍需控制，带副作用的任务也不能为了取样随意向真实系统重放。新发现的失败继续进入专项集合，新的代表性样本用于检查分布变化，两条来源共同维持评测的有效性。

这套体系的起点，可以是一批真实任务和几项清楚的检查。关键是让每个分数保留足够的证据，让一次失败能够被定位到任务、运行环境、裁判或 Agent 行为，并能触发对应的修正。领域人员负责成功条件，工程人员负责状态和证据，评测维护者负责版本与测量质量，发布负责人据此承担取舍；小团队可以由同一人兼任这些职责。

随着应用、任务与测试规则变化，评测资产也需要更新，并在每次比较中留下实际版本。维护者应能说明一次失败依据什么、修正了任务还是系统，以及修正后同批任务的结果怎样变化，发布决定才能被追查。
