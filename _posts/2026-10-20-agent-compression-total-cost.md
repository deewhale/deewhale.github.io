工具输出压缩器试图减少 Coding Agent 需要读取的终端文本。RTK 是这类工具的一个实现：它处理命令输出，再把较短的结果交给模型。对使用者而言，要判断的是这种信息处理能否降低完成合格任务的成本，过滤器显示的压缩比例只是其中一项观测。

Quesma 团队公开的 RTK 成本比较，恰好提供了一个研究起点：两条模型与 Agent 路线，在使用相同压缩工具后得到不同的每成功任务成本变化。要解释这种分歧，需要把工具输出、模型计费和任务结果接起来，而不能仅比较文本长短。

## 一次公开成本比较呈现的分歧

Quesma 团队在 2026 年 9 月公布过 RTK 成本比较。报告使用 RTK 0.45.0 与 Harbor 0.20，在 Terminal-Bench 2.1 上对每个任务、每种设置运行五次。两条路线使用不同模型与执行工具：

| 模型与路由 | Agent 工具 | 纳入任务 | 总费用除以成功次数的变化 |
|---|---|---:|---:|
| Claude Fable 5.0 | Claude Code 2.1.220 | 85 | 使用 RTK 后约便宜 3% |
| DeepSeek V4 Pro 0813，经 OpenRouter | OpenCode 1.18.25 | 89 | 使用 RTK 后约贵 7% |

Fable 路线排除了四项发生拒答的安全任务，两条路线最终共 1,740 次尝试。表中数字是报告作者的批次聚合结果，不能解释为每项任务都同向变化，也不能合并成 RTK 的固定节省率。

报告进一步找到了影响聚合结果的具体任务。`winning-avg-corewars` 在两种设置中都通过：Fable 路线接入 RTK 后约少用一半轮次，构成其大部分节省；DeepSeek 在同一题上反而增加了轮次。除此题以外，Fable 的节省不足 1%。压缩不是只改账单里的输入长度，它还改变了后续执行路径。

另一条轨迹暴露了兼容问题：旧版过滤器改写了一种不支持的 `find` 用法，返回要求直接使用原命令，重试又被改写。报告记录了这一循环；后来的 0.46.0 已修复。这里能够解释的是特定版本的额外往返，不宜将旧故障当作当前版本的固有行为。

还有一个容易被忽略的选择：怎样汇总不同任务。把所有费用相加再除以成功数，会受到高成本任务的较大影响；先算每项任务的比值再等权平均，则把便宜小任务与昂贵大任务赋予相同权重。两者回答不同问题。团队应先说明自己关心总体预算，还是典型任务体验，再选汇总方式，并保留另一种读法作检查。



## RTK 改变的是哪段输入
RTK 会针对支持的命令处理输出，再将处理后的内容交给 Agent。以 `ls` 为例，它把目录条目整理为紧凑行，保留名称、大小和权限，默认不保留原输出的属主、日期等列。查询目录里有什么时，这些字段足够；若任务恰好要核对文件属主，丢弃的就是判断需要的材料。过滤规则必须与当前查询需要的信息对应。操作系统实际执行的命令、命令产生的原始输出、模型最终看见的文本，是三个需要分开的对象。少传一部分文字不会改变已经执行过的测试，却可能改变模型对测试结果的理解。

这种方式与对整段会话做摘要也有差别。会话摘要处理的是多轮对话及其历史；工具输出过滤先处理一次命令结果。两者都可能影响上下文，但输入范围、触发点和回读方式不同。选型时先确定自己要减少哪一段材料，才能知道该测什么。

除了命令结果，工具定义本身也会占用上下文。减少这两类材料，需要分别记录其效果。Pi v1.4.0 的 MCP 支持可以把工具先注册为可发现对象，暂时不把完整输入说明声明给模型；需要时，经 `tool_search` 加载到下一轮请求，或由 Codemode 脚本查到定义后调用。这里减少的是尚未使用的接口说明，接口发现本身仍可能增加模型往返。

Codemode 还允许在脚本内取得 MCP 返回的结构值，检查错误、筛选记录后再输出给模型。这才进入工具结果过滤的环节。把工具定义延迟加载和把查询结果筛短分开记账，才能知道输入减少发生在哪里。评估仍需要累计发现轮次、实际缓存命中、工具与模型开销，并保持最终成功标准一致，不能把少声明的工具数量直接换成费用节省。



## 压缩率与成本使用不同分母

RTK 的 `gain` 统计会把原始输出与过滤后输出的字节数换算成 token 估计，所查文档采用字节数除以 4 的近似。它适合观察过滤器处理了多少文本，但没有调用每个模型的实际计费 tokenizer。中文、代码、数字与不同分词器的关系都可能让这个近似发生偏差。

即使估计完全准确，统计也只涵盖工具输出这个通道。模型的一次请求还可能包含系统指令、用户需求、历史对话、文件正文、其他工具结果；输出部分又单独计价。一份工具日志减少 80%，不意味着整次模型请求减少 80%，更不意味着整个任务费用减少 80%。

| 观察值 | 它回答的问题 | 还缺什么 |
|---|---|---|
| 原始与过滤后的字节数 | 输出文本少了多少 | 模型分词、是否真正发送 |
| 请求的输入 token | 这次模型读了多少 | 缓存类别及价格 |
| 单次请求费用 | 这次请求花了多少 | 整个任务有多少次请求 |
| 任务总费用 | 这次尝试花了多少 | 任务是否完成、质量是否合格 |
| 每成功任务成本 | 为合格结果付出多少 | 任务分布、成功判定及样本量 |

表中各项都可以有用，只是不能互相替代。过滤器面板适合诊断哪类命令产生了大量噪声；采用决定需要追到任务结果那一行。



## 缓存和额外轮次怎样进入费用

模型服务可能对未缓存输入、缓存读取、缓存写入与输出采用不同计费方式。计算时应从实际使用记录提取类别，不能把全部上下文都按同一输入价计费。否则，同样删掉一万个 token，在账本里可能被夸大为完全不同的收益。

如果某段历史已经以较低价格从缓存读取，删减它带来的费用变化，与删减同等数量的新输入不同。过滤也可能改变后续请求的上下文布局，因此需要观察实际命中情况。不能只拿压缩前的缓存命中率，套在压缩后的运行上。

以 Claude Messages 的 usage 为参照，`input_tokens` 记录未缓存输入，`cache_read_input_tokens` 记录缓存读取，`cache_creation_input_tokens` 记录新建缓存。它们是分开的计量，不能先把缓存 token 加入普通输入，再另收缓存费用。缓存写入还可以按五分钟与一小时期限拆分。记相应计数为 U、R、W₅、W₆₀，输出为 O，单价为 p，则每轮费用的符号关系是：

```text
C = U·p输入 + R·p读取 + W₅·p五分钟写入 + W₆₀·p一小时写入 + O·p输出
```

单价和计数须使用相同单位；按百万 token 报价时，右侧再除以一百万。跨轮求和后，加上另行计费的工具、检索与执行资源，才是一次尝试的账单。其他供应商需要按自己的 usage 定义映射，不能直接套字段名。

过滤减少工具文本之后，可能同时改变新输入量、历史前缀、缓存命中与输出轮次。因此费用变化应拆成各项目的变化之和，再回到轨迹解释。输入费用的下降若小于额外轮次或其他计费项目的增加，总费用仍会上涨。

把每轮 usage 与任务验收结果一同保留，才能从总费用回查哪些请求发生变化，并计算获得合格结果的成本。

## 用成功任务成本决定是否采用
定义每成功任务成本为“批次总费用 ÷ 合格结果数”。失败尝试消耗的费用留在分子里，合格结果的数量进入分母。这样才能看见团队为获得结果实际付出了多少。成功数为零时指标未定义，不能记成零成本，也不能把失败尝试删除以后宣布节省。

这个指标也有使用条件。任务难度差异大时，应按任务类型分层；同一个批次的平均值，不是下一次重试必然成功的期望成本。还要同时保留成功率、总费用与耗时，避免一个比值掩盖少量异常昂贵的失败。

可以按同一批真实工作任务做小规模配对试点。先固定模型、努力等级、工具版本、超时和验收标准，随机安排执行顺序，再分别开启和关闭过滤。每次记录实际 usage、缓存类别、轮次、费用、耗时和是否通过验收。发生拒答或工具兼容错误时，预先规定怎样统计；若排除，应同时展示包含与排除后的结果，不能只保留有利样本。

当过滤后成本或失败率上升，先回到轨迹检查：失败栈是否被裁掉、模型是否反复查询同一文件、命令是否因包装方式变化而执行失败、原始输出能否回读。这样才能区分信息缺失、工具兼容与任务本身的随机变化。

对于重复成功记录占比很高的日志，保留错误上下文并减少重复行，是有机制依据的试点方向。对于依赖细粒度差异的调试任务，先保留完整材料更容易检验。是否推广，应由约定的质量下限与成功任务成本共同决定；压缩率留在诊断面板上，用来解释结果怎样发生。
