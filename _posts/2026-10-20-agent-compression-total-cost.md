工具面板显示“输出减少 80%”，同一批任务的账单却可能上涨。先不用判断哪个数字有问题：面板统计的可能是一条命令原本会返回多少文字，账单计算的则是模型为了完成任务，一共处理了多少输入、生成了多少输出，以及这些请求怎样使用缓存。

对使用 Coding Agent 的团队，关键问题是完成一次合格修改要花多少钱。压缩率可以解释成本变化，但不能代替成本。把信息删短以后，Agent 可能更快定位问题，也可能需要重新查询，甚至遗漏一个决定结果的例外。应把这两条路径放在同一张账本里判断。

下面以 RTK 这类工具输出过滤器为对象，区分输出统计、模型计费和任务结果。资料核查截至 2026 年 10 月 20 日；算例中的记录与单价均为教学假设，实际执行的是计算程序，没有将其当作真实模型测量。

## 过滤发生在模型读到工具结果之前

先看一次普通的测试命令。Agent 请求运行测试，执行程序得到一千行结果，其中九百行是重复的通过记录，剩下是失败栈、环境信息和摘要。通常，这份文本会作为工具返回值进入后续模型请求。过滤器介入的是“命令执行结果到模型输入”这段路径。

RTK 会针对支持的命令处理输出，再将处理后的内容交给 Agent。它可以削减重复记录、提取摘要或保留特定内容。操作系统实际执行的命令、命令产生的原始输出、模型最终看见的文本，是三个需要分开的对象。少传一部分文字不会改变已经执行过的测试，却可能改变模型对测试结果的理解。

这种方式与对整段会话做摘要也有差别。会话摘要处理的是多轮对话及其历史；工具输出过滤先处理一次命令结果。两者都可能影响上下文，但输入范围、触发点和回读方式不同。选型时先确定自己要减少哪一段材料，才能知道该测什么。

以一个配置迁移为例。测试日志里反复出现正常租户的成功记录，只有一个租户沿用旧配置。假如过滤器保留失败项及相邻上下文，删掉重复通过行，模型仍能看到这个例外。如果过滤规则只保留最后几行摘要，租户名称与旧配置路径可能一同消失。Agent 随后查询更多文件，是对信息变化的响应；是否值得，需要连同额外请求一起计算。

这里的迁移是自拟情境，用来定位信息损失怎样发生。不能仅凭这个可能的失败过程，断言某款过滤器在真实任务中一定会漏掉例外。

## “省下的 token”有不同分母

RTK 的 `gain` 统计会把原始输出与过滤后输出的字节数换算成 token 估计，所查文档采用字节数除以 4 的近似。它适合观察过滤器处理了多少文本，但没有调用每个模型的实际计费 tokenizer。中文、代码、数字与不同分词器的关系都可能让这个近似发生偏差。

即使估计完全准确，统计也只涵盖工具输出这个通道。模型的一次请求还可能包含系统指令、用户需求、历史对话、文件正文、其他工具结果；输出部分又单独计价。一份工具日志减少 80%，不意味着整次模型请求减少 80%，更不意味着整个任务费用减少 80%。

可以先用一个简化上界理解它。假设被过滤的工具文本原本占某项费用的四分之一，这部分减少八成，其他因素完全不变，那么对应费用最多减少约五分之一。这个推算必须满足“同一计费口径、其他不变”。若四分之一是字符占比，而费用按缓存后的不同 token 类别计算，就还没有足够条件直接相乘。

| 观察值 | 它回答的问题 | 还缺什么 |
|---|---|---|
| 原始与过滤后的字节数 | 输出文本少了多少 | 模型分词、是否真正发送 |
| 请求的输入 token | 这次模型读了多少 | 缓存类别及价格 |
| 单次请求费用 | 这次请求花了多少 | 整个任务有多少次请求 |
| 任务总费用 | 这次尝试花了多少 | 任务是否完成、质量是否合格 |
| 每成功任务成本 | 为合格结果付出多少 | 任务分布、成功判定及样本量 |

表中各项都可以有用，只是不能互相替代。过滤器面板适合诊断哪类命令产生了大量噪声；采用决定需要追到任务结果那一行。

## 缓存改变的是少传文字的边际价值

模型服务可能对未缓存输入、缓存读取、缓存写入与输出采用不同计费方式。计算时应从实际使用记录提取类别，不能把全部上下文都按同一输入价计费。否则，同样删掉一万个 token，在账本里可能被夸大为完全不同的收益。

如果某段历史已经以较低价格从缓存读取，删减它带来的费用变化，与删减同等数量的新输入不同。过滤也可能改变后续请求的上下文布局，因此需要观察实际命中情况。不能只拿压缩前的缓存命中率，套在压缩后的运行上。

本文使用三个类别写一个最小账本。设 `U` 是未缓存输入，`H` 是缓存读取，`O` 是模型输出。单位都采用服务实际计量的 token，而不是过滤器估计值。假定每百万 token 的教学价格分别为 3、0.3 和 15，则费用为：

```text
费用 = (U × 3 + H × 0.3 + O × 15) / 1,000,000
```

这不是任何供应商的报价。它只是让不同类别的权重显露出来。真实账单如果另有缓存写入、工具调用、检索或执行环境费用，就应增加相应项目；没有出现在这个公式中，不代表这些费用不存在。

## 一组减少八成输出却加价的记录

给配置迁移构造两次运行。未过滤路径用了 10 轮请求；过滤路径用了 14 轮。假设过滤路径增加的轮次来自补充查询与重新生成，但账本本身只能记录这一事实，不能证明加轮由压缩造成。真正的因果判断还需要受控运行与轨迹核对。

两次尝试的累计数据如下。工具字节数与计费 token 分列，避免把它们误认为同一个统计量。

| 整次尝试 | 未过滤 | 过滤后 |
|---|---:|---:|
| 请求轮数 | 10 | 14 |
| 工具输出字节 | 100,000 | 20,000 |
| 未缓存输入 token | 100,000 | 90,000 |
| 缓存读取 token | 900,000 | 810,000 |
| 输出 token | 20,000 | 28,000 |

过滤后的输入类别都减少了十分之一，模型输出却增加了四成。按上述教学价格复算：

```python
def cost(uncached, cache_read, output):
    return (uncached * 3 + cache_read * 0.3 + output * 15) / 1_000_000

baseline = cost(100_000, 900_000, 20_000)
filtered = cost(90_000, 810_000, 28_000)
print(round(baseline, 3), round(filtered, 3))
# 0.87 0.933
```

代码只有 Python 标准语法，输入即表中的整次累计使用量。这组计算已执行：工具输出字节减少 80%，总费用却从 0.870 增加到 0.933，约增加 7.24%。差额来自不同计费项的共同变化。

这说明“输出缩短”和“整次变贵”可以同时成立。它没有证明 RTK 实际导致了这个结果，也不能用这组人工数字预测项目收益。算例的用途，是检验自己的面板是否覆盖了足以作决定的变量。

## 一手成本实验能够支持到哪里

Quesma 团队在 2026 年 9 月公布过 RTK 成本比较。报告使用 RTK 0.45.0 与 Harbor 0.20，在 Terminal-Bench 2.1 上对每个任务、每种设置运行五次。两条路线使用不同模型与执行工具：

| 模型与路由 | Agent 工具 | 纳入任务 | 总费用除以成功次数的变化 |
|---|---|---:|---:|
| Claude Fable 5.0 | Claude Code 2.1.220 | 85 | 使用 RTK 后约便宜 3% |
| DeepSeek V4 Pro 0813，经 OpenRouter | OpenCode 1.18.25 | 89 | 使用 RTK 后约贵 7% |

Fable 路线排除了四项发生拒答的安全任务，两条路线最终共 1,740 次尝试。表中数字是报告作者的批次聚合结果，不能解释为每项任务都同向变化，也不能合并成 RTK 的固定节省率。这里没有取得全部原始轨迹并独立复现，也不把当前版本的新能力回填到旧版本实验中。

对工程决策最有用的发现，是相同的输出压缩主张没有转换成一致的任务成本结果。它支持重新检查分母、任务结果和执行兼容性。它不足以否定所有过滤工具，也不足以证明未来版本和其他任务会得到同样的数字。

RTK 当前说明同样区分终端输出减少与最终账单：命令输出只是输入的一部分，模型输出另有成本。因此，可以把双方材料放到同一测量框架里，而不必先选一个宣传数字当结论。

还有一个容易被忽略的选择：怎样汇总不同任务。把所有费用相加再除以成功数，会受到高成本任务的较大影响；先算每项任务的比值再等权平均，则把便宜小任务与昂贵大任务赋予相同权重。两者回答不同问题。团队应先说明自己关心总体预算，还是典型任务体验，再选汇总方式，并保留另一种读法作检查。

## 成功率进入之后，采用判断才完整

继续使用自拟账本。假设每种设置各执行两次，未过滤两次均成功，过滤后只有一次满足验收。定义一个批次指标：

```python
def cost_per_success(costs, successes):
    return sum(costs) / successes if successes else None

print(cost_per_success([0.870, 0.870], 2))  # 0.870
print(cost_per_success([0.933, 0.933], 1))  # 1.866
print(cost_per_success([0.933], 0))         # None
```

失败尝试消耗的费用留在分子里，合格结果的数量进入分母。这样才能看见团队为获得结果实际付出了多少。成功数为零时指标未定义，不能记成零成本，也不能把失败尝试删除以后宣布节省。

这个指标也有使用条件。任务难度差异大时，应按任务类型分层；同一个批次的平均值，不是下一次重试必然成功的期望成本。还要同时保留成功率、总费用与耗时，避免一个比值掩盖少量异常昂贵的失败。

可以按同一批真实工作任务做小规模配对试点。先固定模型、努力等级、工具版本、超时和验收标准，随机安排执行顺序，再分别开启和关闭过滤。每次记录实际 usage、缓存类别、轮次、费用、耗时和是否通过验收。发生拒答或工具兼容错误时，预先规定怎样统计；若排除，应同时展示包含与排除后的结果，不能只保留有利样本。

当过滤后成本或失败率上升，先回到轨迹检查：失败栈是否被裁掉、模型是否反复查询同一文件、命令是否因包装方式变化而执行失败、原始输出能否回读。这样才能区分信息缺失、工具兼容与任务本身的随机变化。

对于重复成功记录占比很高的日志，保留错误上下文并减少重复行，是有机制依据的试点方向。对于依赖细粒度差异的调试任务，先保留完整材料更容易检验。是否推广，应由约定的质量下限与成功任务成本共同决定；压缩率留在诊断面板上，用来解释结果怎样发生。
